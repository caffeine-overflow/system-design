01

What is a URL shortener?

Start from zero: a URL shortener turns a long web address into a short one that redirects to it. bit.ly/abc12 → your-long-link. That's the whole product. Everything else is how to make it fast, huge, and safe.

URL shortener

A service that accepts a long URL and returns a short alias (a short domain plus a short key, like shrt.ly/a9Kx2zQ). When someone visits the alias, the service looks up the original URL and issues an HTTP redirect — an HTTP response that tells the browser "the thing you want is actually over here," so the browser automatically loads the long URL.

⚽ The ticket-stub analogy

Short links are ticket stubs

When you buy a ticket for the cup final, you don't get a document describing your exact seat's latitude and longitude, the stadium gate, and the turnstile number. You get a stub with a short code — say, Gate B · Row 44 · Seat 112 compressed into a QR. At the gate, a scanner looks the code up and waves you through.

A URL shortener is the same deal. The long URL is the full seating plan; the short link is the stub. Visiting the stub triggers a lookup and a redirect — you get waved through to the real page. Keep this analogy in mind: key generation = printing the stubs, the database = the box office ledger, the cache = the ushers who memorize frequent stubs.

Why do short links exist at all?

Not just to look tidy. Each reason hints at a real requirement:

  • Constrained spaces. A 300-character match-preview link doesn't fit in an SMS, a stadium jumbotron QR code, or a printed program. Short links fit.
  • Analytics. A club posts one link across ten channels; per-link click counts say which channel actually converts. The shortener is the click counter.
  • Branded vanity links. club.fc/final-tickets is marketing, not engineering — but the system must support custom aliases.
  • Control. Fix the destination, set an expiry, or revoke a link without reprinting the flyer. The redirect layer gives you a lever on every link you've ever handed out.

The one sentence that carries the whole design

A URL shortener is a write-once, read-many key-value store with a redirect protocol on top. You write once (create the link) and read many times (every click is a lookup). That single asymmetry — far more reads than writes — drives every decision below: the cache strategy, the key-generation choice, and the database pick.

02

Requirements & back-of-the-envelope math

Every design interview starts by pinning down what you're actually building. Nail the requirements first, or every later decision is guesswork. Here's the standard scoping — and the sizing math that comes with it.

Functional requirements

  • Shorten: given a long URL, return a short alias.
  • Redirect: given a short alias, redirect the visitor to the long URL.
  • Custom aliases (optional but expected): let users request shrt.ly/worldcup26 instead of a random key.
  • Expiry: links can have a TTL (time to live — an automatic expiry date).
  • Click analytics: how many times was each link clicked?

Non-functional requirements

  • Availability over consistency. If the database hiccups, a slightly stale redirect is far better than an error page. This is an AP-ish system (from the CAP theorem lesson: partition → choose availability).
  • Low latency. The redirect adds a hop to every click — it must feel instant (sub-100ms).
  • Scale: the numbers below.

The back-of-the-envelope math

Pick round numbers and state them out loud — the arithmetic is the design document. These are the industry-standard assumptions:

QuantityAssumptionResult
New URLs100M / month≈ 40 URLs/second average (100M ÷ 30 days ÷ 86,400 s)
Peak writes~10× average≈ 400 URLs/second
Reads10:1 read-to-write ratio≈ 400 reads/s average, ~4,000/s peak
Lifetime data100M × 60 months (5 years)6 billion URL records
Record size~500 bytes per record6B × 500 B ≈ 3 TB total storage
Bandwidth4,000 reads/s × 500 B≈ 2 MB/s of raw payload (trivial — this system is not bandwidth-bound)

What the math tells you. 3 TB is small for a database; the write rate (400/s peak) is modest. This is not a storage-scale problem — it's a read-latency and key-generation problem. The hard parts are minting unique short keys at speed and answering lookups in milliseconds. Say that sentence out loud in the room and you sound like you've built one.

Assumptions are negotiable; math is not. An interviewer may hand you different numbers ("what if it's 1B URLs/month?"). Never memorize the table above — memorize the method: per-month ÷ seconds-per-month → per-second rate → ×10 for peak; ×60 months → lifetime rows → × record size → storage. Walk through it live.

03

The API surface

Two endpoints. That's the whole public contract — and getting them exactly right is a senior signal.

{
  "shorten": {
    "method": "POST",
    "path": "/api/v1/urls",
    "request": {
      "long_url": "https://stadium.example/matches/2026/final?t=premium&seat=B-44-112",
      "custom_alias": "final-tickets",      // optional
      "expires_at": "2026-12-31T23:59:59Z"  // optional
    },
    "response_201": { "short_url": "https://shrt.ly/final-tickets" }
  },
  "redirect": {
    "method": "GET",
    "path": "/{short_key}",
    "response": "302 Found, Location: "
  }
}
301 vs 302 redirect

301 (Moved Permanently) tells the browser "this alias will always point here — cache it forever and don't ask me again." 302 (Found) says "go here for now — keep asking me each time." For a URL shortener, 302 is the right choice: you keep counting clicks (analytics), and you can change or expire the destination later. With 301, the browser caches the redirect and you lose both. This is a classic senior trap — see Q1 below.

Why a POST body, not query params, for shortening?

Long URLs can contain anything — including characters that break URL parsing. Putting them in the JSON body keeps them intact. Also: creating a link is not idempotent by default (each POST mints a new key), and POST signals that. A idempotent operation is one you can repeat with the same result — like pressing "save" twice saving once. Minting a fresh key on each POST is deliberately non-idempotent, which is why dedup of identical URLs is a separate decision (see §6).

04

The heart of the design: generating short keys

This is the section interviewers zoom in on. Three approaches, each with a real trade-off. There is no perfect one — your job is to pick one and defend it.

⚽ Stub-printing, three ways

Printing ticket stubs for 80,000 fans

Way one: number them sequentially as people buy — 0001, 0002, 0003. Simple, never duplicates, but guessable (see 0007's stub? 0008 exists too — you just enumerated the box office).

Way two: stamp each stub with a random scribble and check it's unique. Unpredictable, but you must check every scribble against every previous one.

Way three: run a stub printer that pre-prints stacks of random stubs overnight. At the gate you just grab the top one — instant, unique, unpredictable. This is the production answer.

Base62 encoding

Writing a number using 62 characters — 0-9, a-z, A-Z — instead of the usual 10 digits. 62 = 10 digits + 26 lowercase + 26 uppercase. It's why a huge number like 12,842,391 becomes a short key like a9Kx2zQ. Why not base64? Base64 includes + and /, which break URLs. Base62 stays URL-safe.

Approach 1: Hash the long URL

Take the long URL, run it through a hash function (a function that turns any input into a fixed-size fingerprint, like MD5), take the first few characters, base62-encode them. Same URL → same key, always.

The birthday problem kills short hash keys

A hash collision is two different inputs producing the same fingerprint. The birthday problem says collisions arrive far earlier than intuition suggests: with a key space of N possible keys, you hit ~50% collision chance after only about √N keys — just like 23 people sharing a birthday in a room (365 days needs only 23 people).

The math: 7 base62 characters = 62⁷ ≈ 3.5 trillion possible keys. 50% collision chance after ≈ 2.3 million keys. We need to store 6 billion. So short hash keys will collide constantly, and every collision forces a check-and-retry loop (hash, check database, collide, tweak, repeat) — which turns a fast write path into a slow, contentious one at scale. The key lab in §9 lets you feel this.

Approach 2: Counter + base62

Keep a global counter, increment it for each new URL, base62-encode the counter value. Key #1,000,000 → 4c92. Guaranteed unique, no collision checks, shortest possible keys.

  • The distributed problem. One counter on one machine is a single point of failure and a bottleneck. The standard fix is range allocation: a coordinator (often ZooKeeper, or a database row) hands each app server a block of 1,000 IDs. Server A mints 1–1,000, server B mints 1,001–2,000, no coordination per URL. Wasted IDs on crashes are fine — gaps are harmless, duplicates are fatal.
  • The guessability problem. Sequential keys are enumerable: shrt.ly/aaaa1 works? Try aaaa2. If links can be private, enumeration is a leak. Mitigation: start the counter at a large random offset, or use approach 3.

Approach 3: KGS — the Key Generation Service (the production answer)

A dedicated microservice (a small service that does one job) whose only job is minting keys. It pre-generates random unique keys in batches, stores them in two tables — keys_unused and keys_used — and hands them out on request.

API server:  "give me a key"
KGS:         UPDATE keys_unused SET used=1 WHERE key='xQ2mP9z'  -- mark used
KGS:         "here: xQ2mP9z"                                     -- hand it over
  • Uniqueness is trivially guaranteed — a key leaves the pool exactly once.
  • Keys are random, so they're not enumerable.
  • The API servers stay fast: they keep a local buffer of a few hundred pre-fetched keys, so the hot path never calls KGS per URL.
  • Standby KGS. Run two KGS instances: primary serves, standby watches the keys_used table. If primary dies, standby promotes itself. Both share the same tables, so no key is ever double-issued.

The verdict to give in the room. Start with KGS: it's the only approach that is unique-by-construction, non-enumerable, and fast on the hot path with a local buffer. If the interviewer pushes for simplicity, counter + base62 with range allocation is the honest second choice — and you can name the enumeration trade-off yourself before they ask. Only mention hashing to show you know why it's wrong at scale (birthday collisions), not as your pick.

05

Where the URLs live: data model & storage

The data model is almost embarrassingly simple — and that's the point. The interesting part is what you choose not to do.

-- the whole core schema
CREATE TABLE urls (
  short_key   VARCHAR(16) PRIMARY KEY,
  long_url    TEXT        NOT NULL,
  created_at  TIMESTAMP   NOT NULL,
  expires_at  TIMESTAMP   NULL,        -- NULL = never expires
  user_id     BIGINT      NULL         -- NULL = anonymous
);

SQL or NoSQL?

Either works, and saying so is a senior move. The access pattern is pure key lookup — no joins, no range scans on the hot path. A relational database (PostgreSQL/MySQL) is perfectly fine and gives you transactions for free. A wide-column store (Cassandra, DynamoDB) shines at 6-billion-row scale with built-in partitioning (splitting the data across many machines — see the sharding lesson). The honest answer: start relational, shard by short_key hash when growth demands it. Interviewers respect "boring until proven otherwise" over NoSQL-by-default.

Three decisions interviewers expect you to raise yourself

  • Dedup of identical URLs? If someone shortens the same match-preview link twice, do you return the existing key or mint a new one? Returning the existing key saves storage — but you need a secondary index on long_url (an extra lookup structure so you can search by long URL), and users lose separate analytics. Most designs skip dedup; say so and give the reason.
  • Don't reuse deleted keys. When a link expires, its key stays dead. Reissuing it lets a stranger inherit someone's printed flyers — a real phishing vector.
  • Expiration: lazy beats eager. A background sweeper deleting expired rows is fine, but the read path should just check expires_at on lookup and 404 if passed. Lazy = do the work when the item is next touched, not on a schedule. Fewer moving parts.
06

Serving billions of redirects fast: the cache story

Reads outnumber writes 10:1. Caching isn't an optimization here — it's the architecture. (This section is the caching lesson applied: if the vocabulary feels new, the cache lab there is the companion.)

⚽ The ushers who memorize stubs

Cache = the regulars' lane

Picture the cup-final turnstiles. A handful of hospitality stubs get scanned thousands of times; most stubs get scanned once. The veteran ushers memorize the frequent ones and wave them through without checking the box-office ledger — that's your cache. And the 80/20 rule (20% of links get 80% of clicks — a viral goal clip, the ticket link) means a cache that holds just the hot keys absorbs the vast majority of traffic. The ledger (database) only hears from the long tail.

The layered design

  1. CDN / edge cache (e.g., CloudFront, Cloudflare) for the hottest keys. A 302 redirect served from the edge is ~10ms and never touches your servers. Set a short TTL — you want to keep control of expiry and analytics.
  2. Application cache (Redis/Memcached) in front of the database, cache-aside pattern: on lookup, check Redis first; on miss, read the database and populate Redis. With an 80/20 traffic split, this layer serves the overwhelming majority of reads.
  3. The database handles cache misses and all writes.

The cache-invalidation trap (and why it barely bites here)

Invalidating caches is famously one of the two hard problems in computer science. But URL shortener entries are effectively immutable — a short key's destination is set at creation and rarely changes. So the classic invalidation nightmare mostly doesn't apply: populate on miss, evict on expiry, and only invalidate on the rare destination-change. This is the "aha" that separates a memorized answer from an understood one: the workload's immutability makes caching almost free.

The thundering-herd footnote. When a hot key's cache entry expires, thousands of concurrent requests can miss simultaneously and all hit the database — a cache stampede (everyone rushing the ledger at once). Mitigations from the caching lesson apply: probabilistic early refresh (refresh the entry slightly before it expires, randomly staggered) or a single-flight lock (first request refreshes, the rest wait). Mention it; it's a one-line senior signal.

07

Abuse, security, and the things that break you

A public URL shortener is a spammer's dream: free, anonymous, and it hides the real destination. Designing for abuse is not a bonus round — it's half the design.

  • Rate limit creation. Cap shortens per IP / per user per minute. The rate limiting lesson gives you the algorithms — a token bucket on the shorten endpoint is the standard pick. This is your #1 defense against link-spam factories.
  • Destination screening. Check submitted URLs against a malware/phishing blocklist (Google Safe Browsing API is the canonical one) before issuing a key. Reject or quarantine matches.
  • Don't leak existence. A lookup for a nonexistent key should return 404 — not an error that distinguishes "never existed" from "expired," and never any hint about other keys. Random non-enumerable keys (KGS) make bulk scraping impractical.
  • Preview pages for suspicious links. Some shorteners show an interstitial ("you're about to visit…") for flagged domains instead of redirecting blindly — a product-level mitigation worth naming.
  • Authenticated custom aliases. Anyone who can claim shrt.ly/worldcup can impersonate the club. Reserve vanity namespaces, require login for custom aliases, and enforce uniqueness at write time with a unique constraint.
08

Analytics: counting clicks without burning the database

"How many clicks did each link get?" sounds trivial. At 4,000 redirects/second, a counter update per click is a write-amplification nightmare.

The naive approach — UPDATE urls SET clicks = clicks + 1 on every redirect — turns your 10:1 read-heavy workload into a write-heavy one and puts a hot row lock on every viral link. Instead:

  1. Decouple with a queue. On each redirect, the API server fires a tiny event {short_key, timestamp, referrer} into a message queue and returns the redirect immediately. Counting is asynchronous — off the critical path.
  2. Aggregate in batches. A consumer drains the queue, aggregates counts per key over a window (say, 1 minute), and writes one batched update per key. 4,000 events/second become a handful of writes.
  3. Approximate when exactness is overkill. For unique-visitor counts, a HyperLogLog sketch estimates distinct visitors in ~12 KB of memory with ~2% error — versus storing every visitor ID. Name-drop this; it's a classic senior-level flourish. (A HyperLogLog is a probabilistic data structure: it trades exact counting for tiny memory by hashing visitors into buckets and estimating from the bucket patterns.)

The principle. Analytics is a separate write path from the core redirect path. The redirect path stays a pure read (fast, cacheable); counting happens asynchronously in bulk. Whenever an interviewer adds "oh, and we need stats," your reflex should be: queue it, batch it, keep it off the hot path.

10

Q&A with full model answers

Four questions that come up in the room, answered the way a senior engineer would answer them — verdict first, reasoning after.

Q1
Why 302 instead of 301 for the redirect?
The interviewer is testing whether you understand the operational consequences of HTTP semantics, not just the status codes.

Model answer: "302, because a shortener's redirect is a policy decision, not a fact about the web. 301 tells the browser to cache the redirect permanently — after one visit, the browser never asks me again. That kills three things I need: click analytics (I stop seeing visits), destination changes (a user edits the long URL and the browser ignores it), and expiry (an expired link keeps working in the user's browser). 302 keeps the browser checking back every time, so I stay in control. The cost is one extra lookup per click, which my cache layer absorbs — that's exactly what the Redis/edge layer is for."

Q2
How do you generate short keys at scale without collisions?
This is the core of the question. They're listening for you to reject the naive answers with math, not just recite KGS.

Model answer: "Three options. Hashing the URL looks clean, but the birthday problem kills it: with 7 base62 chars you have ~3.5 trillion keys and a 50% collision chance after only ~2 million keys — against a 6-billion-row table, every write becomes a check-and-retry loop. A distributed counter with range allocation is unique by construction and gives the shortest keys, but sequential keys are enumerable, which leaks private links. My pick is a Key Generation Service: it pre-generates random keys, stores them in an unused table, and hands them out; API servers keep a local buffer so the hot path never blocks on it. Standby KGS shares the same tables for failover. Uniqueness is structural, keys are unpredictable, and the write path stays fast."

Q3
Walk me through what happens when someone clicks a short link.
They want the full request path, end to end, with the cache layers named. Keep it to five steps.

Model answer: "One: the browser hits shrt.ly/abc12. Two: the CDN edge checks its short-TTL cache — hottest links resolve here in ~10ms. Three: on a miss, the app server checks Redis, cache-aside; hot keys hit here. Four: on a Redis miss, it reads the database by primary key on short_key, checks expires_at, populates Redis, and returns a 302 with the long URL in the Location header. Five: asynchronously — off the critical path — it fires a click event into a queue for the analytics pipeline. The browser follows the 302. Total added latency on the cached path is a few milliseconds."

Q4
How do you stop spammers from abusing your shortener?
A security-flavored follow-up. They're checking whether you treat abuse as a design constraint from the start.

Model answer: "Layered. First, rate limit the shorten endpoint — token bucket per IP and per user — so a spam factory can't mint links faster than a human. Second, screen every submitted destination against a phishing/malware blocklist before issuing a key, and quarantine matches. Third, use random non-enumerable keys so attackers can't scrape the link space. Fourth, require authentication for custom vanity aliases and reserve brand namespaces. And the read path only ever returns 404 for unknown keys — no oracle that tells an attacker which keys exist. The redirect itself stays unauthenticated, because the product only works if anyone can click."

11

Practice drills (untimed)

Untimed, rubric-graded. Do them on paper or out loud — the point is the reasoning, not the clock.

Drill 1 — Size it: 1B URLs/month

Redo the §2 back-of-the-envelope math for 1 billion new URLs per month, 10:1 read ratio, 5-year retention. What breaks first in the design above, and what changes?

Rubric: correct per-second rates (∼400 avg / ∼4,000 peak writes; ∼40,000/s peak reads) and storage (60B rows × 500 B ≈ 30 TB) · identifies that a single relational DB now needs sharding by short_key · notes the KGS key pool must be sized/generated faster, and the analytics queue becomes a first-class citizen · bonus: mentions Redis cluster + CDN becoming mandatory, not optional.

Drill 2 — Defend the choice: counter vs KGS

Your interviewer says: "KGS is an extra service. Why not just use a database auto-increment counter with range allocation? Simpler." Give the two-minute rebuttal.

Rubric: concedes the simplicity honestly · names enumeration as the decisive flaw (sequential keys leak private links) · notes range-allocation still needs a coordinator, so "simpler" is partly an illusion · lands on: KGS buys unpredictability + structural uniqueness for one small service — and offers the compromise (counter with a large random starting offset) if they push.

Drill 3 — Design the expiry

A customer wants: "my campaign link dies exactly at midnight on Dec 31, and I want to see a branded 'expired' page, not a 404." Sketch the read path and the cleanup.

Rubric: read path checks expires_at on lookup (lazy — no sweeper in the hot path) · returns a branded expired page (a 410 Gone is the correct status) instead of 404 · cache entries for expiring keys get TTL ≤ remaining lifetime so no stale redirects after midnight · background sweeper deletes old rows in batches off-peak · never reissues the key.

12

Cheat sheet & 60-second framing

URL shortener — six decisions

  1. Asymmetry: write-once, read-many (10:1) — cache is the architecture, not an optimization.
  2. Redirect: 302, not 301 — keeps analytics, edits, and expiry under your control.
  3. Keys: KGS (unique by construction, non-enumerable); counter+base62 second; hash-and-hope dies to the birthday problem.
  4. Storage: trivial schema, short_key as primary key; SQL fine early, shard by key when growth demands.
  5. Abuse: rate-limit creation, screen destinations, random keys, auth for vanity aliases.
  6. Analytics: separate async write path — queue events, batch-aggregate, HyperLogLog for uniques.

60-second framing — how to open in the room:

"A URL shortener is a write-once, read-many key-value store with a redirect on top. Scope: shorten, 302 redirect, custom aliases, expiry, click analytics — AP-flavored, low latency. Sizing: 100M URLs a month is ~40 writes a second, 400 peak; reads run 10:1; five years of data is about 3 terabytes — so this is a latency and key-generation problem, not a storage problem. Keys are the heart of it: I'll use a Key Generation Service that pre-mints random keys so uniqueness is structural, not checked. Reads go CDN → Redis → database, cache-aside, because entries are effectively immutable. Abuse gets rate limiting plus destination screening from day one, and analytics runs on a separate async queue so counting never touches the hot path."
