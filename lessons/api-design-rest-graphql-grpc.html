API Design: REST vs GraphQL vs gRPC

Every system you have designed so far talks to something else — the app talks to the server, services talk to each other. The contract they speak is the API, and picking the wrong one is how a fast system gets slow, chatty, or impossible to change. This lesson gives you the three contracts, the math behind their costs, and a decision rule you can defend.

1. What is an API? Start from zero

Picture Riverside FC on match day. The club has one vault of facts: fixtures, live scores, player stats, ticket availability. Three different consumers want those facts: the club's phone app, the club website, and a broadcaster's graphics system that puts live scores on TV. None of them is allowed to reach into the vault directly. Instead, each one talks to a counter at the front of the vault, hands over a written request in an agreed format, and gets an answer back in an agreed format. That counter, and the agreed formats, are the API — short for Application Programming Interface, which is just a fancy name for "the agreed way two pieces of software talk."

The vocabulary, defined before it is used:

  • Client is whoever asks — the phone app, the website, another service. Server is whoever answers. The client never touches the server's database; it only sees what the API shows it. That separation is the whole point: the server team can rebuild the vault behind the counter without breaking every client, as long as the counter's format stays the same.
  • Request is the question; response is the answer. A request names what it wants and sometimes carries a payload — the data attached to the request or response, like the JSON body of a match result.
  • Endpoint is one specific counter window: one address that does one job, for example "give me match 42." A whole API is a set of endpoints, or — as you will see with GraphQL — sometimes just one.
  • Schema is the written contract for the data's shape: which fields exist, what type each one is (a number, a string of text, a date), and which are required. If the schema says a player has a goals number, every client can rely on that. Schemas are what make APIs changeable without chaos: change the schema carelessly and every client breaks at once.
  • Serialization is turning in-memory data into bytes that can travel over a network, and back again. JSON (JavaScript Object Notation — human-readable text like {"team": "Riverside", "goals": 2}) is the common one. Protocol Buffers (protobuf) is the compact binary alternative you will meet in the gRPC section: smaller and faster, but not human-readable.
The one-sentence framing to carry through this lesson

REST, GraphQL, and gRPC are not three versions of the same idea getting progressively better. They are three different answers to three different questions: REST answers "how do we expose resources over the web's own rules?", GraphQL answers "how does a fast-moving frontend get exactly the data it needs?", and gRPC answers "how do services inside one company talk to each other as fast as possible?" Most bad API decisions come from answering one question with another question's tool.

2. The running example: one club, three consumers

Keep this picture in mind for every section. Riverside FC serves:

  • The phone app — used by fans on stadium Wi-Fi and patchy mobile data. It shows one match screen: the score, the two teams, the scorers, and the next fixture. It needs a small, exact set of fields, and every extra kilobyte costs battery and waiting time.
  • The website — built by a web team that changes screens every week. Last week the match screen gained a "form guide" (last five results); this week it gains player ratings. The frontend team wants to change what data a screen shows without waiting for the backend team to ship a new endpoint.
  • The broadcaster's graphics engine — a service, not a human, that pulls live match events (goals, cards, substitutions) dozens of times a second and must never miss one. It is written by a different company, but it runs inside a trusted, high-throughput pipeline.
  • Internal services — the ticket service asking the seat service "is seat 42 free?", the notification service asking the user service for a fan's language preference. These calls happen thousands of times a second, machine to machine, inside Riverside's own network.

One club, four very different consumers. Watch how each API style fits some of them beautifully and others badly — that fit, not fashion, is the decision.

3. REST, in full

REST (Representational State Transfer) is the web's home-grown style. Its core idea is disarmingly simple: everything the API exposes is a resource — a noun, like a match, a team, or a player — and you act on resources with the standard verbs the web already has. It is not a protocol with a rulebook; it is a set of conventions on top of HTTP, the protocol browsers already speak.

3.1 Resources, verbs, and status codes

A REST endpoint is a URL naming a resource, plus an HTTP verb saying what to do with it:

GET    /matches/42            — read match 42
GET    /matches/42/scorers    — read match 42's scorers
POST   /matches               — create a new match
PUT    /matches/42            — replace match 42 entirely
PATCH  /matches/42            — change part of match 42
DELETE /matches/42            — delete match 42

The verbs, defined precisely because interviewers probe them:

  • GET reads and never changes anything. It is safe (no side effects) and idempotent — a word that will recur all lesson: doing it twice has the same effect as doing it once. Refreshing a score page a hundred times changes nothing.
  • POST creates something new. It is not idempotent by default: sending "create a ticket order" twice creates two orders — unless you add an idempotency key (a client-chosen unique token sent with the request; the server remembers it and returns the original result for a repeat, covered again in section 7).
  • PUT replaces a whole resource and is idempotent: replacing match 42 with the same body ten times leaves the same match. PATCH changes only the fields you send; DELETE removes, and is idempotent too (deleting an already-deleted match still leaves it deleted).

Responses carry status codes — three-digit numbers that say what happened before you even read the body: 200 OK, 201 created, 204 no content, 400 your request was malformed, 401 you are not authenticated (we do not know who you are), 403 you are authenticated but not allowed, 404 no such resource, 409 conflict (for example, the seat is already taken), 429 too many requests (rate limited — see Lesson 11), 500 the server failed. A good REST API uses these consistently, so a client can branch on the code alone: 2xx means "it worked," 4xx means "the client must fix its request," 5xx means "the server must fix itself." Never return 200 with an error hidden inside the body — that forces every client to parse bodies just to learn something failed.

3.2 REST's two classic costs: over-fetching and under-fetching

Here is REST's structural weakness, and it is worth stating as plainly as possible. A REST endpoint returns a fixed shape: the server decides what GET /matches/42 contains, and every client gets the same shape. The phone app needs 6 fields; the endpoint returns 40 (full team sheets, referee details, weather, broadcast notes). The 34 unneeded fields are over-fetching — data shipped, paid for in bytes and battery, and thrown away.

The mirror problem is under-fetching: one endpoint never has quite enough. The match screen needs the match, both teams, and the scorers — three endpoints, three round trips. Each round trip on a mobile network costs 50–200 milliseconds before a single byte of data moves, so three sequential trips can cost half a second of pure waiting. Clients work around this with tricks — field selection (?fields=score,teams), embedding (?include=scorers) — but every trick is a custom dialect the server team must build and document, and it quietly reinvents half of GraphQL. Lab A below lets you feel both costs in numbers.

3.3 Where REST wins

REST wins wherever the web's own machinery helps you: responses are cacheable by URL (a CDN or browser cache can serve GET /matches/42 without ever reaching the server — this is why Lesson 3's caching patterns fit REST so naturally), it is trivially debuggable (paste a URL into a browser, read JSON), every language and tool speaks HTTP, and its statelessness — each request carries everything the server needs, no server-side session memory — lets any server instance answer any request, which is exactly what load balancers (Lesson 2) want. For a public, long-lived API consumed by many unknown clients, REST is still the default answer, and saying so is not old-fashioned — it is the boring, correct choice.

4. GraphQL, in full

GraphQL is a query language for APIs, invented at Facebook for exactly the phone-app problem above. Its radical idea: there is one endpoint, usually /graphql, and the client writes the query describing exactly what it wants. The server answers with exactly that shape — no more, no less.

query {
  match(id: 42) {
    score
    homeTeam { name formGuide }
    scorers { player { name } minute }
  }
}

Read that query as a shopping list: "give me the score, the home team's name and form guide, and each scorer's name and minute — nothing else." If next week the screen adds player ratings, the frontend team edits the query. No backend change, no new endpoint, no waiting for a release train. That shift — the client defines the response shape — is GraphQL's entire pitch, and it is a genuine superpower for fast-moving frontends with many screens.

4.1 How it works under the hood (just enough)

Three pieces, each defined once:

  • Schema — the server publishes a typed contract of everything queryable: types like Match and Player, their fields, and the entry points (Query for reads, Mutation for writes, Subscription for live streams). Clients can introspect the schema — ask the server to describe itself — so tooling can autocomplete queries and catch typos before runtime.
  • Resolvers — small functions, one per field, that fetch that field's data. The scorers resolver queries the database; the player.name resolver reads a row. Resolvers are the source of GraphQL's famous trap, next.
  • One endpoint, POST only (usually) — every query, read or write, goes to the same URL as a POST body. That is a feature for flexibility and a cost for caching: HTTP caches key on URLs, and one URL for everything means the URL-based caching REST gets for free largely disappears. GraphQL answers with its own caching (persisted queries, per-field cache hints, and client-side normalized caches like Apollo's, which store each object once by ID and reuse it across screens) — but you must build it deliberately; it is not inherited from the web.

4.2 The N+1 problem, explained with a team sheet

Ask for 11 players and each player's club. A naive server runs one query for the 11 players, then one query per player for their club: 1 + 11 = 12 queries. Ask for 11 players × their last 5 matches × each match's stadium and you are suddenly at hundreds. That is the N+1 problem: N items each triggering one extra fetch, turning one client request into N+1 database hits. The standard fix is a DataLoader — a batching layer that collects all the club lookups from one request tick, fires them as a single WHERE club_id IN (...) query, and hands results back to the right resolvers. Name DataLoader in a design discussion and you have shown you know GraphQL's cost, not just its pitch. The second cost is query complexity: a client can ask for a deeply nested query ("every player, every match they ever played, every other player in those matches…") that costs the server enormously. Production GraphQL APIs cap query depth and total complexity, and charge or reject queries above the budget — the same rate-limiting instinct as Lesson 11, applied to query shape instead of request count.

4.3 Where GraphQL wins — and where it does not

GraphQL wins when one backend serves many fast-changing frontend screens (the website team above), when mobile clients on slow networks pay per byte, and when a team wants strongly typed, self-documenting contracts without versioning every change (adding a field is backwards-compatible; clients simply do not ask for it until they want it). It loses, or at least adds needless machinery, when clients are few and stable, when responses are naturally cacheable by URL, when the API is consumed by simple scripts or third parties who would rather read a list of endpoints, and when the workload is file uploads or simple CRUD that REST already expresses cleanly. "GraphQL everywhere" is a fashion statement, not an architecture.

5. gRPC, in full

gRPC (Google's Remote Procedure Call framework) is the style for machines talking to machines. Forget resources and URLs: you define procedures — functions a client can call on a server as if they were local — in a .proto file, and gRPC generates the client and server code for you in every major language.

service SeatService {
  rpc CheckSeat (SeatRequest) returns (SeatResponse);
  rpc StreamMatchEvents (MatchRequest) returns (stream MatchEvent);
}
message SeatRequest { string seat_id = 1; }
message SeatResponse { bool available = 1; }

Three pieces, each defined once:

  • Protocol Buffers (protobuf) — the schema language above and the binary wire format. Fields are numbered (= 1), values are encoded as compact binary instead of JSON text, and unknown fields are skipped, which is what makes protobuf evolution safe: adding field 3 does not break a client that only knows fields 1 and 2. Roughly speaking, protobuf payloads run 3–10× smaller than equivalent JSON and encode/decode faster — which matters when two services exchange millions of calls a day, and barely matters when a human waits on one.
  • HTTP/2 — the transport underneath. Where HTTP/1.1 handles one request at a time per connection (or a handful of parallel connections), HTTP/2 multiplexes — many requests share one connection simultaneously, each in its own stream — and supports server-push-style streaming. That is what makes gRPC's four call patterns possible.
  • Streaming — the four patterns: unary (one request, one response — the normal case), server streaming (one request, a stream of responses — the broadcaster's live match events, delivered as they happen instead of polled), client streaming (many requests, one response — a phone uploading GPS pings), and bidirectional streaming (both sides stream — a live chat or a game session). REST can approximate streaming with long-polling or websockets, but gRPC has it as a first-class pattern with backpressure built in.

Where gRPC wins: internal service-to-service traffic at high volume, polyglot teams (the generated clients keep Java, Go, and Python in lockstep with one schema), and streaming workloads. Where it loses: browsers. Browsers do not speak raw gRPC — they need gRPC-Web, a proxy translation layer — and its binary payloads cannot be pasted into a browser bar and read, so debugging needs dedicated tools. A public API for unknown third parties is almost never gRPC; an internal mesh of services almost always benefits from it. Many real companies run both: gRPC inside, REST (or GraphQL) at the edge.

The decision rule — say this out loud in the room

Ask three questions, in order. (1) Who is the client? Browser or public third party → REST first. Your own fast-moving frontend team → GraphQL earns its place. Your own services → gRPC. (2) What hurts more: bytes, round trips, or change? Bytes on mobile → GraphQL or gRPC's compactness. Round trips → GraphQL's single query or gRPC streaming. Change velocity → GraphQL's client-shaped queries. (3) What does caching need to be? If a CDN must serve it, REST's URL-keyed caching is hard to beat. If you cannot answer question 1, you do not have an API decision yet — you have a requirements question, and naming that is the senior move.

One more honest note: these styles mix in real systems all the time. Riverside FC could expose REST to the public, GraphQL to its own app and website teams, and gRPC between its ticket, seat, and notification services — with an API gateway (a single front door that routes, authenticates, and rate-limits requests before they reach individual services) sitting in front of all of it. "Pick one for everything" is the beginner answer; "pick per boundary, and name the boundary" is the senior one.

7. Cross-cutting: the five things every API needs, whatever its style

7.1 Versioning — how to change without breaking everyone

APIs are promises, and promises change. REST versions most plainly in the URL (/v1/matches → /v2/matches) or a header; GraphQL mostly avoids versions by only ever adding fields and deprecating old ones (marking them "do not use, removal planned") — clients migrate field by field instead of all at once; gRPC versions through protobuf field numbers, where old clients ignore unknown fields. The rule underneath all three: never break a field a client already relies on. Rename a field and you have broken every client that reads it; add a new field alongside it and nothing breaks. When a breaking change is unavoidable, ship the new version, run both side by side, and give clients a dated sunset window — never a surprise.

7.2 Pagination — how to return a list without returning the world

A list endpoint for "all Riverside players" cannot return all of them in one response. Offset pagination (?page=3&limit=20) is simple but drifts: if a player is added while a client pages through, items shift and the client sees duplicates or skips one. Cursor pagination (the server returns an opaque next_cursor token marking "you stopped here"; the client sends it back for the next page) is stable under inserts, because the cursor points at a position in an ordering, not a page number. Use offset for admin screens with stable data; use cursor for feeds and anything a user scrolls through while the world changes. Both need a maximum page size enforced server-side, or one client can ask for a million rows and become an accidental denial-of-service attack on your own database.

7.3 Errors — one contract, everywhere

Pick one error shape and use it on every endpoint: a machine-readable code (SEAT_TAKEN), a human-readable message, and — for validation failures — which field failed and why. Clients then write one error handler, not one per endpoint. Pair it with retry guidance: 5xx errors are retryable (the server may recover), most 4xx are not (retrying a malformed request just fails again), and 429 must come with a Retry-After header saying how long to wait — otherwise clients retry immediately and turn a small overload into a retry storm (Lesson 23).

7.4 Idempotency — making "send again" safe

Networks fail after the server acted but before the client heard the answer — the ticket-order ambiguity from Lesson 26. The fix, repeated because it matters: the client generates a unique idempotency key per logical operation and sends it with the request; the server stores the key with the result, and a repeat of the same key returns the stored result instead of acting again. Keys must be scoped per operation (a new order gets a new key; retrying the same order reuses its key) and stored long enough to outlive realistic retries. This is a property of the operation, not of the API style: REST, GraphQL mutations, and gRPC calls all need it wherever money or inventory moves.

7.5 Caching and authentication, briefly but correctly

Caching: REST responses cache by URL with Cache-Control headers (how long a response may be reused) and ETags (a version fingerprint: the client asks "has this changed since this fingerprint?" and gets a tiny 304 Not Modified instead of the full body when it has not). Private, per-user data must be marked non-cacheable by shared caches, or one fan sees another's tickets. Authentication — proving who you are — and authorization — proving you are allowed — deserve their own lesson; the one line to carry now is that APIs should accept short-lived tokens (a bearer token in the Authorization header, or a signed JWT — a JSON Web Token, a tamper-evident token whose contents the server can verify without a database lookup) rather than raw passwords, and that a token proves identity, not permission: the server must still check, per request, that this fan may touch this resource.

8. Senior-depth traps

  • "GraphQL fixes over-fetching, so it is always faster." Not on a slow network with a naive server: one GraphQL query can hide N+1 database hits and an unbounded nested traversal behind a single round trip. Count the database queries a query causes, not just the HTTP requests. If you cannot bound query complexity, GraphQL's flexibility is a loaded gun pointed at your database.
  • "REST is stateless, so it scales infinitely." Stateless means any server can answer any request — true, and valuable. It does not mean the database behind those servers scales. A REST API that fans every request into an unindexed query still falls over; statelessness removes one bottleneck, not all of them.
  • "gRPC is faster, so expose it to the browser." Browsers cannot speak raw gRPC, and the gRPC-Web proxy you would add erases part of the streaming story and all of the "just paste the URL" debuggability. Faster on the wire is not faster for the team that has to debug it at 2 a.m. through a proxy.

9. Questions with full model answers

Tap each question to reveal a complete model answer — the kind of answer that names the decision, the reason, and the trade-off, in that order.

Q1. "Design the API for a match-day app." Where do you start, and which style do you pick?

Model answer. Start with the consumers, not the style: the app is your own fast-moving frontend on patchy mobile data, showing one screen per match. That points to GraphQL: one query per screen returns exactly the fields that screen needs, so a screen that needs 12 fields does not download 120, and when the screen gains player ratings next week the frontend edits its query without a backend release. Back it with query-depth and complexity limits (so no client can ask for every player, every match, every stadium in one query) and DataLoader batching (so one query does not become hundreds of database hits). If the same backend also serves a public developer API, expose REST alongside it — public third parties want stable, cacheable, browsable endpoints, not your internal query schema. The senior line: one backend, two front doors, each chosen for its consumer.

Q2. "Your REST API is slow on mobile. What is actually wrong, and what do you change?"

Model answer. Diagnose before prescribing: measure whether the cost is round trips (under-fetching: the screen calls match, then teams, then scorers sequentially) or payload (over-fetching: each endpoint returns 40 fields the screen ignores). If it is round trips, first fix cheaply — parallelize independent calls, or add an aggregate endpoint (or ?include= embedding) that returns the screen's data in one trip — and only switch styles if the screens keep changing faster than the backend can ship endpoints, which is the point where GraphQL's client-shaped queries earn their complexity budget. If it is payload, add field selection (?fields=) or trim endpoint shapes. "Switch to GraphQL" without saying which of the two costs dominates is a guess dressed as an answer; naming the measured cost first is what makes it a diagnosis.

Q3. "Two of your services exchange 50,000 messages a second. REST over JSON is struggling. What do you propose?"

Model answer. Propose gRPC, and say why each piece helps: protobuf's binary encoding cuts payload roughly 3–10× versus JSON and encodes faster, HTTP/2 multiplexing lets thousands of calls share connections instead of paying per-call connection costs, and the generated clients from one .proto schema keep both services in lockstep as fields evolve (old clients ignore unknown fields). Add the boundary honestly: keep gRPC internal — browsers cannot speak it natively, so the public edge stays REST — and if the traffic is event-shaped rather than request-shaped (a stream of match events, not "is seat 42 free?"), consider a message queue or log (Lessons 9 and 12) instead of any RPC style, because a queue survives a consumer being down and RPC does not.

Q4. "A client paged through your player list and saw the same player twice. What happened, and how do you fix it?"

Model answer. That is offset pagination drifting under inserts: the client asked for page 1 (players 1–20), a new player was inserted near the top, and page 2 (players 21–40 by the new ordering) now overlaps what page 1 showed. The fix is cursor pagination: the server returns an opaque cursor marking the last item seen in a stable ordering (for example, "after player id 847, ordered by created date then id"), and the next request resumes from that position regardless of inserts. Keep offset pagination only for stable, admin-style lists, enforce a server-side maximum page size so no client can request a million rows, and note the same class of bug anywhere a client assumes a list is frozen while the world changes.

10. Practice drills (untimed — depth over speed)

Drill 1 — Price a screen.

Your match screen needs 8 fields. A REST endpoint returns 45 fields per call and the screen needs 3 calls; a GraphQL query returns exactly 8 fields in 1 call. At 60 bytes per JSON field and 100 ms per round trip, compute the bytes and the round-trip waiting time for each approach, then say which cost matters more on a stadium's congested mobile network — and why.

Rubric: REST = 3 × 45 × 60 = 8,100 bytes and 300 ms of round-trip waiting (if sequential); GraphQL = 8 × 60 = 480 bytes and 100 ms. Full marks for naming that both costs shrink, and that on congested mobile the round trips usually hurt more than the bytes — latency, not bandwidth, is the binding constraint.

Drill 2 — Defend a mixed API.

Riverside FC exposes REST publicly, GraphQL to its app team, and gRPC internally. A reviewer calls this "three APIs to maintain" and proposes standardizing on GraphQL everywhere. Write the three-sentence rebuttal.

Rubric: One sentence per boundary: public third parties need stable, cacheable, browsable endpoints (REST); internal services need compact binary throughput and generated clients (gRPC); browsers cannot speak raw gRPC and public caching does not work through a single GraphQL endpoint. Full marks for framing it as per-boundary choice, not fashion.

Drill 3 — Spot the N+1.

A GraphQL query asks for 20 matches, each match's scorers, and each scorer's club. Sketch the naive resolver behavior, count the database queries, and name the fix.

Rubric: Naive: 1 (matches) + up to 20 scorer queries + one club query per scorer — well over 100 queries for one client request. Fix: DataLoader batching (collect scorer lookups into one IN (...) query, same for clubs) plus a query-complexity budget so nesting depth cannot grow without bound.

11. Cheat sheet: six decisions to carry into the room

  1. Consumer first. Public/third-party → REST. Own fast-moving frontend → GraphQL. Own services → gRPC.
  2. Name the cost. Over-fetching (fixed shapes) vs under-fetching (round trips) vs payload size — measure which one hurts before switching styles.
  3. Caching follows the URL. If a CDN must serve it, REST's URL-keyed caching is the strongest default.
  4. Bound GraphQL. DataLoader for N+1, depth and complexity caps for unbounded queries — flexibility without a budget is a vulnerability.
  5. Never break a field. Add, deprecate, sunset on a date — never rename or remove under a live client.
  6. Idempotency is per operation. Money or inventory moving? The request needs an idempotency key, whatever the style.
60-second framing — say this to open the topic

"An API is the contract between a client and a server. REST exposes resources over HTTP verbs — simple, cacheable, and the right default for public APIs, but its fixed shapes over-fetch and under-fetch. GraphQL lets the client shape each response, which is perfect for fast-moving frontends on mobile, at the cost of N+1 queries and query-complexity budgets you must build. gRPC uses compact binary protobuf over HTTP/2 with streaming, which is ideal for internal services, but browsers cannot speak it. So I choose per boundary: REST at the public edge, GraphQL for our own app, gRPC between services — and I make every money-moving call idempotent whichever style it uses."
