Content Delivery Networks (CDN)

A fan in Sydney taps play on the cup-final highlights two seconds after full time — and the video starts instantly, even though the club's servers are in Virginia and 5 million other fans tapped play at the same moment.

What is a CDN?

Start from zero. A content delivery network, or CDN, is a network of servers placed in cities all over the world whose job is to serve your content from the server closest to the person asking for it, instead of from the one place your own servers live. The origin is your own server (or object store) — the single source of truth where the content is created and stored. An edge server is a CDN server in a city near the user that keeps a copy of popular content. A point of presence, or PoP, is a data-centre location where a CDN runs edge servers — a large CDN has hundreds of PoPs, so almost every user on earth is within a few dozen kilometres of one. When a fan's request is answered by an edge server that already has the content, that is a cache hit; when the edge server does not have it and must fetch it from the origin, that is a cache miss.

The soccer running example: Riverside FC has one club shop at the stadium, but on cup-final day 5 million fans in 100 countries all want the same 2-minute highlights clip at the same moment. If every fan's phone had to reach the one shop in Virginia, two things break: the speed of light (a round trip from Sydney to Virginia is about 160 ms of pure physics, before any server work) and the shop's own bandwidth (5 million simultaneous video streams would need tens of terabits per second). A CDN is the club opening a pop-up stall in every city: the clip is copied to the stall in Sydney, in Lagos, in São Paulo, and each fan walks to their nearest stall. The stall's copy is what a cache is — the same content, stored closer, served faster.

Terms, defined as they appear

Origin: your server, the source of truth. Edge / PoP: a CDN server / data-centre location near the user. Cache hit / miss: the edge has the content, or it does not. TTL (time-to-live): how long an edge server may serve its copy before it must re-check with the origin — the expiry date on a cached copy. Cache key: the identifier the edge uses to look content up — usually the URL, plus any headers that change the answer (like language or device type). Egress: data leaving a server or cloud, billed per gigabyte. Anycast: many servers worldwide sharing one IP address, so the internet's routing sends each user to the nearest one. Origin shield: a middle layer of CDN servers between the edges and your origin, so a miss from a hundred edges becomes one request to the origin instead of a hundred.

The one idea to carry through the whole lesson: a CDN does not make your servers faster — it makes most requests never reach your servers at all. Everything below — routing, cache hierarchies, invalidation, even the security story — is a consequence of deciding which requests the edge can answer on its own and which must travel back to the origin.

Requirements and back-of-the-envelope math

Scope first. We are designing the CDN layer for Riverside FC's public content: match highlights and full-match replays, club-shop product images, the live score page, and the matchday programme PDFs. We are not building the CDN itself (that is a business of laying fibre and operating thousands of servers) — we are deciding how a website uses one, which is exactly the framing an interviewer expects.

  • Functional: serve static content (video segments, images, CSS, JS) from the nearest edge; serve the live score and personalised pages without stale data; invalidate a changed file everywhere within minutes; absorb a cup-final traffic spike without the origin noticing; keep the club's origin reachable only through the CDN.
  • Non-functional: low latency for a fan anywhere (page interactive in well under a second); high cache-hit ratio (the fraction of requests served from the edge — 95%+ for static content); availability — the site must stay up when the origin is briefly down (serve stale copies while revalidating); and cost — egress is the bill, so every gigabyte served from the edge instead of the origin is money saved.

The sizing, with every step shown. Assume 50 million highlight views in the first 24 hours after the cup final, each view downloading a 200 MB clip, with 5 million fans watching at the same moment in the hour after full time at an average video bitrate of 5 Mbps:

  • Total bytes in a day: 50,000,000 × 200 MB = 10,000,000,000 MB = 10 PB/day. Ten petabytes. That is the number the origin would have to send if there were no CDN.
  • Peak bandwidth: 5,000,000 concurrent viewers × 5 Mbps = 25 Tbps. A single origin with 100 Gbps links would need 250 of them, all perfectly utilised — an absurdity. The CDN splits that 25 Tbps across hundreds of PoPs, so each edge handles a few tens of gigabits, which is ordinary hardware.
  • Latency, the physics: light travels through fibre at roughly 200,000 km/s, about two-thirds of its speed in a vacuum. A fan in Sydney is ~16,000 km from an origin in Virginia, so the round trip is 2 × 16,000 ÷ 200,000 = 0.16 s = 160 ms of pure travel time, before the server does anything. The same fan is ~50 km from the Sydney PoP: 2 × 50 ÷ 200,000 = 0.5 ms. No amount of server optimisation can beat that 160 ms — the only fix is to move the content closer, which is precisely what the edge does.
  • Page-load effect: a match centre page loads ~40 assets (images, CSS, JS, fonts). With 6 parallel connections, that is roughly 7 sequential round trips of fetching, plus a 2-round-trip TLS handshake. From the origin (180 ms per round trip once the server's own work is counted): 9 × 180 ms = ~1.6 s of network waiting alone. From the edge at a 95% hit rate, the effective round trip is 0.95 × 5.5 ms + 0.05 × 180 ms ≈ 14 ms, so the same page costs 9 × 14 ms ≈ 128 ms — about 13× faster. That gap is the difference between a fan staying and a fan leaving — and it comes from distance, not from faster code.
  • Cost: origin egress at a typical $0.09/GB vs CDN egress at ~$0.02/GB. Without a CDN, 10 PB = 10,000,000 GB × $0.09 = $900,000/day. With a 95% edge hit rate and an origin shield (see below) cutting origin traffic to ~1% of requests, the bill falls to roughly $207,000/day — a saving of about $693,000 on one day of cup-final traffic. (Lab B lets you check these numbers yourself.)
The decision the numbers force

Bandwidth and latency, not storage, are the problem a CDN solves. Ten petabytes of storage is cheap; ten petabytes delivered from one place in one day, at 25 Tbps, is not physically plausible. The CDN's job is to turn one impossible origin problem into hundreds of small, local ones — and to keep the origin's bill and load at ~1% of what they would be without it.

The architecture, in one pass

One request for a highlights clip flows through five stages, and the edge's decision at stage three is the whole system:

  1. Routing — get the fan to the nearest PoP. The fan's browser asks DNS for video.riversidefc.com. The CDN's DNS answers with the IP of the nearest healthy PoP (measured by the resolver's location and by live load), or the request is routed by Anycast: every PoP announces the same IP address, and the internet's routers deliver the packet to the closest one. DNS routing is flexible (it can weigh load and health per region) but adds a lookup; Anycast is instant (no extra lookup, and it fails over in seconds when a PoP dies) but coarser. Most large CDNs use both: DNS to pick a region, Anycast inside it.
  2. TLS termination at the edge. The fan's encrypted (HTTPS) connection ends at the edge server, not the origin. TLS termination means the edge holds the site's certificate and decrypts the request there. This matters for two reasons: the expensive handshake happens close to the fan (saving round trips across the ocean), and the edge can inspect the request — to apply a cache rule, a firewall rule, or a redirect — before the origin ever sees it.
  3. Cache lookup — the decision point. The edge computes the cache key (the URL, plus headers that change the answer, e.g. Accept-Language for a localised page) and checks its local store. On a hit, it serves the copy immediately and the origin never hears about the request. On a miss, it goes one step deeper — to the origin shield, not straight to the origin.
  4. Origin shield — the middle tier. A miss at one edge is forwarded to a regional shield PoP, a bigger cache that aggregates misses from many edges in its region. If the shield has the clip, it answers and the edge stores a copy for the next fan. Only if the shield also misses does the request reach the origin. With 100 edges missing the same new clip at once, the shield collapses that into a single origin fetch — this is why a viral moment does not melt the origin. The shield is the caching lesson's "cache-aside, one layer up" idea, applied geographically.
  5. Origin fetch and fill. The origin serves the file once, the shield and the edge each store a copy with its TTL, and every subsequent fan in that region is served from cache until the TTL expires. The origin's real job shrinks to: serve each object once per region per TTL window, and answer the small fraction of requests that can never be cached (a logged-in fan's personal feed).

Two supporting pieces complete the picture. The control plane is how the club configures the CDN — cache rules ("images: TTL 1 day", "live score: TTL 5 seconds, never cache the personalised header"), purge commands, and firewall rules — pushed out to every PoP. And the log pipeline streams per-request logs (hit/miss, PoP, latency, status) back to the club's analytics, because a CDN you cannot measure is a CDN you cannot tune: hit ratio per URL pattern is the number that tells you whether your cache rules are working.

The heart of it: what can be cached, and for how long

Three decisions determine whether a CDN helps or quietly serves the wrong thing. Get these right and the rest is configuration.

1. Static vs dynamic — the split that decides everything

Static content is the same for every fan: the highlights clip, a shirt photo, the club crest, the JavaScript bundle. It is cacheable by definition, and the question is only how long. Dynamic content is different per fan: the live score page with their fantasy team, a logged-in season-ticket holder's seat details, the cart. It cannot be cached as one copy — or rather, caching it as one copy serves one fan's data to another, which is the worst bug a CDN can produce. The standard split, and the one to say first in the room: cache the static aggressively, and route the dynamic straight through to the origin (the CDN still helps here — a warm, nearby TLS connection and a fast backbone between PoP and origin beat a cold connection across the ocean — but the origin still does the work). The middle ground is edge compute (Cloudflare Workers, Lambda@Edge): tiny programs that run at the PoP and can personalise a cached page — insert the fan's name into a cached shell, pick the language, A/B test a layout — without a round trip to the origin. The rule for edge compute: it may assemble and decorate, but it must never become a database; state still lives at the origin.

2. TTL and revalidation — how fresh is fresh enough?

A TTL is the edge's permission to serve a copy without asking. A 1-day TTL on a shirt photo means the edge serves it 10,000 times without bothering the origin — and means a changed photo takes up to a day to appear. The trade-off is hit ratio vs freshness, and the tools for managing it are: short TTLs for things that change (live score: 5 seconds — the origin still only gets one request per PoP per 5 seconds, which is a 99%+ reduction from per-fan polling); stale-while-revalidate, where the edge serves a slightly expired copy instantly and fetches a fresh one in the background, so no fan ever waits on a revalidation; and versioned URLs — the strongest trick in the book. If the CSS file is named main.a3f9c1.css (a hash of its contents), it never changes: a new build gets a new name, so it can carry a 1-year TTL and never be invalidated. The HTML page that references it carries a short TTL. This is the correct answer to "how do I cache aggressively without serving stale files": never mutate a cached object — give the new version a new name.

3. Cache keys — the same URL is not always the same answer

The cache key is usually the URL, but the URL alone is not always enough. The same /match-centre URL returns English to a fan in London and Spanish to a fan in Madrid — if the key ignores the language header, the second fan gets the wrong language. The same image URL returns a 4K image to a desktop and a 400-pixel one to a phone — if the key ignores device type, one of them gets the wrong size. The rule: the key must include every input that changes the response (language, device class, sometimes a cookie for a logged-in variant). The trap is the opposite direction: including something that does not change the response (a tracking query parameter like ?utm_source=twitter) fragments the cache — the same clip cached a hundred times under a hundred keys, each with its own cold start. Good CDN configuration is mostly the discipline of normalising the key: strip tracking parameters, include only the headers that matter, and keep the key space small.

The three decisions, in one sentence each

Split static from dynamic — cache the first, route the second through. Set TTLs by change rate, and version immutable files by content hash so they never need invalidating. Key the cache on exactly the inputs that change the answer — no more, no less. Get those three right and the CDN behaves like a local copy of your site in every city; get any one wrong and it serves stale pages, wrong languages, or a hundred cold copies of the same file.

Invalidation — when the wrong copy is out there

Sooner or later the club posts the wrong team sheet, or a shirt price changes, and the old copy is sitting in a hundred PoPs with a 1-day TTL. Three ways out, in order of preference:

  • Wait for the TTL. The honest default for anything with a short TTL. A 5-minute TTL means the bad copy is gone in 5 minutes everywhere. This is why short TTLs exist: they are the cheap, reliable invalidation mechanism, and most "purge" requests are really confessions that the TTL was too long.
  • Version and rename. For content-addressed files (the hashed CSS above), there is nothing to invalidate — the new version has a new URL, and the old one simply stops being referenced. This is the preferred answer for anything you control the naming of.
  • Purge. Send the CDN a command: "forget /team-sheet.pdf everywhere, now." A purge is a broadcast to every PoP, and it takes seconds to minutes to propagate — it is not instant, and during propagation some fans still get the old copy. Purges are also rate-limited and logged (a runaway purge of /* empties the entire cache and sends a thundering herd at the origin — the cache-stampede lesson, at planetary scale). Surrogate keys (also called cache tags) are the grown-up version: tag every product image with product-4821, and purge by tag to invalidate exactly that product's assets across all its URLs in one command.

The interviewer-grade line: purging is a correction mechanism, not a caching strategy. If your design needs frequent purges to stay correct, the TTLs are wrong or the content should have been versioned. Design the TTLs and the naming first; keep purge as the fire extinguisher.

Security and resilience — the edge as a shield

A CDN sits in front of the origin, so it is also the first thing an attacker meets — and that position turns into three defences that are hard to build yourself:

  • DDoS absorption. A distributed denial-of-service attack is a flood of requests meant to overwhelm a server. The CDN absorbs it by design: the flood is spread across hundreds of PoPs, each with far more capacity than the origin, and the edge drops obviously bad traffic (bad bots, malformed requests) before it ever travels toward the origin. The origin, hidden behind the CDN, sees a trickle. The catch: the origin must actually be unreachable except through the CDN (firewall rules allowing only the CDN's IP ranges, plus a secret header the CDN adds) — otherwise an attacker who learns the origin's real IP can bypass the whole shield, which is the classic "origin IP leak" failure.
  • Web application firewall (WAF) at the edge. A WAF is a filter that blocks known attack patterns (SQL injection, cross-site scripting) in incoming requests. Running it at the edge means a malicious request is dropped in Sydney instead of travelling to Virginia to be dropped there — and it means the rule is enforced once, for every request, instead of in every service behind the origin.
  • Stale-on-error. When the origin is down, the edge can keep serving its cached copies (past their TTL) instead of an error page. The site is degraded — the score is a few minutes old — but it is up, which is what a fan notices. This is the availability half of the CAP trade-off, applied to content: serve a slightly old truth rather than no truth at all.

Senior-depth traps

  • "A CDN makes everything faster." It makes cacheable, static content faster. A personalised, uncacheable API call still travels to the origin — the CDN only shortens the TLS handshake and the first network hop. Claiming a CDN speeds up your database queries is the tell that someone has not thought about what is actually cached.
  • "We set a 1-year TTL, so content is always fresh." A long TTL without versioned URLs is a promise you cannot keep: the only way to change the content is a purge, which is slow, rate-limited, and not guaranteed to reach every PoP at the same instant. Long TTLs are safe only for content-addressed, immutable files.
  • "A cache hit ratio of 99% means we're done." Hit ratio is an average that hides the worst case. A 99% hit ratio with the remaining 1% concentrated on one uncacheable, expensive origin endpoint is still an origin-melting design — and a 99% ratio measured across all URLs can hide a 40% ratio on the one page that matters (the match centre). Measure hit ratio per URL pattern, and weight it by origin cost, not by request count.

Questions, with full model answers

Q1. A fan in Sydney loads your site slowly even though you have a CDN. Walk through why, and what you check.

Model answer. A CDN only helps requests it can answer from the edge, so start by measuring, not guessing. Step one: check the cache-hit ratio for the slow page's URL pattern in the CDN logs — if it is low, the edge is mostly forwarding to the origin, and the 160 ms round trip is back in play. Step two: find out why the hit ratio is low. Common causes: a tracking query parameter (?utm_source=...) is fragmenting the cache key, so the same page is cached under a hundred keys; a Cache-Control: no-store or a session cookie is marking the response uncacheable; or the TTL is so short that every fan is the first fan. Step three: check the routing — is the Sydney fan actually reaching the Sydney PoP, or is DNS sending them to Singapore because their resolver's location is misreported? Step four: check the dynamic half — if the slow part is a personalised API call, no cache can help; the fix is a shorter network path (edge TLS termination, a warm backbone) or fewer origin round trips (batch the API, cache the static shell at the edge and fill the personal bits by edge compute). Close with the measurement that proves the fix: hit ratio per URL pattern and p95 time-to-first-byte by region, before and after.

Q2. Your site just published a wrong price on a shirt, and the page is cached in 200 PoPs with a 1-day TTL. What do you do — and what should you have done?

Model answer. Right now: purge by surrogate key (tag product-4821) if you tagged the assets, or purge the exact URLs — and say honestly that the purge takes seconds to minutes to propagate, so some fans will still see the wrong price in that window; if the price error is large enough to take orders at a loss, take the page down or serve a maintenance response at the edge until the purge lands. What you should have done: never let a changeable price live in a 1-day-TTL object. Price pages and product pages should carry short TTLs (minutes), or be versioned, or be served as a cached static shell with the price filled in at the edge or by a small API call. The deeper point: purging is a correction mechanism, not a caching strategy — a design that needs frequent purges has its TTLs wrong. The follow-up fix is to tag every product asset with its product's surrogate key at publish time, so the next correction is one purge command, not a list of URLs.

Q3. Design the CDN layer for a live match: the score updates every few seconds, 10 million fans are refreshing, and the origin must not melt.

Model answer. Split the page into what changes and what does not. The static shell (layout, CSS, images, club crest) gets long TTLs and versioned URLs — served from the edge, never touching the origin. The score itself is a tiny JSON payload with a 5-second TTL: each PoP fetches it from the origin at most once per 5 seconds, so 10 million refreshing fans become a few hundred origin requests per second, which is nothing — and fans still see a score at most 5 seconds old, which is fresh enough for a match. Add stale-while-revalidate so a fan never waits on the revalidation, and add request coalescing at the edge so a hundred fans arriving in the same second share one origin fetch. The live video (if any) is segmented and cached the same way as the highlights: each 2-second segment is immutable once published, so it gets a long TTL and a content-addressed name. Guard the origin behind the CDN's IP allow-list so a direct flood cannot bypass the edge, and pre-warm the PoPs with the shell before kick-off so the first fans are not all cache misses. Success metric: origin requests per second during the match, and p95 score latency by region — not total requests, which the edge absorbed.

Q4. When would you NOT use a CDN?

Model answer. When there is nothing to cache and nobody far away. A purely internal tool used by 50 people in one office, all near the origin, gains nothing from an edge network — the added hop and the configuration complexity are pure cost. A low-traffic site whose origin is already close to its users (a local club site with a mostly local audience) similarly gains little on latency, though the DDoS and WAF benefits can still justify it. And an API that is entirely personalised, real-time, and uncacheable (a trading terminal, a multiplayer game server) gets only the TLS and routing benefit — real, but small, and not worth calling a CDN design. The senior framing: a CDN is a cache with a global footprint, so the test is the same as any cache — is there repeated, shareable content, and are the readers far from the writer? If both answers are no, skip it and spend the effort on the origin.

Practice drills (untimed — depth over speed)

Drill 1 — Draw the request path. A fan in Lagos requests the highlights clip for the first time after the final whistle, then a second fan in Lagos requests it a minute later. Draw the full path of both requests (DNS/Anycast, TLS, edge lookup, shield, origin), marking every place a copy is stored and which requests the origin actually sees. Rubric: the first request reaches the origin exactly once (via the shield); the second is an edge hit; the diagram shows the copy stored at the shield and at the edge, and the TTL on each; and it shows the TLS handshake ending at the edge, not the origin.

Drill 2 — Set the TTLs. You have five objects: the club crest (never changes), the match-day CSS bundle (new every release), the live score JSON (changes every few seconds), a season-ticket holder's seat map (personal), and the cup-final highlights clip (published once, never edited). Assign each a caching policy — TTL, versioning, or do-not-cache — and justify it in one line each. Rubric: crest gets a long TTL (immutable); CSS gets a content-hashed name with a long TTL; score gets a ~5s TTL with stale-while-revalidate; seat map is private, no-store; the clip gets a long TTL with a surrogate key for the emergency purge.

Drill 3 — Diagnose the hit ratio. Your CDN dashboard shows an overall hit ratio of 92%, but the match-centre page loads slowly from the edge and the origin is seeing 10× the traffic you predicted. List three hypotheses, what log or metric confirms each, and the fix. Rubric: (1) cache-key fragmentation from tracking parameters — confirmed by distinct keys per URL in the logs, fixed by stripping them; (2) a session cookie forcing dynamic treatment — confirmed by Cache-Control: private on the response, fixed by splitting the personalised fragment out; (3) a hot uncacheable endpoint dominating origin load — confirmed by per-URL origin request counts, fixed with a short TTL or edge compute.

Sixty-second framing

"A CDN is a copy of your content in every city, so a fan downloads from kilometres away instead of across an ocean. The origin is the source of truth; the edge serves what it has, the origin shield collapses duplicate misses, and the origin only ever sees each object once per region per TTL window. The design decisions are which content is cacheable, how long each copy may live, and what the cache key includes — version immutable files by content hash so they never need invalidating, keep TTLs short on anything that changes, and treat purge as the fire extinguisher, not the strategy. The same position in front of the origin also absorbs DDoS and runs the firewall, as long as the origin is actually unreachable except through the CDN."
