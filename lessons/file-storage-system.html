Design a Distributed File Storage System

Dropbox, Google Drive, OneDrive: a folder on your laptop that is also a folder on your phone, your coach's tablet, and a server farm — even when the team bus has no signal. This lesson is the design behind that magic: chunked uploads, content-hash deduplication, a metadata service that is the real bottleneck, and the sync protocol that decides whose edit wins when two people change the same file offline.

1. What is a file storage system? Start from zero

Picture a filing cabinet in the Riverside FC clubhouse. Every drawer holds folders, every folder holds documents: scouting reports, player contracts, physio notes, match videos. A file storage system is that cabinet, stretched across the internet: you drop a file into a folder on your laptop, and the same file appears in the same folder on your phone, your colleague's tablet, and a web page — without you emailing it to yourself or carrying a USB stick.

The vocabulary, defined before it is used:

  • File is a named bag of bytes — a document, a photo, a video. Folder (or directory) is a container that groups files and other folders into a tree, like /Scouting/2026/Striker targets.pdf.
  • Blob (Binary Large Object) is the system's word for "the raw bytes of a file, stored as one anonymous lump." The blob store does not know or care that a blob is a scouting report; it just stores bytes and hands them back when asked by an ID. Lesson 18's video platform used exactly this idea for video files.
  • Metadata is "data about data": a file's name, size, owner, folder, creation time, modification time, and permissions. Crucially, metadata is not the file's bytes — it is the card in the library catalogue that tells you where the book is. Keeping metadata separate from blobs is the single most important architectural decision in this whole lesson.
  • Chunk (or block) is a fixed-size slice of a file. Instead of storing a 2 GB match video as one lump, the system cuts it into, say, 4 MB chunks. Chunking is what makes uploads resumable, deduplication possible, and sync cheap — you will see all three below.
  • Sync (synchronization) is the act of making two copies of the same folder agree: if a file changed on your laptop, sync copies that change to the server and then down to your phone. Offline means a device that cannot reach the server right now; its changes wait in a queue until it reconnects.
  • Version is one saved state of a file over time. Edit a contract three times and the system can keep all three versions, so a bad edit (or ransomware encrypting everything) can be undone by restoring an older one.
  • Deduplication (dedup) is storing one physical copy of bytes that many files share. If all 30 squad members have the same 500 MB pre-season fitness video, dedup stores it once, not 30 times.
The one-sentence framing to carry through this lesson

A file storage system is two systems pretending to be one: a small, hot, strongly consistent metadata service that answers "what files exist, where, and who may touch them?" and a huge, dumb, cheap blob store that answers "give me these bytes." Almost every hard problem in the design lives in the first system or in the gap between the two — never in the blob store itself.

2. The running example: Riverside FC's shared drive

Keep this picture in mind for every section. Riverside FC runs its whole club off one shared drive:

  • The head coach edits the team sheet on his laptop on the team bus, with no Wi-Fi. It must sync when the bus reaches the stadium.
  • The chief scout uploads a 2 GB video of a striker target from a hotel with flaky Wi-Fi that drops every few minutes. The upload must survive the drops.
  • Thirty players each receive the same 500 MB pre-season fitness program. The system must not store or transfer it 30 times.
  • The physio and the coach both edit the same injury report offline, on different devices, before a cup final. Somebody's edit must not silently vanish.
  • The media team shares one match-highlight clip publicly, and it gets downloaded a million times in an hour after a cup win.

Five people, five different pressures. Watch how one design answers all five — and where it has to say "we cannot have both, so we choose this."

3. Requirements and back-of-the-envelope math

State the requirements before drawing boxes — interviewers reward this discipline, and it stops you designing for a problem nobody stated.

3.1 Functional requirements (what it must do)

  • Upload, download, rename, move, and delete files and folders, from phone, laptop, and web.
  • Sync automatically across a user's devices, including changes made offline.
  • Share a file or folder with specific people, or by link, with read or edit permission.
  • Keep old versions so a file can be restored after a bad edit or deletion.
  • Show the same folder tree everywhere, quickly, even with thousands of files.

3.2 Non-functional requirements (how well it must do it)

  • Durability: a stored file must effectively never be lost — the standard target is 11 nines (99.999999999%) per year, which blob stores achieve with replication or erasure coding (defined in section 5.4).
  • Availability: reading your files should work even if one data centre is down.
  • Consistency, scoped honestly: metadata (names, folders, permissions) needs strong consistency — two people must not both believe they own the same filename. File contents can be eventually consistent across devices; your phone may show yesterday's team sheet for a minute, but it must never show a half-written one.
  • Scale: the numbers below. Latency: listing a folder and starting a download should feel instant; a full upload may take minutes, but it must never restart from zero.

3.3 The math (show your working — interviewers check it)

Users: 10M · files per user: 100 · total files: 1B
Average file size: 2 MB → raw bytes: 1B × 2 MB = 2 PB
Blob replication ×3 → 6 PB of blob storage
Metadata per file ≈ 500 bytes → 1B × 500 B = 500 GB of metadata
Daily uploads: 20M files/day → 20M ÷ 86,400 ≈ 230 files/sec average, ~1,150/sec at 5× peak
Daily ingest bytes: 20M × 2 MB = 40 TB/day ≈ 460 MB/s average

Read those numbers as design guidance, not trivia. 6 PB of blobs is big but cheap and dumb — object storage handles it. 500 GB of metadata is small but hot: every list, rename, share, and sync decision touches it, millions of times a second, and it must be consistent. That asymmetry — huge dumb storage, small smart index — is why the architecture splits in two. Also notice the upload rate: ~1,150 files/sec at peak is entirely manageable for a metadata service if each upload is a handful of small database writes, but it would crush a design that did one database transaction per chunk.

4. The two halves: metadata vs blobs

Draw this split first in any design discussion, before any other box:

Metadata serviceBlob store
StoresFile records, folder tree, chunk lists, versions, sharing rulesRaw chunk bytes, addressed by content hash
Size~500 GB in our math — small~6 PB — enormous
Access patternMany small reads/writes, latency-sensitiveFew large reads/writes, throughput-sensitive
ConsistencyStrong (names and permissions must agree)Immutable chunks: a chunk never changes, so no consistency problem
Typical technologySharded relational database (see below)Object storage (S3-style) or a distributed filesystem

Sharding the metadata. One database cannot hold a billion file records with headroom, so shard it — Lesson 6's sharding, applied here. The natural shard key is user_id (or the shared folder's owner): all of one user's files live on one shard, so listing a folder, renaming, and syncing are single-shard operations with no cross-shard transaction. The price: a shared folder's files live on the owner's shard, so a collaborator's access crosses shards on read — acceptable, because reads are cheap and sharing is rarer than listing your own drive. Never shard metadata by file_id hash alone: then one folder listing scatters across every shard (Lesson 6's scatter-gather cost, paid on the most common operation).

The core tables (one row per concept, nothing more): users, files (file_id, owner_id, parent_folder_id, name, size, latest version, created/modified time), chunks (file_version_id, chunk index, chunk hash, size), versions (file_id, version number, chunk list pointer, timestamp, editor), shares (file/folder_id, grantee, permission). Notice what is not in the database: bytes. The database says "version 7 of this file is chunks [A, B, C]"; the blob store holds A, B, and C. That indirection is what makes chunk-level deduplication and delta sync possible at all.

Why the metadata service is the bottleneck (say this out loud)

Every user action — open a folder, rename a file, share a link, sync a change — is a metadata operation, and there are billions of files but only thousands of blob operations per second of real pain. If your design scales the blob store beautifully and leaves metadata on one database, you have scaled the easy half. Interviewers listen for which half you worry about first.

5. Upload path: chunking, hashing, deduplication, resumability

Uploading a file is a four-step dance, and the order matters:

  1. Chunk on the client. The client splits the file into fixed-size chunks — 4 MB is the industry-standard starting point (Dropbox uses 4 MB). Fixed size, not content-defined, keeps the manifest simple: chunk i is bytes [i×4MB, (i+1)×4MB). The last chunk is smaller, and that is fine.
  2. Hash each chunk. The client computes a cryptographic hash of each chunk — SHA-256, a function that turns any bytes into a fixed 256-bit fingerprint. Change one byte of the chunk and the fingerprint changes completely; two different chunks essentially never share a fingerprint (a collision — two inputs with the same hash — is so unlikely for SHA-256 that systems treat it as impossible, while still verifying chunk size as a cheap second check).
  3. Ask what is missing. The client sends the list of chunk hashes to the server, which replies with the subset it does not already have. Chunks it already has are skipped entirely — no bytes cross the network.
  4. Upload only the missing chunks, in parallel, then commit. Missing chunks go up over separate connections (parallelism beats one long connection on flaky Wi-Fi), each to blob storage, and the client retries any failed chunk individually. Only when all chunks are stored does the client send a final commit: one metadata write recording the new file version and its chunk list. Until that commit lands, the file's old version is untouched — readers never see a half-uploaded file.

That one flow buys three features that look like magic:

  • Deduplication, free. The 30 players' identical fitness video produces identical chunk hashes. The first upload stores the chunks; the other 29 uploads send only hashes, get told "already have them," and commit a metadata record pointing at the same chunks. Storage saved: 29 × 500 MB. The same trick works across users (everyone's copy of a popular installer) and within a file (a video with repeated black frames). A reference count per chunk — how many file versions point at it — tells garbage collection when a chunk is truly orphaned and safe to delete: only when the count hits zero.
  • Resumability, free. The scout's hotel Wi-Fi drops mid-upload of a 2 GB video. On reconnect, the client re-sends the hash list; the server reports only the chunks still missing. Nothing already uploaded is re-sent. The 4 MB chunk size is the trade-off here: smaller chunks mean less re-sent work after a drop, but more manifest entries and more per-chunk request overhead. 4 MB is the sweet spot most systems land on.
  • Delta sync, nearly free. Edit one paragraph of a 100 MB scouting document and only the chunks containing changed bytes get new hashes — usually one or two chunks. The sync uploads those chunks only, not the whole file. (A pedantic note for the senior room: fixed-size chunking has a weakness — inserting one byte at the top of a file shifts every later byte, changing every chunk's hash. Content-defined chunking, which cuts at data-dependent boundaries, fixes this; Dropbox's later designs use it. Name it as the refinement, not the starting point.)

5.1 A privacy caveat you must name honestly

Cross-user deduplication has a sharp edge: if the server tells your client "we already have this chunk," it has confirmed that someone already uploaded those exact bytes — a so-called confirmation-of-file attack. Real systems handle this by only deduplicating within a user or a shared folder by default, requiring proof of full-file knowledge before confirming, or encrypting chunks per user (which kills cross-user dedup entirely — a real trade-off, not a free lunch). Saying "dedup everything globally" without naming this is the beginner answer.

5.2 Durability: replication vs erasure coding

Blob chunks must survive disk failures. Replication (store 3 copies, our math above) is simple and fast to read — any copy serves a download — but costs 3× storage. Erasure coding splits a chunk into, say, 10 data fragments plus 4 parity fragments spread across drives, so any 10 of 14 reconstruct it: ~1.4× storage instead of 3×, at the cost of a reconstruction step on read and slower small writes. The standard production answer is both: replicate hot, recently uploaded chunks for fast reads, then erasure-code them into cold storage as they age — the same hot/cold tiering idea as Lesson 18's video storage.

6. Download path and the hot-file problem

Download is the upload path in reverse, with one extra trick. The client asks the metadata service for the file's chunk list, then fetches chunks from the blob store — in parallel, from the nearest replica or through a CDN (Content Delivery Network: edge servers near the user that cache popular bytes, from Lesson 3). Chunks are verified against their hashes on arrival, so a corrupted chunk is detected and re-fetched, never silently served.

Then the cup-final problem: the media team's highlight clip is downloaded a million times in an hour. The metadata lookup is trivial (one chunk list, cached), but a million clients asking the blob store for the same chunks is a hot key problem (Lesson 24). The fixes stack: serve through the CDN so edge caches absorb nearly all of it, set long cache lifetimes on immutable chunks (a chunk's bytes never change, so caching it is always safe — immutability is a superpower here), and pre-warm the CDN in the regions where the audience lives before the clip goes public. Immutable chunks plus CDN caching is why viral files are a solved problem for storage systems and a crisis for mutable databases.

7. Sync: the change log, delta sync, and conflict resolution

Sync is where file storage earns its reputation for being hard, because it is a distributed-systems problem wearing a folder icon. The design that works:

  • Every device keeps a local copy and a cursor. The client stores files locally, watches the local folder for changes (the operating system's file-watcher API reports "file X changed"), and remembers a cursor — a bookmark in the server's change log saying "I have applied every change up to here."
  • The server keeps an append-only change log. Every metadata change (upload, rename, move, delete, share) appends one entry to a per-user (or per-shared-folder) log, each with a monotonically increasing sequence number. Sync is then beautifully simple: the client asks "give me every change after my cursor," applies them in order, and advances its cursor. No scanning the whole tree, no diffing thousands of files — just "what changed since I last asked." This is the same log idea as Lesson 9's message logs, applied to folders.
  • Local changes upload through the chunk flow, then append to the log. Edit a file offline on the bus: the client chunks it, and when connectivity returns it uploads the changed chunks and commits a new version, which appends to the change log. Other devices pick it up on their next poll (or via a push notification saying "new changes exist" — the poll itself stays cheap because usually the answer is "nothing new").
  • Deletes are tombstones, not erasures. Deleting a file appends a "deleted" entry rather than removing the record, so a device that was offline for a month does not resurrect a deleted file on reconnect — it reads the tombstone and deletes its local copy. (This is the same tombstone idea as Lesson 16's feed deletes.)

7.1 Conflicts: when two offline edits collide

Here is the case that separates a good design answer from a hand-wave. The physio edits the injury report on her tablet offline; the coach edits the same report on his laptop offline. Both reconnect. Both uploads are individually valid. The system cannot merge two edited documents it does not understand — it is not a word processor, it stores bytes. So it must pick a resolution policy, and the policy must be stated, not discovered:

PolicyWhat happensCost
Last-writer-wins (LWW)The later commit overwrites; the earlier edit is kept only as an old versionSimple, but silently discards someone's work — unacceptable for documents people care about
Conflicted copy (Dropbox's answer)Both versions are kept: the first to sync keeps the original name, the second becomes injury-report (Coach's conflicted copy).docxNo data loss, but a human must merge them — honest about the limit
Operational transformation / CRDTsEdits merge automatically at the character or operation levelReal merging, but only works for editors that understand the document format (Google Docs does this; a generic file store cannot)

The senior line: a generic file store picks conflicted copies, because it cannot merge arbitrary bytes, and it preserves the loser's version in history so nothing is ever truly lost. Rename-vs-edit and delete-vs-edit are the same story with different endings: a rename plus an edit produces the renamed file with both changes' metadata applied in log order; an edit to a file another device deleted produces the file resurrected with a note, or kept in the deleter's trash — pick one, document it, and never silently drop the edit. Lab B below walks through these cases.

7.2 Why sync is eventually consistent — and why that is fine

Two devices can disagree about a file's contents for minutes (one offline, one updated). That is eventual consistency (Lesson 7): given connectivity and no new edits, all copies converge to the same state. It is acceptable here because the alternative — refusing offline edits until the server agrees — would make the product useless on the team bus. The non-negotiable part is what eventual consistency must never do: show a half-written file, lose a committed version, or disagree about permissions. Metadata stays strongly consistent; contents converge. That split is the same consistency scoping from section 3.2, and naming it explicitly is what makes the answer sound senior.

8. Sharing, permissions, and versioning

  • Sharing model. A share is a metadata row, not a copy: granting the physio access to /Medical adds a row to shares, and her client can then list that folder from the owner's shard. Permissions are read or edit, inherited down the folder tree unless overridden, and checked on every metadata operation — never cached in a way that survives a revocation for long. Revocation must propagate fast: a revoked collaborator's next sync must fail, not finish "one last sync."
  • Link sharing. A public link is a capability: a long, unguessable token in the URL that grants read access to one file without an account. It is convenient and it is a security decision — anyone with the link has the file, and links leak through forwarded emails. Production systems add expiry dates, passwords, and download counts on links, and let owners see who opened what.
  • Versioning and trash. Every commit creates a new version row pointing at a chunk list; old versions' chunks stay alive while their reference count is above zero. Deleting a file moves it to trash for 30 days (metadata flag + tombstone), then garbage collection sweeps unreferenced chunks. Versioning is also the ransomware answer: encrypting every file just creates new versions, and the owner restores the pre-attack versions in bulk.
  • Encryption. Chunks are encrypted at rest on the blob store (server-side encryption, keys managed by the provider). End-to-end encryption — where only the user's devices hold the keys — is stronger but kills server-side dedup, preview, and search, because the server sees only ciphertext. Another real trade-off to name rather than gloss over.

9. Failure modes

  • Metadata shard down: that shard's users cannot list, upload, or sync — but downloads of already-known chunk lists can continue from the blob store and CDN. This is why metadata and blob failures are decoupled: losing one half degrades, not destroys, the product.
  • Partial upload, then client never returns: orphan chunks accumulate. The sweeper deletes chunks with a zero reference count older than a grace period (the grace period matters: a commit in flight may not have bumped the count yet).
  • Clock skew across devices: never order versions by device wall-clock time — a laptop with a clock set an hour fast would "win" every conflict. Order by the server's log sequence number, assigned at commit time. Device timestamps are display hints, never ordering authority.
  • Small-file overhead: a million 1 KB files each cost a metadata row, a chunk entry, and a blob request — the overhead dwarfs the bytes. Mitigations: pack tiny files' chunks, batch metadata writes, and cache folder listings aggressively. Interviewers love this one because it punishes designs that only think about big videos.
  • Sync loops and rename storms: renaming a folder with 10,000 files must append one log entry ("folder renamed"), not 10,000 file entries — otherwise every rename re-syncs the world. Folder renames are metadata-only operations; chunks never move.

10. Senior-depth traps

  • "Store the file as one blob." One blob means re-uploading 2 GB when one byte changes, no dedup, no resumability, and no delta sync. The moment an interviewer hears "chunk," they are listening for the chunk size trade-off (section 5) and the hash-list protocol — not just the word.
  • "Sync by scanning and comparing whole trees." That is O(all files) per sync and falls over at a thousand files. The change log plus cursor is O(changes since last sync) — the difference between a product that feels instant and one that spins for minutes on every laptop wake.
  • "Resolve conflicts by last-writer-wins." Fast, simple, and it deletes someone's cup-final injury report without telling them. A file store that cannot merge bytes must preserve both versions and let a human merge — data loss disguised as simplicity is the most expensive bug in this design.

11. Questions with full model answers

Tap each question to reveal a complete model answer — the kind of answer that names the decision, the reason, and the trade-off, in that order.

Q1. "Design Dropbox." Where do you start?

Model answer. Start with the split: a metadata service and a blob store, because the workload splits that way — a small, hot, strongly consistent index of names, folders, and permissions, and a huge, dumb store of immutable bytes. Then the upload protocol: client-side chunking into 4 MB chunks, SHA-256 hashes, a hash-list round trip so already-stored chunks are never re-sent (that is dedup and resumability in one mechanism), parallel chunk uploads, and a single metadata commit that publishes the new version atomically. Then sync: a per-user append-only change log plus client cursors, so sync costs O(changes since last sync), not O(all files), with tombstones for deletes and conflicted copies when two offline edits collide — because a file store cannot merge arbitrary bytes, so it must preserve both versions and let a human merge. Close with the numbers: 1B files at 2 MB is 2 PB raw, 6 PB at 3× replication, and 500 GB of metadata — the metadata is the bottleneck to shard, by user_id so a folder listing stays on one shard.

Q2. "A user uploads a 2 GB video on flaky Wi-Fi. How does it ever finish?"

Model answer. Three mechanisms, all from chunking. First, the file is cut into 4 MB chunks, so a dropped connection loses at most one in-flight chunk, not the whole upload. Second, the client sends the chunk hash list before any bytes, and the server replies with only the missing chunks — on reconnect, already-uploaded chunks are skipped, so progress is never lost. Third, chunks upload in parallel over separate connections, so one stalled connection does not block the rest, and each failed chunk retries independently with backoff. The final commit is a single metadata write that only happens once every chunk is stored, so readers never see a half-uploaded video. If you want the senior extra: content-defined chunking would additionally survive a byte inserted at the top of the file, which fixed-size chunking does not.

Q3. "Two users edit the same file offline. Whose edit wins?"

Model answer. Neither, silently. Last-writer-wins would discard one person's work without telling them, which is unacceptable for documents people care about, and a generic file store cannot merge arbitrary bytes the way Google Docs merges text — it does not understand the format. So the system keeps both: the first version to sync keeps the original name, the second becomes a conflicted copy with the editor's name in the filename, and both remain in version history. The user merges by hand. Ordering comes from the server's change-log sequence number, never from device clocks, which can be skewed. The senior line is the honesty: state the policy up front, preserve both versions, and never present data loss as a feature.

Q4. "Your storage bill tripled after a viral file. What happened, and what do you change?"

Model answer. Diagnose first: if the bill is storage, someone is storing duplicates — check whether dedup is actually engaged (per-user encryption, if enabled, disables cross-user dedup by design, so a viral file gets stored once per user). If the bill is egress bandwidth, the viral file is being served from the origin instead of the CDN — check cache lifetimes on immutable chunks, which should be long because chunk bytes never change, and pre-warm edge caches for predictable virality like a cup-final clip. If the bill is request count, the culprit is usually small files or per-chunk request overhead — batch metadata writes and pack tiny files. "The file went viral" is not a diagnosis; storage, egress, and request costs have different fixes, and naming which one tripled is the answer.

12. Practice drills (untimed — depth over speed)

Drill 1 — Price the drive.

A club drive holds 2,000 files averaging 25 MB, with 50% of bytes duplicated across users. At 3× replication, how much blob storage does dedup save versus storing every copy? What does the metadata service store for the chunk lists at 4 MB chunks?

Rubric: Raw = 2,000 × 25 MB = 50 GB; after dedup = 25 GB; at 3× replication, 150 GB vs 75 GB — dedup saves 75 GB. Chunk entries ≈ 2,000 × (25 ÷ 4, rounded up to 7) = 14,000 entries ≈ 900 KB of manifest at 64 bytes each. Full marks for doing dedup before replication (replication multiplies whatever dedup leaves behind).

Drill 2 — Write the sync protocol.

A laptop wakes after a week offline. It changed 3 files, renamed a folder of 500 files, and deleted 2 files. Sketch the exact sync exchange — what it sends, what the server sends back, and in what order — and say why the folder rename costs one log entry, not 500.

Rubric: Client sends its cursor + local change batch (chunk hash lists for the 3 changed files, one rename entry, 2 tombstones); server replies with all log entries after the cursor, then the client uploads missing chunks and commits. Full marks for: rename is metadata-only (chunks never move), deletes are tombstones (so offline devices do not resurrect files), and ordering by server sequence number, not device clocks.

Drill 3 — Spot the data-loss bug.

A design resolves every sync conflict with last-writer-wins by device timestamp, and deletes files by removing their metadata rows immediately. Name the two data-loss scenarios and the fix for each.

Rubric: (1) LWW by device clock: a device with a fast clock wins every conflict and silently discards the other edit — fix with conflicted copies + server sequence ordering + version history. (2) Immediate row deletion: an offline device that missed the delete resurrects the file on reconnect — fix with tombstones kept until all devices have passed that log position, plus a trash grace period before garbage collection.

13. Cheat sheet: six decisions to carry into the room

  1. Split metadata from blobs. Small, hot, consistent index; huge, dumb, immutable byte store. Scale the half that hurts — usually metadata.
  2. Chunk everything (4 MB). Chunking buys dedup, resumability, and delta sync in one mechanism; the hash-list round trip is the protocol.
  3. Commit atomically. Upload chunks first, publish the version with one metadata write. Readers never see a half-written file.
  4. Sync from a log, not a scan. Append-only change log + client cursor = O(changes since last sync). Tombstones for deletes; server sequence numbers, never device clocks.
  5. Never silently discard an edit. A generic file store cannot merge bytes, so conflicting offline edits become conflicted copies, both preserved.
  6. Shard metadata by owner. One user's folder listing stays on one shard; folder renames are one metadata entry, not one per file.
60-second framing — say this to open the topic

"A file storage system is two systems: a small, strongly consistent metadata service that knows every file, folder, and permission, and a huge blob store of immutable chunks. Clients split files into 4 MB chunks, hash them, and only upload the chunks the server doesn't already have — that one protocol gives us deduplication, resumable uploads, and delta sync for free. Sync runs off an append-only change log with client cursors, so a device coming back online asks 'what changed since I last asked' instead of scanning the whole drive. And when two offline edits collide, we don't pick a silent winner — a file store can't merge arbitrary bytes, so we keep both as conflicted copies and let a human merge. Metadata is sharded by owner, chunks are cached forever because they never change, and versions are what make ransomware recoverable."
