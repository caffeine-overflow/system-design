Lesson 14 · Core Building Blocks

Consensus & Raft

The last lesson ended with ZooKeeper and etcd — the systems that make locks safe. This lesson opens them up: how does a group of machines agree on one truth when any of them can crash at any moment? That question is consensus, and the most widely used answer is a protocol called Raft — one leader, heartbeats, majority votes, and a log that refuses to disagree with itself. If you want "exactly one thing happens" across servers — one config value, one elected leader, one official record — this is the machinery underneath.

01

What is consensus?

Consensus is a group of machines agreeing on one shared truth — or agreeing on nothing at all — even when some of them crash. Not "eventually agreeing." Not "mostly agreeing." Every surviving machine ends up with the same answer, and a crashed machine can't leave the group split into two camps with two different answers.

⚽ The running example: the officials' room

Five officials, one official match log, zero disagreements

Championship final. The league keeps an official match log — a single ordered list of everything that happened: KICKOFF 0', GOAL — 67', SAVE — 89', FULL TIME. But the log is maintained by five officials — A, B, C, D, E — each sitting in a different part of the stadium with their own walkie-talkie, each keeping their own copy of the log. Any official's radio can die mid-match. Phones drop. Batteries die.

The league's rule is brutal and simple: at the end of the night, all five copies must be identical — or the match result is void. No "my log says 2–1, yours says 1–1." Every idea in this lesson lands on this officials' room.

Consensus, formally

A set of nodes (machines, processes — our five officials) must agree on a single value (one log entry, one leader, one config). Every node that decides must decide the same value, and the value must be one that was actually proposed — the officials can't invent a goal that nobody saw. A fault is anything going wrong: the classic kind here is a crash fault — a node stops dead, mid-sentence (as opposed to lying, which is a separate, harder model called Byzantine — you'll meet it in blockchains; Raft and Paxos don't handle lying, only crashing).

Why should you care as an engineer? Consensus is the engine under:

  • Leader election — exactly one machine is "in charge" (which database node accepts writes, which instance runs the cron).
  • Distributed locks — the ZooKeeper/etcd from the last lesson are consensus systems first, lock services second.
  • Configuration and membership — "the new config is v42" has to be the same v42 everywhere.
  • Replicated state machines — five copies of a database applying the same commands in the same order stay identical. That's the big one: run consensus on a log of commands, and you get a replicated database for free.
02

Why agreement is so hard

If everyone stayed alive and every message arrived, consensus would be a group chat. The hardness comes entirely from failing mid-conversation.

The crash-mid-sentence problem

Official A sees the 67th-minute goal and starts announcing it over the radio: "GOAL — sixty-sev—" click. Radio dead. Now:

  • Did A finish the sentence before dying? Maybe C heard the whole thing and logged it.
  • Or maybe the radio died before a single syllable went out, and nobody heard anything.
  • Or maybe only one official heard it — C logged GOAL — 67', everyone else logged nothing.

The group now holds different logs, and nobody knows who heard what. A's silence is ambiguous: is A dead, or just quiet? You can't ask — the radio is dead. This is the entire problem of consensus: distinguishing a crashed node from a silent one, and converging on one truth without a perfect communication channel.

The two classic impossibilities

Two famous results frame what you can and can't do:

  • The Two Generals intuition. Two armies must attack at the same time or not at all, coordinating by messenger — and messengers can be captured. No finite number of confirmations ("I got your message" / "I got your confirmation") ever gives certainty, because the last message is always unconfirmed. The takeaway isn't despair — it's that perfect certainty requires unbounded waiting, so real systems settle for overwhelming likelihood plus timeouts.
  • FLP (Fischer–Lynch–Paterson, 1985). The formal version: in a fully asynchronous network — messages take an unknown amount of time, nodes have no shared clock — no deterministic algorithm can guarantee consensus if even one node can crash. The killer detail: without timing bounds, you cannot tell a crashed node from a merely slow one, so any algorithm that waits for everyone can hang forever.

The escape hatch real systems use: don't be fully asynchronous. Use timeouts. "If I haven't heard from you in 200ms, I assume you're dead." That assumption can be wrong (you were just slow) — and the protocol has to survive being wrong about it. That survival story is Raft.

The quorum trick

Here is the one mathematical idea everything rests on. A quorum is a group big enough to decide for everyone. Raft's rule: a quorum is a strict majority — more than half the nodes.

Why majorities: the overlap argument

Take 5 officials. A majority is 3. Now take any two majorities — any two groups of 3 out of 5. They must share at least one member: 3 + 3 − 5 = 1. Always. (This is the pigeonhole principle: two groups of 3 can't fit into 5 slots without overlapping.)

So: if a value was agreed by some majority, then any other majority you later consult contains at least one official who saw that agreement. No two majorities can ever commit to different truths. That overlap is the whole safety argument of Raft — remember it; it answers half the interview questions.

The quorum table for odd cluster sizes (memorize the pattern: majority = ⌊n/2⌋ + 1):

Notice: a 4-node cluster needs a majority of 3 — tolerating exactly 1 failure, same as 3 nodes. Even-numbered clusters add a node without adding fault tolerance. That's why production consensus clusters are 3, 5, or 7. (Drill 2 makes you prove it.)

03

Paxos, at high level

Before Raft there was Paxos (Leslie Lamport, 1989/1998) — the first consensus protocol proven correct, and famously the hardest paper in distributed systems to actually understand. You won't implement Paxos in an interview; you should be able to place it.

Paxos has three roles and two phases:

  • Roles: proposers suggest values, acceptors vote (a majority must accept), learners hear the outcome.
  • Phase 1 — Prepare/Promise. A proposer asks a majority of acceptors: "promise me you won't accept anything older than proposal #n." Each acceptor promises, and hands back the newest value it already accepted.
  • Phase 2 — Propose/Accept. The proposer must propose the newest value it heard back (or its own, if none) — this is what guarantees only one value wins. If a majority accepts, the value is chosen.

Why Paxos has a reputation: the original paper is famously hard to read — Lamport himself later wrote that describing it clearly took a second paper. Practitioners kept finding that the gap between "the algorithm" and "a working system" (leader election, log compaction, membership changes) was where all the bugs lived. Google's Chubby paper noted that real Paxos implementations are "substantially more complex" than the theory. Raft was created in 2013 specifically as the understandable alternative — same guarantees, a design a mortal engineer can hold in their head. That's why this lesson goes deep on Raft and keeps Paxos at this altitude.

04

Raft: the three roles

Raft's big idea: all decisions flow through one elected leader. Instead of everyone proposing (Paxos), the group elects a single spokesperson, and consensus becomes "the leader decides, the majority confirms." At any moment, every node is in exactly one of three states:

RoleWhat it doesIn the officials' room
Leader
(exactly ≤ 1 at a time)		Handles all client writes; appends them to its log; replicates to followers via heartbeats; commits once a majority acks.The head official with the whistle. She announces each event; the others copy her into their own logs.
Follower
(the normal state)		Copies whatever the leader sends; votes in elections; resets its election timer on every heartbeat.The other officials, pens ready, copying the head official's announcements.
Candidate
(transient)		A follower whose timer ran out; campaigns for votes to become leader for a new term.An official whose radio went quiet, shouting "is anyone there? I'll take charge if you'll have me."
Term — Raft's logical clock

A term is a numbered era, like a football season: term 1, term 2, term 3… Terms never go backwards, and a higher term always wins — if a node hears any message from a higher term, it immediately steps down to follower and updates its term. Time in Raft isn't measured in seconds; it's measured in terms. "Who's the leader?" is always answered as "A, in term 5." A stale leader from term 4 can't overrule term 5 — the term number is the authority.

Raft nodes talk through only two RPCs (remote procedure calls — one machine calling a function on another over the network):

  • RequestVote — "I'm a candidate for term T; will you vote for me?"
  • AppendEntries — "here are new log entries to copy" — which doubles as the heartbeat: a leader with nothing new still sends empty AppendEntries on a timer, and every follower resets its election clock on receipt.

That's the whole vocabulary. Everything else in this lesson is choreography with these two messages.

05

Leader election, step by step

How five followers with no coordinator pick exactly one leader — including the randomization trick that stops elections from deadlocking forever.

The steady state: heartbeats

The leader sends AppendEntries heartbeats every ~50ms. Each follower runs an election timer — a countdown that resets on every heartbeat. As long as the leader is alive, the timer never reaches zero. Silence is the only failure signal: a dead leader and a partitioned leader look identical — no heartbeats. Raft treats both the same, and the quorum math keeps it safe (section 8).

The election, numbered

Leader A's radio dies. Walk through what happens, with a cluster of 5:

  1. Timers fire. B, C, D, E stop hearing heartbeats. Their election timers — each set to a different random value in 150–300ms — count down. B's fires first.
  2. B becomes a candidate. B increments its term (3 → 4), votes for itself (votes: 1), resets its timer, and sends RequestVote(term 4) to A, C, D, E.
  3. Followers vote once per term. C receives B's request. C hasn't voted in term 4 yet, and B's log is as fresh as C's — so C grants the vote and records that it voted for B in term 4. C will now reject any other term-4 candidate (say D): one vote per follower per term, first-come-first-served. D does the same. A is dead; E's vote never arrives, but it doesn't matter.
  4. Majority wins. B tallies: self + C + D = 3 of 5 — a majority. B becomes leader of term 4 and immediately starts sending heartbeats ("AppendEntries, term 4") so nobody else starts campaigning.

Why "first-come-first-served, one vote per term" matters: it's what guarantees at most one leader per term. Two candidates can't both reach a majority in the same term, because the majorities would overlap (section 2's argument) — the overlapping voter would have to vote twice, which the rule forbids. At most one leader per term, always. Say that sentence in the room; it's the load-bearing one.

Why the timeouts are randomized — the split-vote problem

Suppose every follower's election timer were exactly 200ms. The leader dies at t=0. At t=200ms, B, C, D, and E all become candidates, all increment to term 4, all vote for themselves, all send RequestVote — and each follower has already used its single term-4 vote on itself. Nobody grants anyone a vote. Result: four candidates, zero winners, term 4 produces no leader — a split vote.

What then? Each candidate's timer fires again, terms bump to 5, and — if timeouts are still identical — it deadlocks again, term after term, forever. The cluster has no leader and takes no writes, indefinitely.

The fix: randomize the timeout

Each follower picks its election timeout randomly from a range (typical: 150–300ms). Now when the leader dies, one follower's timer almost always fires first — it campaigns and wins before the others time out, because its first act as leader is sending heartbeats that reset everyone else's timers. If a split vote does happen (two timers fire within the same few milliseconds), the losers' next timeouts are re-randomized, so the next round almost certainly produces a single winner. Randomization turns a guaranteed deadlock into a near-certain quick election.

The timeout range itself is sized deliberately: it must be much larger than the heartbeat interval (so a live leader never accidentally triggers elections — heartbeats at ~50ms vs timeouts at 150–300ms gives a 3–6× margin) and larger than the network's round-trip time (so a RequestVote round trip fits comfortably inside it). Leader failover takes roughly one election timeout — ~150–300ms — which is why consensus clusters promise sub-second leader recovery.

The election restriction: only fresh logs can win

One more safety rule, and it's subtle: a candidate can only win if its log is at least as up-to-date as the followers'. RequestVote carries the candidate's last log entry (index + term); a follower denies its vote to any candidate whose log is older than its own.

Why: suppose the old leader committed GOAL — 67' (majority has it) but crashed before telling official E, whose radio was already flaky. E's log is missing the goal. If E could become leader, it would overwrite everyone else's logs with its stale one — a committed entry would be lost. The election restriction prevents exactly this: because GOAL — 67' reached a majority, any future majority (which must win the election) contains at least one node that has it, and that node refuses to vote for the stale candidate. E can never win until it catches up. Committed entries survive leader changes — this is the "leader completeness" property, and the election restriction is how Raft enforces it.

06

Log replication: how a write commits

Election picks the leader; replication is where data actually flows. A client write becomes permanent in exactly three steps — and "permanent" has a precise definition: on a majority.

Back in the officials' room: term 4, B is the head official. The league's app (the client) sends B an event: SAVE — 89'.

  1. Append locally. B appends SAVE — 89' to the end of her own log, marked uncommitted — "I've written it in pencil; it doesn't count yet." (If the client had contacted a follower instead, the follower just forwards it to the leader — all writes go through the leader, which is what makes ordering trivial: one decider, one order.)
  2. Replicate. B sends AppendEntries RPCs to C, D, E (and dead A, which won't answer): "copy SAVE — 89' at the end of your log." Each follower appends it to its own log and replies "done." (Each AppendEntries also carries the leader's term and the entry before the new one, so a follower can detect "your log doesn't match mine here" — the log consistency check — and the leader retries with earlier entries until the logs line up. This is how a healed follower's divergent tail gets overwritten.)
  3. Commit on majority. B counts acks: herself + C + D = 3 of 5. Majority reached. B advances her commit index — the pointer to "the last entry that is permanent" — past SAVE — 89', applies it to her state machine (the actual scoreboard), and replies to the client: "recorded." Her next heartbeat tells the followers "commit index moved," and they apply it too.
Committed = on a majority

An entry is committed the moment a majority of nodes hold it in their logs. From that instant it is permanent: the quorum-overlap argument guarantees every future leader's election majority includes at least one node carrying it, the election restriction guarantees that node won't vote for anyone missing it, and so every future leader's log contains it. The client can be told "it's durable" after ~2 network round trips (leader→followers→leader) — that's the write latency of a consensus cluster, and it's why you don't put hot data paths through one.

Two guarantees worth naming, because interviewers do:

  • State machine safety: if two nodes have applied (committed) an entry at the same log index, the entries are identical. No two officials ever officially record different events at position 7 of the log.
  • Leader completeness: if an entry is committed in some term, every leader of every later term holds it. (Enforced by the election restriction above.)
07

When the leader dies: the full walkthrough

The scenario every interviewer asks for, with every number on the table. Five officials, term 5, C is the leader.

The log so far (all committed): KICKOFF 0', GOAL — 67', SAVE — 89'. Then:

  1. t = 0ms — the client sends GOAL — 91' to C. C appends it (uncommitted, pencil), sends AppendEntries to A, B, D, E.
  2. t = 0ms — C's radio dies mid-replication. Acks arrive from A and B only: 3 of 5 (C + A + B). Majority reached before the crash — the entry is committed. C dies before telling anyone the commit index moved, but it doesn't matter: A and B hold it, and it's on a majority.
  3. t ≈ 150–300ms — silence. A, B, D, E's election timers (randomized, remember) count down with no heartbeats. D's fires first.
  4. D becomes candidate, term 6. D votes for itself (1/5), sends RequestVote(term 6, "my last entry is GOAL — 91'"). A and B check: D's log is as fresh as theirs → grant. A used its term-6 vote, B used its term-6 vote. Votes: D + A + B = 3/5, majority. D is leader of term 6. E's vote is irrelevant; C is dead.
  5. D's first act: send AppendEntries(term 6) heartbeats with commit index past GOAL — 91'. A and B apply it (already had it); E copies the entry, applies it. C stays dead. All live logs identical, entry committed, zero loss.

Now the darker variant: suppose C crashed before reaching a majority — only C held GOAL — 91', acks from A and B never arrived. Then the entry was never committed, and D's election proceeds identically — except now nobody's log contains GOAL — 91', so D (term 6) simply never replicates it. The entry vanishes as if the client never sent it. That's not a bug; it's the contract. Raft guarantees committed entries survive — uncommitted ones are allowed to disappear, because the client never got its "recorded" ack. This is why clients retry on timeout: an unacked write might or might not have committed, and retrying must be safe — which is why the state machine should be idempotent (lesson 9's idempotency keys, coming back around).

08

Partitions: the minority goes quiet

A crashed leader and a partitioned leader look identical — no heartbeats. The quorum math is what keeps the partition from creating two competing truths.

Five officials. The stadium network splits: A and B are cut off together on one side; C, D, E stay connected on the other. C is the current leader. Walk it through:

  • Majority side (C, D, E = 3/5): C's heartbeats still reach D and E — 3 of 5, a majority. Elections can succeed here, writes commit here. The cluster keeps working. To these three, A and B look "crashed."
  • Minority side (A, B = 2/5): A and B stop hearing C. Their election timers fire; one becomes candidate, bumps the term, sends RequestVote — and can collect at most 2 votes out of 5. No majority, no leader. Terms keep climbing pointlessly on every timeout. The minority can do nothing but wait. To these two, C, D, E look "crashed."

No split brain — by construction

Why can't the minority elect its own competing leader and commit conflicting entries? Because a leader needs a majority, and there's only one majority's worth of votes to go around: if C's side elected a leader (3 votes), only 2 votes remain — the minority's candidate can never reach 3. And crucially, A cannot commit anything either: even if A somehow declared itself leader, its writes would need 3 acks, and only 2 nodes can hear it. The partition doesn't create two working clusters; it creates one working cluster and one frozen one. This is Raft choosing consistency over availability — the CP corner of the CAP theorem (lesson 7), deliberately.

When the partition heals: A and B rejoin with stale logs and inflated terms (their solo elections kept bumping the term). The first AppendEntries from the real leader (with its commit index) triggers the log consistency check: "your tail doesn't match mine" → A and B's divergent uncommitted entries are overwritten by the leader's log, their terms snap back, and all five copies converge. The leader's log is always the truth the cluster converges to — never the reverse.

The price, stated plainly: during a partition, the minority side is unavailable for writes — and if the partition is 2–3 in a 5-node cluster, a client routed to the wrong side sees errors until it heals. You buy unbreakable agreement; you pay with availability. That's not a flaw to fix — it's the trade the whole protocol is built around.

09

Where consensus lives in real systems

You will almost never implement Raft yourself. You will stand on systems built on it — so know which ones, and what job consensus does inside them.

SystemProtocolWhat consensus is used for
etcdRaftKubernetes' brain: every cluster object, config, and lease lives in etcd. When you kubectl apply, you're writing through Raft.
ConsulRaftService discovery + KV: the service catalog and leader election for its own servers.
ZooKeeperZAB (same family)Coordination: locks, leader election, config (lesson 13's lock service — now you know what's underneath).
CockroachDB / TiKVRaft (per shard)Each data range is its own little Raft group — consensus replicated at the storage layer, not just the metadata layer.
Redis (default)NoneExactly why lesson 13 needed fencing tokens: no consensus means no guaranteed single truth, so the application enforces safety itself.

The pattern: consensus guards the small, precious state — configs, locks, membership, schema — the few kilobytes the whole system must agree on. It does not guard your terabytes of user data on the hot path (section 11 explains why).

11

When you DON'T need consensus

Consensus is expensive. Knowing when not to pay for it is the senior part of this lesson.

The costs, honestly:

  • Write latency: every write costs ~2 round trips to a majority before the client gets its ack. Across availability zones that's single-digit milliseconds — fine for config, fatal for a 100k-writes/sec event stream.
  • Throughput ceiling: one leader does all writes. A well-tuned Raft group (etcd-class) sustains on the order of ~10k writes/sec — plenty for coordination, nothing like a sharded database.
  • Minority stalls: partitions freeze the small side (section 8). If you need "always writable everywhere," you need AP, not Raft.
  • Operational weight: odd-sized clusters, quorum monitoring, careful timeout tuning, membership changes done one node at a time (joint consensus) so you never accidentally create two majorities mid-change.

The decision rule

Reach for consensus (etcd / ZooKeeper / Consul) when: the state is small, precious, and must be single-valued — leader election, locks, config, schema, membership. Don't when: the data is large or hot (use sharding + replication, lessons 5–6), when stale reads are acceptable (use quorum reads/writes without a leader, Dynamo-style — lesson 5's leaderless quorum), when one writer can be designated by construction (a single-writer service needs no election), or when the operation is idempotent and retryable (a queue + idempotency keys, lesson 9, gets you "exactly once" effect far cheaper than exactly-once agreement).

13

Q&A — with full model answers

Four questions that come up constantly, each with the spoken answer — verdict first, reasoning, and what earns the top mark.

Q1 · FAILURE
"The Raft leader just died. Walk me through exactly what happens next."
The single most-asked Raft question. They want the timeline with terms, timers, and votes — not "a new leader is elected."
Reveal model answer
Verdict

"Silence triggers it: followers' election timers fire, one becomes candidate in a new term, wins a majority of votes, and resumes as leader — carrying every committed entry with it. Recovery takes about one election timeout, ~150–300ms."

Reasoning

"The leader's job includes sending heartbeats — empty AppendEntries — every ~50ms, and every follower resets its election timer on each one. When the leader dies, the heartbeats stop, and the timers count down. Each timer was set to a different random value in 150–300ms, so one follower's fires first. That follower becomes a candidate: it increments its term — say 5 to 6 — votes for itself, and sends RequestVote(term 6) to everyone.

Each follower votes at most once per term, first-come-first-served, and only for a candidate whose log is at least as up-to-date as its own — that's the election restriction. The candidate needs a majority: 3 of 5. Once it has 3 votes it becomes leader of term 6 and its first act is sending heartbeats, which reset everyone else's timers and stop further campaigning.

Two things the answer must include. First, committed entries are never lost: the dead leader committed an entry only after a majority held it, so any election-winning majority overlaps that majority and contains the entry — and the election restriction stops a stale node from winning. Second, the uncommitted tail can vanish: entries the dead leader replicated but never got a majority for simply never happened — the client never got its ack, so it retries, which is why the state machine should be idempotent."

What earns top marks

The numbers (3 of 5, 150–300ms, ~50ms heartbeats), the one-vote-per-term rule stated as the reason two leaders can't coexist in one term, and volunteering the committed-vs-uncommitted distinction before being asked.

Q2 · MECHANICS
"Why do election timeouts have to be randomized? What breaks if every node uses exactly 200ms?"
The split-vote trap. They want the deadlock story and the probability intuition, not just "to avoid ties."
Reveal model answer
Verdict

"Identical timeouts produce repeated split votes — every follower campaigns at the same instant, nobody wins, and the cluster can sit leaderless forever. Randomization makes one candidate win before the others time out, and re-randomization makes repeat splits exponentially unlikely."

Reasoning

"With identical 200ms timeouts, the leader dies at t=0 and at t=200ms four followers all become candidates simultaneously. Each votes for itself — using up its single term-N vote — and each sends RequestVote to the others, who all reject because they've already voted. Four candidates, zero majorities: a split vote, no leader. Their timers fire again, terms bump, and the same thing happens in term N+1 — it's a deterministic deadlock that can repeat indefinitely, and the cluster takes no writes the whole time.

Random timeouts — say each follower picks 150–300ms — break the symmetry: one timer almost always fires first, that candidate campaigns and wins before the others fire, and its first act as leader is heartbeats that reset everyone else's timers. If two timers do collide within a few milliseconds and split the vote, the losers re-randomize, so the chance of k consecutive splits shrinks geometrically — in practice elections resolve in one round. The range itself is sized so heartbeats (~50ms) can never accidentally trigger an election: a 3–6× margin between heartbeat interval and minimum timeout."

What earns top marks

Walking the identical-timeout deadlock concretely (all vote for self → all reject each other → repeat forever) rather than hand-waving "ties," plus the sizing rationale for the 150–300ms range relative to heartbeats.

Q3 · SAFETY
"A write committed one millisecond before the leader crashed. How does Raft guarantee it's never lost?"
The safety question. They want the two mechanisms — majority overlap and the election restriction — composed into one argument.
Reveal model answer
Verdict

"Two mechanisms compose: 'committed' means a majority holds it, so every future election majority contains a witness — and the election restriction means a candidate missing that entry can never win. The entry rides into every future leader's log."

Reasoning

"'Committed' has a precise definition in Raft: the entry is on a majority of nodes — 3 of 5. Now the leader crashes and an election starts. Any winning candidate needs a majority of votes — another 3 of 5. Two majorities of 5 always overlap in at least one node (3+3−5=1), so the election-winning majority necessarily includes at least one node carrying the committed entry.

That's necessary but not sufficient — the overlapping node could just… vote for someone stale anyway. It can't: the election restriction says a follower denies its vote to any candidate whose log is older than its own. RequestVote carries the candidate's last log entry; the witness node compares and rejects stale candidates. So the only candidates that can win are ones whose logs are at least as fresh — which means they already hold the committed entry. Therefore every future leader holds every committed entry: leader completeness, and the entry is never lost, never overwritten. This is also why the leader's log is the convergence target when partitions heal — the leader is guaranteed to be the freshest node in the cluster."

What earns top marks

Doing the 3+3−5=1 overlap arithmetic explicitly, naming both mechanisms (not just "majority"), and stating leader completeness as the conclusion rather than the premise.

Q4 · QUORUM MATH
"A 4-node Raft cluster tolerates exactly 1 failure — the same as 3 nodes. So why would anyone ever run 4?"
The even-number trap. The correct answer is "you wouldn't" — said with the math.
Reveal model answer
Verdict

"You wouldn't — a 4-node cluster costs a node and gains nothing. Majority of 4 is 3, so one failure leaves exactly 3: the cluster survives 1 failure, identical to 3 nodes, while paying for an extra machine and a slower quorum."

Reasoning

"Majority is ⌊n/2⌋+1. For n=3: 2 — one failure leaves 2, the cluster survives 1. For n=4: 3 — one failure leaves 3, the cluster survives 1; but two failures leave 2, which is not a majority of 4, so it still dies at 2 failures. Same fault tolerance as 3 nodes. Worse, every write now needs 3 acks instead of 2, so the write path is slower and the quorum is harder to assemble — you've paid for a fourth machine to make the cluster more fragile to assemble and no more resilient. The only thing the 4th node adds is read capacity, which is never worth it for a consensus group. Production consensus clusters are 3, 5, or 7 — odd numbers, where every added pair of nodes buys one more tolerated failure."

What earns top marks

The ⌊n/2⌋+1 formula applied to both sizes, the explicit "dies at 2 failures either way," and the punchline that the 4th node makes quorums harder while adding nothing — plus the 3/5/7 rule as the takeaway.

Practice drills

Untimed. Work each on paper first, then check the rubric — the rubric is the lesson.

Drill 1 — Hand-run an election

A 7-node Raft cluster. The leader crashes in term 6; all logs are identical and fully committed. (a) How many votes does the new leader need? (b) What term does the new leader serve? (c) Two candidates campaign at nearly the same instant and split the votes 3–3, with the 7th node abstaining because its timer hasn't fired. What happens in term 7, and what happens next?

Reveal rubric

(a) 4 votes — majority of 7 is ⌊7/2⌋+1 = 4. (b) Term 7 — a candidate always increments before campaigning; there's no "term 6.5." (c) No leader in term 7: 3+3 with one abstention means nobody reached 4, and the abstainer's single vote can't be cast twice (it votes once when its timer fires — for one of them — but 4 is unreachable now). Both candidates' timers fire again with re-randomized timeouts, terms bump to 8, and the next round almost certainly produces a single winner before the other fires. Full marks for: the vote count, the term increment, and "split vote → re-randomize → next round elects" rather than "they keep splitting forever."

Drill 2 — The quorum table from memory

Without looking back: for cluster sizes 3, 5, 7, 9, write the majority and the failures tolerated. Then, in one sentence, explain why a 4-node cluster has the same resilience as a 3-node one.

Reveal rubric

3→majority 2, tolerates 1 · 5→3, tolerates 2 · 7→4, tolerates 3 · 9→5, tolerates 4. The pattern: majority = ⌊n/2⌋+1, tolerated = majority−1… equivalently ⌊(n−1)/2⌋. One sentence for the 4-node case: "Majority of 4 is 3, so it dies on the second failure exactly like a 3-node cluster — the fourth node buys no fault tolerance, only a slower quorum." Full marks for deriving from the formula rather than memorizing the table.

Drill 3 — The partition that eats a write

5-node cluster, leader L. The network splits 3–2 mid-write: L's AppendEntries for entry X reached only L and one follower before the cut (2 of 5). (a) Which side keeps serving writes? (b) What happens to entry X — and what must the client do? (c) When the partition heals, whose log wins, and by what mechanism?

Reveal rubric

(a) The side of 3 — whichever side holds the majority keeps electing leaders and committing; the side of 2 can reach at most 2 votes/acks and stalls. (Note: if L is on the minority side, the majority side elects a new leader.) (b) X vanishes — it never reached a majority, so it was never committed; the client never got its ack and must retry. The retry must be safe: the state machine should be idempotent (idempotency keys), because the client can't know whether X committed or not. (c) The leader's log wins — on heal, AppendEntries' log-consistency check finds the minority's divergent tail, and the leader overwrites it entry by entry until the logs match. Full marks for: "uncommitted entries are allowed to disappear," the idempotent-retry consequence, and naming the consistency check as the heal mechanism.

Cheat sheet: the 6 consensus decisions

The decisions you'd actually make when putting a consensus cluster into a design.

#DecisionThe rule
1Cluster sizeOdd: 3, 5, or 7. Majority = ⌊n/2⌋+1. Every even node past the odd one adds cost without fault tolerance.
2Timeout budgetElection timeout ≫ heartbeat interval ≫ network RTT. Typical: heartbeats ~50ms, timeouts randomized 150–300ms → sub-second failover, no false elections.
3What goes in the logSmall, precious state only: configs, locks, membership, schema. Never the hot write path — throughput ceiling is ~10k writes/sec for one leader.
4Write latencyBudget ~2 RTTs to a majority before the client ack. Batch and pipeline if it matters.
5Partition planMinority stalls by design (CP). Route clients to the majority side; on heal, the leader's log overwrites divergent tails — never the reverse.
6Build vs borrowBorrow: etcd / ZooKeeper / Consul. If you need always-writable everywhere, you don't want Raft — you want Dynamo-style leaderless quorums (AP).

Consensus in 60 seconds

"Consensus means a group of machines agrees on one truth even when some crash. You can't do it with perfect certainty — FLP says so — so Raft uses timeouts and majorities. One elected leader takes all writes, replicates each entry, and commits it once a majority acks — about 2 round trips. If the leader dies, randomized election timeouts pick a new one in a new term within ~300ms, and the election restriction guarantees the new leader holds every committed entry. Partitions freeze the minority by design — that's the CP trade — and when they heal, the leader's log wins. Use it for small precious state: leader election, locks, config. Never for the hot path."

16

How to talk about consensus in the room

A five-step talk track for "design the coordination layer" or any "how does etcd work" follow-up.

  1. Open with the problem, not the protocol. "Five machines must agree on one value, and any of them can die mid-sentence — a dead node and a silent node are indistinguishable, so we can't just vote once and wait."
  2. State Raft's shape. "Raft funnels everything through one elected leader: followers, candidates, terms as the logical clock, heartbeats doubling as liveness, randomized election timeouts so elections resolve in one round."
  3. Walk a write with the numbers. "Client → leader appends → AppendEntries to followers → commit on majority, 3 of 5 → ack. About 2 RTTs. Committed means on a majority, and that's the durability contract."
  4. Walk the failure. "Leader dies → timers fire → candidate, new term, majority vote — but only a candidate with a fresh log can win, so committed entries survive every leader change. Uncommitted ones may vanish; clients retry idempotently."
  5. Close with the cost and the placement. "Minority partitions stall — CP by design — single-leader throughput caps around ~10k writes/sec, so consensus guards the small precious state: election, locks, config in etcd. Hot data goes through sharding and replication instead."

The sentence to keep

"At most one leader per term, committed means on a majority, and the leader's log is the truth the cluster converges to."
