Lesson 30 · Classic design

Design a Search System

Type a few words, get the right page in under half a second — from billions of documents. The trick is doing almost all the work before the query ever arrives.

What is a search system?

Start from zero. A document is one searchable item: a web page, a match report, a player profile, a video with a title and description. A corpus is the whole collection of documents. A query is the few words a user types. A search system answers one question: given this query, which documents in the corpus match best, in what order?

The naive answer — scan every document for the query words on every search — is correct and hopeless. Scanning billions of documents per query would take minutes, and users expect an answer in milliseconds. So a search system splits the work in two: indexing (done once, offline, when documents arrive) builds a data structure that makes lookup fast, and serving (done per query, online) consults that structure and ranks the matches. Nearly everything in this lesson is a consequence of that split: the index is the product, the query path just reads it well.

The soccer running example: Riverside FC's archive holds every match report, player profile, press-conference transcript, and training video description the club has ever published — say, tens of thousands of items for the club version, billions for the web version. A fan types "derby hat-trick". The system must find the report where the striker scored three in the derby, not the hundred reports that merely mention derbies, and it must do it before the fan loses patience. Two words carry the whole lesson: find (which documents contain the words) and rank (which of those the fan actually wants).

Terms, defined as they appear

Term: one searchable word after normalisation (lowercased, punctuation stripped, so "Derby!" and "derby" are the same term). Posting list: for one term, the list of documents containing it. Relevance: how well a document satisfies the query — a score, not a yes/no. Recall: of all the documents that should have matched, how many were returned. Precision: of the documents returned, how many were actually wanted. A good system trades these off deliberately: returning everything has perfect recall and terrible precision.

Requirements and back-of-the-envelope math

Scope first. We are building web-style search: a huge corpus that changes constantly, short keyword queries, a ranked top-10 answer, and a latency budget under ~500 ms. We are not building site search over one database, and we are not building an AI chatbot — the ranking here is term-based, which is the foundation every fancier system still stands on.

  • Functional: index new and changed documents within minutes; answer keyword queries with a ranked top 10; support phrase queries ("clean sheet" as a phrase, not two loose words); autocomplete as the user types; spell correction ("hattrick" → "hat-trick").
  • Non-functional: p99 query latency under 500 ms; availability over perfect freshness — a document indexed a minute late is fine, a search page that fails is not; the index must survive individual shard failures without wrong answers.

The sizing, with every step shown. Assume a corpus of 2 billion documents, an average of 500 distinct terms per document, and 500 million queries per day:

  • Index size: 2 billion documents × 500 terms = 1 trillion postings (one posting = one term appearing in one document). Compressed with delta encoding and variable-length integers (storing gaps between document IDs instead of the IDs themselves, in a few bytes each), a posting averages ~2 bytes → 1 trillion × 2 bytes = ~2 TB of index. That is large but entirely manageable once sharded.
  • Document store: 2 billion documents × ~2 KB of extracted text each = ~4 TB of text to keep for snippets and re-indexing. The raw HTML is far bigger and is not kept hot — the crawler's job (Lesson 20) ends where this lesson's index build begins.
  • Query load: 500 million queries/day ÷ 86,400 seconds = ~5,800 queries/sec average, and traffic is spiky — a 5× peak factor gives ~29,000 queries/sec at peak. This is the number the serving tier must be built for, not the average.
  • Fan-out: if the 2 TB index is split into 200 shards of 10 GB each, every query touches all 200 shards (see the sharding section for why) → 29,000 × 200 = 5.8 million shard-queries/sec at peak. If one shard replica serves 5,000 shard-queries/sec, that is 5.8M ÷ 5,000 = 1,160 replicas ÷ 200 shards ≈ 6 replicas per shard. The fan-out, not the corpus size, is what sets the serving fleet size.
  • Merge cost: each shard returns its top 10 → 200 × 10 = 2,000 candidates per query for the aggregator to merge and re-rank → 29,000 × 2,000 = 58 million candidates/sec at peak. The aggregator tier must itself be a fleet, and it does almost no disk work — it merges lists in memory.
The decision the numbers force

Because a query fans out to every shard, query latency is set by the slowest shard, not the average one. Everything in the serving design — timeouts, partial results, replicas, in-memory posting lists — exists to tame that one fact: at 200 shards, even a 1% slow-shard rate would spoil nearly every query without a mitigation.

The architecture, in one pass

Two pipelines, kept strictly separate. The indexing pipeline runs continuously in the background; the serving pipeline answers queries and never waits on the indexing pipeline.

  1. Crawl and fetch. The web crawler (Lesson 20) discovers pages and fetches them, respecting politeness and dedup. Its output — raw page content — is the input here.
  2. Parse and analyse. Each document is stripped to text, split into terms (tokenisation: splitting text into terms, handling hyphens, numbers, and languages), normalised (lowercasing, removing common stop words like "the" and "and" that appear everywhere and discriminate nothing), and reduced to stems (stemming: "scoring", "scored", and "scores" all become "score", so a query for one matches the others). The output is a list of (term, document) pairs, plus term positions for phrase queries.
  3. Index build. Pairs are sorted by term and written as posting lists into immutable segments (chunks of index, each covering a batch of documents). New segments are added as documents arrive; old segments are periodically merged (compaction, the same idea as LSM compaction in Lesson 8), which is how updated documents replace stale ones — the new version wins, the old posting is dropped at merge time. This segmented design is what makes near-real-time indexing possible: a fresh document is searchable as soon as its small new segment is published, minutes after arrival, without rebuilding a 2 TB index.
  4. Serve. A query arrives at an aggregator (also called a broker or scatter-gather coordinator). The aggregator parses the query, sends it to every shard, collects each shard's top 10, merges them into a global top 10, fetches snippets from the document store, and returns the page. The aggregator holds no index data itself, so it scales by adding more aggregators.
  5. Auxiliary services. Autocomplete, spell correction, and query caching sit beside the main path (see the query-path section) — they answer before the fan-out or avoid it entirely.

Why not keep the index in a database and query it with SQL? Because a posting-list lookup — "give me the documents for these three terms, intersected, ranked" — is a workload databases are not shaped for: it needs the posting lists in memory, compressed, sharded by document, and scanned in a tight loop. A search engine is a specialised database, and the specialisation is the whole point.

The inverted index, from zero

An inverted index is a map from term to posting list — the inverse of a document, which maps a document to its terms. "Inverted" because you look things up backwards: instead of asking each document "do you contain this word?", you ask the word "which documents contain you?"

Worked example, tiny corpus. Three documents, already tokenised:

Doc 1: riverside striker scores derby hat trick
Doc 2: derby day riverside wins derby
Doc 3: striker transfer riverside signs striker

The inverted index (posting lists show document IDs; a real one also stores term frequency and positions):

riverside → [1, 2, 3]     derby → [1, 2]     striker → [1, 3]
scores    → [1]            hat   → [1]      trick → [1]
day       → [2]            wins  → [2]      transfer → [3]  signs → [3]

Now answer the query "derby hat trick". Look up three posting lists — derby [1, 2], hat [1], trick [1] — and intersect them (keep only documents present in all lists): [1]. One document, no scan. For an OR query ("derby OR striker"), union the lists: [1, 2, 3]. Intersection is done by walking the sorted lists together with two pointers — linear in the size of the lists, and fast in practice because lists are compressed and, crucially, because the query planner starts with the shortest list: "hat" has 1 document, so the intersection is decided after checking at most that one document against the other lists. Start from the rarest term is a rule worth memorising: it is why rare words make queries fast and common words ("riverside" in a club archive, "the" anywhere) make them slow.

Phrase queries need one more ingredient: term positions. "clean sheet" as a phrase means "clean" immediately followed by "sheet" in the same document — the posting list must store, per document, the positions where the term occurs, so the engine can check that position(clean) + 1 = position(sheet). Positions roughly double index size, which is why some systems store them only for the most useful terms, or in a separate positional index consulted only for phrase queries. The trade-off is explicit: phrase support costs storage; without positions, every multi-word query is a bag of words and "sheet clean" matches "clean sheet".

Why the index is sorted by term, not by document

A document store answers "what is in document 42?" An index answers "which documents contain term X?" — the opposite question, so it needs the opposite layout. Every search system, from a library catalogue to a web engine, is this one inversion plus ranking. If you remember one sentence from this lesson, make it this one.

Ranking: from matching to ordering

Matching finds candidates; ranking orders them. A query that matches a million documents is useless unless the right ten come first. The classical foundation is TF-IDF (term frequency × inverse document frequency), and its grown-up successor is BM25. Both rest on two intuitions, and you should be able to state both without notes.

Intuition 1 — frequency in the document (TF). A document that mentions "hat-trick" five times is more about hat-tricks than one that mentions it once. But the fifth mention matters less than the first: relevance saturates. Counting raw mentions over-rewards long, repetitive documents, so real formulas use a saturating curve, and they also normalise by document length — a 50-word match report mentioning "derby" twice is more about the derby than a 5,000-word season review mentioning it twice.

Intuition 2 — rarity in the corpus (IDF). A term that appears in nearly every document ("riverside" in a club archive) tells you almost nothing; a term that appears in few documents ("hat-trick") tells you a lot. IDF formalises that: IDF(term) = log(N ÷ df), where N is the number of documents and df is how many contain the term. Rare term → large IDF → heavy weight. Common term → IDF near zero → almost no weight.

Worked TF-IDF example, with the arithmetic shown. Corpus: 4 documents. Term "derby" appears in 3 of them, so IDF(derby) = log₁₀(4 ÷ 3) ≈ 0.125. Term "hat-trick" appears in 1, so IDF(hat-trick) = log₁₀(4 ÷ 1) ≈ 0.602 — nearly five times the weight, because it is five times rarer in log terms. Query: "derby hat-trick". Document A mentions derby once and hat-trick twice: score = 1 × 0.125 + 2 × 0.602 = 1.329. Document B mentions derby three times and no hat-trick: score = 3 × 0.125 = 0.375. Document A wins by a wide margin even though B mentions "derby" more — because the rare term dominates, as it should. That is the whole TF-IDF idea in one calculation: count what matters, weight it by how surprising it is.

BM25 is TF-IDF with the two corrections above built in properly: TF saturates (the 20th mention adds almost nothing) and document length is normalised (long documents are not rewarded just for being long). It has two tunable constants, k₁ (how fast TF saturates, typically ~1.2) and b (how strongly length normalisation applies, typically ~0.75) — naming those defaults in the room signals you have actually used it, not just read about it. On top of BM25, production systems layer PageRank (a page linked to by many important pages is probably important — links as votes, computed over the whole web graph offline) and, later, learning to rank (a model trained on click data that combines BM25, PageRank, freshness, and hundreds of other signals). The order matters: BM25 retrieves and roughly ranks; the expensive model re-ranks only the top few hundred. Never run the expensive model over the whole corpus.

Two ranking cautions. First, freshness: for "Riverside injury news", yesterday's report beats a perfect 2019 match — so a freshness signal (recency decay) is blended in for news-like queries, and not for evergreen ones ("rules of offside"). Detecting which kind of query it is — query intent — is itself a classifier. Second, clicks are not truth: users click the top result because it is on top (position bias), so training on raw clicks teaches the model to reproduce the old ranking. Production systems correct for position bias or use human-rated relevance judgements. Saying "we cannot just train on clicks" is a senior sentence.

Sharding the index: by document, not by term

There are two ways to split a 2 TB index across machines, and the choice defines the serving path:

Sharding by termSharding by document
Split ruleTerms A–M on one set of machines, N–Z on anotherDocuments 1–10M on shard 1, 10M–20M on shard 2, and so on
A query touchesOnly the shards holding its terms — a few machinesEvery shard — all 200 of them
Fatal flawHot terms: "derby" on cup-final day hammers one shard while the rest idle, and a multi-term query must merge partial scores across machines that each saw only part of the queryTail latency: the query waits for the slowest of 200 shards
VerdictAlmost never used at scaleThe standard choice — and the tail-latency problem is solved, not avoided

Document sharding wins because it balances load by construction: every shard holds a similar slice of the corpus, every query spreads evenly, and each shard can compute a complete, correctly normalised score for its documents (it knows its own document frequencies; global IDF is replicated to every shard as a small shared table). The price — tail latency — is paid with four mitigations, and you should name all four: (1) replication, so a slow shard's replica can answer instead; (2) hedged requests, re-sending to a replica if the first has not answered in, say, 50 ms, and taking whichever returns first; (3) timeouts with partial results, returning the best-so-far top 10 after ~400 ms rather than failing the whole query because one shard of 200 is stuck; and (4) keeping posting lists in memory on the shard, so a lookup never waits on disk. A search page missing one shard's candidates is still a good page; a search page that times out is a failed query. That judgement — partial beats failed — is the senior call.

Index updates ride on the segment design from the architecture section: new documents land in fresh segments on every shard, and a shard's replica set must all receive the segment before it serves traffic — otherwise two replicas of the same shard would return different top 10s for the same query, and users would see results flicker on refresh. Replication of index segments is therefore done by a controlled rollout (publish segment, wait for all replicas to load it, then flip), not by casual background copying. Stale-by-minutes is acceptable; inconsistent-between-replicas is not.

The query path, step by step

Walk "derby hat-trick" from keyboard to results page:

  1. Autocomplete (before the search). As each character is typed, a trie (a tree where each node is a character and each path from the root is a prefix — "d" → "de" → "der" → "derby") suggests completions, ranked by past query popularity. The trie is small, held in memory, and updated from query logs — it answers in single-digit milliseconds and never touches the index. This is also why suggestions appear before you finish typing: the system is not searching, it is completing a prefix.
  2. Query parsing and correction. The raw query is tokenised the same way documents were (same normalisation, or "hattrick" would never match "hat-trick"). A spell corrector — built from the corpus vocabulary and past queries, using edit distance ("how many single-character changes to reach a known term?") — suggests "hat-trick" for "hattrick" and, if confidence is high, silently searches the corrected form while showing "showing results for hat-trick". Synonyms ("striker" ≈ "forward") are expanded here, cautiously: over-expansion destroys precision, so expansions are weighted lower than the original terms.
  3. Cache check. Popular queries ("Riverside fixtures") are served from a query-result cache in front of the fan-out — the same cache-aside idea from Lesson 3, keyed by the normalised query string. Cache hit rates are high because query popularity is extremely skewed: a small fraction of distinct queries accounts for most traffic. The cache is what makes the 5× peak survivable. Posting-list caches (caching the lists for hot terms) sit one level deeper, on the shards.
  4. Fan-out, merge, snippets. On a cache miss, the aggregator fans out to all shards with a deadline, merges each shard's top 10, re-ranks globally, and fetches the snippet text for the top 10 from the document store. Snippets are generated by finding the query terms in the document and showing the surrounding words with the terms highlighted — which is why the document store keeps the original text, not just the index.
  5. Logging for the next query. Every query, its results, and its clicks (with position-bias caveats) are logged to the analytics pipeline that retrains ranking, refreshes autocomplete popularity, and feeds the spell corrector. Search improves because yesterday's queries teach today's ranking — the feedback loop is part of the design, not an afterthought.

Hard parts, failure modes, and senior-depth traps

  • Hot terms on a hot day. Cup-final day: every query contains "derby". The posting list for "derby" is enormous, and every shard scans it. Fixes: cache the posting list in memory (it is read far more than written), start intersections from the rarest term so the huge list is consulted last and pruned early, and cap the work with early termination — once a shard has found enough high-scoring candidates, it can stop scanning (the WAND family of algorithms: skip documents that cannot beat the current 10th-best score). Stating "we prune with a score threshold, not just intersect fully" is a strong senior detail.
  • Duplicate and near-duplicate content. The same match report syndicated to fifty sites would flood the top 10 with identical text. Fix: near-dup detection at index time (shingles and MinHash, from Lesson 20's dedup section), keeping one canonical copy and clustering the rest under "similar pages". Duplicates are an index-build problem, not a ranking problem — solve them before they reach the ranking stage.
  • Spam and SEO gaming. Pages stuffed with "derby hat-trick" repeated a hundred times would win naive TF scoring. Fixes: TF saturation in BM25 already blunts repetition, link-based signals (PageRank) cannot be faked by one page alone, and a spam classifier demotes or drops known gaming patterns. Ranking is adversarial: whatever signal you publish, someone optimises against it, so no single signal is ever trusted alone.
  • Stale results after a fast-moving event. A transfer is announced; fans search the player's name and get yesterday's speculation. Fixes: freshness-aware ranking for news-like queries, a fast indexing lane for high-churn sources (segments published in minutes, not hours), and cache invalidation keyed to trending terms — the query-result cache must not serve yesterday's top 10 for today's news. The cache TTL for a trending query is minutes; for an evergreen query, hours.
  • Multilingual and tokenisation traps. Languages without spaces between words, compound words, and names with accents all break naive tokenisation ("hat-trick" vs "hattrick" vs "hat trick" are three tokenisations of one idea). Fix: language detection per document, language-specific analysers, and normalisation (accent folding) applied identically at index time and query time. The rule: index-time and query-time analysis must be the same function — any mismatch is a class of bug, not a single bug.
Three senior-depth traps

1. "Sharding by term is more efficient because a query touches fewer machines." It touches fewer machines and still loses: hot terms unbalance it, and partial scores across term shards cannot be merged correctly without extra coordination. Document sharding plus tail-latency mitigations is the standard answer — name the mitigations, don't just name the shard key. 2. "TF-IDF is the ranking." It is the foundation, not the system: BM25 corrects its two flaws (saturation, length), and production ranking re-ranks BM25's top few hundred with a learned model. Quoting BM25's defaults (k₁ ≈ 1.2, b ≈ 0.75) beats reciting its formula. 3. "Caching the top 10 is enough." The query cache helps only popular queries; the long tail of rare queries — most distinct queries, a minority of traffic — still fans out. Size the shard fleet for the tail, and let the cache absorb the head.

Questions with full model answers

Tap each question to reveal its model answer. The answers are written as you would say them, not as bullet-point hints.

1. A user types a query and expects an answer in under half a second from billions of documents. How is that possible?

Because almost all the work happened before the query arrived. At index time, documents are tokenised and stored in an inverted index — a map from each term to the list of documents containing it — so a query never scans documents, it looks up a few posting lists and intersects them, starting from the rarest term. The index is sharded by document across hundreds of machines with posting lists held in memory, so each shard answers in milliseconds; an aggregator fans the query out to all shards, merges each shard's top 10, and returns the global top 10. Ranking is precomputed as far as possible — BM25 scores from term statistics, PageRank from the link graph — so the per-query work is lookup, intersection, and a merge, not analysis. The half second is a budget for fan-out and merging, not for thinking.

2. Would you shard the index by term or by document, and why?

By document. Term sharding looks efficient — a query touches only the shards holding its terms — but it fails twice: a popular term on a big day hammers one shard while the rest idle, and a multi-term query's scores are computed from partial information spread across machines, so merging them correctly needs extra coordination. Document sharding spreads every query evenly across all shards and lets each shard compute complete, correctly normalised scores, because global term statistics are replicated to every shard as a small table. The real cost of document sharding is tail latency — the query waits for the slowest of hundreds of shards — and that is a solved problem: replicate shards, hedge slow requests to a second replica, time out with partial results rather than failing, and keep posting lists in memory. Partial results beat failed queries.

3. Why does a rare word matter more than a common word in ranking?

Because rarity is information. If a word appears in nearly every document, knowing a document contains it tells you almost nothing about whether it is the document the user wants; if a word appears in few documents, its presence is a strong signal. TF-IDF makes that precise: IDF = log(N ÷ df), so a term in 1 of 4 documents scores log₁₀(4) ≈ 0.602 while a term in 3 of 4 scores log₁₀(4 ÷ 3) ≈ 0.125. In the worked example, a document mentioning "derby" three times scores 0.375 while a document mentioning "derby" once and "hat-trick" twice scores 1.329 — the rare term dominates, correctly. BM25 keeps this idea and fixes TF-IDF's two flaws: term frequency saturates so repetition stops paying, and scores are normalised by document length so long documents are not rewarded just for being long.

4. Search results for breaking news go stale within minutes. What do you change?

Three things, in order. First, a fast indexing lane: new documents from high-churn sources land in fresh index segments within minutes, because segments are immutable and publishable independently — you never rebuild the whole index to add a document. Second, freshness-aware ranking: for news-like queries, blend a recency decay into the score so today's report outranks a perfect 2019 match, while evergreen queries keep their time-independent ranking — which means detecting query intent, not applying freshness blindly. Third, cache discipline: the query-result cache must use short TTLs for trending terms, or it will keep serving yesterday's top 10 no matter how fresh the index is. Stale-by-minutes is a design parameter you set deliberately per query class; stale-because-the-cache-says-so is a bug.

Practice drills (untimed)

Work these without a timer. The rubric under each one is what a strong answer covers.

  1. Intersect by hand. Posting lists: riverside → [1, 2, 3, 4, 5, 6], derby → [1, 2, 4, 6], hat → [1], trick → [1]. For the query "derby hat trick", which list do you start from, what is the intersection, and how many documents do you actually check? Rubric: start from the shortest list ("hat", 1 document); intersection is [1]; you check at most that one document against the other lists, not all six. Starting from "riverside" or scanning all lists is the miss — the rule is rarest term first.
  2. Score it. Corpus: 10 documents. Term "striker" appears in 5, term "bicycle" (as in bicycle kick) in 1. Document A mentions striker twice; document B mentions bicycle once. Using IDF = log₁₀(N ÷ df) and score = mentions × IDF, which document ranks higher for the query "striker bicycle", and by how much? Rubric: IDF(striker) = log₁₀(2) ≈ 0.301, so A scores 2 × 0.301 = 0.602; IDF(bicycle) = log₁₀(10) = 1.0, so B scores 1.0; B wins despite one mention vs two, because rarity dominates. Any answer ranking A first has missed the IDF idea.
  3. Size the fleet. A corpus of 1 billion documents, 400 distinct terms each, 2 bytes per posting, 20 GB shards, 10,000 peak queries/sec, one replica serving 5,000 shard-queries/sec. How many shards, and how many replicas per shard? Rubric: postings = 4 × 10¹¹, index = 800 GB, shards = 800 ÷ 20 = 40; fan-out = 10,000 × 40 = 400,000 shard-queries/sec; replicas per shard = ceil(400,000 ÷ 5,000 ÷ 40) = 2. A missing fan-out step (sizing for queries/sec instead of shard-queries/sec) is the classic error.

60-second framing

Use this when asked to design it cold: "Search splits into indexing and serving, and the index is the product. Documents are tokenised and stored in an inverted index — each term maps to the list of documents containing it — so a query intersects a few posting lists starting from the rarest term instead of scanning anything. Ranking starts with BM25: term frequency that saturates, weighted by inverse document frequency so rare terms dominate, normalised by document length, with PageRank and a learned re-ranker layered on top of the top few hundred. The index is sharded by document, not by term, because term sharding collapses under hot terms and partial scores; the cost is tail latency across hundreds of shards, paid with replicas, hedged requests, and timeouts that return partial results rather than failing. Fresh documents arrive as new immutable segments in minutes, autocomplete is a trie over past queries, and the query-result cache absorbs the skewed head of query popularity while the shard fleet is sized for the long tail. The hard parts are hot terms, near-duplicates, spam, and freshness — each handled at index time or in the serving path, never by hoping the ranking model sorts it out."
