Sharding & partitioning: split the data to survive the load

One machine can only take so much. Sharding spreads one dataset across many databases — and the hard part is deciding who owns which row, finding that row again fast, and surviving the day when one row becomes everyone’s favorite.

The thread to follow Every sharding decision answers three questions: how is a row placed on a shard, how is it found again without searching everywhere, and what happens when the placement plan changes or goes wrong.

01 / FOUNDATION

What is sharding?

Start here. Everything in this lesson — strategies, hot keys, resharding pain — is a consequence of one decision: splitting one dataset into many pieces.

READ · SETTLE IN — NO CLICKING YET
Database sharding is the act of splitting one large database into smaller, independent databases — called shards — that each hold a different slice of the rows, so the load and storage are spread across many machines.
90′

Soccer model: picture a squad of 500 players and one team bus that seats 50. The club does not buy one magic 500-seat bus; it runs ten buses, each carrying its own group of players. Every player still has exactly one seat, the club keeps one registry of who sits where, and away trips scale by adding a bus — but asking “which bus is player 9 on?” now needs the registry, and if one bus breaks down you have a real problem with exactly fifty players. A shard is one of those buses.

Shard
One independent database instance holding a slice of the rows — the team bus. A player with id 90542 lives on exactly one of them.
Shard key
The row attribute that decides placement: the value the router computes with. Like the rule “player surname A–G → bus 1”. Usually the id, sometimes not.
Partition
The general word for one slice of a divided dataset. “Partition” is the family name; sharding is partitioning across machines, each slice owned by its own server.
Hot shard
A shard receiving far more than its fair share of traffic — a bus everyone keeps boarding because their star-player friend sits there.
Hot key
The single row responsible: one player id that is read or written far more than anything else — like everyone wanting the star striker’s jersey at the club shop.
Resharding
Changing the placement plan — adding shards and moving rows between them. Reassigning players when the club buys more buses.
Scatter-gather
What happens when a query has no shard key supplied: it fans out (“scatters”) to every shard and the results are combined (“gathered”) — asking all ten buses one by one where player 9 sits.
Consistent hashing
A placement algorithm where adding or removing a shard moves only ~1/(n+1) of the rows instead of everything. The famous fix for the “more buses, total chaos” problem.
Router
The component that computes or looks up which shard owns a shard key, sending each query to the right database. The club’s ticket gate: “player 9? That’s bus 3.”

Why this matters at senior level: sharding is not a free multiplier. Every strategy below is a trade-off between even spread and easy lookup, and every running system eventually meets the same two enemies: the row everyone wants (hot key) and the day the plan must change (resharding).

02 / MOTIVATION

Why shard at all?

Sharding has real costs, so teams don’t do it for fun. Here are the concrete walls you hit on one machine — and the moment replication stops helping.

READ · LEARN THE CEILINGS

The write ceiling

A single relational primary typically tops out around 5,000–20,000 committed writes/sec for normal small rows — copy rates fall fast as you add secondary indexes, constraints, and large rows. A disk-bound insert is a disk-bound insert; you cannot spin the platter faster. When the league’s match-day traffic passes that line, one box stops keeping up no matter how big you make it.

The storage ceiling

One database server comfortably holds roughly 2–6 TB of working data at good performance (bigger is possible but painful). Backups, restores, schema migrations, and replica rebuilds get measured in hours to days. A 20 TB database means a failed replica rebuild eating the whole weekend — and one unlucky disk holding your entire world.

The leader bottleneck

Replication adds read capacity — followers take reads off the leader. But every write still funnels through one leader that must order and log it, and every follower stores the entire dataset. Reads scale, writes and storage don’t. That’s the moment replication stops being enough. Sharding attacks the two axes replication cannot reach: write throughput and dataset size.

Honest senior framing: sharding buys write throughput, storage scale, and smaller blast radius — and it charges you in weaker transactions, painful cross-shard queries, and operational complexity. Respectable strong answers name the ceilings (what will break), then name the tax (what the fix costs) before choosing.

03 / TWO AXES

Horizontal vs vertical partitioning

Two different ways to cut a database apart, from zero. Know both, and know which one buys your next order of magnitude.

READ · TWO IDEAS, ONE TO PICK

Vertical partitioning: cut by table or column

Split different kinds of data onto different servers. User profiles move to one cluster, match-event logs to another, media metadata to a third — or even split one table into “fat columns” (bios, photos) and “hot columns” (ids, stats). This is the soccer analogy of splitting the squad’s staff: the physiotherapy office, the ticket office, and the coaching office each get their own building. Traffic patterns differ per table, so you size each independently.

It delays the hard problem: it works until one table alone is too big or one table’s writes exceed one server. Then vertical cuts have nothing left to offer, because any single table still lives on one box.

Horizontal partitioning: cut by row (this is sharding)

Split different rows of the same table onto different servers. The players table: player ids 1–1M on shard 1, 1M–2M on shard 2. Now no single server holds all players, so each shard’s write stream and storage both shrink toward 1/N. That is the squad-split-across-buses move. It is the only option here that scales writes and storage for one hot table.

It costs you: routing (which shard owns this row?), cross-shard joins and transactions (or the lack of them), and the resharding plan when N must grow. The rest of this lesson is about this axis — how to place, find, balance, and migrate rows.

Do both, in this order: vertical partitioning is usually the first move (easy, cheap, buys one generation), horizontal sharding the second (hard, expensive, buys many generations). In an interview, say which ceiling each one attacks — signal you’re not just reciting a name you memorized.

04 / STRATEGY FAMILY

Four ways to place a row

One family of ideas, one running scenario: a fan taps the profile card for star striker player_id 90542. Read each strategy first — the explorer below is practice, not your first explanation.

READ FIRST · THEN TRY THE EXPLORER

The running scenario

Your football app stores player_profiles on 4 shards (S0–S3). A fan taps the card for player_id 90542 (the star striker). The app asks the router where the row lives; the router computes or looks up the shard; the owning shard serves the row. Every strategy below walks this exact path.

1. Range-based sharding SHARD BY VALUE RANGE

The idea: the key space is chopped into contiguous ranges: ids 0–249,999 live on S0, 250,000–499,999 on S1, and so on — like seat blocks at a stadium (Rows A–D in the east stand). Neighboring values cluster on the same shard. A tiny range map makes routing instant.

Read: fan taps profile 90542

  1. App: asks the router “who owns player 90542?”
  2. Router: binary-searches the range map: 90542 ∈ [0, 249,999] → S0.
  3. Router: forwards the query to S0.
  4. S0: looks up the row in its local index and returns the profile.

Write: the striker scores, stat row updates

  1. App: sends the update with the shard key (player_id).
  2. Router: maps 90542 → S0 as above.
  3. S0: commits the write (its own ACID transaction — local, full-strength).
  4. Router: returns success to the app.
Why pick it

Adjacent keys sit together — perfect for ordered scans (“top 100 scorers this season”) and growing near the newest ids.

The price

Auto-increment and timestamp keys pile the newest, hottest rows onto one shard — the classic “today’s match is all on bus 3” hotspot.

2. Hash-based sharding (modulo) SHARD = HASH(KEY) % N

The idea: run the key through a hash and take the remainder modulo the shard count: shard = hash(player_id) % 4. Random-feeling ids spread nearly evenly, no lookup table needed — like dealing cards from the squad deck, one per bus, round after round. Routing is pure arithmetic.

Read: fan taps profile 90542

  1. App: asks the router “who owns player 90542?”
  2. Router: computes hash(90542) % 4 — say 1 → S1.
  3. Router: forwards the query to S1.
  4. S1: reads the row locally and returns the profile.

Write: the striker signs a new boot deal

  1. App: sends the update with player_id 90542.
  2. Router: computes the same hash % 4 = 1 → S1. Deterministic — the same key always lands on the same shard.
  3. S1: commits the write locally.
  4. Router: returns success to the app.
Why pick it

Even distribution with zero bookkeeping — router math replaces a lookup service entirely.

The price

Change N, and remainders reshuffle: adding one shard moves roughly n/(n+1) of your rows. Range queries are dead — consecutive ids are on different shards.

3. Consistent hashing THE RING + VIRTUAL NODES

The idea: wrap the hash space into a ring (0–1023 here). Each shard claims several virtual nodes — ghost copies pinned at random ring positions. To place a key, hash it onto the ring and walk clockwise until you hit a virtual node; the real shard behind it owns the key. Picture twelve flag posts around a football pitch, three owned by each of four clubs; a ball belongs to whichever club owns the next flag clockwise. Most keys keep their owner when a club joins — only the keys in the new club’s arc segments move.

Read: fan taps profile 90542

  1. App: asks the router “who owns player 90542?”
  2. Router: hashes the key to ring position, e.g. 731, and walks clockwise to the next virtual node — one of S2’s.
  3. Router: forwards the query to S2.
  4. S2: reads the row locally and returns the profile.

Write: goal of the season goes to a vote

  1. App: sends the update tagged with player_id 90542.
  2. Router: repeats the identical ring walk → S2.
  3. S2: commits the write locally.
  4. Router: returns success; no other shard is involved.
Why pick it

Add/remove a shard and only ~1/(n+1) of keys move (virtual nodes make the arcs evenly sized). The standard dynamic for elastic clusters.

The price

More bookkeeping (the ring and vnodes need replication), and luck can still leave one shard slightly heavier — heartbeat on balance is required.

4. Directory / lookup-based A ROUTING TABLE SERVICE

The idea: keep an explicit table — player_id → shard (or ranges → shard, clubs → shard) — on a small dedicated service (often just a replicated database table with caching). Routing asks the directory instead of computing. It’s the club’s actual registry book: exact, changeable, but someone must maintain it. This is how you place related rows together deliberately — for example, every player of one club on the same shard so team queries stay shard-local.

Read: fan taps profile 90542

  1. App: asks the router “who owns player 90542?”
  2. Router: consults the directory: “player 90542 → S3 (whatever it says today).”
  3. Router: forwards the query to S3.
  4. S3: reads the row locally and returns the profile.

Write: transfer window — the striker changes clubs

  1. App: sends the update with player_id 90542.
  2. Router: reads the directory → S3. (Cache directory entries so this is one local memory lookup, not a network round trip.)
  3. S3: commits the write locally.
  4. Ops: if the club wanted its squad co-located, it could move the row and update the directory entry — placement is a policy decision, not arithmetic fate.
Why pick it

Total control: arbitrary placement, easy co-location, moves exactly the rows you want. The directory is small enough to cache aggressively.

The price

One more system to keep correct and highly available — a stale directory entry sends reads to an empty shard.

    05 / THE KEY DECISION

    Choosing the shard key

    Three properties, in priority order, decide whether a shard key is good. Get this wrong and no strategy above can save you.

    READ · FRAME FOR INTERVIEWS

    1. High cardinality

    Cardinality means the number of distinct values. You need far more distinct key values than shards, so slicing the space can never leave a shard sparse. player_id (50 million players, 64 shards) is excellent. continent (7 values, 64 shards) is absurd: at least 57 shards stand empty. More values isn’t just nicer — it’s what makes balance possible.

    2. Even distribution

    Rows and traffic must reach every shard roughly equally. Sharding 50 million players by national_team fails: Brazil and France absorb populations while San Marino sits near-empty (low-cardinality again). Sharding by club_id looks better until the derby week, when one club’s traffic dwarfs the rest. This is why hashing raw ids is the default template — it evens out whatever history drew.

    3. Locality

    Rows that are queried together should live together, so queries stay inside one shard. A fan’s “squad page” query asks for all 11 players of a club; if every club-mate sits on the same shard, that’s one fast local query instead of 11 cross-shard hops. This is the tension of sharding: team_id gives locality but risks load imbalance; player_id gives balance but scatters the squad page. Strong answers say which access pattern they’re optimizing for.

    The interview answer frame

    Name your access patterns first (“80% of reads are by player id, 15% by club, 5% admin scans”), then pick the key that keeps most traffic shard-local and balanced, then name the tier-two problem you’re accepting (“squad pages fan out, but cached at the edge”). Design the key around the queries, never the schema diagram alone.

    One line to say in the room: “I’d pick player_id hashed for balance on the read path, accept that club-scoped pages fan out, and co-locate club rosters on the same shard if the squad page is actually a hot query.” That sentence alone marks you as thinking, not reciting.

    06 / HOT SHARDS

    When one row rules them all

    Your layout is perfect and one key destroys it: the star striker’s profile becomes 95% of traffic. Read how detection and mitigation work, then inject a viral moment yourself.

    READ · THEN INJECT A VIRAL MOMENT
    A hot key is one row (one shard-key value) that attracts a wildly disproportionate share of traffic. The shard that owns it becomes a hot shard — and since a hot key can’t be helped by moving other rows away, no placement strategy fixes it. Only treatments for the key itself do.

    How it happens

    Our star striker scores a 90th-minute winner in the cup final. Every fan taps his profile at once. This mirrors the celebrity fan-out problem from social feeds: one celebrity publishes, millions of timelines must update. Any id that can “go viral” — a featured player, a trending product, the league dashboard’s aggregate row — is a hot-key candidate before it’s ever a victim.

    How you detect it

    Track per-shard QPS, CPU, and latency side by side; a hot shard breaks the line. Then sample top-k keys by traffic per shard and look for skew (shard traffic ÷ average traffic ≥ ~3× is a smell; 20× is a fire). A thundering herd — a surge of clients hitting one key the instant a shared cache entry expires — is its close cousin: same shape, different trigger.

    How you mitigate it

    Cache the key at the router or edge — reads stop reaching the shard. Add read replicas per shard — every shard keeps its own replica set for read fan-out. Salt/spread the key — write a few copies (player_90542#1 … #4) across shards, reads pick a random copy, writes fan out to all copies. More copies raise write cost: the trade, stated honestly.

    07 / SCATTER-GATHER

    Queries without a shard key

    What breaks when the query can’t name its shard: the fan-out tax, the tail-latency math, and the three standard escapes.

    READ · DO THE COST MATH
    A scatter-gather query hits every shard because the router can’t tell whose row it is — “find the five fastest players in the league” when rows are placed by player_id. The router scatters the query across all shards and gathers the answers.

    Exactly what happens, step by step

    1. App: asks “top 5 scorers league-wide?” — no player_id in the filter.
    2. Router: has no key to compute with, so it sends the query to S0, S1, S2, S3 all at once.
    3. Each shard: runs “its own top 5” locally and returns them.
    4. Router: gathers 20 candidates, sorts, and returns the global top 5.

    The cost math, with numbers. p99 latency means 99 of 100 requests finish faster than this number — it’s how you quote “how slow can it get?” If one shard-side query has p99 = 8 ms, the scatter’s chance of finishing under 8 ms across 16 shards is 0.99⁰¹ ≈ 0.85 — so roughly 15% of fan-out queries exceed the slowest shard’s p99. You now pay the slowest shard’s tail on every such query, multiplied by sixteen shard-CPU costs, for results users expect instantly. A few background analytics can afford this. User-facing pages cannot.

    Denormalization

    Copy the needed fields into each row or into a dedicated table at write time: leaderboard snapshots, tri-computed aggregates. You trade write amplification (keeping copies updated) and careful staleness budgets for read-side locality.

    Secondary indexes (GSI)

    A global secondary index is a separate index sharded by its key (e.g. goals), kept in sync by the write path: updates write the row AND the index entries. Async sync keeps writes fast at the price of briefly stale indexes.

    CQRS read models

    CQRS (Command Query Responsibility Segregation) means maintaining a dedicated read store shaped exactly like your queries. Score events stream into leaderboard, stat-page, and search stores, each optimized for one need. Most buildable at real scale: this is how the big football apps actually serve live leaderboards.

    08 / CROSS-SHARD REALITY

    Joins and transactions across shards

    Why the database stops helping you: cross-shard joins move mountains, and cross-shard transactions ask you to trust a protocol everybody hates.

    READ · NAME THE PAIN BEFORE THE FIX

    Cross-shard joins are expensive

    A join between players (sharded by player_id) and contracts (sharded by contract_id) has no local co-location: the router must pull candidate rows from many shards over the network and stitch them in memory (or broadcast one side everywhere). That’s hundred-megabyte, seconds-long stitching, not a fast database join. Workarounds: co-locate related rows on the same shard via the shard-key choice (contracts keyed under their player), denormalize the fields you need, or do the join in the application in two phased queries.

    Transactions lose their atomicity

    A transaction fails or commits as a whole only inside one shard. When a transfer writes “player leaves club A” on S1 and “player joins club B” on S2, one leg can commit while the other aborts, leaving the data inconsistent. You cannot ask the database to make it atomic — there is no single database anymore.

    Two-phase commit: why teams avoid it

    Two-phase commit (2PC) is a protocol that makes multiple databases commit together: a coordinator asks every shard “ready?” (prepare phase), and commits everywhere only if all agree. It works, but the price is why production systems dodge it: every participant holds locks from prepare until the coordinator decides, so one slow shard or one lost coordinator leaves transactions dangling and the whole path slow. Latency spikes and availability risk concentrate exactly where you can least afford them.

    Saga-style: eventual approaches

    A saga is a sequence of small, local transactions, one per shard, each with a compensating action (an undo) if a later leg fails. Transfer example: leg 1 “remove from club A” (local commit on S1), leg 2 “add to club B” (local commit on S2); if leg 2 fails, run the undo “restore club A membership”. Make every leg idempotent (idempotent = safe to retry; running it twice has the same effect as once), driven by a durable outbox or event log so a crash mid-saga resumes instead of corrupting. Not instantaneous consistency — correctly-eventually one.

    ⇆

    Wallet-invisible middle ground: not every cross-shard operation needs sagas. Many teams scope transactions so that each business operation touches one shard: account for a transfer as a single “settlement row” on one shard, or route the whole workflow by one primary key. Design your shard key so the operations you care about stay atomic. That is sharding discipline, not sharding luck.

    09 / RESHARDING

    Changing the plan while it runs

    Adding shards means moving rows without a maintenance window. How data moves, the live-migration ritual, and the trick that makes it nearly painless.

    READ · THE OPERATION EVERYONE DREADS
    Resharding is adding (or removing) shards and moving rows to the new owners — while fans are tapping profiles. It is the operation every sharded team most fears, and it is exactly what consistent hashing was invented to soften.

    Doubling with range shards: split the range

    Each shard’s range is cut in half: S0 takes [0, 124,999], new S4 takes [125,000, 249,999]. Only rows in the split half move. Clean and predictable — but it’s surgery per range, and you can only split where the load actually needs it, which you must know per shard. Range migrations pair naturally with adding capacity exactly where it hurts.

    Doubling with hash shards: rehash the world

    Changing N from 8 to 16 in hash(key) % N reshuffles roughly 15/16 of rows — basically everything moves, and the router’s mental map changes completely. That’s a full-dataset migration measured in hours or days, which is why plain modulo hash is nearly extinct at big shops and why consistent hashing exists.

    The live ritual (no downtime)

    1. Provision new shards and start double-writing (every write goes to old owner and new owner). 2. Backfill historical rows into new owners in the background. 3. Verify: checksums, sample reads, row counts per key must match. 4. Cut over the router in stages (percent of traffic, watching errors), then retire double-writes. 5. Keep the old copies as rollback insurance before deleting. The word “simple” appears nowhere in this ritual.

    The senior trick: logical shards

    Most real systems shard logically, not physically: pick 512 or 4096 tiny logical shards up front, and map those onto a handful of physical servers. Growing means re-assigning logical shards to new boxes — a metadata change plus copying small units, not re-hashing the universe. You set the ceiling once (512 logical shards won’t be outgrown by accident); the physical fleet catches up as budget demands.

    Why teams choose “enough shards up front.” Picking 64 or 128 small shards on day one (each mostly empty) looks wasteful — and then it quietly pays for years: growth is quiet rebalancing, never a rush-job migration under a deadline. The tax is modest per-shard overhead and more moving parts to operate. Teams that under-shard early pay in resharding theater; teams that over-shard a little pay in spare capacity. Only one of those is embarrassing.

    10 / PUTTING IT TOGETHER

    Sharding vs replication: a marriage

    Not rivals — they compose. Each shard gets its own replica set, and each mechanism scales a different axis.

    READ · CONNECT THE TWO LESSONS
    In practice, every shard is a replicated group: one shard owns 1/N of the rows, and that shard’s rows live on one primary plus its followers. Sharding splits the dataset; replication copies each slice.

    12 / QUESTION LAB

    Defend your shard plan

    Try each aloud as if the interviewer asked it. Then open the model answer and check whether you named the trade-off, not just the tactic.

    QUIZ YOURSELF · ANSWER OUT LOUD FIRST
    Q1

    Your players table lives on a single PostgreSQL primary: 12,000 writes/sec at match time, 4 TB of data, max-sharding-compatible replicas serving reads. The team asks: "Should we shard?" Walk them through your decision.

    “I’ll start with the ceilings, then the tax.”

    First I’d verify we’re actually at a wall. 12,000 writes per second is within the top end of what a tuned single primary can sustain if the rows are small and indexes shallow, so I’d check the actual saturation signals: write latency tail during match time, replication lag on the replicas, page-cache hit rate on a 4 TB dataset, and how long a replica rebuild takes. If rebuilds take most of a day and the leader’s log flush is queueing, we’re not near one wall, we’re near two — writes and storage — and replication can’t fix either, because followers copy the whole dataset and the leader still serializes every write.

    Before sharding I’d take the easier wins in order: vertical partitioning of rarely-touched columns (bios, photos) off the hot table, pruning or archiving cold rows, and making sure match-time write paths aren’t doing one heavy row lock at a time. If those buy a year, I’d take the year — sharding is the most expensive move on the menu.

    If the math still doesn’t work, I’d commit to sharding on player_id, hashed, because profile reads dominate and players are independent — a natural locality-free workload. I’d pick a fixed logical shard count (say 128) mapped to physical servers so growth is rebalancing, not rehashing. I’d name the tax out loud: club-scoped squad pages will fan out across shards, so I’d decide whether to co-locate club members or cache squad pages at the edge; cross-shard transactions simply won’t exist, so anything that must be atomic stays on one shard by design.

    My first actual move would be: build the router and the shard-key contract, shard the table into empty logical shards on the same cluster, dual-write to prove the routing path end-to-end, then move a low-traffic slice first and watch per-shard latencies for a week before touching the hot slice.

    Q2

    "We keep match events in a table keyed by timestamp. Range or hash sharding — pick one and defend it."

    “Range-sharding by timestamp is the standard mistake; I’d only do it knowingly, and I’d rather shard by match id.”

    The trap is that today’s shard — under range-by-timestamp — receives nearly all new writes and nearly all fresh reads. Match events are the canonical hot-write flow: a cup final writes tens of thousands of events in ninety minutes, all landing in “this week’s” range. That’s a hot shard drawn by its own blueprint.

    So I’d ask what the queries actually are. If it’s mostly “all events for match X,” which is the usual pattern for match pages and highlights, then match_id as the shard key is clearly better: one match’s events are co-located (locality), matches are independent (no hot-write cluster at any one time unless there’s one huge final, which is rare and cachable), and time-ordered scans of a match stay inside one shard.

    And I’d defend the pick against the failure mode: sharding by match_id does mean one World Cup final writes to a single shard for two hours. I’d size shards for that burst — a single match’s event stream is still a bounded write rate — and put the live match feed behind an edge cache so reads don’t amplify it. If I truly had to shard by timestamp for range-scan analytics, I’d do it in a separate CQRS read store, not on the system of record.

    Q3

    "Explain consistent hashing in three minutes — and tell me why virtual nodes exist."

    “Think of the hash space as a clock face.”

    You place both your servers and your keys on a ring — say 0 to 1023. To store a key, hash it, find its position on the ring, and walk clockwise until you hit the first server; that server owns the key. Removing a server only redistributes the keys in the arc behind it, to its clockwise neighbor — and adding a server only peels off the keys in the arcs it now occupies, roughly 1 over (n+1) of the data. Contrast that with hash(key) % n, where changing n remainders almost everything. That’s the whole economic argument: growth and failure move a sliver, not the dataset.

    Virtual nodes exist because luck is a bad scheduler. If you place one point per server, big arcs and small arcs are pure chance; one server can inherit 30% of the ring while another gets 4%. So each physical server claims, say, 100 virtual points scattered around the ring. The law of averages then gives each server a fair total share, and when you add hardware you add its virtual points and only its arcs move. You’d also weight virtual-node counts by server capacity — a big box gets more points than a small one.

    One more thing worth saying in the room: the ring must be replicated to everyone doing routing, with versioned updates, because two routers disagreeing means reads hunting on the wrong server.

    Q4

    "One shard is melting at 95% CPU while the others sit at 20%. Walk me through your debugging and live mitigation."

    “That shape — one shard hot, siblings idle — is a hot key or hot query until proven otherwise.”

    I’d confirm in layers. First, per-shard QPS: is the hot shard receiving more queries, or doing more work per query? If QPS is skewed 20×, I sample top-k keys on that shard and likely find one key — the viral star, a featured jersey, a league dashboard row. If QPS looks even, it’s a capacity problem on the shard itself: a bad plan, lock contention, a runaway compaction, or siblings with faster disks. That distinction matters because a hot-key plan won’t fix a broken box.

    Assuming it’s a hot key, reads are cacheable but nothing on the critical path is doing that — so the fastest mitigation is caching the hot key at the router or edge with a short TTL, which can absorb 90%+ of read traffic in minutes. That’s a bandage worth applying immediately.

    The durable fix depends on whether the heat is reads or writes. For write-hot keys, I’d split the key into salted copies — the same player id with hash suffixes landing on different shards, reads load-balancing across copies, writes fanning out to all of them — accepting the write-amplification cost. For read-hot keys that change rarely, mitigation is caching plus moving the traffic upstream forever. I’d note explicitly what adding generic replicas won’t do: divide all shards equally does nothing to the skew ratio, because the relative heat stays 20×.

    And afterwards, I’d add per-key traffic sampling and per-shard QPS-ratio alerting — the hot key should announce itself next time, not arrive as a page at 2 a.m.

    Q5

    "Two fans swap jersey badges: debit badge from user A on shard 3, credit to user B on shard 7. It's money. Do you use two-phase commit?"

    “I probably wouldn’t use two-phase commit — here’s what I’d do instead, and the honest exception.”

    Two-phase commit would give me atomicity, but it holds locks across both shards from the prepare vote until the coordinator decides. With money, our transactions concentrate at the hot users — exactly the shards where a dangling 2PC locks an unlucky shard commit during a slow coordinator. The latency tail and availability risk concentrate on the money path, which is where I want the least risk. So 2PC is out for the hot path.

    The better design is to not need cross-shard atomicity. First choice: scope the data so the operation is shard-local — badges minted per-shard, and the transfer recorded as a leg pair routed by a single transaction id into one settlement shard. If the product genuinely requires cross-shard debits and credits, I’d use a saga: debit on shard 3 as a local, idempotent transaction, then credit on shard 7 as another local transaction, each emitting a durable event; if the credit fails, a compensating action re-credits shard 3. I’d make the whole thing reconcilable: a periodic job matches debits against credits and pages on any unreconciled delta beyond a few minutes.

    The honest exception is where the business can’t tolerate even eventual inconsistency — some ledger products, some payment settlements. Then I’d isolate 2PC to a tiny transaction coordinator touching only those participants, with timeouts, lock monitoring, and explicit acceptance of the slower tail. I’d name that cost to the interviewer: I’m paying lock time and coordinator availability for exact atomicity, and outside that narrow domain I’m not.

    Q6

    Design a sharded profile store for a billion users — choose your shard key and defend it.

    “I’ll work from estimates to placement, then defend every choice and name the weaknesses.”

    First the estimates. A billion profiles. Say average profile metadata is 4 KB (id, handle, bio, settings, avatar pointer) — that’s 4 TB of row data, plus indexes maybe 6–8 TB total. Read pattern: hundreds of thousands of reads per second at peak; writes tiny by comparison — a few thousand per second. So this workload is read-dominated, storage-dominated, with strict per-row lookups by user id being 90% of reads. Those facts drive the whole design.

    I’d shard by user_id, hashed, across 512 logical shards mapped onto physical servers. 512 because I want growth as rebalancing between boxes, never a rehash of the universe — the logical-to-physical mapping moves small units. Hashing because the workload has no locality worth paying for on the write path, and user ids are high-cardinality enough to make balance automatic. Routing: hash(user_id) to logical shard, mapping table to the physical owner, the map cached aggressively on the router fleet.

    Physically, I’d put maybe 8–16 physical boxes to start, each owning 32–64 logical shards, each shard’s data replicated to followers in two more regions for geo-proximity reads and blast isolation. That composition is the classic one: shards divide rows and writes, replication copies each slice for reads and HA.

    Now I’d defend against the two enemies. Hot keys: a viral celebrity profile is a certainty. I’d layer a cache in front of the profile path with a moderate TTL for viral keys, per-shard QPS skew alerting, and the salted-copy pattern ready for the top few dozen ids — writes to the celebrity’s row fan out to copies, reads spread. Because this is read-heavy, I’d also split replicas onto dedicated read fleet so a viral read surge never touches write capacity.

    Scatter-gather: search-by-handle, leaderboards, and country filters have no user_id, so they cannot touch the profile store’s hot path. I’d put those behind a CQRS read store — handle-to-id lookup table, leaderboard snapshots — updated asynchronously from the profile write stream, with explicit staleness budgets. I’d say this in the room: “the profile store answers one question — ‘who is user X?’ — and the read models answer everything else.”

    I’d name the costs I’m accepting: profile updates that depend on cross-user state (mutual follows, badge swaps) become sagas or pre-scoped transactions, and resharding at the logical layer still requires moving small units between boxes with double-write and verification — but at 512 shards, each move is one small, verifiable unit. The weakest point in the design is the viral-key plan depending on the cache fleet; if the cache dies, the hot shard dies — so I’d cache hot keys at two layers (edge and router memory) rather than one.

    What a strong answer covers: estimates grounding the shard math, the key choice defended against the real access pattern, explicit locality decisions, composition of sharding and replication, hot-key lifecycle, scatter-gather escapes, and named costs. If I hit all of those with numbers attached, I’ve shown not a memorized name but a working systems instinct.

    The 30-second summary

    Sharding splits one dataset so writes and storage scale across machines, with each shard replicated for reads and HA. The router math (range, hash, consistent hash, directory) decides placement; the shard key decides balance versus locality; hot keys and scatter-gather are the two enemies you plan for on day one; and resharding is the operation everyone fears and consistent hashing (or logical shards) was built to soften.
