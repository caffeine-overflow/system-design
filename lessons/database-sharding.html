Database sharding, from first principles

When one database can no longer hold the data or survive the writes, split it into many small ones — and learn why the way you split decides whether the system stays fast.

01 / FOUNDATION

What is database sharding?

Database sharding is the practice of splitting one large database into smaller, independent databases called shards, where each shard owns a different slice of the data. Together the shards behave like one logical database; physically, each one is separate, and each can grow on its own hardware.
Shard
One of the smaller databases. It holds a slice of the data and serves the reads and writes for that slice. Losing one shard means losing one slice, not the whole system — so each shard is usually replicated too.
Shard key
The field (or combination of fields) used to decide which shard owns a row, for example user_id or team_id. Choosing it is the single most important sharding decision; everything else follows from it.
Partitioning
The general idea of splitting data. Horizontal partitioning splits rows across databases (this lesson — that is sharding). Vertical partitioning splits columns or whole tables onto different servers, like keeping a huge photos table apart from users.
🏟

Soccer model: a stadium holds 60,000 fans, and one turnstile gate cannot process them all. So the club shards the crowd: turnstile A takes ticket numbers 1–20,000, turnstile B takes 20,001–40,000, and so on. Each gate owns a slice of the fans, and each slice flows at its own speed. Sharding is the same move: when one database gate cannot process the crowd, open more gates and decide, for every fan, which gate is theirs.

Writes scale out

Replication adds read capacity, but every replica still replays every write. Sharding is what splits write throughput across machines: each shard's leader only orders the writes for its own slice.

Datasets stay operable

A table that will not fit on one machine — or whose backups and index rebuilds take a weekend — becomes several independent tables. Each shard is small enough to back up, restore, and reason about.

Complexity you pay daily

Queries that touch several shards get slower and harder. Joins, transactions, and global aggregates all cross shard boundaries. You shard to survive, not for fun — never shard before you need to.

🚦

When to actually shard: when writes overwhelm one leader's capacity (CPU, I/O, or connection limits), when the dataset exceeds comfortable single-machine size, or when backup/recovery windows stop meeting the recovery objectives. Before that, the cheaper answers are: bigger machine (vertical scaling), read replicas, caching, and archiving cold data. Interviewers love candidates who say "I would not shard on day one" and can name the concrete signal that changes the answer.

02 / THE KEY DECISION

Choose the shard key like your system depends on it

The shard key is the field that decides which shard owns each row. It cannot be chosen lightly, because it is effectively immutable and it shapes every query you will ever write.

A good shard key has three properties: high cardinality (many distinct values, so the data can spread), even distribution (no single value dominates the traffic), and query isolation (most queries ask about one key value, so they touch one shard).
🎫

Soccer model: shard by ticket number (one per fan — high cardinality, beautifully even). Do not shard by match result — only three values (win, draw, loss), so one "shard" ends up holding every win. That is low cardinality, and it defeats the point. And do not shard by player of the match, because almost every fan's query — "what are his stats tonight?" — would fan out to every shard, since nobody remembers which shard a player landed on.

If 90% of requests are "show me this user's feed," shard by user_id. The router then computes the shard from a value the request already has, and the query stays on one shard. If queries mostly come with team_id, shard by that. Mismatch here is the most common sharding regret: every request becomes a scatter-gather across all shards because no request carries the shard key.

With 8 shards, a key with 8 distinct values is a coin toss per shard; a key with millions of distinct values balances itself statistically. As a rule of thumb, want at least hundreds to thousands of distinct key values per shard. Low-cardinality keys (country, status, gender) are disqualifying on their own — combine them into a composite key if you must.

Related rows should live on the same shard. In a chat app, shard conversations and their messages by conversation_id, not by message_id: loading a thread is then one shard, not one shard per message. Sharding by the wrong grain turns a single-row read into a fan-out.

Changing a row's shard key means moving the row — a cross-shard migration with delete, copy, and ordering hazards. Never choose a mutable field (username, email, team name) as the shard key. Use a stable surrogate key (an internal ID) instead, and let the mutable fields be ordinary columns.

⚠️

The re-shard-key rule: a shard key decision is a one-way door. Everything — application queries, the router, backfills, operational tooling — hardens around it. Interviewers probe this by asking "what if you chose wrong?" A strong answer names the migration cost explicitly: dual-writes, backfill, and a cutover, or in the worst case, a rewrite of every query's routing logic.

04 / SKEW

Hot shards: when one gate takes the whole crowd

A hot shard is a shard receiving a disproportionate share of traffic. It is the failure mode of an otherwise balanced design.

Rows can be evenly spread while requests are not. One celebrity profile, one trending match thread, one launch-day tenant — a tiny fraction of keys can carry most of the traffic.

Time-ordered keys

Range-sharded created_at or auto-increment IDs route all new writes to the newest shard — the current minute's shard does all the work.

  • Shard by hash of ID instead, or bucket time coarsely.
  • Expect this on write-heavy ingestion pipelines.

Superstar keys

A famous user, a final match, a viral post. Millions of requests target one key, hence one shard.

  • No shard key choice fixes popularity; cache it or split it.
  • Detect by per-shard request share, not row count.

Lumpy tenants

Multi-tenant apps shard by tenant; one tenant grows 100× the others and saturates its shard.

  • Split the big tenant across shards, or give it a dedicated shard.
  • Track per-tenant traffic, not just per-shard traffic.

Sequential scans

A reporting job or backfill walks a range that lives on one shard, starving live traffic there.

  • Run heavy jobs on replicas, throttled.
  • Quarantine analytical traffic off the serving shards.

Divide the hot shard's key range in two (range strategy) or move some of its virtual nodes to a new shard (consistent hashing). This is targeted resharding: move only the hot slice, not the whole cluster. It works when the heat comes from a key range, not a single key.

When the heat is one key — the final's match page, the celebrity profile — absorb the reads in a cache in front of the shard. The shard still owns the truth; the cache owns the traffic. Watch cache stampedes when the key expires (the caching lesson's stampede mitigations apply directly).

Rewrite a hot key match:final as match:final:0 … match:final:9 and spread writes across the salted variants. Reads aggregate the variants. This deliberately trades read complexity for write distribution — use it for counters and vote tallies, not for data you query by the original key.

Add read replicas to the hot shard so read traffic fans out while writes stay on one leader. Or precompute the expensive aggregation into a small read-optimized store. Both buy time, but neither fixes a write hotspot — writes must still land on one owner.

🌡

Measure heat, not size: dashboards should show per-shard request share (QPS), per-shard CPU and latency, and the top keys by traffic — not just row counts. A shard at 8% of rows and 60% of traffic is hot; a shard at 40% of rows and 10% of traffic is fine. Interviewers notice when candidates monitor requests, not storage.

05 / TRADE-OFFS

What sharding takes away

Every cross-shard operation is a distributed-systems problem in miniature. Name them before the interviewer does.

Cross-shard joins disappear

You cannot JOIN a users shard with an orders shard cheaply. Either denormalize (store a copy of the needed user fields with each order), accept scatter-gather queries, or rethink the shard key so related data is colocated.

Transactions get expensive

Single-shard transactions stay cheap (each shard is a normal database). A write touching two shards needs two-phase commit — slow and fragile — or a Saga: a sequence of local transactions with compensating actions if one fails. Design to avoid cross-shard writes.

Global aggregates fan out

"Count all users" or "top 100 products" must query every shard and merge results — a scatter-gather. Latency becomes the slowest shard's latency, and the merge logic lives in your application or proxy.

The router is new infrastructure

Something must map shard keys to shards: application code, a proxy layer (like Vitess or ProxySQL), or a dedicated routing service with a shard map. It needs its own caching, failover, and versioning — it is a system you now own.

Unique constraints go local

A UNIQUE constraint on email only works within one shard. Enforcing global uniqueness needs a separate coordination mechanism — a directory shard, a conditional write pattern, or accepting probabilistic enforcement.

Schema changes multiply

A migration must run on every shard, in order, with rollback planned per shard. Expand-and-contract migrations (from the replication lesson) still apply — now orchestrated N times, and a stuck shard blocks the fleet.

They compose, they don't compete: real systems shard and replicate. Each shard gets its own leader and followers: sharding splits the data and the writes, replication copies each slice for read scale and failure recovery. If an interviewer asks "replication or sharding?", the senior answer is usually "sharding for the writes, replication inside each shard for everything else."

06 / GROWTH

Resharding: growing without downtime

Adding shards to a live cluster is the operation every sharded system eventually faces. The strategies differ in how much data moves and how long the cluster limps.

Resharding is changing the shard mapping on a live system — adding shards, splitting hot ones, or rebalancing. The hard part is doing it while reads and writes keep flowing.

Keys and shards share a hash ring; each key belongs to the nearest shard clockwise. Adding a shard means it takes over only the key ranges immediately before it on the ring — roughly 1/N of the data moves, where N is the new shard count. Virtual nodes (each physical shard owning many small ring segments) smooth the distribution further, so one new shard takes small bites from many old ones instead of one big bite from a neighbor.

Trade-off: you give up ordered range queries, and the ring bookkeeping is real infrastructure. Dynamo-style systems (Cassandra, DynamoDB) live here.

With range sharding, split the busiest shard's key range in two and move half to a new shard. Only the split range's data moves, and range queries stay efficient. This is the go-to for time-ordered or naturally ranged data — but you must detect the hot range and orchestrate the split.

For changing the shard key itself or rebalancing wholesale: write every new change to both old and new shards, backfill historical data in the background, verify checksums, then flip reads to the new mapping and stop the old writes. Slow and storage-hungry, but it is the only approach that survives a wrong-key decision. This is the honest answer to "we chose the wrong shard key."

controller → shard A : start split of range [500k, 1M)
shard A    → shard B : copy snapshot of range
shard A    → shard B : stream new writes (dual phase)
controller → router  : publish new shard map (v42)
router     → clients : route [500k, 750k) to B
controller → shard A : drop moved range, reclaim space
🗺

The shard map is a versioned contract: routers cache "key → shard" mappings, so publish map versions (v41, v42) and have routers cut over atomically. During migration, dual-read (prefer new, fall back to old) and dual-write keep the system correct across the boundary. Never let half your fleet route on an old map while the other half uses the new one — mixed mappings write the same key to two owners.

07 / SENIOR DEPTH

What strong answers make explicit

Move beyond "split the database." Name the routing, the failure boundary, the query plan, and the day-two operations.

Shard-aware queries

Every query must answer "which shard?" before it runs. Queries carrying the shard key are single-shard and fast; queries without it are scatter-gather. Audit your query patterns against the key before committing to it.

Scatter-gather math

A fan-out query's latency is the maximum shard latency, not the average. One slow shard poisons every global query. Set per-shard timeouts, merge partial results explicitly, and say what "partial" means to the caller.

Failure domains

Shards in the same rack or availability zone can fail together. Place shard leaders across zones, replicate each shard across zones, and make sure a zone loss degrades to some shards missing — not the whole dataset.

Backups per shard

Each shard backs up independently, which means restore is per-shard too. A point-in-time restore of the whole cluster needs coordinated snapshots — decide what "consistent across shards" means for your recovery story.

Tenant isolation

Noisy tenants get dedicated shards; small tenants share. This is sharding as a business tool: blast radius, per-tenant SLOs, and the option to physically relocate a customer all fall out of shard boundaries.

Ordering and IDs

Auto-increment IDs stop working globally — two shards mint the same ID. Use UUIDs, Snowflake-style IDs (timestamp + shard ID + sequence), or a dedicated ID service. Each option trades size, sortability, and coordination cost.

Locality and compliance

Geo-sharding keeps EU data in the EU and puts Asian users' data near Asia. It also means shard placement is now a legal decision, and cross-region queries inherit wide-area latency.

Start with more shards than you need

Small shards are easier to split and move than huge ones, and empty headroom costs little. But do not shard prematurely — a dozen tiny shards add operational cost with no traffic to justify it. Right-size to your growth curve.

08 / QUESTION LAB

Explain the decision, not just the pattern

Try each prompt aloud. Then compare your answer with the model response.

Q1

Design the database layer for a global football fan platform: 50M fans, profiles, and a live match feed with huge write spikes during goals. Shard it.

I would split by access pattern, not by one key for everything.

  1. Shard fan profiles by hash(user_id): cardinality is huge, distribution is even, and nearly every profile request carries user_id, so queries stay single-shard.
  2. Shard match events by match_id with salting for the final: goal spikes concentrate on one match key, so I would suffix hot match keys (match:final:0…9) and aggregate reads. Alternatively, hash-shard the events stream and accept scatter-gather for per-match views.
  3. Each shard gets its own leader plus async read replicas (sharding for writes, replication for reads and failover). Range queries I cannot avoid — "recent matches" — go to a small directory or a time-bucketed index shard.
  4. Resharding plan: consistent hashing with virtual nodes, so adding shards moves ~1/N of the data; publish versioned shard maps and dual-write during migration.
  5. Guardrails: per-shard QPS and top-key dashboards, per-shard timeouts on scatter-gather, and no cross-shard transactions — match events are append-only, so eventual aggregation is acceptable.

The key trade-off: fan data shards cleanly by user, but live events are inherently hot around one key, so I salt the hot keys and absorb reads in cache rather than pretending hashing alone fixes popularity.

Q2

We sharded users by user_id ranges, but shard 4 (the newest range) is at 95% CPU while the others idle. Diagnose and fix.

This is the classic range-sharding write hotspot: new users get the highest IDs, so all new-user writes land on the newest shard. Diagnosis is quick: compare per-shard write QPS against per-shard row counts — rows look balanced, writes do not.

Short term, split shard 4's range in two and move half to a new shard. Medium term, switch the mapping to hash(user_id) % N (or consistent hashing) via a double-write migration: write both mappings, backfill, verify, cut reads over, retire the old mapping. Long term, accept that ordered-ID range sharding concentrates recency, and never range-shard a monotonically growing key again unless range queries justify it.

Q3

A teammate proposes sharding by country to "keep queries simple." When is that a good idea, and what breaks?

It is good when locality is the product requirement: data-residency laws, regional latency, or per-region operations. Country is then a composite key's prefix — (country, user_id) — so each country's data is further spreadable.

What breaks: cardinality is tiny (countries do not scale with users), distribution is lumpy (one country can hold half the users), and any feature that crosses countries — global leaderboards, cross-border follows, worldwide search — becomes scatter-gather across every shard. I would push back: use country as a placement policy for locality, but shard by a high-cardinality key inside each region.

Q4

You need globally unique order IDs across 16 shards. Give three options and pick one, with the trade-off stated.

Option 1: UUIDs — no coordination, but 128 bits, unsortable, and unfriendly to indexes (random inserts fragment index pages and bloat storage). Option 2: Snowflake-style IDs — 64 bits encoding timestamp, shard/worker ID, and a per-millisecond sequence; roughly sortable and compact, but requires unique worker-ID assignment and clock discipline. Option 3: a dedicated ID service (or a single auto-increment table) — perfectly sequential, but a new single point of contention and a network hop per ID.

I would pick Snowflake-style IDs: they give global uniqueness without coordination, stay compact and roughly time-ordered for range scans, and the shard ID embedded in the key is itself a debugging gift — you can read which shard owns a row from the ID. I would reject the central service at high write rates and accept UUIDs only if sortability and index density truly do not matter.

The 30-second summary

Sharding splits one database into many, each owning a slice of the data. The shard key decides everything: it must be high-cardinality, evenly distributed, and carried by your queries. Hashing spreads rows evenly; consistent hashing makes growth cheap; range keeps order but concentrates recency. Hot shards come from traffic, not row counts — cache, salt, or split them. And each shard still needs replication, because sharding splits the data, not the failure.

Five phrases worth keeping

  • “The shard key is a one-way door.”
  • “Replication scales reads; sharding scales writes.”
  • “Measure heat in requests, not rows.”
  • “Scatter-gather latency is the max, not the average.”
  • “A shard without replicas is a single point of failure.”
