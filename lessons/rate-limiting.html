Lesson 11 · Core Building Blocks

Rate Limiting

Every public API has a bouncer — something that decides how many requests a client may make before being told to wait. Without one, a single greedy script can drown your backend, one tenant can starve the rest, and a brute-force attack gets unlimited guesses. This lesson covers the five limiting algorithms (with the math), where to enforce limits, how to do it across many servers, and how to design a rate limiter in an interview.

01

What is rate limiting?

A rate limiter is a bouncer for your API: it caps how many requests one client may make inside a time window, and rejects the extras — usually with HTTP status 429 Too Many Requests. "100 requests per minute per API key" is a rate limit. Request #101 inside that minute doesn't get served; it gets a polite rejection telling the client when to come back.

Rate limiting

Capping the number of requests a single client may make within a fixed time window, and rejecting (not queueing) anything beyond the cap. The rejected request fails fast with a 429 so the client — not your backend — absorbs the wait.

Why it matters — four reasons, each a real outage class

  1. Protect the backend from overload. A runaway script, a misconfigured retry loop, or a viral moment can send 50× normal traffic. Without a limiter, your database falls over and everyone's requests fail. With one, only the offender gets 429s.
  2. Fairness across tenants. In a multi-tenant system (many customers sharing your servers), one greedy tenant's bulk export shouldn't starve the other 999. Per-tenant limits turn "noisy neighbor" from an outage into a policy.
  3. Cost control on metered APIs. Every request costs you compute, bandwidth, or a per-call fee to an upstream provider. A limit is a ceiling on your bill — and the basis of your pricing tiers.
  4. Defense against abuse. Login endpoints, password resets, and signup forms are brute-force and scraping targets. Capping guesses per minute per IP turns a 10-million-guess attack into a 60-guess-per-hour trickle.

Rate limiting vs throttling vs debouncing — the three cousins

Throttling

Slowing requests down instead of rejecting them. The request still gets served — it just waits its turn in a queue. If rate limiting is a bouncer who turns you away, throttling is a velvet rope that makes you wait in line. People often use the two words interchangeably; in an interview, state your meaning: "by throttling I mean delaying excess requests; by rate limiting I mean rejecting them."

Debouncing

A client-side pattern: wait until the user stops doing something, then fire one request. Search-as-you-type waits ~300 ms after the last keystroke before calling the API, so typing "haaland" sends 1 request instead of 7. Debouncing merges requests; rate limiting caps them. Different problem, different layer.

The one-liner to keep: rate limiting rejects, throttling delays, debouncing merges. This lesson is about the first one — the bouncer, not the queue.

The running example: the derby turnstiles

Every algorithm in this lesson lands on the same stadium. Keep it in your head: one derby, one gate, and a crowd that arrives in bursts.

The running example: derby day at the gate

60,000 fans, one stand, turnstiles with rules

It's the derby and 60,000 fans are pouring toward the North Stand. The concourse inside can safely hold only so many people at once — if everyone rushes in together, the crush is dangerous. So the stewards run the turnstiles with a rule: at most N fans per minute through each gate. Every idea in this lesson is a different way of enforcing that sentence.

The ticket bucket at the main gate makes it concrete: the steward holds a bucket of entry tickets. A runner tops the bucket up with fresh tickets at a steady pace. A fan gets in only by taking a ticket — no ticket, no entry; empty bucket, everybody waits. That bucket is the token bucket algorithm, and you'll meet it in section 6.

Mapping for the whole lesson: a fan is a request, a turnstile is the limiter, the concourse is your backend, and the per-minute rule is the limit. Keep the bucket image handy — you'll keep coming back to it.

03

Algorithm 1: fixed window counter

The simplest possible limiter: a counter and a clock. Count requests in the current minute; when the minute flips, throw the counter away and start over.

How it works

Divide time into fixed windows — say, one minute each: 11:59:00–11:59:59, 12:00:00–12:00:59, and so on. Keep one counter per client per window. On each request: if the counter for the current window is below the limit, increment and allow; otherwise reject. When the clock crosses into a new window, the counter resets to zero.

window = floor(now / 60 seconds)        // which minute is it?
count = counters[client][window] or 0
if count < LIMIT:
    counters[client][window] = count + 1
    allow
else:
    reject (429)

Stadium version: the steward's clicker resets to zero every time the big clock ticks to a new minute. "100 fans per minute" means the clicker may reach 100 before the reset.

The boundary-burst flaw — do the math

Here's where the junior answer stops and the senior answer starts. Watch what happens at the boundary between two windows. Limit: 100 requests per minute.

  • At 11:59:59.5 the client fires 100 requests — all counted in the 11:59 window. Clicker hits 100. All allowed.
  • At 12:00:00.2 the client fires 100 more requests — the window flipped, the counter reset, so all 100 are allowed again.

The limiter did exactly what it was told, and the result is absurd: 200 requests landed within about 700 milliseconds against a rule that was supposed to mean "100 per minute." The client gets 2N requests through in an arbitrarily short interval around any window boundary — up to twice the configured limit.

The boundary-burst rule to quote: a fixed window counter guarantees at most N requests per window, but only 2N requests per any sliding 60-second interval. If your backend can only survive N per minute, fixed window alone doesn't protect it — the burst fits inside a sub-second gap the limiter never sees. Stadium version: 100 fans slip through at 11:59:59 and 100 more at 12:00:01 — the concourse gets 200 fans in two seconds, and the clicker says everything was legal.

Why does anyone use it then? One counter per client per window is tiny state, the math is trivial, and the reset is automatic. It's fine when 2N briefly is harmless — generous internal limits, or per-user limits where the limit is set with headroom. When 2N would hurt, you need one of the sliding algorithms next.

04

Algorithm 2: sliding window log

The exact answer: remember the timestamp of every request, and on each new request count only the ones inside the trailing window. No boundary can be gamed, because there are no boundaries — just the last 60 seconds, wherever they fall.

How it works

Keep a list of timestamps per client. On each request: drop every timestamp older than now − window; count what's left; if the count is below the limit, append now and allow, else reject.

log = timestamps[client]                      // sorted list
log = [t for t in log if t > now - 60s]      // drop the expired
if len(log) < LIMIT:
    log.append(now)
    allow
else:
    reject (429)

Replay the boundary trick against this: the client fires 100 requests at 11:59:59.5 — all logged. At 12:00:00.2 it fires 100 more. The limiter drops nothing (all 200 timestamps are within the trailing 60 seconds), counts 200 ≥ 100, and rejects every request in the second batch. The 2N burst is impossible. The guarantee is now the honest one: at most N requests in any 60-second interval.

Stadium version: instead of a clicker that resets, the steward writes down the entry time of every single fan and, before letting the next one in, counts how many entries in the book are less than a minute old. No minute-boundary exists to game.

The price: memory — quantify it

Exactness costs one stored timestamp per request. A timestamp is 8 bytes as a 64-bit integer. Now scale it: one hot API key doing 1,000,000 requests per second with a 60-second window keeps 60 million timestamps — that's 60M × 8 bytes = 480 MB for one key, just for the raw timestamps.

And that's the fantasy number. In Redis you'd implement this as a sorted set (more in section 9), where each entry carries a score, a member string, and pointers — realistically 90+ bytes per entry. That same key would eat several gigabytes of Redis memory. For a thousand hot keys, you're buying a Redis fleet to store timestamps.

The senior line

"Sliding window log is O(n) memory per key — exact, and I only pay for it where exactness is worth it." Use it for low-volume, high-stakes limits: login attempts (5 per minute per account — the log holds at most a handful of timestamps), password resets, signup. Never for per-key limits on a hot API path. When the interviewer asks "what breaks at scale," this paragraph is the answer.

05

Algorithm 3: sliding window counter

The compromise the industry actually ships: fixed-window counters (tiny memory), but weighted so the previous window's count fades out smoothly instead of vanishing at the boundary. This is the algorithm Cloudflare documents for its own rate limiting.

Sliding window counter (approximate)

Keep the last two fixed-window counters — the previous window and the current one. Estimate the trailing-window count as previous × overlap + current, where overlap is the fraction of the previous window that still falls inside the trailing 60 seconds. Memory: two integers per client. No per-request storage.

Deriving the formula

Let the window length be T (60 s) and let t be how many seconds into the current window we are. The trailing 60-second interval reaches back into the previous window by T − t seconds — that's the overlap. The overlap fraction is:

overlap = (T − t) / T
estimate = prev_count × overlap + cur_count

The intuition: we don't know when inside the previous window its requests arrived, so we assume they were spread evenly and count only the fraction that still overlaps our trailing window. Even spread is an approximation — hence the name — but it's a cheap and good one.

Worked example — and the boundary trick, defeated

Limit: 100/min, T = 60 s. Previous window (11:59): 100 requests. Now it's 11:59:30 — 30 seconds into the current window — and the current window has 40 requests so far. overlap = (60 − 30)/60 = 0.5. Estimate = 100 × 0.5 + 40 = 90 < 100 → allow.

Now the attack: the client did the 2N trick — 100 requests at 11:59:59.5, 100 more at 12:00:00.2. It's now 12:00:01, one second into the new window: prev = 100, cur = 100, overlap = 59/60 ≈ 0.983. Estimate = 100 × 0.983 + 100 = 198.3 > 100 → reject. The fixed-window flaw is gone, at the cost of two integers per client.

Stadium version: the steward keeps two clickers — last minute's and this minute's — and estimates the crowd in the last 60 seconds as "half of last minute's count (we're halfway through this minute) plus this minute's count so far." Good enough to keep the concourse safe, no notebook of timestamps needed.

The error bound — the trap question, answered

"Prove the estimate can never exceed the true count by more than one window." Here's the proof sketch to give in the room. The estimate's only fiction is the previous window: it assumes those requests were spread evenly, counting prev × overlap. The true trailing count includes only the previous-window requests that actually fall in the overlap — call that actual. The overestimate is prev × overlap − actual, which is biggest when actual = 0 (all of the previous window's requests landed in its first, non-overlapping part). Then the error is prev × overlap — at most the previous window's full count: one window's worth.

So the estimate errs conservative: it can reject a request that was technically fine (it counted phantom requests), but it never lets through much more than the limit. For a limiter, conservative is the safe direction — you'd rather 429 an innocent request occasionally than let a burst through.

Algorithm 4: token bucket

The ticket bucket from the gate, formalized: a bucket that holds tokens, refills at a steady rate, and spends one token per request. It is the only algorithm here that wants bursts — up to the bucket's size.

Token bucket

Each client has a bucket holding at most C tokens (capacity). Tokens are added at a steady refill rate R per second. Each request spends one token; if the bucket is empty, the request is rejected. Refilling is capped — a full bucket doesn't overflow.

The two numbers and what each controls

  • Capacity C — the burst allowance. A full bucket lets C requests through instantly, back to back, with zero spacing. That's the ticket bucket with C tickets in it.
  • Refill rate R — the sustained rate. Over the long run, the client can make at most R requests per second, because that's all the tokens that ever arrive.

Stadium version, precisely: the steward's bucket holds 10 tickets (C = 10); the runner adds 1 ticket per second (R = 1/s). Ten fans sprint through together — then the eleventh waits, and after that one fan per second, because that's the ticket supply.

Worked example — steady state vs burst

C = 10, R = 1 token/sec. The bucket starts full.

  • t = 0: the client fires 10 requests at once — all allowed, bucket now empty. This is the designed burst: 10× the sustained rate, perfectly legal.
  • t = 0: an 11th request arrives — rejected (429). No token, no entry.
  • t = 3 s: 3 tokens have refilled. The client fires 5 requests — 3 allowed, 2 rejected.
  • Steady state: a client firing exactly 1 request/sec never sees a rejection — each request consumes the token that just arrived. A client firing 2/sec drains the bucket and then gets every other request rejected.

Refill math, since interviewers love it: refilling an empty bucket of capacity C at rate R takes C / R seconds (10 tokens ÷ 1/s = 10 s). And the long-run average can never exceed R — tokens are created at R per second, and a request needs a token, so the arrival rate of served requests is bounded by R no matter what.

// lazy refill: no background timer needed
tokens = min(C, tokens + R × (now − last_refill_time))
last_refill_time = now
if tokens >= 1:
    tokens −= 1; allow
else:
    reject (429)

The lazy refill is the implementation detail worth naming: you don't run a timer adding tokens every millisecond. You just record when you last looked, and compute how many tokens would have arrived since. Same result, zero background work — this is how the lab below is built.

Why token bucket is the default for public APIs: real clients are bursty — a page load fires 12 API calls at once, then nothing for a minute. Token bucket forgives the burst (up to C) while capping the sustained rate (R). Fixed windows punish the page load; token bucket was built for it. AWS API Gateway's throttling and Stripe's rate limits are token-bucket-shaped for exactly this reason.

07

Algorithm 5: leaky bucket

The mirror image of the token bucket: requests pour into a bucket, and the bucket leaks at a constant rate. Bursts get absorbed; what comes out the bottom is a perfectly smooth stream.

Leaky bucket

A queue with a constant drip: incoming requests join the bucket; one request leaves (is processed) every 1/R seconds. If the bucket is full when a request arrives, that request is rejected. The output rate is constant R no matter how bursty the input.

How it works, concretely

Bucket size 10, leak rate 1 request/sec. Ten requests arrive at once — they fill the bucket and are released one per second over the next 10 seconds. The downstream service sees a metronome: tick, tick, tick — never a burst. An 11th request arriving while the bucket is full is rejected.

if bucket_size < CAPACITY:
    bucket.enqueue(request)     // will be processed at the steady drip
    allow (accepted for processing)
else:
    reject (429)                // bucket full — no room

Stadium version: a narrow corridor after the turnstiles that physically fits one fan every two seconds. A surge of fans piles up in the corridor (the bucket); the concourse beyond sees exactly one fan every two seconds. If the corridor fills wall to wall, the steward stops admitting — that's the rejection.

Token bucket vs leaky bucket — the comparison

Token bucketLeaky bucket
BurstsAllowed by design — up to C requests instantlyAbsorbed — the output is always a smooth R/sec
What it protectsThe average load on the backend (bursts are tolerated)The instantaneous load (downstream never sees a spike)
MemoryTwo numbers per client: token count + last-refill timeA queue of waiting requests per client (bounded by capacity)

The sentence that settles "which one?"

"Token bucket controls the average and forgives bursts; leaky bucket controls the instantaneous rate and smooths everything." If the interviewer asks which you'd pick for a public API, the usual answer is token bucket — real clients burst. If they then say "but the downstream is a single-threaded legacy billing system," you switch to leaky bucket and explain why the requirement changed the answer. That's the senior move: the requirement picks the algorithm, not habit.

08

Where to enforce it

A limiter is a layer, not a library call. Put it as close to the client as you can afford — every layer the abusive request penetrates is work your systems did for nothing.

The enforcement ladder, outside in

  1. CDN / edge — Cloudflare, Akamai, Fastly. The request dies in a data center near the attacker, before it ever touches your infrastructure. Best place for volumetric abuse and DDoS-shaped traffic. This is where the coarse IP-level limits live.
  2. Reverse proxy / load balancer — nginx limit_req, Envoy's rate limit filter. You already terminate traffic here; adding the limit costs almost nothing and protects every service behind the proxy at once.
  3. API gateway — Kong, AWS API Gateway, Apigee. The gateway already knows the tenant, the plan tier, and the API key — so this is where tiered, per-key limits naturally live ("free tier: 100/min, pro: 10,000/min").
  4. In-service middleware — a rate-limit middleware in your app framework (Express, Django, Spring). The last line of defense, and the only place that can do resource-level limits: the login endpoint gets 5/min per account even though the API overall allows 1,000/min.

Stadium version: edge is the police cordon streets away (stops the mob before it reaches the ground); the proxy is the outer gate; the gateway is the ticket check that knows your seat tier; in-service is the steward at the specific vomitory door. A real stadium uses all four — so does a real API. And note the cost logic from the queues lesson: rejecting early is cheaper — a request killed at the edge never consumed your app servers, your database, or your on-call's sleep.

The 429 contract — what a good rejection looks like

When the limiter rejects, it must say three things: what the limit is, how much is left, and when to retry. The standard headers:

HeaderMeaningExample
X-RateLimit-LimitThe cap for this window100
X-RateLimit-RemainingRequests left before the cap0
X-RateLimit-ResetWhen the window resets (unix timestamp, or seconds until reset — document which)1696598460
Retry-AfterHow many seconds the client should wait before retrying (or an HTTP date)23

Send the X-RateLimit-* headers on every response, not just rejections — a well-behaved client watches Remaining hit single digits and slows down before it ever sees a 429. And the 429 body itself should be machine-readable JSON in your API's normal envelope, not an HTML error page:

HTTP/1.1 429 Too Many Requests
Retry-After: 23
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1696598460

{
  "error": "rate_limit_exceeded",
  "message": "You have made 100 requests in the last 60 seconds. Slow down and retry.",
  "retry_after_seconds": 23,
  "limit": 100,
  "window_seconds": 60,
  "docs": "https://api.example.com/docs/rate-limits"
}

Two 429 details interviewers check: one, Retry-After must be honored by your own SDKs and retry logic — a client that retries instantly on 429 turns one rejection into a retry storm (section 11's thundering herd). Two, never return 429 from an endpoint the client needs in order to learn the limit — the docs link and the headers on successful responses are how clients stay under the cap in the first place.

Distributed rate limiting

One server's counter is a toy. Production has eight app servers behind a load balancer, and a client whose requests land on a different server each time. This is where the senior depth lives.

The N× over-admit problem

Give each of 8 servers its own fixed-window counter with a limit of 100/min per API key. A client sprays requests evenly across all 8. Each server sees ~1/8 of the traffic and each happily allows its own 100/min. Global total: 800/min against a 100/min policy — 8× over-admission. In general, per-server counters over-admit by up to N×, where N is the server count. Stadium version: twelve gates, each steward with his own "100 per minute" clicker — the stand admits 1,200 per minute while the safety certificate says 100.

The fix is a shared counter every server checks: in practice, Redis — fast enough (sub-millisecond), with data structures that fit each algorithm.

The Redis approach, in three steps of sophistication

Step 1: INCR + EXPIRE — and the race

The naive pattern: INCR rl:{key}:{minute} to bump the counter, then EXPIRE key 60 so it resets. Two separate commands — and two commands are not atomic. If the app server crashes (or the connection drops) between the INCR and the EXPIRE, the key is left with no TTL — it never expires. The counter keeps its value forever, every future request sees count ≥ limit, and that client is 429'd permanently until someone manually deletes the key. One crash, one immortal key, one locked-out customer.

Step 2: the atomic Lua script

Redis executes a Lua script atomically — it's single-threaded, so no other command can interleave mid-script. Bundle the check-and-expire into one script:

-- KEYS[1] = the counter key, ARGV[1] = window seconds, ARGV[2] = limit
local current = redis.call('INCR', KEYS[1])
if current == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[1])
end
if current > tonumber(ARGV[2]) then
  return 0   -- rejected
else
  return 1   -- allowed
end

The crash window is gone: INCR and the conditional EXPIRE happen as one indivisible step. (Modern Redis also offers SET key 0 EX 60 NX before INCR, but the Lua pattern is the one interviewers expect you to write.) For the token bucket in Redis, name-drop redis-cell's CL.THROTTLE — a Redis module that implements the whole token bucket as a single command.

Step 3: sorted-set sliding window log

For the exact algorithm at modest volume, Redis sorted sets are the natural fit — score = timestamp, member = unique request ID:

ZREMRANGEBYSCORE key 0 (now - window)   -- drop expired timestamps
ZADD key now unique_request_id            -- log this request
ZCARD key                                 -- count survivors
EXPIRE key window                         -- don't leak keys for idle clients

Run it as a Lua script (or a pipeline) so the four commands are atomic. Note the member must be unique per request (a UUID or timestamp:counter) — the score alone can't be the member because two requests in the same millisecond would collapse into one entry.

The hot-key problem

Hot key

A single Redis key that receives a disproportionate share of all operations — e.g. the rate-limit counter for your biggest tenant's API key. Redis is single-threaded per instance: every request for that tenant queues on the same key, and the key becomes a throughput bottleneck (and in Redis Cluster, it pins to one slot on one node).

Mitigations, cheapest first:

  • Shard the key: split one counter into K sub-keys (rl:{key}:0 … rl:{key}:k-1); each request picks a random sub-key and the effective limit is K × sub-limit. Precision loosens (a sub-key can fill while others are empty), but the hot key is gone.
  • Local buckets + reconciliation: each app server keeps an in-memory token bucket (no Redis round trip) and periodically gossips its usage to peers, or a background job reconciles. Fuzzy limits — over-admission bounded by the gossip interval — but zero coordination per request.
  • Accept approximate: for most abuse-prevention limits, ±10% accuracy is fine. Say so out loud — precision is a cost, and naming what you'd trade it for is the senior move.

Centralized vs decentralized

Centralized (Redis)Decentralized (local buckets + gossip)
AccuracyExact (single shared counter)Approximate — over-admits between reconciliations
Per-request costA Redis round trip (~0.5 ms) on the critical pathZero — pure in-memory check
Failure modeRedis down = limiter down (see fail-open vs fail-closed, section 11)No single point of failure
Scales toRedis throughput; hot keys need shardingLinearly — each server is independent
Use whenBilling-adjacent limits, abuse prevention — where exactness mattersHigh-volume edge protection — where speed matters more than precision

Clock-skew caveat

Sliding-window algorithms compare timestamps from different app servers. If server A's clock is 2 seconds ahead of server B's (NTP drift is real, typically milliseconds but occasionally seconds after a leap second or a VM pause), their window edges disagree and counts shift. The fix: take now from Redis itself (TIME command) inside the Lua script instead of trusting the app server's clock — one clock, no skew. For short windows, just budget the skew into the limit and say so.

Identifying the client

A limiter is only as good as its key. Limit by the wrong identifier and you either punish innocents or let the abuser walk around the limit.

Limit byWhat it isStrengthWeakness
API keyThe credential on the requestIdentifies the actual customer; survives IP changesOnly works for authenticated APIs
User / account IDThe logged-in user behind the keyStops one user burning a shared org key's budget unfairlyRequires auth; a user with 5 keys still has 5 budgets unless you aggregate
IP addressThe source IP of the TCP connectionThe only option for unauthenticated endpoints (login, signup)NAT/CGNAT: a university, an office, or a mobile carrier puts thousands of humans behind one public IP — one abuser's limit punishes them all
Resource + tenantPer-endpoint or per-resource limits ("login: 5/min/account", "exports: 2/hour/tenant")Protects the expensive operations specifically, instead of one blunt global capMore keys to manage; needs the gateway to know the resource
NAT / CGNAT (Carrier-Grade NAT)

Network address translation: many devices share one public IP address. Your phone's mobile carrier routes thousands of subscribers through a handful of IPs. So "limit by IP" can mean "limit a whole neighborhood by one shared budget" — the reason IP limits must be generous, and why authenticated identifiers are preferred wherever they exist.

Tiered limits — the VIP gate vs general admission

Free tier: 100 requests/min. Pro tier: 10,000/min. Enterprise: custom. The gateway reads the plan from the auth token's claims (or a plan lookup) and selects the bucket — the stadium's VIP gate with its own, wider turnstile next to general admission. Two details that matter:

  • Enforce the tier at the gateway, where the key and plan are already known — not deep in each service.
  • Header-based limits on shared gateways: behind a CDN or shared ingress, the app server sees the edge's IP, not the client's. The edge must forward the real identifier in a header (X-Forwarded-For, X-Api-Key) — and the app must only trust that header from its own edge, never from the open internet, or any client can spoof their identifier and dodge the limit.

The layering rule

Use all three granularities at once: a generous IP-level limit at the edge (catches dumb floods), a per-key/per-tier limit at the gateway (the business policy), and tight per-resource limits in-service (login 5/min, exports 2/hour). An attacker who rotates IPs still hits the key limit; a legitimate power user never feels the IP limit. Defense in depth, each layer with its own key.

11

Design a rate limiter

The classic interview question, answered as a five-step walk-through. Each step has the numbers — interviewers promote candidates who quantify.

Step 1 — Requirements

  • Functional: per-API-key limits (100/min free, 10k/min pro), per-IP coarse limits at the edge, per-resource tight limits (login 5/min). Reject with 429 + Retry-After + X-RateLimit-* headers. Clients must see remaining quota on every response.
  • Non-functional: the limit check adds < 1 ms at p99 (it's on every request's critical path); the limiter must not become a single point of failure; ±5% accuracy is acceptable (abuse prevention, not billing).
  • Out of scope: billing metering, per-endpoint analytics — say so, don't build them.

Step 2 — Capacity estimation (do the arithmetic out loud)

Assume 50M requests/day ≈ 580 requests/sec average, with a 5× peak → ~3,000 QPS peak. Each check is one Redis Lua script (INCR + conditional EXPIRE): ~0.3 ms. One Redis node handles ~100k ops/sec — so a single Redis primary absorbs the peak 30× over, with a replica for failover. State per key: one counter + TTL ≈ 200 bytes; 1M active keys → ~200 MB — fits in RAM comfortably. The math says: this is a small Redis, not a distributed systems moonshot. Say that; it shows judgment.

Step 3 — API design

// middleware on the gateway — every request passes through it
key = "rl:" + api_key + ":" + current_minute
allowed = redis.eval(FIXED_WINDOW_LUA, key, window=60, limit=tier_limit(api_key))
if not allowed:
    return 429, headers(Retry-After, X-RateLimit-*)
else:
    serve request, with X-RateLimit-Remaining on the way out

The tier lookup (tier_limit) comes from the auth token's plan claim — cached, not a database call per request.

Step 4 — Data model

Key format rl:{api_key}:{window_start_minute} → integer counter, TTL = window length. One key per client per minute: old windows expire automatically, so there's nothing to clean up. For the login endpoint, the same pattern with key rl:login:{account_id}:{window} and limit 5 — resource-level limiting is just a different key.

Step 5 — Deep dives: the traps, landed before they're asked

Senior-depth traps — land these unprompted

"Your limiter is a single point of failure." "Redis runs as primary + replica with Sentinel failover. And if Redis is unreachable, the limiter fails open — allows the request and fires an alert — because a down limiter must not take down the API. The exception: security-critical endpoints (login brute-force protection) fail closed, because an open gate there is worse than an outage."

"Prove the sliding-window counter can't over-admit by more than a window." "The only fiction is the previous window's distribution. The overestimate is prev × overlap − actual_overlap_count, maximized when the previous window's requests all landed outside the overlap — so the error is bounded by one full window's count. It errs conservative: occasional false 429, never a burst through."

"Every client retries the instant Retry-After expires — a thundering herd." "A thundering herd is N clients waking at the same millisecond and re-hitting the limit together. Fix it on both sides: the server jitters Retry-After per client (23 s, 27 s, 31 s…), and our own SDKs retry with exponential backoff + jitter — wait 1 s, then 2 s, then 4 s, each plus a random fraction — so retries spread instead of synchronizing."

"One tenant's runaway script eats the whole org's budget." "Hierarchical limits: per-user and per-tenant. The runaway user gets 429'd individually while the rest of the tenant is untouched. One blunt org-level cap is the junior design."

Fail open · Fail closed

Fail open: when the limiter itself breaks, allow the request — availability wins, abuse risk rises, and an alert fires. Fail closed: when the limiter breaks, reject the request — protection wins, the API is down for everyone. Default to open; close only where abuse is worse than downtime.

Thundering herd

Many clients retrying at the same instant — e.g. all waking when an identical Retry-After expires — so the second wave hits as one synchronized spike. The cure is jitter: a small random spread added to every wait, so the wake-ups scatter.

Q&A — with full model answers

Four questions, the way an interviewer would ask them. Read the context first — it tells you what they're really testing.

Q1 · ARCHITECTURE
"Design a rate limiter for our public API. 3,000 requests per second at peak, per-API-key limits, and it can't add noticeable latency."
The full walk-through question. They want requirements → numbers → API → data model → deep dives, in that order, without rambling.
Reveal model answer
Verdict

"Gateway middleware backed by Redis, one atomic Lua script per request, tiered per-key limits, fail-open on Redis failure. The numbers say a single Redis primary handles the peak 30× over."

Reasoning

"Requirements first: per-key limits (100/min free, 10k/min pro, from the auth token's plan claim), a coarse per-IP limit at the edge for dumb floods, and tight per-resource limits in-service — login gets 5/min per account regardless of tier. Every response carries X-RateLimit-Limit/Remaining/Reset; rejections are 429 with Retry-After and a JSON body. Non-functionally: the check must add under a millisecond at p99, and ±5% accuracy is fine — this is abuse prevention, not billing.

Capacity: 3,000 QPS peak, one Redis Lua script per request at ~0.3 ms — a single Redis node does ~100k ops/sec, so one primary plus a replica for failover is plenty. State is one counter + TTL per key per minute, ~200 bytes; a million active keys is ~200 MB. This is a small Redis, not a distributed systems moonshot.

API: gateway middleware computes rl:{api_key}:{current_minute}, runs the fixed-window Lua script (INCR + conditional EXPIRE, atomically — no crash-between-commands race), and either serves with the remaining-quota headers or returns 429. Old windows expire on their own; nothing to clean up. I'd start with fixed window for simplicity and note the 2N boundary behavior, upgrading hot keys to the sliding-window counter (prev × overlap + cur) where the boundary burst would actually hurt.

Deep dives, unprompted: Redis is primary + replica with Sentinel so the limiter isn't a single point of failure — and if Redis is unreachable the limiter fails open with an alert, because a down limiter must not down the API; the login endpoint alone fails closed. Retry-After is jittered per client and our SDKs use backoff + jitter, so 429s don't synchronize into a thundering herd. And the hottest tenant keys get sharded into sub-keys if a hot key ever shows up."

What earns top marks

The arithmetic said out loud (3k QPS vs 100k ops/sec), the Lua atomicity named as the fix for the INCR/EXPIRE race, and fail-open vs fail-closed stated as a decision with a reason — not a default you stumbled into.

Q2 · DIAGNOSIS
"Our limiter is configured for 100 requests per minute, but the metrics show a client doing 200 requests within a single second and getting zero rejections. Explain."
The boundary-burst flaw. They want the mechanism, the 2N math, and the fix — not just "use a better algorithm."
Reveal model answer
Verdict

"Fixed-window boundary burst. The client put 100 requests at the tail of one window and 100 at the head of the next — each window's counter stayed legal while 200 requests landed ~a second apart. The fix is a sliding window counter."

Reasoning

"The mechanism: a fixed window counter guarantees at most N requests per window, but the promise you actually wanted was at most N per any 60-second interval. Those are different promises, and the gap is exactly 2N at the boundary: 100 requests at 11:59:59.5 count against the 11:59 window, 100 more at 12:00:00.2 count against the 12:00 window after the reset. Both counters read ≤ 100. Nothing malfunctioned — the algorithm's guarantee is just weaker than it looks.

The fix I'd ship is the sliding window counter: keep the previous and current window counts and estimate the trailing window as prev × overlap + cur, where overlap = (60 − seconds_into_current_window)/60. Replaying the attack at 12:00:01: prev = 100, cur = 100, overlap ≈ 0.983, estimate ≈ 198 > 100 — rejected. Two integers of state per client, no per-request storage, and the estimate errs conservative: it can only over-count by at most one window's worth, so it may 429 an innocent request but never lets a burst through."

What earns top marks

Stating the two different guarantees ("per window" vs "per any interval") before naming the fix, and quantifying the error bound of the replacement instead of just asserting it's better.

Q3 · DISTRIBUTED
"We run eight API servers sharing one Redis for rate limiting, using INCR followed by EXPIRE. Two problems have bitten us. Name them and fix both."
They're testing the atomicity race and the hot key — the two classic Redis limiter failures. "Two problems" is a hint to structure the answer in two beats.
Reveal model answer
Verdict

"One: the INCR/EXPIRE race — a crash between the two commands leaves an immortal key that 429s the client forever. Two: the hot key — your biggest tenant's counter serializes on Redis's single thread. Fix one with a Lua script, the other with key sharding."

Reasoning

"Problem one is atomicity. INCR and EXPIRE are two commands; if the app server crashes or the connection drops between them, the key keeps its count but never gets a TTL. The counter never resets, every future request reads count ≥ limit, and that client is rejected permanently until someone deletes the key by hand. The fix is a Lua script — Redis executes scripts atomically, single-threaded, so the INCR and the conditional EXPIRE become one indivisible step. No interleaving, no immortal key.

Problem two is the hot key. Eight servers each doing a Lua script per request against one key for your biggest tenant means every request for that tenant queues on the same key on the same Redis node. The fix is sharding: split the counter into K sub-keys, have each request pick one at random, and treat the limit as K × sub-limit. You trade a little precision — one sub-key can fill while others have room — for the removal of the bottleneck. If even that's not enough, the escape hatch is local in-memory buckets per server with periodic gossip: zero coordination per request, fuzzy limits, no hot key at all."

What earns top marks

Describing the user-visible consequence of the race (permanent 429s, not just "a race condition"), and naming precision as the explicit price of sharding — "I'd accept ±10% here because this is abuse prevention, not billing."

Q4 · JUDGMENT
"Redis goes down at 2 AM. Your rate limiter can't reach it. Do you fail open or fail closed — and does your answer change for the login endpoint?"
A judgment question with a deliberate twist at the end. They want a default, a reason, and the exception — stated as policy, not waffling.
Reveal model answer
Verdict

"Fail open everywhere, with an alert — except the login and auth endpoints, which fail closed. The default protects availability; the exception protects against the attack the limiter exists to stop."

Reasoning

"Fail open means: limiter broken → allow the request. The reasoning is blast radius. If the rate limiter fails closed, then a Redis outage — which has nothing to do with my API's actual health — becomes a full API outage for every customer. The limiter is a protective layer; a protective layer must never be more dangerous than what it protects against. So the default is open, plus a paging alert, plus a fallback to local in-memory buckets so there's still some coarse protection while Redis is down.

The login endpoint flips the calculus. Its rate limit exists to stop brute-force password guessing — and fail-open there means an attacker gets unlimited guesses exactly when our defenses are down, which is precisely when they'd attack. A locked-out login page during a Redis outage is bad; an unguarded login page is worse. So: security-critical endpoints fail closed, everything else fails open. I'd want that split written down as policy before the 2 AM page, not decided during it."

What earns top marks

The blast-radius framing ("a protective layer must never be more dangerous than what it protects"), the alert + local-bucket fallback showing the open failure isn't just "allow everything and hope," and treating the login exception as pre-written policy rather than an on-the-spot improvisation.

Practice drills

Untimed — think like you're whiteboarding. Write your answer, then check the rubric.

Drill 1 — The boundary, with numbers

A fixed-window limiter allows 200 requests/minute. A client sends 200 requests between 11:59:58 and 11:59:59, then 200 more between 12:00:00 and 12:00:01. (a) How many requests land inside the 3-second span 11:59:59–12:00:01, and what multiple of the intended rate is that? (b) At 12:00:01, what does the sliding-window-counter estimate read (prev = 200, cur = 200), and is the next request allowed?

Reveal rubric
  • (a) 400 requests in ~3 seconds — 2× the configured rate. Full marks for naming it the 2N boundary burst and stating the two guarantees: ≤ N per window vs ≤ N per any 60-second interval.
  • (b) overlap = (60 − 1)/60 ≈ 0.983; estimate = 200 × 0.983 + 200 ≈ 396.7 > 200 → rejected. Full marks for the arithmetic, not just "it rejects."
  • Half marks for "switch to sliding window" with no numbers; zero for "the limiter is broken" — nothing malfunctioned, the guarantee was just weaker than assumed.

What earns top marks: the explicit contrast — fixed window saw two legal windows (200 ≤ 200, 200 ≤ 200) while the trailing 60 seconds held 400 — then the estimate math showing the sliding counter sees the 400.

Drill 2 — Token bucket arithmetic

Token bucket, capacity C = 20, refill R = 2/sec, bucket starts full. (a) The client fires 30 requests instantly: how many allowed, how many rejected, tokens left? (b) The client then waits 5 seconds and fires 30 more: allowed / rejected / tokens left? (c) What is the maximum sustained rate the client can hold forever without rejections?

Reveal rubric
  • (a) 20 allowed, 10 rejected, 0 tokens left. The burst allowance is exactly C — no more.
  • (b) 5 seconds × 2/sec = 10 tokens refilled → 10 allowed, 20 rejected, 0 tokens left. Full marks for showing the refill computation min(20, 0 + 2×5).
  • (c) 2 requests/sec — the sustained rate can never exceed R, because tokens are created at R/sec and each request spends one. Full marks for the one-sentence proof, not just the number.
  • Deduction for answering (c) with anything involving C — capacity controls burst size, never the long-run rate.

What earns top marks: clean separation of the two knobs in every answer — "C answered (a), R answered (b) and (c)" — stated explicitly.

Drill 3 — Eight servers, one limit

Eight app servers sit behind a load balancer. A tenant's API key has a global limit of 1,000 requests/min. Each server runs its own fixed-window counter at 1,000/min. (a) Worst case, how many requests per minute can the tenant actually make? (b) Redesign with Redis: give the key format, the atomicity fix, and one scaling risk of your design with its mitigation.

Reveal rubric
  • (a) 8,000/min — 8× over-admission. Each server sees ~1/8 of traffic and allows its own 1,000. Full marks for the general rule: per-server counters over-admit by up to N×.
  • Key format: rl:{api_key}:{window_start_minute} with TTL = 60 s. Full marks for the TTL — no cleanup job needed.
  • Atomicity fix: a Lua script doing INCR + conditional EXPIRE atomically; full marks for the failure it prevents — a crash between INCR and EXPIRE leaves an immortal key that 429s the client forever.
  • Scaling risk + mitigation: the hot key (one key for the biggest tenant serializes on Redis's single thread) → shard into K sub-keys with K × sub-limit, accepting slightly looser precision; or local buckets + gossip. Full marks only if the price of the mitigation is named.

What earns top marks: all four beats in order — the N× math, the key, the race with its user-visible consequence, the hot key with its price — without being asked twice.

✓

Cheat sheet: picking the algorithm + the 60-second framing

Which algorithm for which situation — then the one-paragraph framing that opens any rate-limiting answer.

1. What are you protecting? Backend overload → limit at the edge/proxy, reject early. One greedy tenant → per-tenant limits (fairness). Brute force / scraping → exact low-volume counters on the sensitive endpoints. Cost → tiered per-key limits at the gateway.

2. Pick the algorithm: need bursts forgiven → token bucket (C = burst, R = sustained). Need output perfectly smooth → leaky bucket (fragile downstream). Need exactness, low volume → sliding window log (login attempts). Need cheap + no 2N boundary → sliding window counter (prev × overlap + cur, two integers per key). Simplest thing that works, 2N tolerable → fixed window.

3. Enforce outside-in: edge (coarse IP) → proxy (nginx limit_req) → gateway (per-key tiers) → in-service middleware (per-resource). Every layer the bad request penetrates is work you did for nothing.

4. The 429 contract: X-RateLimit-Limit/Remaining/Reset on every response; 429 carries Retry-After plus a JSON body with the limit, the window, and a docs link. Your own SDKs honor Retry-After with backoff + jitter.

5. Distributed: one shared counter in Redis via an atomic Lua script (INCR + conditional EXPIRE — never two separate commands). Shard hot keys into sub-keys; take now from Redis to dodge clock skew. Fail open with an alert; fail closed only for auth endpoints.

6. The 60-second framing: "Rate limiting caps requests per client per window and rejects the excess with 429. I'd enforce it at the gateway with per-key tiers from the auth token, back it with Redis through one atomic Lua script per request, use a token bucket where clients burst and a sliding window counter where the fixed-window 2N boundary would hurt, identify by API key with per-resource limits on sensitive endpoints, and fail open on Redis failure except auth, which fails closed."

60s

How to talk about rate limiting in sixty seconds

When the question is "design a rate limiter" or "how would you stop one tenant drowning the API," run this structure. Verdict first, numbers second, traps unprompted.

  1. State the policy in one sentence. "Per-API-key limits — 100/min free, 10k/min pro — enforced at the gateway, rejected with 429 and a Retry-After the client can honor."
  2. Name the algorithm and why. "Token bucket: capacity for the burst a page load needs, refill rate for the sustained cap. Two numbers per client, lazy refill, no timers." If they probe the boundary: "fixed window allows 2N at the minute edge; sliding window counter kills that with prev × overlap + cur."
  3. Go distributed before they ask. "One Redis, one atomic Lua script per request — INCR plus conditional EXPIRE, never two commands, or a crash leaves an immortal key. 3k QPS against a 100k ops/sec node is comfortable."
  4. Name what breaks. Hot keys get sharded; Retry-After is jittered so 429s don't herd; Redis down means fail open with an alert — fail closed only on login."
  5. Close with the key choice. "API key at the gateway, IP only at the edge for unauthenticated floods, per-resource limits in-service — layered, so rotating IPs doesn't dodge the key limit."

Senior-depth traps — land these unprompted

Fixed window's guarantee is weaker than it looks. "≤ N per window" is not "≤ N per any 60 seconds" — the boundary admits 2N. Name both promises.

Two Redis commands are not atomic. The INCR/EXPIRE crash leaves a key with no TTL — permanent 429s for that client. Lua or it didn't happen.

A protective layer must never be more dangerous than what it protects. Fail open on limiter failure — except where the limiter is the security (login), which fails closed.
