Lesson 45 · Classic design

Design a Distributed Cache — the database's memory, spread across twenty-four boxes

It is cup-final day at Riverside FC and the fan app is taking 200,000 reads a second — the live score, the league table, player pages, ticket availability — and the database behind it can serve about 2,000 reads a second per instance. Without a cache the club needs 100 database instances to survive kickoff; with one, it needs five. The cache is not a clever optimisation on top of the system, it is the thing that makes the system affordable at all — and it is also the thing that, designed badly, takes the database down with it the first time it goes cold. Today you design the cache itself: how 400 GB of hot data is spread across 24 boxes, what happens when one key gets 50,000 reads a second, and what happens when the whole fleet restarts an hour before kickoff.

What is a distributed cache?

Start from zero. A cache is a fast copy of data that lives somewhere quicker to reach than the original — memory instead of disk, the edge instead of the origin. A distributed cache is that copy spread across many machines, so that no single machine has to hold all of it and no single machine failing takes all of it away. The soccer running example: the club shop is the database — it holds everything, but there is one of it, and every fan queuing at its door waits. On matchday the club does not make the shop bigger; it sends programme sellers out around the stadium, each carrying copies of the popular items — the match programme, the scarf, the cup-final shirt. A fan buys from the nearest seller in seconds instead of queuing at the shop for twenty minutes, and the shop only ever sees the rare requests — the signed shirt in size small, the item nobody else wants. The sellers are the cache nodes, the shop is the database, and the whole trick of this lesson is deciding what each seller carries, how they know what to carry, and what happens when a seller goes home early.

Terms, defined as they appear

Cache node: one machine in the fleet, holding a slice of the cached data in its RAM — our fleet has 24 of them. Key / value: the lookup name and the data behind it — match:8741:score is a key, the string "Riverside 2–1 Athletic, 67'" is the value. Hit / miss: the key is in the cache (a hit, answered in about a millisecond) or it is not (a miss, answered by the database, then stored in the cache for next time). Hit rate: the fraction of reads that hit — 95% here, so 5 in 100 reads reach the database. TTL (time to live): how long a cached value is allowed to live before it is thrown away — the live score gets 5 seconds, a player profile gets an hour. Eviction: what the cache does when it runs out of room — it throws something away, usually the least recently used item. Replication factor: how many copies of each key exist — RF = 3 here, so every key lives on three nodes. Shard / partition: one slice of the key space, owned by one node (plus its replicas). Working set: the data that is actually read, as opposed to everything stored — 400 GB here, against petabytes in the database. Hot key: one key that gets a wildly disproportionate share of the reads — the live score on cup-final day. Stampede (thundering herd): thousands of requests hitting the database at once because the one key they all wanted just expired. Singleflight (request coalescing): the fix for a stampede — the first request recomputes the value while the rest wait for it, so the database sees one query instead of ten thousand. Cache-aside: the read pattern where the application checks the cache first and fills it on a miss — the application, not the cache, owns the filling. Write-through: the pattern where every write goes to the cache and the database together. Cold start / warm-up: a cache fleet with nothing in it yet, and the slow process of filling it — 5.6 hours here, if you fill it naively.

Why does this lesson exist, when Lesson 3 already covered caching strategies and Lesson 10 built consistent hashing and Lesson 38 built a key-value store? Because knowing the patterns is not the same as designing the system that runs them. Lesson 3 taught you cache-aside and TTLs as patterns; this lesson sizes the fleet that runs them, decides how keys are spread across it, and works out what breaks when the fleet is hot, cold, or one node short. Lesson 10 taught you the ring; this lesson puts 200 million keys on it. Lesson 38 taught you quorums and vector clocks for a store that is the source of truth; a cache is the opposite — it is a copy, and a copy has different rules: it may be thrown away, it may be stale, and it must never be the only place the data exists. The one idea to carry through the whole lesson: a cache is a copy, and everything about the design — the sizing, the eviction, the hot keys, the cold start — follows from deciding what it means to be a copy: fast, disposable, and never the truth.

Requirements and back-of-the-envelope math

Scope first. We are sizing a distributed cache for the Riverside FC fan app at cup-final scale: 200 million keys, an average value of 2 KB, a peak of 200,000 reads a second, and a database that manages 2,000 reads a second per instance. Every number below is computed from one formula each, and Lab A and Lab B let you re-run all of them.

  • The dataset: 200 million keys × 2 KB = 400 GB of hot data — and at RF = 3 that is 1,200 GB to store. The keys are player pages, match events, standings, sessions, and ticket availability — the working set, the data fans actually read, not the petabytes of history sitting in the database. Each key exists on three nodes, because a cache node will fail on matchday and the data must survive it. So the fleet must hold 400 × 3 = 1,200 GB in RAM.
  • The fleet: 24 nodes — each a 64 GB box with about 50 GB usable for cache. A 64 GB box does not give you 64 GB of cache: the operating system, the cache process itself, and headroom for a spike take roughly a fifth, leaving about 50 GB per node. 1,200 ÷ 50 = 24 nodes exactly. Each node holds 200M × 3 ÷ 24 = 25 million keys, 50 GB of values — plus the per-key overhead, about 90 bytes per key for the hash table entry and the object header, which is 200M × 3 × 90 bytes ≈ 54 GB across the fleet, or 2.25 GB per node. The overhead is not a footnote: at a billion keys it would be 270 GB, and a design that forgets it sizes the fleet 5% too small. (Lab A runs the sizing.)
  • The read load: 200,000 reads a second at peak is 8,333 a second per node — about 8% of what one node can do. A single cache node serves on the order of 100,000 operations a second from memory, so 200,000 ÷ 24 ≈ 8,333 reads a second per node leaves enormous headroom — which is the point: the fleet is sized by memory, not by throughput, and the throughput headroom is what absorbs the spike when the goal goes in. The average is far lower — the peak is the number that sizes the system, and the peak is 40 times the quiet-hour load.
  • The hit rate is the whole economics: at 95%, the database sees 10,000 reads a second — 5 instances instead of 100. 200,000 reads a second × 5% misses = 10,000 reads a second reaching the database. At 2,000 reads a second per instance, that is 5 database instances. Without the cache, the same 200,000 reads a second would need 100 instances. Each percentage point of hit rate at this scale is worth 2,000 reads a second — one whole database instance — which is why the hit rate, not the fleet size, is the number the team watches on matchday. At a 99% hit rate the database would see 2,000 reads a second: a single instance. (Lab A runs the hit-rate dial.)
  • The latency: a hit costs about 1 ms, a miss costs about 20 ms — and the p99 is set by the misses, not the hits. A cache hit is a round trip inside one availability zone plus a memory lookup, roughly 1 ms; a miss is a database query with a disk read, roughly 20 ms. The average read is 0.95 × 1 + 0.05 × 20 ≈ 1.95 ms — but the average is not the product. The p99 read is a miss, so the p99 is about 20 ms: 99 reads in 100 are fast, and the one that is slow is the one the fan notices when the score does not update. A design that quotes the average latency is hiding the misses.
  • The hot key: the live score takes 50,000 reads a second — 16,667 a second on each of its three replicas. One key, match:8741:score, takes a quarter of the entire read load, because every fan in the stadium is watching the same number. With RF = 3 the load splits three ways, so each replica serves about 16,667 reads a second — survivable for a node that can do 100,000, but it is a sixth of a node's capacity spent on one key, and a traffic spike doubles it. Replicate that key to 10 copies instead of 3 and each copy serves 5,000 a second. The average load per node is a lie; the hottest key is the design. (Lab B runs the hot-key dial.)
  • The stampede: when that key expires, 10,000 requests pile up on the database in 200 ms. The live score's TTL expires mid-match; recomputing it takes 200 ms; in those 200 ms, 50,000 requests a second × 0.2 seconds = 10,000 requests arrive, find the key gone, and all ten thousand go to the database. With singleflight, the first request recomputes the value and the other 9,999 wait for it — the database sees one query. The stampede is not a traffic problem, it is an expiry problem, and it is fixed at the cache, not by adding database instances.
  • The cold start: filling 200 million keys at 10,000 a second takes 5.6 hours — so the fleet is never allowed to start cold on matchday. 200,000,000 keys ÷ 10,000 keys a second = 20,000 seconds, about 5.6 hours; at 50,000 a second it is still 1.1 hours. A fleet that restarts empty at 8am is still warming up at kickoff, and every read in the meantime is a miss — 200,000 reads a second hitting a database built for 10,000. The fleet is warmed from a snapshot, restarted one node at a time, or pre-filled with the hot keys before the gates open — never cold, never all at once. (Lab B runs the warm-up clock.)
  • Losing a node: 1 of 24 nodes takes 25 million keys and 50 GB with it — 4.2% of the fleet, absorbed as 2.2 GB extra per remaining node. Consistent hashing (Lesson 10) means removing one node moves only its keys: 1 ÷ 24 ≈ 4.2% of the key space, 25 million keys and 50 GB, and the other 23 nodes each absorb about 2.2 GB extra — a shrug, not a crisis, because the fleet has headroom and the replicas already hold copies. The failure that matters is not one node dying; it is all of them dying at once, which is the cold start above.
  • The price tag: 24 nodes at about $200 a month is about $4,800 a month — against 95 database instances it replaces. The fleet costs roughly $4,800 a month to run, and it removes the need for 95 extra database instances — the cache pays for itself many times over, which is why "add a cache" is the first answer to a read-scaling question and usually the last one needed. And the working set grows: at 5% a month, 400 GB becomes 536 GB in six months — 32 nodes by then, not 24 — so the sizing is re-run every quarter, not once.
The decision the numbers force

Three numbers decide the shape of this design, and they pull in different directions. The 400 GB working set at RF = 3 says the fleet is 24 nodes of 50 GB usable each — sized by memory, not by throughput, because 8,333 reads a second per node is a tenth of what a node can do. The 95% hit rate says the database fleet is 5 instances instead of 100 — each percentage point of hit rate is one database instance, so the hit rate is the number the team watches, not the node count. And the 50,000 reads a second on one key says the average is a lie — the live score alone is a quarter of the load, 16,667 a second per replica, and the design lives or dies on what it does with that one key: replicate it to 10 copies, coalesce its recompute to a single query, and never let its expiry become a stampede. A design that sizes for the average load, quotes the average latency, and warms the fleet on matchday has built a cache that works on a quiet Tuesday and takes the database down on cup-final day.

The architecture, in one pass

Follow one read — a fan opening the app to check the live score — through the system. There are seven stages, and each one exists because a different failure is waiting in it.

  1. The client and the ring — the fan's phone knows which seller to ask. The app hashes the key (match:8741:score) and looks it up on the consistent-hash ring from Lesson 10, with virtual nodes so the 24 physical boxes share the load evenly. The ring lives in the client library, so there is no proxy hop — the phone talks straight to the node that owns the key. A node joining or leaving moves only about 1/24 of the keys, and the client re-reads the ring on a membership change. The alternative — a proxy fleet in front of the cache — adds a hop and a fleet of its own to operate; the ring in the client is the simpler answer while the fleet is one cluster in one region.
  2. The read path — cache-aside: check the copy first, fill it on a miss. The app asks the owning node for the key. On a hit, the value comes back in about a millisecond. On a miss, the app reads the database, writes the value into the cache with its TTL, and returns it — the application does the filling, not the cache. That is cache-aside, and it is the default because the cache never has to know where the truth lives: if the cache is empty, the app still works, just slower. The TTL is set by the data, not by the system: the live score gets 5 seconds, the league table 60 seconds, a player profile an hour, a session 30 minutes. Ticket availability gets 5 seconds plus an explicit invalidation on every sale — inventory is the one thing this cache is never allowed to be wrong about for long, and Lesson 26 is why.
  3. The write path — update the database, then delete the key: the order is the design. When the score changes, the app writes the new value to the database first, and then deletes the key from the cache — it does not write the new value into the cache. Deleting is deliberate: the next read refills the cache from the database, so the cache can never hold a value the database does not. The order matters and it is the one thing to get right: database first, cache delete second. If the delete fails or is lost, the TTL bounds the damage — the stale value lives for at most 5 seconds on a live score, an hour on a player profile — which is why the TTL is a correctness decision, not a performance tweak. Write-through — writing to cache and database together on every write — is the alternative, and it is rejected here: it puts cache latency on the write path for data that may never be read again, and it does not fix the race anyway.
  4. Partitioning and replication — 24 shards, three copies each, and a preference list. The key space is split into 24 shards by the ring, and each key lives on three nodes: its owner and the next two nodes clockwise. A read goes to the owner first and falls back to a replica if the owner is slow; a write to the cache updates all three. When a node dies, its replica is promoted and a new third copy is built in the background — the fleet heals itself without the application noticing, and the 4.2% of keys that moved are the only ones that miss. Adding a node is the same operation in reverse: the ring rebalances, about 1/24 of the keys move, and the fleet is bigger by one box.
  5. Eviction — when the box is full, something has to go, and the policy is the design. Each node holds 50 GB and the working set grows at 5% a month, so the fleet will fill up — the question is never whether eviction happens, it is what gets evicted. The default is allkeys-lru: when memory is full, evict the least recently used key — implemented as an approximation, sampling five random keys and evicting the least recently used of the five, which is O(1) and close enough to true LRU that nobody can tell the difference. For skewed access — a handful of player pages taking most of the reads — allkeys-lfu is better: it evicts by frequency, so a page read ten thousand times an hour is never evicted for a page read once. The TTLs do half the work for free: expired keys are removed lazily on access and swept in the background, so the eviction policy only ever decides between live keys.
  6. Hot keys and stampedes — the one key that breaks the average. The live score's 50,000 reads a second are handled in three layers. First, the key is replicated to 10 copies instead of 3, so each copy serves 5,000 a second instead of 16,667 — the replicas are read-only copies, refreshed from the owner, and the client library knows to spread the reads across them. Second, its TTL is jittered — each copy expires at a slightly different time, so the fleet never has to recompute it all at once. Third, the recompute is coalesced: when the key expires, the first request recomputes it and the other 9,999 wait — singleflight — so the database sees one query. And for the very hottest keys, the edge cache in front of the fleet (Lesson 32) absorbs the first wave entirely: the CDN serves the score for 5 seconds, and the fleet sees a fraction of the load. A hot key is not solved by adding nodes — the key still lives on the same three boxes — it is solved by copying the key more widely and by making its expiry boring.
  7. Failure and recovery — the cache may die; the database must not. The fleet's failure modes are handled in layers. One node dies: its replica is promoted, a new copy is built, 4.2% of keys miss once. The whole fleet restarts: it warms from a snapshot — each node loads its last persisted snapshot from disk, so the fleet comes back mostly full instead of empty — and restarts roll one node at a time, never all at once. The database is protected from the refill by a rate limit: the cache is allowed to refill at, say, 10,000 keys a second, and the rest of the misses wait — a cold cache is allowed to be slow, it is not allowed to kill the database. And the final rule, the one that makes all the others safe: the cache is a copy, so losing it loses nothing but speed. If the fleet is gone, the app reads the database directly — slowly, and with a circuit breaker — and the fans see a slower app, not a broken one.

The heart of it: three decisions that make or break the design

1. Where the truth lives — the cache is a copy, and the design must never forget it

The seductive mistake is to start treating the cache as the database: writing to it first, reading from it as if it were authoritative, building features that assume the cached value is the value. It is not. The cache may be evicted, it may expire, it may be lost when a node dies — and every one of those is fine, because the database still has the truth. The whole write path follows from this one sentence: update the database, then delete the cache key, and let the next read refill it. The delete-after-write order is what keeps the copy from ever being newer than the truth, and the TTL is what bounds the damage when the delete is lost — a stale live score lives for 5 seconds, a stale player profile for an hour, and those bounds are chosen per key, in the open, as design decisions. The senior line: a cache that is treated as the source of truth is a database with no durability, no transactions, and an eviction policy — and it will delete your data on a busy afternoon and call it a feature.

2. The hot key is the whole design — the average load is a lie

The fleet averages 8,333 reads a second per node, and that number is useless, because one key takes 50,000 reads a second and the other 199,999,999 keys share the rest. A design sized for the average builds a fleet that is bored 99% of the time and melting on the one key that matters — and the fix is never "add more nodes", because the key still lives on the same three boxes no matter how big the fleet gets. The fix is to copy the hot key more widely (10 replicas instead of 3, so each serves 5,000 a second), to make its expiry boring (jittered TTLs so the copies never expire together, singleflight so one recompute serves ten thousand waiters), and to push it to the edge (the CDN serves the score for 5 seconds and the fleet never sees most of the reads at all). The same thinking applies to the write side: the score changes once a second, but it is read 50,000 times a second — a 50,000:1 read-to-write ratio — so every optimisation in this design is a read optimisation, and a design that optimises the writes has optimised the wrong side. The senior line: find the hottest key first, design for it explicitly, and let the average take care of itself — the average is a statistic, the hot key is the match.

3. Size for the working set, not the dataset — and the eviction policy is the design

The database holds petabytes; the cache holds 400 GB. That gap is the whole point of a cache — it holds the data fans actually read, and the data fans actually read is a small, skewed slice of everything stored. So the fleet is sized from the working set (400 GB × RF = 3 ÷ 50 GB a node = 24 nodes), not from the database, and the eviction policy is what keeps the working set in the fleet when the fleet fills up: LRU for recency, LFU for skewed popularity, TTLs for the data that ages out on its own. Get the policy wrong and the cache evicts the working set to make room for one-off reads — the hit rate collapses, the database takes the full load, and the cache is still there, still costing $4,800 a month, doing nothing. And the working set grows — 5% a month, 536 GB in six months — so the sizing is a quarterly habit, not a one-off calculation: the fleet that is exactly right today is 8 nodes short by the summer. The senior line: a cache that holds the working set is a cache; a cache that holds a random sample of it is a lottery ticket that costs $4,800 a month.

The senior line on the three decisions

Every distributed cache is the same three sentences, and the room is won by saying them with numbers attached. The cache is a copy, never the truth — so writes go to the database first and the cache key is deleted after, and the TTL is the bound on staleness: 5 seconds on a live score, an hour on a player profile, with the delete lost meaning stale for at most that long. The hot key is the design — one key takes 50,000 reads a second, a quarter of the whole load, so it is replicated to 10 copies at 5,000 each, its TTL is jittered, and its recompute is coalesced to a single database query instead of the 10,000 that would pile up in 200 ms. And the fleet is sized for the working set — 200 million keys at 2 KB is 400 GB, times RF = 3 is 1,200 GB, divided by 50 GB usable per node is exactly 24 nodes, holding 25 million keys each, serving 8,333 reads a second each at a 95% hit rate that turns 100 database instances into 5. Say those three sentences, with the arithmetic — 400 GB, 1,200 GB, 24 nodes, 50,000 reads on one key, 10,000 requests in 200 ms, 5.6 hours to warm cold — and the rest of the design — the ring in the client, the delete-after-write order, the sampled LRU, the snapshot warm-up — is machinery that follows.

Senior-depth traps

  • "The cache is fast, so make it the source of truth." No: the cache is fast because it is a copy — it skips durability, transactions, and fsync, and it throws data away when it runs out of room. A value that exists only in the cache is a value that will disappear on a busy afternoon, and the team will discover it was the only copy when a fan's ticket, session, or purchase is gone. If the data cannot be rebuilt from the database, it does not belong in the cache — and if a feature needs the cache to be durable, the feature needs a database.
  • "One key is hot — add more nodes." Adding nodes does not help a hot key, because the key still lives on the same three boxes: the ring puts it on one owner and two replicas, and a fleet of 100 nodes has the same three boxes serving it. The hot key is fixed by copying the key more widely (10 replicas, 5,000 reads a second each), by coalescing its recompute (singleflight), and by pushing it to the edge (the CDN serves it for 5 seconds) — three answers, and none of them is "more nodes". Sizing the fleet for the average load while the hottest key melts one node is the most common sizing error in this whole area.
  • "Write-through keeps the cache and the database consistent." Write-through keeps them consistent only if every write goes through the cache, every write succeeds in both places, and no write ever bypasses it — and in a real system, writes come from batch jobs, admin tools, and other services that never touch the cache. A stale value written around the cache is still stale, and a write that fails halfway leaves the two disagreeing in the other direction. The honest answer is cache-aside with delete-after-write and a TTL bound: the cache is allowed to be stale for at most the TTL, the bound is stated in the open, and the fast-changing data gets the short TTL. Consistency in a cache is a bound, not a guarantee — and a design that claims otherwise is hiding the race.

Questions, with full model answers

Q1. Design the cache for the matchday app: 200,000 reads a second at peak, 200 million keys, average value 2 KB. How many nodes, and why?

Model answer. I start from the working set, because the fleet is sized by memory, not by throughput. 200 million keys × 2 KB is 400 GB of hot data, and at a replication factor of 3 — every key on three nodes, so a node can die on matchday without losing data — that is 1,200 GB to store. A 64 GB box gives about 50 GB of usable cache once the operating system and the process itself are accounted for, so 1,200 ÷ 50 is exactly 24 nodes, each holding 25 million keys and 50 GB of values, plus about 2.25 GB of per-key overhead. The throughput then checks out rather than driving the design: 200,000 reads a second ÷ 24 nodes is about 8,333 a second per node, against roughly 100,000 operations a second that a single node can serve from memory — about 8% of capacity, which is the headroom that absorbs the spike when the goal goes in. The hit rate is the number that matters next: at 95%, 10,000 reads a second reach the database, which is 5 database instances at 2,000 reads a second each — against 100 instances with no cache at all, so each percentage point of hit rate is worth one database instance. The keys are spread by consistent hashing with virtual nodes in the client library, so a node joining or leaving moves only about 1/24 of the keys, and the read path is cache-aside with TTLs set by the data: 5 seconds on the live score, 60 on the table, an hour on a player profile. And I would close with the two numbers that are not averages: the hottest key takes 50,000 reads a second on its own and is handled separately (Lab B's answer), and the fleet takes 5.6 hours to warm from cold, so it is never restarted whole on matchday.

Q2. The live score key is hit 50,000 times a second. One node owns it. What happens, and how do you fix it?

Model answer. I start with the arithmetic, because the average load hides it: the fleet averages 8,333 reads a second per node, but this one key takes 50,000 a second — a quarter of the entire read load — and with a replication factor of 3 it splits three ways, so each replica serves about 16,667 reads a second. That is survivable — a node can do roughly 100,000 operations a second — but it is a sixth of a node's capacity spent on one key, and a traffic spike doubles it, so the node that owns the score is the first thing to saturate while the other 23 boxes idle. The fix is not more nodes: the key still lives on the same three boxes in a fleet of any size, because the ring puts it there. The fix has three layers. First, copy the key more widely — replicate it to 10 copies instead of 3, so each copy serves 5,000 a second, with the copies refreshed from the owner and the client library spreading reads across them. Second, make its expiry boring — jitter the TTLs so the copies never expire together, and coalesce the recompute with singleflight, so when a copy does expire, the first request recomputes the value and the other 9,999 wait, and the database sees one query instead of the 10,000 that would pile up in the 200 ms recompute. Third, push it to the edge — the CDN in front of the fleet serves the score for 5 seconds, and the fleet never sees most of the reads at all. And I would close with the principle: the average load is a lie, the hottest key is the design, and any answer that starts with "add nodes" has not understood where the key lives.

Q3. The cache fleet restarts at 8am on cup-final day. Kickoff is 9am. What happens, and how do you prevent it?

Model answer. I start with the clock, because the failure is arithmetic: the fleet holds 200 million keys, and filling it at 10,000 keys a second takes 200,000,000 ÷ 10,000 = 20,000 seconds, about 5.6 hours — at 50,000 a second it is still 1.1 hours. A fleet that restarts empty at 8am is still warming up at kickoff, and every read in the meantime is a miss, so the database — built for the 10,000 reads a second that get through at a 95% hit rate — suddenly faces the full 200,000 a second, which is 100 instances' worth of load on 5 instances. The outage is the database's, but the cause is the cache. The prevention has four layers. First, warm from a snapshot: each node loads its last persisted snapshot from disk on restart, so the fleet comes back mostly full instead of empty — the snapshot is a copy of a copy, and losing the newest few minutes of it is fine, because the database is the truth and the next read refills what is missing. Second, restart one node at a time: a rolling restart means 23 nodes keep serving while one warms, and only 1/24 of the keys miss at any moment. Third, pre-fill the hot keys before the gates open: the live score, the table, the top player pages are loaded deliberately, not left to the first fan who asks. Fourth, rate-limit the refill: the cache is allowed to refill at, say, 10,000 keys a second, and the misses beyond that wait — a cold cache is allowed to be slow, it is never allowed to kill the database. And I would close with the rule that makes all four safe: the cache is a copy, so a fleet that is gone costs speed, not data — the app fails open to the database, slowly, behind a circuit breaker, and the fans see a slower app rather than a broken one.

Q4. A fan sees last season's standings after the table updated. The cache said the data was fresh. What happened, and what is the fix — in the design, not in the moment?

Model answer. I start with what happened, because the failure has a specific shape: the standings key held a value that was true when it was written and false by the time it was read, and the cache served it anyway — because a cache serves what it holds, and it holds whatever was put there, for as long as its TTL allows. The usual mechanism is the cache-aside race: a read misses, fetches the old table from the database, and before it can fill the cache, a write updates the database — the read then writes the old table into the cache, and the new table waits out the TTL. Or the write updated the database and the cache delete after it was lost, and the old value sat there until its TTL expired. Nothing is broken; the cache did exactly what its contract promises, and the bug is in the system around it: the design treated the cache as if it held the truth. The fix in the moment is the TTL doing its job — the stale value expires, the next read refills from the database, and the fan sees the new table. The fix in the design has three parts. First, the write order is enforced: database first, cache delete second, so the cache can never hold a value newer than the database, and the delete is retried rather than forgotten. Second, the TTL is set by how fast the data changes: the table gets 60 seconds, the live score 5 — and that bound is stated in the open, so the team knows a fan can see a table up to 60 seconds old, and has decided that is acceptable. Third, the boundary is named: where a stale value is a wrong answer rather than a slow one — ticket availability, a seat that has just been sold — the data is not cached on a long TTL at all, it is invalidated on every sale or read from the database. And I would close with the line that prevents the next incident: staleness in a cache is a bound, chosen per key and written down, not a surprise — and a design that cannot say how stale its data can be has not designed its cache.

Practice drills (untimed — depth over speed)

Drill 1 — Size the fleet. A fan app has 500 million keys with an average value of 1 KB, a replication factor of 3, and nodes with 32 GB usable for cache. (a) How much raw data is there, and how much with replication? (b) How many nodes? (c) How much memory and how many keys per node? Rubric: (a) 500,000,000 × 1 KB = 500 GB raw, × 3 = 1,500 GB with replication; (b) 1,500 ÷ 32 = 46.9, so 47 nodes; (c) 1,500 ÷ 47 ≈ 31.9 GB per node, and 500M × 3 ÷ 47 ≈ 31.9 million keys per node — plus about 90 bytes of overhead per key, roughly 2.9 GB per node, which is why the usable figure, not the box size, is the one that sizes the fleet.

Drill 2 — The hit-rate dial. A service takes 100,000 reads a second. A database instance serves 2,000 reads a second. (a) How many database instances with no cache? (b) How many at a 90% hit rate? (c) How many at a 99% hit rate? (d) What is one percentage point of hit rate worth? Rubric: (a) 100,000 ÷ 2,000 = 50 instances; (b) 10% miss, so 10,000 reads a second reach the database — 5 instances; (c) 1% miss, so 1,000 reads a second — 1 instance (0.5 rounded up, because half an instance does not exist); (d) one point is 1,000 reads a second, or half a database instance — which is why the hit rate, not the node count, is the number the team watches.

Drill 3 — The stampede. A hot key is read 20,000 times a second. Its TTL expires, and recomputing the value takes 500 ms. (a) How many requests pile up on the database during the recompute? (b) How many database queries with singleflight? (c) The recompute fails — what do the waiting requests get? Rubric: (a) 20,000 × 0.5 seconds = 10,000 requests; (b) one — the first request recomputes and the other 9,999 wait for its result; (c) they get the error, or a stale value if the design serves stale-while-revalidating — which is why the recompute path has its own timeout and its own fallback, and why a hot key's recompute is never allowed to be the only way the value exists.

Sixty-second framing

"A distributed cache is the database's memory, spread across boxes so no one box holds it all: 200 million keys at 2 KB is 400 GB of hot data, times a replication factor of 3 is 1,200 GB, divided by 50 GB usable per node is exactly 24 nodes, each holding 25 million keys. The read path is cache-aside — a hit in about a millisecond, a miss that reads the database and fills the cache with a TTL set by the data — and at a 95% hit rate the database sees 10,000 reads a second instead of 200,000, which is 5 instances instead of 100: each percentage point of hit rate is one database instance. The write path is database first, cache delete second, and the TTL is the bound on staleness — 5 seconds on a live score, an hour on a player profile. The three decisions are where the truth lives, the hot key, and the working set: the cache is a copy and must never be treated as the truth, the hottest key takes 50,000 reads a second — a quarter of the whole load — so it is replicated to 10 copies, its TTL is jittered, and its recompute is coalesced to a single query instead of the 10,000 that would pile up in 200 ms, and the fleet is sized for the working set, not the dataset, with the eviction policy — LRU, or LFU where access is skewed — deciding what stays when the box fills. And the trap to name: a cold fleet takes 5.6 hours to warm at 10,000 keys a second, so it is warmed from snapshots, restarted one node at a time, and its refill is rate-limited — because a cache that restarts empty on matchday takes the database down with it."

Talk-track for the room

  1. Scope and the one idea: a cache is a copy — fast, disposable, never the truth — and everything in the design follows from that sentence.
  2. Back-of-the-envelope: 400 GB working set, RF = 3, 1,200 GB, 24 nodes of 50 GB usable, 25 million keys each; 8,333 reads a second per node; 95% hit rate turns 100 database instances into 5; the live score takes 50,000 reads a second on one key.
  3. Architecture: the ring in the client, cache-aside reads with TTLs set by the data, database-first writes with delete-after, 24 shards at RF = 3, sampled LRU or LFU eviction, hot-key replication with jittered TTLs and singleflight, and snapshot warm-up with a rate-limited refill.
  4. Deep dive: the truth lives in the database and the cache is a copy; the hot key is the design and the average is a lie; the fleet is sized for the working set and the eviction policy is what keeps it there.
  5. Failure modes and the close: the stampede, the hot key melting a node, the stale-read race, the cold fleet at kickoff, eviction eating the working set, and the cache becoming the truth — and the line to end on: losing the cache costs speed, not data, and a design that forgets that will lose both.
