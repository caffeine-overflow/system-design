READ · WHAT CACHING IS

Learn what a cache actually is

Get the core idea and the four words this whole lesson runs on.

A cache is a fast, limited store of copies of data that is expensive to produce or fetch. Instead of doing the expensive work every time, the system checks the fast copy first — and only does the real work when the copy isn't there.

Think of your kitchen. The grocery store is the database: full selection, far away, slow. Your fridge is the cache: limited space, nearby, fast. You restock the fridge from the store (populate), eat from the fridge when the food is there, and drive to the store when it isn't. Caching is that idea, applied to computers.

The four words that run this lesson
  • Hit — the cache had the data. Fast, cheap, no origin work needed.
  • Miss — the cache didn't have it. The request falls through to the origin (the database or service), which does the real work and hands back a copy for the cache to store.
  • TTL (time to live) — how long a copy stays in the cache before it's treated as stale and refreshed. TTL is the dial that trades freshness for speed.
  • Eviction — when the cache runs out of space, it must throw something out. How it chooses (section 05) decides how well your hit ratio survives under pressure.

Trade-off stated out loud: caching turns repeated expensive work into cheap copies — but copies can be stale, memory is finite, and the cache itself becomes a thing you must operate and defend.

READ · WHY CACHING MATTERS

Read the latency ladder

Compare the orders of magnitude, then connect them to request latency.

Caching is often the highest-leverage performance tool because it replaces repeated expensive work with a nearby copy. The win is not 10%; crossing a storage or network boundary can cost 10× to 1,000,000× more.

OPERATIONROUGH LATENCYRELATIVE SCALE
Memory access~100 ns
SSD access~100 µs
Intra-data-center network~1 ms
Typical database query~1–20 ms
Cross-region round trip~100 ms

These are order-of-magnitude estimates, not service-level guarantees. A database query may include network delay, lock waits, disk reads, and CPU. At 50,000 reads/s, a 95% cache hit ratio leaves only 2,500 reads/s for the database. That can be the difference between one healthy primary and a costly fleet of replicas.

What a strong answer saysCache the measured bottleneck, not “the database” in the abstract. Name the expensive operation removed, the permitted staleness, and the safe path when the cache misses or fails.

Trade-off stated out loud: lower latency and origin load in exchange for stale copies, memory cost, and a new coordination problem.

Definitions to keep straight

Cache-aside, also called lazy loading, means the application fills the cache only after a miss. Read-through hides that loading behind a cache interface. Write-through updates the authoritative store before acknowledging success. Write-back or write-behind acknowledges at the cache and persists asynchronously, so durability and ordering become first-class requirements. Refresh-ahead renews a hot item before it expires.

Interview moveDo not select a pattern by name alone. State read/write ratio, freshness target, acknowledgment semantics, miss behavior, and what happens during partial failure.
READ + TRY IT · EVICTION

Decide what leaves when memory is full

Read the four policies, then step through the fixed sequence to see least-recently-used eviction.

TTL · time to live

A per-entry lifetime after which the value expires. It bounds staleness and cleans forgotten keys, but it is not an admission or memory-pressure policy by itself.

Wins when: freshness has a natural time bound.

LRU · least recently used

Evicts the key not accessed for the longest time. It adapts to changing locality but a large one-time scan can push useful keys out.

Wins when: recent access predicts near-future access.

LFU · least frequently used

Evicts the key with the lowest access count, often with aging so old popularity fades. It protects stable hot items but adapts more slowly.

Wins when: a persistent popular set dominates traffic.

FIFO · first in, first out

Evicts the oldest inserted key, regardless of reads. It is simple and predictable but can evict a heavily used old item.

Wins when: simplicity matters and age approximates usefulness.

READ · INVALIDATION

Choose how stale copies disappear

Compare the staleness window against implementation complexity.

Phil Karlton’s famous line says there are only two hard things in computer science: cache invalidation and naming things. Invalidation is hard because a write and every cached copy rarely change atomically.

TTL expiry

Let entries disappear after a fixed lifetime. Add random jitter so thousands of keys do not expire together.

Staleness: up to the TTL. Complexity: low.

Explicit invalidation on write

Commit the database change, then delete affected keys. Deleting is safer than recomputing derived values in the write path.

Staleness: event/operation delay. Complexity: medium; races remain.

Versioned or stamped keys

Use keys such as price:42:v19. Advancing the version makes old copies unreachable; TTL cleans them later.

Staleness: version lookup delay. Complexity: medium; extra metadata and memory.

Event-driven invalidation

Publish changes through pub/sub or CDC (change data capture, a stream of database mutations). Consumers evict local and shared copies.

Staleness: propagation lag. Complexity: high; delivery and replay matter.

The cache-aside race

T1 reader misses → reads old A
T2 writer commits B → deletes cache
T1 reader stores stale A after the delete

Mitigations include version checks before fill, immutable versioned keys, short TTLs, delayed double-delete, or a CDC event that arrives after the stale fill. For strict read-after-write, bypass the cache, read the primary, or carry a session version token that rejects older cached values.

READ · STAMPEDE PROTECTION

Protect the database from synchronized misses

Learn the failure shape, then match each mitigation to it.

A cache stampede, also called a thundering herd, happens when a hot key expires and thousands of requests hit the database at once. A cache intended to reduce load becomes the trigger for an origin overload.

  1. Request coalescing / singleflight

    Allow one in-flight load per key while other callers wait or receive stale data. Across machines, use a short lease with a unique owner token and expiry.

  2. Probabilistic early refresh

    As expiry approaches, each request has a small, increasing chance to refresh. Work spreads over time without a fixed refresh boundary.

  3. Jittered TTLs

    Add bounded randomness to expiration times so many unrelated keys do not expire simultaneously. This does not split one hot key.

  4. Stale-while-revalidate

    Serve a recently expired copy immediately while one worker refreshes it. This trades bounded staleness for predictable tail latency.

p99 latency is the latency below which 99% of requests complete; the slowest 1% is worse. Stampedes often look harmless in average latency while p99 and database queues explode. Also cap total and per-tenant fill concurrency: a per-key lock cannot protect the origin when 100,000 different keys miss.

READ · CDN EDGE CASES

Design the edge cache key before chasing hit ratio

Use the key example to separate variants that matter from dimensions that destroy reuse.

Example CDN cache key

GET /products/42?currency=CAD · Accept-Language=en-CA
INCLUDE WHEN OUTPUT CHANGESPath, normalized relevant query parameters, host, encoding, and headers such as Accept-Language.
AVOID BY DEFAULTTracking parameters, header order, cookies, authorization headers, and user identity. They fragment the cache or risk leaks.

The HTTP Vary header tells a shared cache which request headers select different response variants—for example, Vary: Accept-Language. A missing variant can serve the wrong content; too many variants collapse hit ratio. Never cache a personalized response under a public key.

Purge vs TTL

A purge actively removes content, but propagation may take seconds and can fail. TTL is simpler and bounds forgotten invalidations. Strong designs often use both: purge for speed, TTL for repair.

Stale controls

stale-while-revalidate serves stale content during refresh. stale-if-error serves stale content when the origin fails. Both require an explicit acceptable stale window.

Origin shielding

A shield cache sits between edge locations and the origin. Many edge misses collapse into one shield fill, reducing cross-region requests and protecting the origin.

Personalization

Cache a public shell and fetch personal fragments separately. Edge-side includes can assemble fragments, but add operational complexity and can leak data if fragment keys are wrong.

Negative caching

Briefly cache 404s and selected failures to stop repeated requests for missing objects. Keep TTLs short; never cache permission failures so broadly that one user’s denial affects another.

Edge herd

A global purge can make every point of presence miss together. Use shield layers, request coalescing, staggered expiry, and controlled prewarming for proven hot objects.

What a strong answer coversKey cardinality, personalization boundaries, cache-control directives, purge propagation, origin shielding, stale-on-error behavior, and protection against a synchronized global refill.
READ · DISTRIBUTED CACHING

Shard capacity without creating invisible skew

Connect partitioning, replication, and hot-key handling to concrete node limits.

Consistent hashing maps both cache nodes and keys onto a logical ring so adding or removing a node remaps only a fraction of keys, instead of nearly all of them. Virtual nodes spread each physical node across many ring positions. It improves rebalancing, but does not solve replication, failover, or one disproportionately popular key.

EXAMPLE CLUSTER10 nodes
EACH NODE100k ops/s
HOT KEY250k reads/s

Even though the cluster advertises roughly 1M ops/s, a single 250k-read/s key can overload the one node that owns it. Mitigate by replicating immutable values under several salted keys, adding a short local L1 cache, or splitting reducible aggregates. Ordinary sharding only places the hot key; it does not divide its traffic.

Redis Cluster vs client-side sharding

Redis Cluster owns hash slots, membership, replica promotion, and redirection. Clients must understand cluster topology, and multi-key operations generally require keys in one slot. Client-side sharding lets the application hash keys across simpler nodes, but every client must converge on membership, retries, failover, and rebalancing. A managed clustered cache is usually the default unless the workload or infrastructure justifies owning the control plane.

Trade-off stated out loud: more nodes add capacity and availability, but create coordination, replication, rebalance traffic, and failure semantics. Design for one node unavailable and keep enough headroom to absorb its traffic.

READ · BACK-OF-THE-ENVELOPE SIZING

Estimate the working set and origin reduction

Follow the arithmetic, then name the hidden overheads.

Suppose a catalog receives 50,000 reads/s. There are 10 million products, but the active one-hour working set is 1 million products. Each cached product serializes to 2 KB, and cache metadata plus allocator overhead adds an estimated 30%.

raw working set = 1,000,000 × 2 KB = 2 GB
with 30% overhead = 2.6 GB
with 2 replicas = 5.2 GB
at 70% target utilization ≈ 7.4 GB provisioned

At a 95% hit ratio, the database sees the remaining 5%: 50,000 × 0.05 = 2,500 reads/s. At 90%, it sees 5,000 reads/s—twice the load. Near high hit ratios, a few percentage points matter enormously.

Validate assumptions with the actual key distribution and value sizes. Include fragmentation, expiry indexes, network buffers, replication, failover headroom, and rebalancing. Track hit ratio by endpoint plus cost-weighted hit ratio: missing one 200 ms aggregation can cost more than missing 100 cheap lookups.

QUIZ YOURSELF · FULL MODEL ANSWERS

Answer first, then open the model

For each question, state requirements, choose a design, quantify it, and cover failure behavior before revealing the answer.

1. Design caching for a product-catalog service. Which pattern do you choose, and why?

Model answer: I would split the response by freshness and personalization. Public product descriptions, images, and category metadata are read-heavy and tolerate seconds or minutes of staleness, so I would use cache-aside in a distributed cache and CDN caching for public HTTP responses. Price may use a shorter TTL and event-driven invalidation; checkout inventory must be revalidated against the inventory authority rather than trusted from cache.

  1. Key: tenant:product:id:schemaVersion:locale; exclude user identity from public objects.
  2. Read: CDN → service L1 → distributed L2 → database on miss. One request fills a missing hot key; others wait briefly or receive bounded stale data.
  3. Write: commit the database, publish an outbox-backed product-changed event, and delete affected L2/L1/CDN keys. TTL plus jitter repairs missed invalidations.
  4. Capacity: at 50k reads/s and 95% hits, plan the database for at least 2.5k steady read/s plus a constrained miss wave. Do not allow full fall-through during cache failure.
  5. Observe: cost-weighted hit rate, p99, fill concurrency, invalidation lag, hot keys, evictions, stale-served count, and origin QPS.

The choice favors low read latency and independent cache failure over perfectly immediate visibility. If price freshness must be sub-second, I would consider pushed invalidation/version stamps rather than simply shrinking every TTL.

2. Compare cache-aside, read-through, and write-through. Choose one for user profiles.

Model answer: Cache-aside makes the application read the cache, fetch the database on miss, and fill it; it offers control and caches only demanded data, but callers own miss races. Read-through puts that miss logic behind the cache interface; it simplifies callers but couples cache infrastructure to the data loader. Write-through is a write policy: the cache path updates the authoritative store before acknowledging, increasing write latency but keeping the cached value warm.

For mostly-read user profiles with moderate write frequency, I would choose cache-aside: read by user ID, fill on miss, then commit profile updates and invalidate the key. It is easy to degrade to the database and avoids populating profiles nobody rereads. For read-after-write in the same session, return the committed value directly or carry a version token so an older cache entry is rejected. If many teams need identical loading semantics, I might wrap the same behavior behind read-through. I would choose write-through only if immediate cache warmth justifies adding cache and database latency to every write and I can define partial-failure semantics.

3. A hot key expires and 10,000 requests hit the database at once. What happened, and how do you fix it?

Model answer: This is a cache stampede: the expiry created a synchronized miss, and all 10,000 callers attempted the same load. I would first cap origin concurrency so the database cannot be overwhelmed. Then I would add per-key singleflight: one caller gets a short refresh lease; others either wait within budget or receive a stale value. The lease has an expiry and unique owner token so a delayed worker cannot release a successor’s lease.

I would enable stale-while-revalidate for an explicitly bounded window, refresh proven hot keys before hard expiry, and add TTL jitter for unrelated keys. If one key itself exceeds a shard’s capacity, I would replicate or L1-cache that value; jitter alone cannot split one key. I would test cold start and cache outage, and alert on fill concurrency, lease contention, stale-served volume, database queue depth, and p99—not just hit ratio.

4. How do you invalidate caches across many application servers when a price changes?

Model answer: I would make the database the authority and use the transactional outbox pattern: the price update and an event record commit together. A publisher sends PriceChanged(productId, version) to pub/sub; every app instance idempotently invalidates its local L1, while a consumer deletes or supersedes the distributed L2 key and triggers a CDN purge if the public response contains price.

The event carries a monotonically increasing version. Cache fills include that version, and consumers ignore older events, which handles duplicates and reordering. Versioned keys prevent a late stale fill from overwriting the new value. Short L1 TTLs and a longer L2 TTL provide bounded repair if an event is lost or delayed. For a user who just changed a price, I would read from the primary or require at least the committed version. I would measure outbox age, consumer lag, invalidation failures, and stale-price sightings; “pub/sub” alone is not a consistency guarantee.

5. Your CDN hit ratio is 40%. Walk through improving it.

Model answer: I would segment the metric before changing TTLs: hit ratio by path, status, method, region, object size, and origin cost. Then I would inspect cache-status headers and sample keys to find fragmentation. Common causes are irrelevant query parameters, cookies, authorization headers, inconsistent parameter order, too many Vary dimensions, short TTLs, or responses marked private/no-store.

I would normalize the key to path plus only output-changing parameters and headers; strip tracking parameters; separate public content from personalized fragments; and set explicit cache-control directives. For safe content, extend TTL and pair purge-on-change with TTL as repair. Add stale-while-revalidate and stale-if-error, use an origin shield to coalesce misses across edge locations, and negative-cache eligible 404s briefly. I would prewarm only measured hot content, not the full catalog.

Finally, I would verify correctness with variant and authorization tests, then compare byte hit ratio, request hit ratio, origin offload, and p99. A higher hit ratio is not worth serving the wrong language, price, or user data.

TAKEAWAYS · REMEMBER THESE

Use the senior-level checklist

Before ending a design, make each statement concrete for that system.

  • The source of truth owns correctness.
  • Freshness is a requirement; TTL is a mechanism.
  • Every cache key is a data-isolation decision.
  • Protect the origin before optimizing hit ratio.
  • Singleflight fixes one-key stampedes; jitter spreads many expiries.
  • A hot key defeats ordinary sharding.
  • Purge quickly; TTL repairs missed purges.
  • Separate public content from personalization.
  • Size the working set, overhead, replicas, and failover headroom.
  • Measure cost-weighted hits and p99, not averages alone.
The sentence to remember

“Add a cache” is not the design. The design is where the copy lives, how fresh it must be, who updates it, and how the system survives when it disappears.
