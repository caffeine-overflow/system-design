Lesson 8 · Foundations

Database Indexing

Every "find the fast player" query is really a search problem: without an index, the database re-reads every row, every time. An index is the difference between scanning 100 million rows and touching 4 pages. This lesson covers how indexes work, how to design them, what they cost — and the one alternative structure every senior should know.

01

What is an index?

An index is a separate, sorted data structure that maps the values in one or more columns to the locations of the rows holding those values — so the database can find matching rows without reading the rows that don't match. It trades write speed and disk space for read speed.

⚽ The running example: the scouting database

A table of 50,000 players

You work for a club. Your database has a table players with 50,000 rows — one per player scouted worldwide — and columns player_id, name, team, position, goals, assists, minutes_played. The app is full of queries like: "Find the row for Bukayo Saka." "List every striker with more than 20 goals." "Show all Arsenal midfielders."

Every idea in this lesson lands on this table. Keep it in your head: 50,000 rows, 7 columns, and one very impatient scout.

Life without an index: the full table scan

Full table scan (sequential scan)

Reading every row of the table, one by one, and checking whether each row matches the query's condition. The table itself — the rows as stored on disk — is called the heap in PostgreSQL (or the clustered data in MySQL/InnoDB).

For SELECT * FROM players WHERE name = 'Bukayo Saka' with no index, the database starts at row 1 and reads through all 50,000 rows, comparing each name, until it finds the match. It had to touch 50,000 rows to return 1. That's a full table scan: correct, simple, and linear — it costs O(n), meaning the work doubles when the table doubles.

Rows live on disk in chunks called pages — typically 8 KB each in PostgreSQL and MySQL. A row of ~80 bytes means roughly 100 rows per page, so our 50,000-row table occupies about 500 pages. A scan reads all 500 pages to answer the Saka query.

Life with an index

Index

An auxiliary data structure — separate from the table — that stores the indexed column's values in sorted order, each paired with a row pointer (the physical location of the row: which page, which slot). It answers one question fast: "given this value, where are the rows?"

With an index on name, the database searches the sorted structure for "Bukayo Saka" — a search that costs O(log n), not O(n) — gets the row pointer (say, page 214, slot 7), and reads exactly that page. It touched ~4 pages instead of 500. The index never replaces the table; it is a shortcut to it.

⚽ The match-program analogy

A full table scan is reading the match program front to back to find one player's profile. An index is the alphabetical player list at the back of the program: each name paired with a page number. You look up the name in the sorted list, jump straight to the page. The analogy even captures the cost: the club must reprint the index every time a player is added, removed, or renamed — just as a database must update the index on every write (section 5).

Why not index everything, then? Three reasons, and they are the entire second half of this lesson: (1) every index must be updated on every write — inserts, updates, deletes all get slower; (2) each index consumes disk; (3) the query planner can be confused by too many choices. Index design is a budget: spend it where reads are expensive, never where writes dominate.

02

How a B-tree index works

The default index in PostgreSQL and MySQL is a B-tree (specifically a B+tree, but everyone says B-tree). Understanding its shape — wide, shallow, sorted — explains why lookups cost O(log n), why inserts stay fast, and why the structure is built for disk, not RAM.

B-tree

A balanced tree where each node holds many keys (hundreds), sorted, instead of the 1–2 keys of a classroom binary tree. Balanced means every path from the root to a leaf is the same length, so the worst-case lookup cost is predictable. The B is usually read as "balanced" — nobody agrees what Bayer originally meant.

Node: root, internal, leaf

Each tree level is made of nodes, and one node = one disk page (8 KB). The root is the single top node. Internal nodes hold keys plus pointers down to child nodes. Leaf nodes (the bottom level) hold the actual index entries: key value + row pointer into the heap. Searching means: start at the root, follow the right child pointer at each level, land on the leaf.

⚽ Walk through a lookup: "goals > 20"

The scouts constantly ask: "Which players scored more than 20 goals this season?" There's an index on goals. Here's the physical journey:

  1. Root page: holds separator keys like [5 → child A] [12 → child B] [21 → child C]. "More than 20" points at child C.
  2. Internal page C: finer separators: [21 → leaf 1] [24 → leaf 2] [28 → leaf 3]. Pick leaf 1.
  3. Leaf page 1: holds the actual entries sorted by goals: (21 → page 214 slot 7), (22 → page 88 slot 2), …. Everything from here on matches the query — scan forward through the leaf pages.
  4. Heap fetch: for each entry, follow the row pointer and read the row from the table.

Within each node, keys are sorted, so finding the right child is a binary search over a few hundred keys — ~9 comparisons per page, basically free. The expensive part is never the comparisons; it's the page reads. And a lookup touches exactly one page per level: root, internal, leaf — three pages, then the heap rows.

Why O(log n) — from zero, with the time-complexity lesson

Fanout

The number of children each node points to — roughly the number of keys that fit in one 8 KB page. A (goals, row-pointer) entry is ~16 bytes, so a page holds about 500 entries. Fanout ≈ 500. Height = how many levels the tree has.

From Lesson 4 (time complexity): logarithmic growth means the work increases by a fixed step each time the input multiplies. With fanout 500, each new level multiplies capacity by 500:

  • 1 level (root only): 500 entries
  • 2 levels: 500 × 500 = 250,000 entries
  • 3 levels: 500³ = 125 million entries
  • 4 levels: 500⁴ = 62.5 billion entries

So a table of 100 million rows needs a tree just 3 levels deep: a lookup reads 3 index pages. Double the table to 200M rows? Still 3 levels. Grow it 500× to 50 billion rows? Only then do you need a 4th level. That's O(log n) — the height (and therefore the number of page reads) barely moves as data explodes. A lookup on 100M rows costs essentially the same as on 10K rows.

⚽ Why not a binary tree? The stadium-seating version

A binary tree has fanout 2: each node points to 2 children. For 100M rows its height is log₂(100M) ≈ 27 levels — 27 random page reads per lookup. A B-tree with fanout 500 needs 3. Think of finding a seat: a binary tree is like an usher who answers one yes/no question per page of the stadium map; a B-tree is an usher who hands you a whole section map (one page, hundreds of entries) at each step. Because disk reads happen in whole pages anyway — the drive won't read 16 bytes for you — packing hundreds of keys into each page-read is nearly free. B-trees exist because disk I/O is page-shaped.

Inserts: page splits keep the tree balanced

What happens when the club signs a new player and a leaf page is already full? The database splits the page: it allocates a fresh page, moves half the entries over, and inserts a new separator key in the parent — recursively, up to the root if needed. The split keeps every root-to-leaf path the same length, which is exactly what "balanced" guarantees. Splits cost extra writes (another entry in the write-amplification story of section 5), and they leave pages half full — the first seed of fragmentation.

The one-paragraph mental model. A B-tree index is a sorted, page-shaped shortcut to your rows. Each level is one disk read; the tree is only 3–4 levels deep for any table you'll ever see; within a page, keys are binary-searched. Reads cost O(log n) page fetches, inserts cost O(log n) plus the occasional page split. Everything else in this lesson — composite keys, covering indexes, write costs, LSM trees — is a variation on, or a reaction to, this structure.

03

Composite indexes & column order

Most real queries filter on more than one column. A composite index (one index on several columns) is the tool for that — but column order decides which queries it can serve. Get the order wrong and the index is dead weight.

Composite index

A single index built on two or more columns, e.g. CREATE INDEX ON players (team, position, goals). Entries are sorted by the first column; rows tied on the first are sorted by the second; ties on the second by the third — like words in a dictionary sorted letter by letter.

⚽ The worked example: (team, position, goals)

The match-analysis app runs these queries all day:

Q1: SELECT * FROM players WHERE team = 'Arsenal';
Q2: SELECT * FROM players WHERE team = 'Arsenal' AND position = 'FW';
Q3: SELECT * FROM players WHERE team = 'Arsenal' AND position = 'FW' AND goals > 20;
Q4: SELECT * FROM players WHERE position = 'FW';
Q5: SELECT * FROM players WHERE goals > 20;

An index on (team, position, goals) sorts all 50,000 entries: first by team, then within each team by position, then within each team+position by goals. Picture the sorted list:

Arsenal   | FW |  8   → row…
Arsenal   | FW | 21   → row…
Arsenal   | FW | 27   → row…
Arsenal   | MF |  3   → row…
…
Chelsea   | FW | 19   → row…
Leftmost-prefix rule

A composite index (a, b, c) can serve any query that filters on a leftmost prefix of its columns: a alone, a + b, or a + b + c. It cannot efficiently serve queries on b alone, c alone, or b + c — because entries are only sorted by b within each value of a.

Against our five queries:

  • Q1 (team) ✅ — team is the leftmost column; binary-search straight to the Arsenal block.
  • Q2 (team + position) ✅ — full prefix; jumps to the Arsenal/FW block.
  • Q3 (team + position + goals) ✅ — the whole key; lands exactly on Arsenal forwards with 20+ goals.
  • Q4 (position alone) ❌ — "FW" entries are scattered: one FW block per team. The index can't jump to "all FWs" because it's sorted by team first. (MySQL/Postgres might still scan the whole index if that's cheaper than the heap — but it's no better than a scan.)
  • Q5 (goals alone) ❌ — same problem, worse: goals is only sorted within each team+position group.

The phone-book intuition: a phone book sorted by (last name, first name) finds "all Smiths" instantly and "John Smith" instantly — but "everyone named John" still requires reading the whole book. Last name is the leftmost prefix; first name alone is not.

Which column goes first? Selectivity and the equality rule

Cardinality & selectivity

Cardinality = the number of distinct values a column has. player_id has cardinality 50,000 (every row distinct); position has cardinality ~4 (GK, DF, MF, FW). Selectivity = how much a filter narrows the search: the fraction of rows a condition matches. team = 'Arsenal' matches ~1,000 of 50,000 rows (selectivity 2%) — highly selective. position = 'MF' matches ~20,000 rows (40%) — barely selective.

The rule of thumb for ordering a composite index:

  1. Equality columns first, range columns last. In Q3, team = and position = are equality conditions, goals > 20 is a range. The index can only use columns up to the first range condition for seeking — after the range on goals, deeper columns (if any) would only filter, not seek. So ranges go last.
  2. Among equality columns, most selective first — the column that eliminates the most rows narrows the search fastest. team (2% of rows) before position (25% of rows).

This is a rule of thumb, not physics: if Q4 (position alone) were the app's hottest query, you'd build a separate index on (position) — or reconsider the composite as (position, team, goals). Index design starts from the query workload, not the table.

Index intersection vs. one good composite

Index intersection

When a query filters on columns covered by separate indexes, the database can scan each index, collect matching row pointers, and intersect the sets (often as bitmaps) before touching the heap. It works — but it's plan B.

For Q2, intersecting an index on (team) with one on (position) requires two index traversals plus a bitmap AND. One composite on (team, position) needs one traversal and lands directly on the matching block. Intersection is a fine fallback the planner finds on its own; a composite is what you design deliberately for a known hot query.

The trap: indexing for Q5 with the composite. A junior move is creating (team, position, goals) and assuming "goals is in the index, so WHERE goals > 20 is covered." It isn't — the leftmost-prefix rule kills it. If "top scorers across all teams" is a real query pattern, it needs its own index on (goals). Always test an index against each query you expect it to serve, left to right.

04

Covering indexes & index-only scans

The most expensive step in an indexed lookup is usually not the index traversal — it's the heap fetch: jumping from the index to random pages of the table to read full rows. A covering index removes that step entirely.

Covering index & index-only scan

An index covers a query when it contains every column the query needs — in its key or in INCLUDEd payload columns. The database then performs an index-only scan: it answers the query from the index pages alone and never touches the heap.

⚽ The worked example: the top-scorers leaderboard

The app's most-hit query powers a leaderboard widget:

SELECT name, team, goals
FROM players
WHERE goals > 20
ORDER BY goals DESC;

An index on (goals) finds the right entries fast — but then must fetch each player's name and team from the heap: dozens of random page reads for what is logically a tiny answer. The index locates but doesn't answer.

Now create the index as:

CREATE INDEX ON players (goals) INCLUDE (name, team);
INCLUDE columns

Extra columns stored in the index's leaf pages only — they are not part of the sort key, so they don't affect ordering or seek behavior; they just ride along as payload. (PostgreSQL syntax; MySQL achieves the same by adding columns to the key, at the cost of a wider sort key.)

Now the leaf entry for a 27-goal striker holds (27, "Erling Haaland", "Man City", → row pointer). The query walks the sorted leaf pages, reads name/team/goals directly, and never visits the heap. This is an index-only scan, and it's typically several times faster than the same query with heap fetches — because index leaf pages are narrow (few columns), they pack far more entries per page, so the whole answer may fit in a handful of pages.

Why index-only scans are so much faster: the math of page density

A heap page holds ~100 full rows (all 7 columns). An index leaf page for (goals) INCLUDE (name, team) holds ~500 narrow entries. To list 400 top scorers: the heap version touches ~400 scattered rows across maybe 300+ pages; the covering version reads one or two dense leaf pages. Same answer, two orders of magnitude less I/O. Covering indexes win by making the data the query needs physically denser.

The visibility-map caveat (PostgreSQL)

Postgres still needs to confirm each row is visible to your transaction (not deleted by a concurrent one). It checks a small visibility map — one bit per heap page. If the map says "all rows on this heap page are visible," no heap visit is needed and the scan is truly index-only. If recent writes left the map stale, Postgres falls back to heap fetches for those pages. In practice: index-only scans shine on read-mostly tables (the map stays clean) and degrade gracefully on write-heavy ones. MySQL/InnoDB has no such map — its covering scans are index-only unconditionally.

Don't INCLUDE the kitchen sink. Every INCLUDEd column widens every leaf entry, lowering page density and making the index bigger, slower to scan, and more expensive to maintain. Cover the columns your hottest queries select — typically 1–3 — not all seven. A covering index is a precision tool, not a second copy of the table.

05

The write cost of indexes

Indexes are not free. Every index on a table is a second structure that must be kept in sync on every write — and that tax compounds with each index you add. Senior engineers design indexes with the write path in mind, not just the read path.

Write amplification

One logical write turning into multiple physical writes. Inserting one player row with 5 indexes means: 1 heap write + 5 index writes (each an O(log n) traversal, possibly with a page split) = 6 physical writes for 1 logical insert. The amplification factor ≈ 1 + (number of indexes).

What each write type costs

  • INSERT: the new row goes to the heap, and every index gets a new entry — each an O(log n) descent plus possible page splits. ⚽ Every new signing is filed into the heap and into the alphabetical list, the goals-sorted list, the team list…
  • UPDATE of an indexed column: the old entry must be removed and the new one inserted (the key moved in sort order) — roughly double the cost of an insert into that index. ⚽ A player transfers from Arsenal to Chelsea: the (team, …) index entries are deleted under "Arsenal" and re-inserted under "Chelsea."
  • UPDATE of a non-indexed column: heap only — the indexes don't care. (Postgres can even do this as a HOT update — Heap-Only Tuple — reusing the same page without touching any index at all.)
  • DELETE: the heap row is marked dead and every index entry is removed.

The practical rule: a table with N indexes pays roughly N index-maintenance operations per write. A scouting table that ingests 10,000 new player reports a day with 8 indexes performs ~90,000 index writes for those 10,000 inserts. That is why write-heavy tables (event logs, clickstreams) carry few or no secondary indexes.

Fragmentation, bloat, and maintenance

Fragmentation / bloat

Over time, page splits leave index pages half empty, and updates/deletes leave dead entries behind. The index grows physically larger than the live data it holds — this wasted space is bloat. A bloated index reads more pages per lookup and fits less of itself in RAM.

How databases fight it:

  • Autovacuum (PostgreSQL): a background process that reclaims dead heap rows and dead index entries, and refreshes the visibility map (which keeps index-only scans fast). It runs automatically — but on very write-heavy tables it can fall behind, and DBAs tune it to be more aggressive.
  • REINDEX / index rebuild: rewriting an index from scratch into compact, dense pages. The heavy hammer for severe bloat — in Postgres 12+, REINDEX CONCURRENTLY does it without locking out writes.
  • Fillfactor: deliberately leaving free space (e.g. 85% full) in each page at build time, so future inserts and updates land in existing pages instead of triggering splits. A tuning knob for write-heavy indexes.
  • MySQL/InnoDB: merges half-empty pages automatically during operation and offers OPTIMIZE TABLE (rebuild) for the rest.

⚽ The match-program analogy, continued

The club's printed program has three indexes: alphabetical, by team, by goals. After the January transfer window — 40 signings, 25 departures, a dozen renames — someone has to re-typeset all three lists (write amplification), the lists are now printed with gaps and crossed-out names (bloat), and eventually the club reprints a clean edition (REINDEX). Nobody questions that the program needs its indexes — the readers (queries) far outnumber the editors (writes). But a program reprinted daily would spend more effort on its indexes than on its content. That is the write-heavy table with too many indexes.

The index-budget rule

Every index must earn its keep in reads. Before adding one, ask: (1) Is there a real, frequent query this serves? (2) Does the table's write volume make the maintenance tax painful? (3) Would a composite or covering index serve two queries with one structure? Indexes you can't justify against the workload are not "harmless extras" — they are a permanent tax on every write and disk space you'll never get back.

06

LSM trees: the write-optimized rival

B-trees are read-optimized: they update data in place, keeping lookups at O(log n) — but every write is a random page touch plus possible splits. LSM trees (Log-Structured Merge trees) flip the priority: they make writes blazingly fast by never updating in place, at the cost of slower, more complex reads. If the workload is write-heavy, this is the structure senior engineers reach for.

LSM tree (Log-Structured Merge tree)

A storage structure that buffers writes in memory and periodically flushes them to disk as immutable, sorted files, merging those files in the background. Writes are sequential appends (fast); reads may need to check several files (slower). Used by Cassandra, RocksDB, LevelDB, and Bigtable-derived systems.

How it works: three moving parts

Memtable

An in-memory sorted structure (usually a skip list) that absorbs all writes. Inserts, updates, and deletes all land here first — in RAM, at memory speed. Every write is also appended to a write-ahead log on disk first, so nothing is lost if the machine crashes before the flush.

SSTable (Sorted String Table)

When the memtable fills up, it is flushed to disk as one immutable, sorted file — an SSTable — and a fresh empty memtable takes over. Immutability is the key trick: because files are never modified in place, writing one is a pure sequential write, the fastest thing a disk does. Over time, many SSTables accumulate, each holding a newer-or-older slice of the data.

Compaction

A background merge of SSTables: it reads several overlapping files, merges their sorted contents (newer values win, deleted keys are dropped), and writes out fewer, larger, cleaner files. Compaction is what keeps read costs bounded — without it, reads would check an ever-growing pile of files.

⚽ Reading a player's record in an LSM world

The scouts' app now logs every touch of every match — millions of events per day — into a Cassandra-style store. To read "Haaland's latest stats", the database must check: the memtable first, then SSTables from newest to oldest, stopping at the first file that has the key. If Haaland's record was updated yesterday and again today, both copies exist; the newest wins.

To avoid opening files that can't possibly contain the key, each SSTable carries a Bloom filter — a tiny probabilistic structure that answers "definitely not here" or "maybe here" in a few bytes. Bloom filters make the multi-file check affordable — but the read still touches more structures than a B-tree's single root-to-leaf descent.

The trade-off, precisely: write amplification vs. read amplification

Read amplification

One logical read turning into multiple physical reads — the read-side mirror of write amplification. In an LSM tree, a single key lookup may check the memtable plus several SSTables: 1 logical read → several physical reads.

Here's the fundamental tension, stated once and remembered forever:

  • B-tree: writes update in place → high write amplification (random page writes, splits, one per index) — but reads are surgical: low read amplification (one root-to-leaf path).
  • LSM tree: writes are sequential appends → low write amplification (memory-speed ingest) — but reads fan out across files: high read amplification (memtable + several SSTables + compaction I/O in the background).

⚽ Back to the club: the scouting report database (analysts querying player histories all day, moderate writes) wants a B-tree — reads dominate. The match event stream (every pass, tackle, and sprint logged live, written far more than read) wants an LSM tree — writes dominate. The workload picks the structure.

Why this matters even if you only use Postgres

Two reasons. First, modern architectures mix both: Postgres (B-tree) for the transactional core, Cassandra or a Kafka-backed store (LSM) for the event firehose — and design discussions expect you to place each workload on the right side. Second, the amplification vocabulary — write amplification vs. read amplification — is how senior engineers compare any storage choice. Saying "I'd take the LSM here because the workload is 100:1 writes-to-reads, and I accept the read amplification" is a complete, defensible design sentence.

08

Interview Q&A — with full model answers

Tap a question to reveal a complete model answer — structured verdict-first, then reasoning, then a real-system reference. Each is written to be spoken aloud in about a minute.

Q1 · THE 60-SECOND ANSWER
What is a database index, and when would you add one?
The opener. They want the crisp definition plus evidence you think about cost, not just speed.
Reveal model answer
Verdict

"An index is a separate, sorted data structure that maps column values to row locations, so the database can find matching rows without scanning the whole table. I'd add one when a frequent, selective read is doing full table scans — and I'd weigh it against the write tax."

Reasoning

"Without an index, a lookup is a full table scan: O(n), every row checked. With a B-tree index, the database binary-searches sorted pages — O(log n) — and because each level multiplies capacity by the fanout, even a 100M-row table needs only 3 levels: 3–4 page reads instead of a million. That's the core win.

But every index is maintained on every write — an insert with 5 indexes is roughly 6 physical writes — plus disk space and planner overhead. So I add indexes driven by the query workload: columns in WHERE, JOIN, and ORDER BY clauses of hot queries, starting with the most selective equality columns. On a write-heavy table like an event log, I'd think twice or skip secondary indexes entirely."

Real-system reference

"In PostgreSQL I'd verify with EXPLAIN ANALYZE — looking for an Index Scan or Index Only Scan replacing a Seq Scan — and I'd check pg_stat_user_indexes to confirm the index is actually being used before keeping it. In MySQL the same check is EXPLAIN showing type: ref/range instead of ALL."

Q2 · DIAGNOSIS
You created an index on (team, position), but a query filtering only on position still does a full table scan. Why?
They're testing the leftmost-prefix rule — and whether you can enumerate the other reasons an index gets ignored.
Reveal model answer
Verdict

"The leftmost-prefix rule: the index is sorted by team first, so entries for one position are scattered across every team's block — the index can't jump to 'all forwards' any faster than scanning. But I'd also check three other suspects before concluding."

Reasoning

"First, the rule itself: a composite (team, position) serves team, or team + position — never position alone. It's the phone-book problem: sorted by last name, you can't efficiently find everyone named John. The fix, if that query is hot, is a separate index on (position) — or reordering the composite if the workload justifies it.

Second, selectivity: if position = 'MF' matches 40% of the table, the planner may correctly choose a sequential scan — random index+heap hops for 20,000 rows cost more than one sequential pass. An unused index isn't always a bug; sometimes the planner is right.

Third, query-shape killers: a function on the column (WHERE LOWER(position) = 'fw'), a leading-wildcard LIKE ('%FW'), or a type mismatch (position = 7 on a text column, forcing a cast) all defeat the index even when the column order is fine."

Real-system reference

"In PostgreSQL, EXPLAIN tells the story: I'd look for Seq Scan with a Filter and check the row-count estimate. For the function-on-column case, the fix is an expression index — CREATE INDEX ON players (LOWER(position)) — which indexes the transformed value directly. In MySQL, I'd check EXPLAIN output for possible_keys vs key to see whether the optimizer even considered it."

Q3 · JUDGMENT
When would you deliberately avoid adding an index?
The flip side of Q1. They want to hear that you treat indexes as a budget with a write-side cost.
Reveal model answer
Verdict

"Whenever the write tax exceeds the read benefit: write-heavy tables, low-selectivity columns, tiny tables, and indexes nobody's queries actually use."

Reasoning

"Four concrete cases. One: write-heavy tables. An event-ingest table doing 50K inserts/sec with 6 indexes pays ~350K index writes/sec — the indexes can become the bottleneck. I'd keep maybe the primary key and nothing else. Two: low-selectivity columns — an index on a boolean is_active that's 95% true rarely beats a scan, because the planner still has to fetch nearly every heap row. Three: small tables — a 500-row lookup table fits in a page or two; the index adds planning overhead for zero measurable gain. Four: speculative indexes — 'we might query by this someday' is how tables end up with 12 indexes slowing every deploy's migration.

The discipline is: every index must be traceable to a real query in the workload, and I re-audit periodically — an index with zero scans in pg_stat_user_indexes over a representative window is a candidate for removal."

Real-system reference

"PostgreSQL's pg_stat_user_indexes.idx_scan is the source of truth here — zero scans means zero reads served. MySQL's performance_schema.table_io_waits_summary_by_index_usage gives the same signal. Dropping a dead index is one of the cheapest performance wins: it speeds up every future write with zero read cost."

Q4 · ARCHITECTURE
B-tree or LSM tree — how do you choose?
They're checking you know the write-optimized alternative and can place a workload on the right side.
Reveal model answer
Verdict

"B-tree for read-heavy transactional workloads, LSM for write-heavy ingest. It's a trade-off between write amplification and read amplification, and the workload's read/write ratio decides."

Reasoning

"A B-tree updates in place: every write is a random page touch plus splits across each index — high write amplification — but reads are surgical, one root-to-leaf descent, O(log n) pages. An LSM tree buffers writes in an in-memory memtable and flushes them as immutable sorted SSTables — writes are sequential appends at memory speed, so write amplification is low — but a read may check the memtable plus several SSTables, so read amplification is higher, with background compaction merging files to keep it bounded.

So: the club's scouting database — analysts querying player histories all day, moderate writes — is a B-tree workload. The live match-event stream — millions of touch events written per match, rarely re-read individually — is an LSM workload. If someone proposes Cassandra for a read-heavy OLTP app, I'd push back on the read amplification; if they propose Postgres for a 100K-events/sec firehose, I'd push back on the write amplification."

Real-system reference

"PostgreSQL and MySQL/InnoDB are B-tree systems — their default indexes are B-trees. Cassandra, ScyllaDB, RocksDB, and LevelDB are LSM-based. In practice most architectures use both: Postgres for the transactional core, an LSM store for the event stream — and the design discussion is about placing each workload correctly, not picking a universal winner."

Practice drills

Untimed — think like you're whiteboarding. Write your answer, then check the rubric.

Drill 1 — Design the scouting app's indexes

The players table (50,000 rows) serves three hot queries:
(a) WHERE team = ? AND position = ? — the lineup builder, 10K/day.
(b) WHERE goals > ? ORDER BY goals DESC — the top-scorers leaderboard, 50K/day, selecting only name, team, goals.
(c) WHERE player_id = ? — the player profile page, 100K/day.
Propose the index set. For each index, state the columns, the order, and one line of justification.

Reveal rubric
  • (c) — primary key / unique index on (player_id). Equality on a unique key: one root-to-leaf descent, one row. (Full marks for noting this likely already exists as the PK — don't create a duplicate.)
  • (a) — composite (team, position). Both are equality columns; team first as the more selective one. Serves the exact leftmost prefix. (Full marks for the selectivity ordering argument.)
  • (b) — covering index (goals) INCLUDE (name, team). Range on goals goes last (only key column); name, team ride along so the leaderboard never touches the heap — an index-only scan. (Full marks for INCLUDE rather than widening the key, and for naming "index-only scan.")

What earns top marks: exactly three indexes (no speculative extras), the leftmost-prefix check against each query, and the observation that (b)'s index also serves "goals > ?" count queries. Deductions for proposing (position, team) without a selectivity argument, or for covering all 7 columns.

Drill 2 — The index that gets ignored

There's an index on (team). EXPLAIN shows a sequential scan for SELECT * FROM players WHERE team = 'Arsenal'. List three distinct hypotheses for why the planner ignored the index, and how you'd confirm each.

Reveal rubric
  • Hypothesis 1 — low selectivity / stale statistics. If 'Arsenal' matches a large share of rows (or the planner thinks it does because stats are stale), a scan is genuinely cheaper. Confirm: check the estimated vs. actual row counts in EXPLAIN ANALYZE; run ANALYZE players and re-check.
  • Hypothesis 2 — small table / everything cached. On a tiny table the index saves nothing. Confirm: check table size (pg_relation_size); on 50K rows this shouldn't apply, which is itself diagnostic.
  • Hypothesis 3 — the query defeats the index shape. A function or cast on the column (WHERE LOWER(team) = 'arsenal'), or an implicit type mismatch, makes the index unusable. Confirm: inspect the exact predicate in EXPLAIN output for casts/functions; fix with an expression index or a corrected predicate.

What earns top marks: three mechanistically different hypotheses (not three wordings of "the index is bad"), each paired with a concrete confirmation step. Bonus for mentioning that the planner being right (hypothesis 1) is a valid outcome, not a failure.

Drill 3 — Size the tree

A B-tree index has ~500 entries per page. A table grows from 1 million rows to 1 billion rows (1000×). How many page reads does a single-key lookup need before and after? What does that tell you about index scalability?

Reveal rubric

Before: 500² = 250K < 1M < 500³ = 125M → 3 levels → 3 index page reads (+1 heap fetch). After: 500³ = 125M < 1B < 500⁴ → 4 levels → 4 index page reads (+1 heap fetch).

The lesson: a 1000× growth in data added exactly one page read. That's O(log n) in action — index lookup cost is effectively flat across any realistic scale, which is why "will the index still work at 10× the data?" is almost always answered yes, and why B-trees survived five decades of database evolution.

What earns top marks: showing the fanout-power arithmetic (not just "3 and 4"), including the +1 heap fetch, and stating the general principle rather than just the two numbers.

✓

Cheat sheet: the 6 index-design decisions

Every index design is these six decisions, in this order. Tape this to your mental whiteboard.

1. Which queries? Start from the workload, not the table. Index the columns in WHERE, JOIN … ON, and ORDER BY of your hottest, slowest queries — verified with EXPLAIN, not guessed.

2. One composite or several singles? Multi-column filters get one composite (index intersection is plan B). Single-column filters get single-column indexes.

3. What column order? Equality columns first (most selective first), range columns last — and check every query against the leftmost-prefix rule before shipping.

4. Should it cover? If a hot query selects few columns, INCLUDE them and get an index-only scan — but don't INCLUDE the kitchen sink; density is the whole win.

5. Can the table afford it? Each index taxes every write (write amplification ≈ 1 + index count). Write-heavy tables get few indexes; every index must be traceable to a real query; drop what pg_stat_user_indexes shows is never scanned.

6. B-tree or LSM? Read-heavy transactional data → B-tree (surgical reads). Write-heavy ingest → LSM (sequential writes, pay read amplification). Most architectures use both, placed per workload.
