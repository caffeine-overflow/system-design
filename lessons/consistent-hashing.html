Lesson 10 · Core building blocks

Consistent Hashing

Every growing system eventually adds or removes a server. The naive way to spread data across servers reshuffles almost everything each time that happens. Consistent hashing is the trick that makes scaling almost free: add a machine, and only about one machine's worth of data moves. This lesson covers how the ring works, why virtual nodes fix its skew, and how Dynamo, Cassandra, and every serious cache use it.

01

What is consistent hashing?

Start with the pain. You've got 3 cache servers and a million user sessions to spread across them. The obvious answer creates a hidden trap — one that only springs when your system is already under stress.

The naive way (and its trap)

The first thing everyone reaches for: hash the key, then take the remainder after dividing by the number of servers.

server = hash(key) mod N

With 3 servers, a session whose hash is 842 lands on server 842 mod 3 = 2. Simple, deterministic, even spread. What's not to like?

Now it's Black Friday, server 2 is melting, and you add a 4th server. Same key: 842 mod 4 = 0 — it now belongs to server 0. Nothing about the key changed; only N changed. And N is in every single lookup, so when N changes, the mapping of nearly every key changes with it.

The remap problem

With hash(key) mod N, adding one server moves roughly N / (N+1) of your keys — with 3 servers going to 4, about 75% of everything relocates. Your caches go cold all at once, your database takes the full hit it was being shielded from, and the scaling operation meant to relieve pressure causes the worst spike of the day.

⚽ Running example: match-day entry

The stadium concourse

Picture a stadium with a circular concourse — a ring you can walk all the way around. There are entry gates spaced along it: Gate A, Gate B, Gate C. Every fan has a ticket number. The rule: walk clockwise from the main entrance until you reach the first gate — that's your gate.

Now the club opens a new Gate D between A and B. Which fans get rerouted? Only the fans whose clockwise walk previously passed through D's position to reach B — the fans standing between A's gate and D's gate. Everyone else keeps walking to exactly the same gate as before.

That is consistent hashing. The concourse is the hash ring, the gates are servers, the fans are keys, and "first gate clockwise" is the lookup rule. Opening or closing a gate disturbs only its neighbours.

Consistent hashing

A way to assign keys to servers such that adding or removing a server moves only about 1/n of the keys (where n is the number of servers), instead of nearly all of them. It does this by hashing keys and servers onto the same circle — the hash ring — and giving each key to the first server clockwise from it.

Why "consistent"?

Not consistent as in the CAP theorem's consistency (Lesson 7) — nothing about data agreement here. "Consistent" means the mapping stays consistent: keys keep mapping to the same servers even as servers come and go. Different word, different meaning, same industry. Interviewers love watching candidates untangle the two.

02

How the ring works

Four mechanics, each simple, and together they make scaling nearly free: a shared circle, both sides hashed onto it, clockwise ownership, and neighbour-only disturbance.

The hash space, bent into a circle

A hash function (a deterministic function that turns any string into a big number — MD5, SHA-1, and murmur3 are common) produces values in some fixed range, say 0 to 2³² − 1. Take that number line and bend it so the biggest number touches zero again. That's the ring: a clock face with 4 billion positions instead of 12.

The two rules:

  1. Hash every server onto the ring. Gate A sits at hash("server-A"), Gate B at hash("server-B"), and so on. Servers get random-looking positions because the hash scrambles their names.
  2. Hash every key onto the ring, then walk clockwise. A key's owner is the first server you meet walking clockwise from the key's position. Each server owns the arc of the ring from the previous server's position up to its own.

A worked example (small numbers, same mechanics)

Real rings use 2³² positions; for readability, imagine a ring of positions 0–99. Three gates hash to: A → 20, B → 55, C → 90.

  • Key user:7 hashes to 10 → walk clockwise → first gate is A at 20. Owner: A.
  • Key user:12 hashes to 30 → clockwise → B at 55. Owner: B.
  • Key user:31 hashes to 60 → clockwise → C at 90. Owner: C.
  • Key user:44 hashes to 95 → clockwise → wraps past 99 to 0 → A at 20. Owner: A. (The ring wraps; positions after the last gate belong to the first gate.)

So A's arc is (90, 20] wrapping around — positions 91–99 and 0–20. B owns (20, 55]. C owns (55, 90].

Adding a server: only one arc splits

Open a new gate D at 40. It lands inside B's arc. D now owns (20, 40], and B keeps (40, 55]. Which keys move? Only the keys sitting between 20 and 40 — previously B's, now D's. Keys at 10, 60, 95 don't even notice.

In general, a new server steals exactly one arc from its clockwise neighbour. With n servers sharing the ring, each owns ~1/n of it, so an addition moves ~1/n of the keys. Four servers → roughly a quarter of keys move. Compare that to the naive 75%.

Removing a server: its arc slides to the neighbour

Gate B fails at 3am. Its arc (40, 55] doesn't vanish — the keys in it now walk clockwise past B's empty spot to the next gate, D… wait, no: clockwise from 40–55, the first live gate is now C at 90 (B's own position is gone). So B's keys slide to C, the next clockwise neighbour. Every other key's walk is unchanged. Then you bring up a replacement, it rejoins at its hashed position, and takes its arc back.

The one-sentence mechanics: keys never point at server number anything — they point at positions on a circle, and servers stand on that circle too. Adding or removing a server only reassigns the arcs touching it. That's the whole trick, and everything else in this lesson is refinement.

03

Why it beats naive sharding

In the sharding lesson (Lesson 6), consistent hashing appeared as one of four sharding strategies. Here's the head-to-head that shows why it's the default choice whenever the set of machines changes over time.

hash(key) mod NConsistent hashingRange sharding
Adding a server moves… ~N/(N+1) of keys (75% when going 3→4) ~1/n of keys (25% when going 3→4) Half of one shard's range
Who moves? Keys everywhere, unpredictably Only keys in the new server's arc Keys in the split range
Range queries ("all users 800–900") Scattered across servers Scattered across servers (hashing destroys order) Contained — ranges stay together
Skew risk Low (mod spreads evenly) Real — random arcs vary (fixed by virtual nodes, §04) Real — hot ranges (needs splitting)
Needs a lookup directory? No No — any client can compute the ring itself Yes — a router must know the ranges

The interview one-liner

"Mod-N sharding is simple but every membership change reshuffles the deck. Consistent hashing keeps the reshuffle local — about one server's worth of data moves per server added or removed — and any client can compute placement itself with no central router. The price is losing key order, so it's for point lookups, not range scans."

04

The skew problem: virtual nodes

The ring has one genuine flaw, and it's the first thing a good interviewer will poke at. Random positions mean random arc sizes — and random arc sizes mean unfair workloads.

Random arcs are unfair arcs

Back to our stadium: gates hash to 20, 22, and 90. Gate B (at 22) owns the arc (20, 22] — a sliver. Gate C (at 90) owns (22, 90] — 68% of the whole ring. Gate C's staff handle two-thirds of the fans while Gate B's staff nap.

This isn't a freak accident; it's the mathematics of random points on a circle. With n random gates, arc sizes average 1/n of the ring but vary wildly — the spread (standard deviation) is nearly as big as the average itself. In practice, the busiest server routinely carries multiples of the average load. Throwing more servers at it doesn't fix it; each new gate is just another random dice roll.

Load skew

When random ring positions give some servers much larger arcs than others, so a few servers do most of the work while the rest idle. The fix is not better randomness — it's more points per server.

Virtual nodes: many small arcs instead of one big one

Instead of placing each physical server on the ring once, place it many times — say 100 or 200 positions. Each of these positions is a virtual node (or vnode): a fake extra copy of the server that owns its own small arc, and forwards to the real machine behind it.

⚽ The stadium, fixed

Turnstiles, not gates

Instead of one big Gate C, the club installs turnstiles all around the concourse — 100 little entry points, each painted in its gate's colour. A fan still walks clockwise to the first turnstile, then gets directed to that turnstile's gate. Gate C's turnstiles are scattered everywhere, so its fans come from a hundred small slices of the ring instead of one giant arc. Some slices are bigger, some smaller — but with a hundred slices, the big and small average out, and every gate ends up with close to its fair third.

The math behind the intuition: one server's total share is now the sum of 100 random arcs. Sums of many random pieces cluster tightly around the average — that's the law of large numbers doing your load balancing for you. With enough vnodes, every server's load hugs the mean, and the worst-loaded server is barely above average.

How many vnodes?

More vnodes = fairer split, but each vnode is bookkeeping (the ring holds n × vnodes points). The industry settled on hundreds per server: Amazon's Dynamo used on the order of a hundred-plus vnodes per node, Cassandra defaults to 256 tokens (its word for vnodes) per node, and the memcached consistent-hash library ketama uses 160. You don't tune this by hand — you pick a big number and move on.

The bonus superpower: unequal machines

Here's the move that turns vnodes from a fix into a feature. Vnode counts don't have to be equal. Got a beefy new server with twice the RAM? Give it twice the vnodes. Its arcs cover twice the ring, so it naturally receives twice the keys. This is weighted placement, and it falls out of vnodes for free — no special-casing, no capacity planner spreadsheet.

In our stadium: the new north stand has wider turnstiles and double the staff, so it gets 200 turnstiles while the old gates keep 100. Fans distribute proportionally, automatically.

What vnodes don't fix: they balance how many keys each server owns, not how hot those keys are. If one key gets a million hits a second, its whole server still melts — vnodes can't split a single key. That's the hot key problem, and it gets its own section in the traps below (§07).

05

Replication on the ring

So far every key lives on exactly one server. That's fine for a cache (a miss just refetches), but for a database, one dead server means lost data. The ring handles replication with the same clockwise trick.

The preference list

Instead of one owner, give each key a preference list: the first R servers clockwise from the key's position. With R = 3, every key is stored on its owner plus the next two clockwise neighbours.

  • If the owner dies, the next server on the list already has the data — it promotes itself to serve those keys. No copying needed at failover time.
  • Reads and writes can use quorums over the preference list — the W + R > N rule from the CAP lesson (Lesson 7) — to stay available during failures. This is exactly how Amazon's Dynamo combined the ring with quorum replication to build an always-writable store.
  • When the dead server returns, it asks its neighbours for the keys it missed — via anti-entropy (a background process where replicas compare their data and sync up differences) and hinted handoff (neighbours temporarily hold writes destined for the dead node, then hand them over when it returns).
Replication factor

The number of copies of each key, usually written as R (Dynamo) or RF (Cassandra). Higher R = survives more simultaneous failures, but every write costs R copies of work and storage. The ring makes placement of all R copies a one-line rule: "the next R servers clockwise."

Notice the elegance: membership change, failure handling, and replica placement are all the same clockwise walk. One mental model covers the whole system.

06

Where it's used in the real world

This isn't textbook theory — the ring is load-bearing infrastructure at massive scale. Name-dropping these correctly signals senior depth.

  • Amazon Dynamo (2007) — the paper that popularised the ring. Consistent hashing + virtual nodes + preference-list replication + quorum reads/writes. The blueprint for an entire generation of stores.
  • Apache Cassandra — a Dynamo descendant. The ring is divided into token ranges; vnodes are called tokens (256 per node by default). Same clockwise ownership, same neighbour failover.
  • DynamoDB — AWS's managed descendant of the same lineage; partitions are placed on a hash ring under the hood.
  • Memcached clients (ketama) — memcached servers don't coordinate with each other, so the client library builds the ring (160 vnodes per server) and picks which server to ask. Same idea, pushed to the client.
  • CDNs — consistent-hash routing sends the same URL to the same edge cache, keeping hit rates high as edge nodes are added and removed.
  • Load balancers (Google's Maglev) — a variant of the ring (a lookup table rebuilt on membership change) keeps connections pinned to backends with minimal disruption.
  • Peer-to-peer systems (Chord, Kademlia) — the ring idea extended so nodes themselves route lookups around the circle with no central directory. BitTorrent's DHT works this way.

The pattern to recognise

Whenever an interviewer says "nodes join and leave" and "minimal data movement," the answer they're fishing for is the ring. Caches, key-value stores, CDN routing, distributed rate limiters — anywhere placement must survive membership churn, consistent hashing is the default first answer.

07

Senior-depth traps

Saying "consistent hashing" in a design discussion is table stakes. Surviving the follow-ups is what separates the senior answer. These are the six follow-ups that actually get asked.

1. Hot keys: the ring balances counts, not heat

Vnodes guarantee every server owns a fair number of keys. They say nothing about request rates. If one key — a celebrity's profile, the World Cup final's live score — gets 100k reads/sec, its owning server melts while the ring looks perfectly balanced. This is the hot key (or celebrity) problem.

Fixes, in order of preference: cache the hot key at the client or a fronting cache layer so most reads never reach the ring; split the key (write to score:1 … score:10, read a random one and merge — the same salting trick from the sharding lesson); or replicate the hot key to several servers deliberately. The ring can't do this for you — you detect and handle it above the ring.

2. Range queries die on the ring

Hashing destroys order: user:800 and user:801 land on opposite sides of the circle. "Give me users 800–900" becomes a scatter-gather across every server. If the workload needs range scans, the ring is the wrong tool — you want range sharding (Lesson 6), or a secondary index alongside the ring. Real systems often run both: ring for point lookups, an ordered structure for scans.

3. Who maintains the ring? Membership is a protocol, not magic

The ring tells you where data should go, but every server must agree on who's on the ring right now. Dynamo and Cassandra use gossip: servers periodically swap membership lists with random peers, so news of a dead or new node spreads epidemically in seconds. Gossip is eventually consistent — two servers can briefly disagree about the ring, which is why writes go to a preference list with quorums rather than trusting one owner's view. Alternative: a control plane (like a load balancer's) pushes the authoritative ring to everyone.

Interview trap: "You add a server while another is down — what breaks?" During the churn, different servers hold different rings, so a key's preference list differs depending on who you ask. Quorum writes plus read-repair (fixing a stale replica when a read notices it disagrees with the others) paper over this, but there's a window of extra work and possible conflicts. The disciplined answer: membership changes are operations with a blast radius — drain, add, and verify one node at a time.

4. The hash function is load-bearing

Everything assumes the hash uniformly scatters inputs around the ring. A weak hash clusters points, recreates the skew vnodes were meant to fix, and can even be attacked (hash-flooding DoS). Production rings use well-studied non-cryptographic hashes like murmur3 or xxHash (fast, uniform), or MD5/SHA-1 in older systems. "Just use a good hash" is a legitimate line in a design discussion — and interviewers accept it if you can say why uniformity matters.

5. Consistent hashing doesn't elect leaders

The ring answers placement: which servers hold this key. It does not answer coordination: who is the leader, who commits a transaction, who owns a lock. If your design needs a single decider, you still need consensus (Raft/Paxos) for that role — the ring and consensus solve different problems and routinely appear in the same architecture (e.g., a Raft group per shard, shards placed by a ring).

6. Graceful removal beats abrupt removal

Yanking a server moves its arc instantly to the neighbour — a sudden load spike on exactly one machine. The mature approach: mark the node leaving, let it keep serving reads while the neighbour warms its copies, then decommission. Same destination, controlled ramp. In the stadium: you don't lock a gate mid-rush; you stop sending new fans to it and let the queue drain.

09

Interview questions with full model answers

Read the question, answer it out loud in your own words, then check against the model. The model answers are deliberately complete — borrow their structure, not their script.

Q1
Design a distributed cache. A server dies at peak traffic — walk me through exactly what happens.
Tests whether you can operate the ring under failure, not just describe it.
Model answer

"I'd place cache servers on a consistent hash ring with virtual nodes — say 160 vnodes per server, ketama-style — so keys map to servers by clockwise ownership and the client library can compute placement with no router. Each key's value is also held by the next two clockwise servers as a preference list, giving replication factor 3.

When a server dies: first, membership. Servers gossip heartbeats, so within seconds everyone marks it down and rebuilds the ring without it. Its arcs now belong to the next clockwise vnodes — spread across many physical servers thanks to the vnodes, so no single survivor takes the whole hit.

Second, data. Keys it owned are already on the two replicas, which promote themselves — reads keep serving immediately, no re-copy needed. New writes go to the surviving preference-list members, and the replicas hold hinted handoffs — writes destined for the dead node — to replay when it returns.

Third, the cold-start spike: the failed server's cache was warm and its replacements' copies may be warm too, but to be safe I'd have the clients fall back to the database with request coalescing, and bring the replacement up as joining so it warms before taking full traffic. The key property: only ~1/n of key ownership changed, so the blast radius is bounded and proportional, not total."

Q2
Why not just do hash(key) % N? It spreads keys evenly and it's one line of code.
The classic "justify the complexity" probe. They want the failure mode, quantified.
Model answer

"It does spread evenly — while N is constant. The problem is that N is an input to every lookup, so changing N changes every lookup. Going from 3 servers to 4, hash(key) % 3 and hash(key) % 4 agree only ~25% of the time, so ~75% of keys relocate at once. In a cache that means a simultaneous cold start and a thundering herd on the database — the scaling event causes the outage it was meant to prevent.

Consistent hashing decouples placement from the server count: keys map to ring positions, servers occupy ring positions, and only the arcs adjacent to a joining or leaving server change hands — about 1/n of keys per membership change. The cost is a bit more machinery (the ring, vnodes for skew) and losing key order, which rules out range scans. For a cache or key-value workload where nodes come and go, that's the right trade."

Q3
Your 5-node ring is healthy, but one node consistently runs at 3× the CPU of the others. What's wrong, and how do you fix it without adding hardware?
Distinguishes "the ring balances counts" from "the ring balances heat."
Model answer

"First I'd check which kind of skew it is, because the fixes differ. Two candidates: arc skew — the node owns a disproportionate share of keys — or hot keys — it owns a normal share of keys but a few of them are extremely popular.

For arc skew, the fix is virtual nodes: if we're running one ring position per server, a random large arc explains it exactly. Move to ~100+ vnodes per node and the shares converge on the mean by the law of large numbers. If the node is also just a bigger machine, I'd additionally weight it — more vnodes — so it intentionally takes more.

For hot keys, vnodes won't help — they'd just move the hot key to a different victim. The fix is above the ring: cache the hot keys in front of the ring, or split them with a salt suffix and fan reads out across the splits. I'd verify with per-key request metrics before choosing, because the two problems look identical in CPU graphs."

Q4
You need both "fetch user 842" and "list users 800–900" at scale. Does consistent hashing help with both?
Tests whether you know the ring's hard boundary: it destroys order.
Model answer

"It helps the first and hurts the second. Point lookup is the ring's home turf: hash the user id, walk clockwise, one hop, done — and it stays cheap as nodes join and leave. But hashing destroys ordering, so 'users 800–900' scatters across the whole ring and becomes a scatter-gather over every node — the worst possible access pattern for that query.

So I'd use both strategies for their strengths: the ring for point lookups by id, and range sharding — or a secondary ordered index — for the range queries. In practice that means either two stores, or one store with the ring as primary placement plus an ordered index maintained alongside. The senior move is recognising that no single placement strategy serves both access patterns, and saying so explicitly."

10

Practice drills

Untimed — work them on paper, then check the rubric. A drill is "done" when your answer would earn every rubric point.

Drill 1 — Draw the ring by hand

Ring positions 0–99. Servers hash to A→10, B→40, C→70. Keys hash to 5, 25, 45, 80.

  1. Which server owns each key?
  2. A new server D joins at 50. Which keys move, and to whom?
  3. C fails. Which keys move now, and to whom?
Rubric
  • Initial: 5→A (wrap: clockwise from 5 is 10), 25→B, 45→C, 80→A (wrap past 99 to 10). 2 pts — the two wraps are the point.
  • D at 50 lands in C's arc (40, 70]: D owns (40, 50], C keeps (50, 70]. Key 45 moves B→D. Only key 45 moves. 2 pts.
  • C fails: its arc (50, 70] slides to the next clockwise server, A at 10 (wrapping). Keys 45 (now on D — unaffected) … careful: key 45 is on D, not C. C owns no keys in this set after D joined, so nothing moves. 2 pts — the trap is noticing D already took C's only key.

Drill 2 — Weighted vnodes for a mixed cluster

You have 2 old servers (8 GB RAM each) and 2 new servers (32 GB each) on one ring, 100 vnodes per "unit". How many vnodes per server, and what share of keys does each server get? What goes wrong if you give everyone 100?

Rubric
  • Weight by capacity: old = 1 unit → 100 vnodes; new = 4 units → 400 vnodes. Total 1000 vnodes: old servers 10% each, new servers 40% each. 2 pts.
  • Equal vnodes (100 each) gives every server 25% of keys — the 8 GB machines hold as much data and take as much traffic as the 32 GB ones, so the old nodes saturate first and become the system's ceiling. 2 pts — must name that the weakest node sets the limit.
  • Bonus: mention this only balances key counts; if the workload is read-heavy, weight by expected request rate or add caching, not just RAM. 1 pt.

Drill 3 — Diagnose the 3am page

One cache server's CPU is pinned at 100%; its four peers sit at 20%. Key counts per server are nearly equal. List your top three hypotheses in order, and the single metric that confirms or kills each.

Rubric
  • Hot key — check per-key request rate (top-K keys by hits). A single key with outsized traffic confirms it. 2 pts.
  • Expensive keys, not hot keys — check bytes/request or compute per key. A few large values (or keys triggering slow fallback fetches) explain high CPU at equal key counts. 2 pts.
  • Noisy neighbour / hardware — check steal time, GC pauses, or NIC errors on that host. Equal keys + equal request rates + unequal CPU = the box, not the ring. 2 pts — must be third, after ruling out data causes.
11

Cheat sheet + how to talk through it

Six decisions, then the 60-second framing that opens any design discussion on this topic.

✅ The six consistent-hashing decisions

  1. Ring or mod-N? — nodes join/leave over time → ring. Fixed fleet, range scans needed → mod-N or range sharding.
  2. Hash function — murmur3/xxHash (fast, uniform); MD5/SHA-1 in older systems. Uniformity is load-bearing.
  3. Vnode count — ~100–256 per node; weight by capacity for mixed hardware.
  4. Replication factor — preference list = next R clockwise; R=3 is the industry default.
  5. Membership protocol — gossip (Dynamo/Cassandra) or control-plane pushes; changes are one-at-a-time operations.
  6. Hot keys — detect per-key rates; cache or salt-split above the ring. The ring can't fix this.

🎙️ The 60-second framing

"For placement I'll use consistent hashing: keys and servers both hash onto a ring, each key goes to the first server clockwise, so adding or removing a node moves only about one-nth of the data instead of nearly all of it. I'll run ~160 virtual nodes per server to keep the split even — weighted if the hardware is mixed — and replicate each key to the next two clockwise neighbours for failover. Point lookups stay one hop; range queries would need a separate ordered index since hashing destroys order. Hot keys get cached in front, because the ring balances key counts, not heat."
