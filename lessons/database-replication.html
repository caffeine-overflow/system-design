READ · WHAT DATABASE REPLICATION IS

Same data, several machines

Get the core idea and the three words this whole lesson runs on.

Database replication means keeping identical copies of the same data on multiple machines, so the system keeps working — and keeps accepting reads — even when one machine dies, slows down, or sits on another continent.

Picture a football club's master playbook. The head coach holds the one true playbook at the training ground. Each assistant coach carries a copy — one at the academy, one at the away ground, one studying video at home. Whenever the head coach rewrites a tactic, every assistant updates their copy. Replication is exactly this: one source of truth, several mirrors, and a disciplined process for keeping the mirrors in step.

The three words that run this lesson
  • Primary (also called leader or master) — the machine that accepts writes. One writer per copy-set in the simplest setup. Writes = changes to data (INSERT, UPDATE, DELETE). Reads = queries that only look (SELECT).
  • Replica (also called follower or secondary) — a machine holding a copy, updated from the primary. Replicas serve reads and stand by to take over if the primary dies.
  • Replication log — the ordered stream of "what changed" that the primary streams to replicas so they can replay the same changes. Databases name it differently: PostgreSQL calls it the WAL (write-ahead log), MySQL calls it the binlog. Same idea: a diary of every write, in order.

Trade-off stated out loud: copies buy you survival and scale — but every copy is a machine you must keep in step. The entire lesson is about choosing how in step they must be.

READ · WHY COPY YOUR DATA

Three reasons the mirrors exist

Learn the three jobs replication does — and one job it does not.

SURVIVALIf the primary's machine dies, a replica takes over. Without a copy, the data — and the service — is simply gone. Replicas are hot standbys: already running, already have the data.
READ SCALINGOne database can only answer so many reads. Spread read traffic across the primary plus N replicas and you roughly multiply read capacity. Writes still funnel through the primary.
GEOGRAPHYPut a replica in the same region as your users and reads stop crossing an ocean. The data still originates from one place, but it travels closer to the reader.
Replication is not a backupA backup is a point-in-time snapshot you can restore from after a disaster — including a disaster a replica would happily copy, like an accidental DROP TABLE or a deleted account. Replicas faithfully mirror mistakes the moment they happen. You need both: replication for survival, backups for regret.

Trade-off stated out loud: replicas multiply your read capacity but not your write capacity — every write still goes through one primary (in this setup). Scaling writes is a different trick: that's sharding, tomorrow's topic.

READ · SINGLE-LEADER REPLICATION

One writer, many mirrors

Follow one write through the whole journey, step by step.

In single-leader replication, the simplest and most common setup, every write goes to the primary first. The primary records the change in its replication log and streams that log to each replica, which replays the changes in the same order.

Back to the playbook: the head coach scribbles "switch to a 4-3-3" on page 12 of the master playbook. That page number matters — assistants must apply page 12 after page 11, or their copy diverges from the master's. Order is the whole game: the replication log is numbered precisely so every replica applies changes in exactly the same sequence.

STEP 1Your app sends a write to the primary: "set user 42's name to Ada."
STEP 2The primary writes it to its own storage and appends the change to the replication log.
STEP 3Each replica receives the log entry and replays it — same change, same order.

Reads, meanwhile, can go anywhere: the primary, or any replica. That's where the read-scaling win comes from — and, as section 06 shows, where the trouble starts, because a replica that hasn't replayed step 3 yet is still showing yesterday's answer.

Why "single" leader?Having exactly one writer means writes never fight over who is right. Two writers editing the same row at the same time create a write conflict — two contradictory truths — which needs resolving (sections 07–08). One writer sidesteps the entire problem, which is why single-leader is the default.
READ · SYNC VS ASYNC REPLICATION

The latency-versus-safety dial

Learn the one decision every replicated database makes on every write.

When the primary writes a change, it faces a choice: how long does it wait for replicas to confirm they have it? The answer is a dial with three common positions.

MODEHOW LONG THE PRIMARY WAITSTHE SOCCER VERSION
SynchronousUntil every replica confirms "copied."The head coach radios every assistant and waits for all replies before the match resumes. Slow, but the tactic survives even if the coach's phone dies mid-sentence.
Semi-syncUntil at least one replica confirms.The coach waits for one "got it" — enough to know the tactic exists somewhere besides his own head — then plays on.
AsynchronousNot at all. Fire and forget.The coach shouts the change across the pitch and immediately moves on. Fast — but if he loses his voice (crash) before the assistants heard it, that change is gone.
LOCAL REPLICA WRITE~1 ms
CROSS-REGION REPLICA~80 ms
SYNC ACROSS 3 REGIONS~160 ms

Those numbers are why synchronous replication across regions is rare: every user write would wait ~160 ms for round-trips, and if one region has an outage, writes stop everywhere — the primary can't get its confirmations. That availability cost is real.

Data loss, stated preciselyAsync can lose writes that happened after the last confirmation — if the primary crashes, anything not yet shipped to a replica is gone. Sync loses nothing that was acknowledged, but trades availability and speed. Semi-sync is the middle ground: you lose at most what's newer than the one confirmed replica. There is no mode that is free.

Trade-off stated out loud: synchronous = durability and consistency at the cost of write latency and availability during partitions. Asynchronous = speed and availability at the cost of possible data loss. Semi-sync splits the difference. In interviews, name this dial explicitly — it's the answer to half of all replication questions.

READ · REPLICATION LAG

The replica that lives in the past

Understand the most common replication bug in production — and its three fixes.

Replication lag is the delay between a write landing on the primary and the same write being replayable on a replica. Under async replication the lag is normally milliseconds — but under heavy load, a slow disk, or a network hiccup, it can stretch to seconds or minutes.

Why it bites: reads spread across replicas (section 02's read scaling) can land on a replica that hasn't replayed the newest writes yet. The user experience is maddening and familiar: you update your profile name, the app says "saved," you reload — and the old name is back. Then you reload again and it's the new one. The classic symptom has a name: a failure of read-after-write consistency (also called read-your-writes) — the guarantee that "after I write something, I see my own write."

The soccer version: the assistant coach at the far training pitch receives tactic updates by post while the academy assistant gets them by text. A player who suggested the new 4-3-3 asks the far-pitch assistant, "did you write down what I told you?" The assistant checks his copy — the post hasn't arrived — and says "no." The player knows he's right, but the mirror is stale.

Three fixes, in order of popularity

ROUTE OWN WRITES TO PRIMARYFor a short window after a user writes, send that user's reads to the primary. Simple, effective; costs some read capacity.
STICKY READERSSticky sessions pin a user to one replica after they write, so they never bounce between fresh and stale copies mid-session.
VERSION GATINGTrack how far each replica has replayed (a log position). A read waits until its chosen replica has passed the position of the user's write.

Trade-off stated out loud: read-after-write consistency costs you the thing replicas were bought for — reads that bypass the primary. Every fix is a compromise: spend some primary read capacity, or pin users to specific replicas, or wait. Lag doesn't get eliminated; it gets managed.

READ · MULTI-LEADER REPLICATION

When one writer isn't enough

Learn when a second leader is worth the trouble — and what conflicts cost.

In multi-leader replication, more than one machine accepts writes. Each leader streams its own changes to the others. The motive is usually geography with local writes: users in Berlin write to a Berlin leader, users in Tokyo write to a Tokyo leader, and each gets single-digit-millisecond write latency instead of a trans-Pacific round trip.

The price is the thing single-leader avoided: write conflicts. Two leaders can change the same row at the same time, and the changes genuinely contradict each other. The soccer version: two coaches rewrite page 12 of the playbook at two different pitches. Coach A writes "press high." Coach B writes "drop deep." Both pages are shipped. The playbook now contains both — and somebody must decide.

Conflict resolution strategies, from blunt to careful
  • Last-write-wins (LWW): attach a timestamp to every write; the newest one wins, no questions asked. Simple, deterministic — and silently discards the loser's change. Databases like Cassandra and DynamoDB default to this.
  • Convergent data types (CRDTs): data structures designed so conflicting edits merge cleanly (e.g., two people adding items to a shared cart — a set union just works). Elegant, but only for operations that merge.
  • Application-level merge: hand the conflict to your code — show both versions, like a merge conflict in git, and let a human or rule decide. Correct but expensive.

Trade-off stated out loud: multi-leader buys local-latency writes everywhere at the cost of conflict resolution you must design for. If your writes never touch the same rows (users only edit their own profile), conflicts are rare and multi-leader is nearly free. If they do (seat inventory, balances), think hard.

READ · LEADERLESS & QUORUM

Consistency without a boss

Learn how math replaces the leader — and try the formula yourself.

Leaderless replication has no primary at all. Every node accepts writes and gossips them to the others. Clients enforce order with a simple rule: a write is sent to W nodes, a read asks R nodes, and the client picks the newest value it sees.

Why does that work? A quorum is a minimum number of nodes that must agree. The magic formula is W + R > N, where N is the total number of nodes. When that holds, the write set and the read set must overlap on at least one node — so every read is guaranteed to see at least one copy of the latest write.

The soccer version: instead of trusting the head coach's word, the club takes a team vote. The tactic change is announced to W players; the referee later asks R players what the tactic is. If W + R is more than the squad size, the two groups must share at least one player — someone who heard the change — so the referee always learns the truth.

N = 3, W = 2, R = 2 → 2 + 2 = 4 > 3 ✓
The write reached 2 nodes; the read asks 2 nodes; overlap is guaranteed.

N = 3, W = 1, R = 1 → 1 + 1 = 2 ≤ 3 ✗
No guaranteed overlap — a read can miss the latest write entirely.
The dial you get with quorumTune W and R to choose your pain. W = N, R = 1: fast reads, slow writes. W = 1, R = N: fast writes, slow reads. W = R = majority: balanced, and a write survives as long as a majority is alive. There is no setting that makes both instant — the formula only lets you move the cost around.

Two vocabulary notes. Eventual consistency means the system promises replicas will eventually agree, not that they agree now — the promise leaderless replication makes by default. Read repair is how stragglers catch up: when a read notices a node holding an older value, the client sends it the newer one. DynamoDB, Cassandra, and Riak are the classic leaderless systems.

READ · FAILOVER & SPLIT-BRAIN

When the leader dies mid-match

Learn how a replica gets promoted — and the nightmare you must prevent.

Failover is the promotion of a replica to primary when the old primary stops responding. The system watches the primary with heartbeats — small "I'm alive" messages sent every second or so. Miss several heartbeats in a row and the system declares the primary dead.

The promotion follows a script: pick the replica with the most complete replication log (fewest missing writes), make it the new primary, redirect all writers to it, and let the other replicas re-sync from the new leader. Under a good setup this takes seconds. The soccer version: the head coach is stretchered off; the senior assistant — the one with the most complete copy of the playbook — takes the touchline, and everyone follows his instructions now.

Split-brain: the nightmare

Split-brain happens when the old primary isn't dead — the network just cut it off from the replicas. The replicas, seeing no heartbeats, promote one of their own. Now two primaries accept writes, each unaware of the other. When the network heals, the two divergent histories must be reconciled — often by throwing one side's writes away. A network partition is simply the network splitting into groups that can't reach each other; split-brain is what a bad failover does with it.

The standard defense is fencing: before promoting the new primary, the system actively disables the old one — revokes its credentials, blocks its network, or uses a fencing token (a number that increments on each promotion; storage only accepts writes carrying the newest token, so the old primary's writes get rejected). The classic nickname for the blunt version is STONITH — "shoot the other node in the head."

Why fencing matters more than detectionDetecting a dead primary is easy — heartbeats. Detecting a partitioned primary is impossible from inside either side. So good systems don't try to distinguish: they fence first, promote second, and never trust a primary they can't reach.

Trade-off stated out loud: aggressive failover (short heartbeat timeouts) restores writes fast but risks split-brain on a mere network blip; cautious failover avoids false promotions but leaves you without a writer longer. Every real system picks a timeout and lives with it.

TEST · QUIZ YOURSELF

Say the answer before you peek

Each question has the full model answer underneath. Cover the answer, say yours out loud, then check.

Why replicate the database instead of just taking backups?

Model answer: Backups and replication solve different problems. A backup is a point-in-time snapshot for recovery from mistakes — it restores data after an accidental DROP TABLE, a bad migration, or a data-corruption bug. But restoring from a backup takes minutes to hours, during which the service is down.

Replication is about survival without downtime: hot replicas take over in seconds when a machine dies, and they spread read traffic across machines to scale read capacity. A replica would also faithfully copy a mistaken DROP TABLE the instant it happened — so replication is no substitute for a backup. The complete answer names both jobs: replicate for availability and read scaling, back up for regret.

A user updates their name, refreshes, and sees the old name. What happened, and how would you fix it?

Model answer: The read landed on an async replica that hadn't replayed the write yet — replication lag broke read-after-write consistency (the guarantee that you see your own writes). The write is fine on the primary; the mirror is just behind.

Three fixes: (1) route that user's reads to the primary for a short window after they write — simple, costs some primary read capacity; (2) use sticky sessions so the user stays pinned to one replica and never bounces between fresh and stale copies; (3) version gating — track each replica's log position and only read from replicas that have replayed past the user's write. I'd start with (1) and escalate only if primary read load demands it.

Why not make every write synchronous?

Model answer: Two costs. First, latency: a synchronous write waits for the slowest replica's confirmation, so cross-region writes pay full network round-trips — ~80 ms per region — on every user action. Second, availability: if any one replica is unreachable, the primary can't collect its confirmations, so writes stop everywhere, even in healthy regions. You trade away the very resilience replication was bought for.

The standard middle ground is semi-synchronous replication — wait for at least one replica — which bounds the data-loss window to one unconfirmed write while surviving a single region's failure. Or keep async and accept bounded loss for non-critical writes. In an interview, draw the dial: sync = durability at the cost of latency and availability, async = speed at the cost of possible loss.

What is split-brain, and how do you prevent it?

Model answer: Split-brain is when a network partition — not a real death — separates the primary from its replicas. The replicas see no heartbeats, assume the primary is dead, and promote one of their own. Now two primaries accept writes independently, and their histories diverge. When the network heals, reconciling means discarding one side's writes — data loss by design of the recovery.

Prevention is fencing: before promotion, actively disable the old primary — revoke its access, cut its network, or use a fencing token (monotonically increasing; storage rejects writes from any primary holding a stale token). The principle: never trust a primary you can't reach; fence first, promote second. Tightening heartbeat timeouts helps too, but on its own it just makes false promotions faster — fencing is what makes them safe.

When would you pick multi-leader replication over single-leader?

Model answer: Pick multi-leader when you need local write latency in multiple regions — users in Berlin and Tokyo both writing with single-digit-millisecond latency instead of a trans-Pacific round trip on every write. It also survives a whole region's outage while still accepting writes elsewhere.

The cost is write conflicts: two leaders can change the same row concurrently, so you must design conflict resolution up front — last-write-wins (simple, silently drops the loser), CRDTs (mergeable data types, only for mergeable operations), or application-level merge (correct, expensive). Multi-leader is nearly free when writers never touch the same rows (users editing only their own data). It's a liability when they do (inventory counts, account balances) — there I'd stay single-leader and pay the write latency.

Without a leader, how can a read be sure it saw the latest write?

Model answer: With the quorum rule W + R > N. Writes go to W of N nodes, reads query R nodes and pick the newest value. When W + R exceeds N, the write set and read set must overlap on at least one node — so every read sees at least one copy of the latest write. No leader needed; the math enforces the overlap.

The trade-off is a dial: W = N, R = 1 gives fast reads and slow writes; W = 1, R = N the reverse; W = R = majority balances both and keeps writes working as long as a majority is alive. And the caveat: the guarantee only holds while enough nodes are reachable — a partition can still force the system to choose between availability and the guarantee. That's the CAP trade-off showing up in quorum clothing.

SUMMARY · TAKEAWAYS

Carry these into the room

  • Replication = identical copies on multiple machines: one primary takes writes, replicas mirror them.
  • Replicas exist for survival, read scaling, and geography — not as backups. Backups are for regret.
  • The sync/async/semi-sync dial trades write latency and availability against data loss. Name it explicitly.
  • Replication lag breaks read-after-write consistency; fix it by routing fresh writes' reads to the primary.
  • Multi-leader buys local writes everywhere but forces you to design conflict resolution.
  • W + R > N gives leaderless consistency through guaranteed set overlap — quorum math replaces the boss.
  • Failover promotes the most complete replica; fencing prevents split-brain when the "dead" primary was only partitioned.
  • Every replication choice is one sentence: what does this mode lose when a machine — or a network — fails?
