01 / FOUNDATION

What is database replication?

Database replication is the process of keeping copies of the same data on multiple database nodes by transferring and applying changes from one node to others.
Leader
The node that accepts writes for a dataset. It serializes changes into an ordered replication log.
Follower
A node that replays the leader’s log. It can serve reads, stand by for failover, or both.
Replication lag
The delay between a change committing on the leader and becoming visible on a follower.
90′

Soccer model: the leader is the official match clock; follower scoreboards copy its events. A scoreboard can be fast and nearby yet briefly show 1–0 after the official feed has recorded 2–0. Adding scoreboards improves reach and resilience, not truth by itself.

Asynchronous

Leader acknowledges after its own commit. Lowest write latency, but an acknowledged write can be lost if failover picks a follower that never received it.

Semi-synchronous

Acknowledge after at least one follower confirms receipt—often not durable application. A useful latency/durability compromise.

Synchronous

Acknowledge only after required replicas confirm. Stronger durability, but every write now pays for network and follower health.

04 / SESSION GUARANTEE

Read-your-own-write

After a user changes something, that same user should immediately see the change—even when ordinary reads go to replicas.

Read-your-own-write is a session guarantee, not global strong consistency. It constrains what one client sees after its own successful write.

After a write, route that user’s related reads to the leader for a short window. Simple and robust, but it adds leader read load and the timeout is only a guess about lag.

Return the commit position with the write, for example LSN 1043. On the next read, choose a replica whose applied position is at least 1043, wait briefly, or fall back to the leader. This makes the guarantee explicit rather than time-based.

Route only high-expectation reads—profile edits, payment state, a newly created post—to the leader. Keep feed browsing and historical reads on followers. Correctness follows product semantics, not a blanket database rule.

Render the accepted write from client state while replicas catch up. This improves perception but is not a database consistency guarantee; another device can still observe stale data, and failed writes need reconciliation.

↻

Do not confuse guarantees: read-your-own-write prevents you from seeing your own update disappear. Monotonic reads prevent any later read in your session from going backwards. A replica switch can violate monotonic reads even when no new write occurred.

05 / FAILURE

Failover is where the contract is tested

Replication does not automatically create high availability. Detection, leader election, fencing, and client rerouting must agree.

Leader crash

A controller selects a follower, promotes it, and redirects writes.

  • Prefer the most up-to-date eligible follower.
  • Define recovery point objective: how much acknowledged data may be lost?
  • Repair and rejoin the old leader as a follower.

Network partition

The old leader may still be alive but cut off from the controller.

  • Use quorum/leases to grant leadership.
  • Fence the old leader with an epoch or term.
  • Reject writes carrying a stale term.

Follower falls behind

A slow query, disk pressure, or burst can outpace log application.

  • Stop routing freshness-sensitive reads there.
  • Scale apply capacity or rebuild from snapshot.
  • Protect the leader from unlimited log retention.

Split brain

Two nodes accept writes as leader, creating divergent histories.

  • Make leadership exclusive, not best-effort.
  • Attach monotonically increasing terms to writes.
  • Require conflict repair if divergence occurs.

06 / SENIOR DEPTH

What strong answers make explicit

Move beyond “add read replicas.” Name the replication mechanism, the consistency contract, the failure boundary, and the operational signals.

Ordering source

The leader’s write-ahead log (WAL) or logical change log gives mutations an order. Physical replication copies storage-level changes; logical replication copies row or statement-level changes and is often more flexible across versions and schemas.

Commit vs apply

A follower may have received or even durably stored a log entry without having applied it to queryable state. Ask which point an acknowledgement or health metric represents.

Backpressure

If replicas cannot keep up, the leader’s retained log grows. Eventually disk or retention limits force a choice: throttle writes, drop the lagging replica, or rebuild it from a fresh snapshot.

Schema changes

Logs cross versions during rolling deploys. Use backward-compatible, expand-and-contract migrations: add fields first, dual-read/write if needed, backfill, then remove old fields later.

Hotspot reality

Followers scale reads, not leader write throughput. If one leader cannot serialize the write volume, partition the dataset; each shard can then have its own leader and replicas.

Idempotent replay

Retries and reconnects happen. Replication/apply logic should identify operations by stable log position or event ID so duplicate delivery does not duplicate effects.

Cross-region physics

Synchronous cross-region acknowledgement adds at least a wide-area network round trip to writes. Async remote followers reduce latency but widen the disaster-recovery loss window.

Useful SLOs

Track p50/p95/p99 apply lag, stale-read rate for guarded endpoints, failover time, lost-acknowledged-write count, replica rebuild duration, and leader write saturation.

07 / QUESTION LAB

Explain the decision, not just the pattern

Try each prompt aloud. Then compare your answer with the model response.

Q1

Design replication for a global sports-score service. Scores must update quickly, and fans may tolerate a few seconds of staleness—but the official match operator must immediately see their own correction.

I would separate the public-read contract from the operator-write contract.

  1. Partition matches, with one write leader per match or region. The leader serializes score events into an append-only log.
  2. Replicate asynchronously to regional read replicas. Public reads use the nearest healthy replica because a bounded stale score is acceptable and read volume dominates.
  3. The write response returns the committed event version or LSN. Operator reads carry that minimum version; the router selects a caught-up replica, waits briefly, or falls back to the leader. That provides read-your-own-write without sending every fan to the leader.
  4. Expose event version and last-updated time so caches and clients avoid regressing to an older score. Use monotonic version checks in the client.
  5. Monitor apply lag by region and remove over-lagged replicas from score routing. During leader failure, promote the most current eligible follower with a fenced term to prevent two leaders.

The key trade-off: public availability and latency favor async replication; operator correctness gets a targeted session guarantee.

Q2

A user updates their profile, refreshes, and sees the old name. Diagnose the likely cause and propose fixes.

The likely path is: the write committed on the leader, the refresh was load-balanced to a follower, and that follower had not applied the corresponding log entry. I would confirm this by correlating request IDs, commit LSN, routed replica, applied LSN, and cache behavior.

Fixes, from simplest to most explicit: (1) read the profile from the leader for a short post-write window; (2) return a commit token and require the next read to use a replica at or beyond it; (3) route only self-profile reads to the leader; (4) render accepted values optimistically for UX, while retaining a server-side guarantee for correctness. If a cache sits in front, update or invalidate it after commit and make sure stale cache fill cannot race the invalidation.

Q3

When would you choose synchronous replication, and what failure does it still not solve?

I would choose synchronous acknowledgement where losing an acknowledged write violates the product contract—for example, a ledger entry—provided the latency and availability cost is acceptable. I would define exactly how many replicas, in which failure domains, must durably store or apply the change.

It still does not solve everything. A software bug can replicate corruption everywhere; an operator can delete data on all replicas; correlated regional failure can take all synchronous members down; and an unsafe failover can still create split brain. Backups, point-in-time recovery, tested fencing, and failure-domain placement remain necessary. Replication is not backup.

Q4

Your follower is 20 minutes behind. What do you inspect before adding more replicas?

First split lag into stages: leader log generation rate, network shipping delay, follower receive/durable position, and follower applied position. That reveals whether the bottleneck is network, disk, CPU, lock contention, or apply serialization.

Then inspect recent traffic and schema events: write burst, large transaction, index build, long-running read blocking apply, storage throttling, or a version mismatch. Compare apply throughput with incoming log throughput; if the former stays lower, lag cannot recover on its own. Adding replicas multiplies copying work and does not fix a slow apply path. I would protect the leader’s retention budget, stop freshness-sensitive routing to the replica, remediate the bottleneck, and rebuild from snapshot if catch-up is slower or riskier than replacement.

The 30-second summary

Leader–follower replication orders writes at a leader and replays them elsewhere. Async followers improve read scale and geographic reach, but introduce lag and a failover loss window. Stronger acknowledgement reduces that window by adding latency and coupling availability to replica health.

Five phrases worth keeping

  • “What exactly does acknowledged mean?”
  • “Received is not the same as applied.”
  • “I’ll carry a minimum LSN for read-your-own-write.”
  • “Failover needs fencing, not just detection.”
  • “Replication is not backup.”
