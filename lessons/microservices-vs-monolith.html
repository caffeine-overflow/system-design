Lesson 34 · Foundations

Microservices vs Monolith

Riverside FC's platform started as one codebase and forty engineers. Now the ticket team cannot ship without the merch team, a bug in the fantasy league takes down ticket sales, and every deploy is a whole-club event. Splitting the system apart would fix that — and create a whole new set of problems.

What is a monolith? What is a microservice?

Start from zero. A monolith is an application built as a single deployable unit: one codebase, one process (or one set of identical processes behind a load balancer), one database, and one deploy. Every feature — tickets, merch, fantasy league, live scores — lives in the same program, and a function in the ticket code calls a function in the merch code directly, in the same memory, in nanoseconds. A microservice is the opposite shape: the application is split into many small services, each one a separate process with its own codebase, its own database, and its own deploy, talking to the others over the network through defined APIs (application programming interfaces — the contract of endpoints and message formats a service offers to the outside world).

The soccer running example: Riverside FC's platform as a football club. A monolith is one club where every department — ticketing, merch, catering, the academy — shares one building, one phone system, and one front door. If the catering team wants to rearrange its kitchen, the whole building closes for the day. A microservices club is a training ground of separate buildings, each with its own door, its own staff, and its own budget: the ticket office can repaint and reopen on its own schedule, but now a fan who wants a ticket, a shirt, and a pie has to walk between three buildings, and if the path between buildings is closed, the fan's errand fails even though every building is open. That walk between buildings — the network — is the entire trade-off of this lesson.

Terms, defined as they appear

Deployment unit: the thing you ship as one piece — one binary, one container image, one deploy. A monolith has one; a microservices system has one per service. Service: a small, independently deployable program that owns one business capability and its data. Bounded context: a boundary inside which one meaning of a word holds — "ticket" means a seat in the ticketing context and a support request in the helpdesk context, and the two must not share a model. Conway's law: the observation that a system ends up mirroring the communication structure of the organisation that builds it — teams that never talk build services that never talk. Two-pizza team: a team small enough to be fed by two pizzas, roughly 6–8 people — the unit Amazon popularised as the right size to own one service. Service discovery: the mechanism by which a service finds the current address of another service, since addresses change every time a service redeploys or scales. API gateway: the single front door for clients — one address that routes, authenticates, and rate-limits requests before fanning them out to services. Distributed monolith: a system split into services that still cannot be deployed, scaled, or failed independently — all the cost of microservices with none of the benefit.

The one idea to carry through the whole lesson: a monolith makes the easy things easy and the organisational things hard; microservices make the organisational things easy and the technical things hard. The split is not a technical upgrade — it is a trade of one kind of pain (coordination, one deploy train, one blast radius) for another (network latency, distributed failure, no shared transactions). The interviewer is not listening for which side you pick. They are listening for whether you can name what each side costs.

Requirements and back-of-the-envelope math

Scope first. We are deciding the shape of Riverside FC's platform: ticketing, merch shop, fantasy league, live scores, and the staff tools, built and run by 40 engineers. We are not deciding which framework or cloud to use — we are deciding how the code is organised, deployed, and owned, which is exactly the framing an interviewer expects.

  • Functional: six product areas ship independently (a ticket fix must not wait for a merch release); a failure in the fantasy league must not take down ticket sales; each area owns its data and its release schedule; the platform keeps working while individual pieces deploy.
  • Non-functional: a fan-facing request must still answer in well under a second; deploys must not need all 40 engineers to coordinate; a bug's damage must be bounded to one area; and the system must stay operable — debuggable, observable, and testable — by a team of 40, not 400.

The sizing, with every step shown. These are the numbers that decide the shape before any opinion enters the room:

  • The network is not free — it is ~10,000× slower than a function call. Inside one process, calling a function costs about 50 nanoseconds (a nanosecond is a billionth of a second). One network hop between two services in the same data centre costs about 0.5 milliseconds round trip — 500,000 nanoseconds — before you count serialising the request into JSON and parsing the reply, roughly another 100 microseconds for a 10 KB payload. So one service-to-service call costs roughly 10,000× what an in-process call costs. A request that fans out through 5 services in sequence pays 5 × (0.5 ms + 0.1 ms) ≈ 3 ms of pure plumbing, against ~0.00025 ms in a monolith. Three milliseconds sounds small — until the chain is 20 hops deep, or the hop crosses regions, and then it is the whole latency budget. (Lab A lets you run these numbers yourself.)
  • Sequential availability multiplies downwards. If each service is 99.9% available and a checkout request depends on 4 services in sequence, the request's availability is 0.999 × 0.999 × 0.999 × 0.999 = 0.9994 ≈ 99.6% — worse than the monolith's 99.9%, because every hop is another chance to fail. The same multiplication is why the critical path matters more than the service count: 20 services that never call each other in sequence cost nothing; 4 services chained on the checkout path cost 0.3 percentage points of availability. (This is the same chain math as Lesson 9: 0.9996 ≈ 99.4%.)
  • Deploys: more of them, but none of them a ceremony. A monolith with 40 engineers typically runs one deploy train — say 1 deploy a week, 30 minutes of coordinated rollout, and every team waiting on the same window. Twenty services, each deploying 3 times a week at 3 minutes a deploy, is 20 × 3 = 60 deploys a week and 60 × 3 minutes = 3 engineer-hours a week of deploy toil — six times the monolith's 30 minutes. That is the honest price: microservices cost more total deploy effort, and buy you zero coordination. The ticket team ships at 10:00 on a Tuesday without asking the merch team anything. (Lab B shows the whole trade-off.)
  • Team shape follows the architecture — or fights it. Forty engineers in two-pizza teams of ~7 is about 6 teams, which maps naturally to about 6 services. Forty engineers on one codebase is 40 people landing ~200 commits a day into the same main branch, where every merge conflict and every broken build blocks everyone. The monolith's coordination cost grows with the square of the team size (every pair of engineers can step on each other); the microservices cost grows with the number of service boundaries instead. Conway's law says the architecture will match the org chart eventually — the choice is whether you pick the shape deliberately or discover it by accident.
  • Data has a price either way. A monolith's one database gives you joins and ACID transactions (Lesson 21) for free. Twenty services with twenty databases give you twenty independent schemas — and no joins, no cross-service transactions, and a read that needs data from three services is now three network calls or a duplicated copy of the data kept in sync by events. Duplication is not a bug here; it is the accepted cost of independence, and it is why every microservices design eventually grows an event stream and a materialised view or two.
The decision the numbers force

Every hop you add costs latency, availability, and a copy of the data — so a service boundary must pay for itself in independence: its own team, its own deploy, its own failure domain. A boundary that buys none of those is pure cost, and a system full of such boundaries is a distributed monolith wearing a microservices costume.

The architecture, in one pass

One fan buying a ticket and a shirt flows through two very different systems. The interesting decisions are at the boundaries — where one piece ends and another begins.

Shape 1: the monolith

One codebase, one deploy, one database. The fan's request arrives at a load balancer (Lesson 2), lands on one of several identical copies of the whole application, and the ticket code calls the merch code as a function, in the same process, in nanoseconds. The database is one schema, so "show me this fan's tickets and their orders" is one SQL join, and "charge the card and reserve the seat" is one transaction — both succeed or both fail, atomically. Scaling is simple: add more identical copies of the whole thing. The cost is organisational: every team edits the same codebase, every release ships everyone's changes together, and a bug in the fantasy league's new feature takes down ticket sales, because there is only one process to crash. A monolith is not a bad architecture — it is a small-team architecture, and most systems should start as one.

Shape 2: microservices

Now the same fan journey, split apart. Six stages:

  1. The client talks to one front door. The app calls the API gateway, which authenticates the fan (Lesson 33), applies rate limits (Lesson 11), and routes the request — tickets go to the ticketing service, shirts to the merch service. The client never learns the services' addresses.
  2. Each service owns its capability and its data. The ticketing service owns seats, holds, and orders; the merch service owns products and stock. Each has its own database, its own schema, and its own deploy. No service reads another service's database directly — that rule is the whole point, because the moment two services share a table, they share a deploy.
  3. Services find each other through discovery. When the ticketing service needs the fan's discount tier from the membership service, it asks the service registry (Consul, etcd, or the platform's built-in discovery — the same consensus-backed stores from Lesson 14) for the membership service's current address, then calls it. Addresses change on every deploy and every scale-out, so nothing may be hard-coded.
  4. Reads cross boundaries by API or by copy. A request that needs data from three services either calls all three (slow, and availability multiplies downwards) or reads a local copy: each service publishes the changes other services need as events, and interested services keep a materialised view — a read-optimised copy of someone else's data, kept up to date by consuming those events. The copy is eventually consistent (Lesson 7), which is a trade-off you must name, not hide.
  5. Writes that span services become sagas. "Charge the card and reserve the seat" can no longer be one database transaction, because the payment service and the ticketing service own different databases. The write becomes a saga (Lesson 21): local transactions plus compensating transactions, driven by an orchestrator or by choreography over events — with the explicit acceptance that a failure halfway through leaves a visible intermediate state (seat held, payment pending) that must be resolved, not hidden.
  6. Every service is observable from the outside. Because a request now crosses five processes, debugging by reading one log file is dead. Each service emits the same three signals — metrics (numbers over time: request rate, error rate, latency), logs (timestamped events), and traces (the request's journey across services, tied together by one ID) — and a shared platform collects them. Observability is not a feature you add later; it is the price of admission for this shape, and it gets its own lesson next.

Two supporting pieces complete the picture. Configuration lives outside the code — feature flags, timeouts, and connection strings in a config service or environment, so a threshold can change without a redeploy. And versioning is a discipline, not a tool: a service's API is a contract, old versions keep working while clients migrate, and a breaking change is a negotiation with every caller, not a commit.

The heart of it: how to split — and how not to

Splitting is the whole skill. A bad split is worse than no split, because the network makes every wrong boundary permanent and expensive. There are three standard ways to find the boundaries, and one test that judges all of them.

1. Split by business capability

Ask what the club does, not what the code looks like: sell tickets, sell merch, run the fantasy league, publish live scores, manage memberships. Each capability becomes a service. This is the most common starting point, because the boundaries match the org chart — the ticket team already exists, so the ticketing service already has an owner. The risk is a capability that is secretly two capabilities: "ticketing" that is really "seat allocation" plus "payment" plus "fraud checks" will split again later, and a late split is more expensive than an early one.

2. Split by subdomain — bounded contexts

Ask where the words change meaning. In ticketing, a "ticket" is a seat for a match. In the helpdesk, a "ticket" is a support request. In the shop, a "ticket" does not exist at all. Each meaning is a bounded context, and each context gets its own model, its own service, and its own database. This is the domain-driven design (DDD) approach, and it is the strongest of the three, because it finds boundaries in the language of the business rather than in the org chart. The tell that you have the boundary right: two teams can argue about what a word means and both be correct, because they are in different contexts. The tell that you have it wrong: the same word means the same thing in two services, and they keep needing to agree on its shape — that is one context, not two.

3. Split gradually — the strangler fig

Almost nobody gets to start greenfield. The realistic path is the strangler fig pattern, named for the vine that grows around a tree and eventually replaces it: put the API gateway in front of the monolith, then carve one capability out at a time — first the fantasy league, because it is the least entangled — and route its traffic to the new service while the monolith keeps serving everything else. Each carve-out is small, reversible, and independently valuable, and the monolith shrinks until the last piece moves out or, honestly, until the remaining core is small enough that splitting it further buys nothing. A big-bang rewrite, by contrast, is how you spend a year with two systems and no shipping.

The one test for every boundary

Ask three questions: can this service deploy without the others? Can it fail without taking the others down? Can one team own it end to end? If the answer to all three is yes, the boundary is real. If any answer is no — if a deploy of the ticket service always needs a matching deploy of the merch service, or a crash in one always cascades to the other — you have drawn a line on a diagram, not a boundary in the system, and you are paying network costs for monolith behaviour. That is the distributed monolith, and it is the most common failure mode in this space.

One more rule that belongs in every answer: split when the organisation hurts, not when the diagram looks tidy. A team of 5 engineers with one product area should be a monolith — the split buys them nothing and costs them a network, a saga, and an observability platform. A team of 40 with six product areas and a deploy train that takes a week to coordinate has outgrown the monolith, and the split is paying for itself in shipping speed. The question is never "microservices or monolith?" in the abstract. It is "what is hurting right now, and which shape removes that pain?"

Communication: synchronous calls vs events

Once split, services must talk, and there are two families of conversation, each with a clear home:

StyleHow it worksBest forWhere it breaks
Synchronous — request/response (REST, gRPC)Service A calls service B and waits for the reply, over HTTP or gRPC (Lesson 27).Reads that need a fresh answer now: "is this seat still available?"Availability multiplies downwards along the chain; a slow B makes A slow; retry storms when B is down (Lesson 23).
Asynchronous — events and queues (pub/sub, message queues)Service A publishes an event ("ticket sold") to a broker; interested services consume it when they can (Lessons 9 and 12).Things that can happen later: updating the fan's order history, sending the confirmation email, feeding analytics.Eventual consistency — the merch service's copy of the fan's tier is minutes old; debugging a flow that spans five inboxes is hard; event schemas become contracts.

The senior line: synchronous calls are for questions, events are for facts. "What is the price of this seat?" is a question — ask it and wait. "This ticket was sold" is a fact — announce it and move on. The design error is making facts into questions: a checkout that synchronously calls five services in sequence to announce what happened has built a distributed transaction out of hope, and the first slow service in the chain teaches it why. Conversely, the design error in the other direction is making questions into events: a fan staring at a loading spinner while the answer travels through a queue has been given eventual consistency where they needed an answer.

Data per service — the rule and its price

Each service owns its database, and no other service touches it. That rule is what makes independent deploys possible: the ticketing team can rename a column without asking anyone. The price is threefold, and a strong answer names all three. First, no joins: a screen that shows a fan's tickets, orders, and membership tier reads three services or one materialised view — never one query. Second, no cross-service transactions: multi-service writes are sagas, with compensating transactions and visible intermediate states (Lesson 21). Third, duplication is normal: the merch service keeps its own copy of the fan's discount tier, updated by events, because calling the membership service on every product page is a latency and availability tax. The duplicated copy is stale by seconds or minutes, and the design must say which reads can tolerate that staleness and which cannot — a discount shown on a product page can be a minute old; a seat's availability cannot.

Two patterns complete the picture. CQRS (command query responsibility segregation) is the admission that writes and reads want different shapes: the service that takes orders keeps its write model normalised and correct, and serves reads from a purpose-built view — a different table, or a different service entirely. And the outbox pattern is how a service publishes events reliably: it writes the business change and the event into the same local transaction, in an outbox table, and a relay publishes the outbox rows to the broker — so a crash can never produce a changed database with a lost event, or an event with no change behind it.

Senior-depth traps

  • "Microservices are more scalable." A monolith scales fine — you run more copies of it behind a load balancer, and the whole industry did exactly that for a decade. Microservices let you scale one piece independently (the live-score service on match day, without scaling the merch service), and they let teams ship independently. That is organisational scaling and per-piece scaling, not raw throughput — and if the bottleneck is the database, splitting the application into twenty services that all hit the same database has scaled nothing.
  • "We split by team, so the boundaries must be right." Team boundaries and service boundaries usually coincide, because of Conway's law — but a team that owns two services that always deploy together has one service with extra steps, and a service owned by two teams has no owner. The test is the three questions (deploy, fail, own), not the org chart. Conway's law describes what happens by default; the architect's job is to decide deliberately, and to reorganise the teams when the architecture needs it, not only the other way around.
  • "Each service has its own database, so data is decoupled." Separate databases stop shared-table coupling, but the coupling moves: into the events (a change to the "ticket sold" event breaks every consumer), into the synchronous calls (a slow membership service is now everyone's problem), and into the duplicated copies (whose staleness budget nobody wrote down). Decoupling is not achieved by drawing a line — it is achieved by versioning the contracts across the line and naming what happens when the other side is slow, down, or changed.

Questions, with full model answers

Q1. You have a team of 8 engineers building a new product with one feature area. Monolith or microservices — and why?

Model answer. A monolith, without hesitation — and I would say so in the first sentence, because the question is testing whether I reach for microservices by default. Eight engineers is one two-pizza team with one product area, so the split buys nothing: there is no second team to unblock, no deploy train to escape, and no failure domain to isolate. What it costs is real — every call between features becomes a network hop at ~10,000× the cost of a function call, every multi-feature write becomes a saga instead of a transaction, and the team now needs service discovery, an API gateway, and distributed tracing just to debug a request. A well-structured monolith — modules with clear boundaries inside one codebase, one deploy — gives the team everything it needs: fast iteration, one database with real transactions, and trivial debugging. The honest close is the trigger for revisiting: when the team grows past ~20 engineers, or a second product area needs its own release cadence, or one feature's failure starts taking down the rest, that is when I would start carving pieces out with the strangler fig pattern — one capability at a time, behind the gateway, with the monolith shrinking rather than being rewritten.

Q2. Your checkout calls four services in sequence — pricing, inventory, payment, and fraud — and p99 latency doubled after the split. What do you do?

Model answer. First, I would measure before moving anything: put a trace ID on the request and read the trace, because "latency doubled" could be four network hops, or one slow service, or serialisation of a huge payload, and each has a different fix. If it is the hops themselves — four sequential calls at ~0.5 ms RTT plus serialisation — the fix is structural, in order of strength. One: collapse calls that are really questions into one — pricing and inventory can often be answered by a single service that owns a materialised view, or by one call that returns both. Two: parallelise what does not depend on the previous answer — pricing and fraud can run at the same time, so the chain costs the slowest call, not the sum. Three: move facts to events — the fraud check does not need to block the reply if the payment can be held and reviewed asynchronously, which turns a synchronous chain into a fire-and-forget event. Four: if the chain is genuinely necessary, shorten it — put the services in the same availability zone, keep payloads small, and use gRPC instead of JSON where the serialisation cost shows up in the trace. And I would name the trade-off out loud: every one of these fixes trades something — a materialised view trades freshness, parallel calls trade partial-failure handling, async fraud trades immediate certainty — and the right answer depends on which of those the checkout can afford. What I would not do is add a cache in front of a chain that is slow because it is long; a cache hides latency, it does not remove hops.

Q3. Two of your services always deploy together, and a change to one always means a change to the other. What is wrong, and what do you do about it?

Model answer. That is a distributed monolith — the boundary is drawn on a diagram but does not exist in the system. The test is the three questions: can it deploy alone, can it fail alone, can one team own it — and here the answer is no on the first, which means the two services are one service with a network hop in the middle, paying ~10,000× per call for the privilege. I would find out why they are coupled before touching the code: usually it is a shared data model (both services need the same "order" shape), a synchronous call chain (A cannot answer without B), or a shared database table they both write to. The fix depends on the cause. If it is a shared model, split the model along the bounded contexts — each service keeps its own view of an order, and the shared shape becomes an event both consume. If it is a call chain, move the fact to an event: B publishes what A needs, A keeps a materialised view, and the synchronous dependency disappears. If it is a shared table, one service owns the table and the other goes through its API. And if none of that is practical — if the two really are one capability — the honest fix is to merge them back into one service, which is a fix, not a failure. Merging a wrong split is how you learn where the boundary actually is, and a system that has merged one service is healthier than a system carrying a boundary nobody dares to question.

Q4. Design the split of a monolithic e-commerce platform into services. Where do you draw the lines, and what do you deliberately leave together?

Model answer. I would start from the business, not the code: the capabilities are catalogue, search, cart, checkout, payment, orders, inventory, shipping, membership, and notifications — and the first cut follows those, because each has a team or a natural owner. Then I would check each cut against bounded contexts: a "product" in the catalogue (title, description, images) is not the same object as a "product" in inventory (SKU, stock count, warehouse), so catalogue and inventory are genuinely separate contexts even though they talk about the same shirt. The deliberate non-splits matter as much as the splits: cart and checkout stay close, because a checkout that reads a cart through a network call on every step is a latency and consistency headache — and many teams keep them in one service until the cart needs its own scale. Search stays a read model fed by events from the catalogue, not a service that queries the catalogue live. And payment is its own service from day one, because it has different compliance, different availability, and different failure handling from everything else — it is the one place where a shared transaction would be genuinely dangerous to lose. The migration is strangler fig: gateway in front, carve the least entangled capability first (notifications, then catalogue), route traffic service by service, and leave the monolith running the core until the last piece moves. I would close with the numbers: a checkout through 4 chained services at 99.9% each is ~99.6% available, so the checkout path gets parallel calls and a materialised view where it can, and the deploy math — 60 small deploys a week instead of one coordinated train — is the payoff the split is actually buying.

Practice drills (untimed — depth over speed)

Drill 1 — Find the real boundary. A club platform has one service called "fan-service" that handles login, membership tiers, ticket purchases, and support tickets. Apply the three-question test (deploy alone, fail alone, one owner) and the bounded-context test (does "ticket" mean the same thing everywhere?). Propose a split — or argue it should stay whole — and name what changes in the split. Rubric: "ticket" fails the bounded-context test (seat vs support request), so the service is at least two contexts; login/membership is one context, seat ticketing is another, support is a third; the split is justified only if the teams and deploy cadences differ — if one team owns all of it and ships weekly, the honest answer is to keep it one service with internal modules; and the answer names the cost of splitting (the membership tier becomes a network call or a duplicated copy with a staleness budget).

Drill 2 — Collapse the chain. A matchday page loads by calling five services in sequence: fan profile, membership tier, ticket history, merch recommendations, and live scores. p99 is 400 ms and the budget is 100 ms. The trace shows each hop costs ~60 ms, mostly waiting on the previous answer. Redesign the read path without changing what the page shows. Rubric: the five calls are independent, so parallelise them — the chain costs the slowest call (~60 ms) instead of the sum (~300 ms); the membership tier and ticket history can be served from a materialised view owned by the page's own service, removing two hops entirely; live scores come from the edge cache (Lesson 32), not a service call; and the answer names what is lost — the view is eventually consistent, so a tier upgraded seconds ago may not show yet, which is acceptable for a page but not for a checkout.

Drill 3 — Size the split. A platform has 30 services, each deploying twice a week at 4 minutes of toil per deploy. A monolith alternative would deploy once a week at 45 minutes. Compare the weekly toil, then argue whether the split is worth it — and name the one fact that would change your answer. Rubric: 30 × 2 × 4 = 240 minutes (4 hours) a week vs 45 minutes for the monolith — the split costs ~3.25 extra hours of toil a week; it is worth it if the deploys are independent (no coordination meetings, no waiting for other teams) and if a bad deploy's blast radius is one service, not the platform; the fact that changes the answer is whether deploys are actually independent — if every deploy still needs a coordinated release window, the split costs 4 hours and buys nothing, and the right move is to merge back or fix the coupling first.

Sixty-second framing

"A monolith is one codebase, one deploy, one database — fast to build, fast to debug, and painful to scale organisationally, because every team ships together and one bug can take down everything. Microservices split the system into small services with their own code, data, and deploys, which buys independent shipping and a bounded blast radius — and charges for it in network latency, about ten thousand times the cost of a function call per hop, in availability that multiplies downwards along every chain, and in data that has to be duplicated or reached through events. So the split is justified by the organisation, not by the diagram: split by business capability and bounded contexts, migrate with the strangler fig one piece at a time, keep synchronous calls for questions and events for facts, and test every boundary with three questions — can it deploy alone, can it fail alone, can one team own it? If the answer is no, it is a distributed monolith, and the fix is to merge it back."

  3. Architecture: gateway → services with their own databases → discovery → materialised views for reads → sagas for multi-service writes → observability across it all.
  4. Deep dive: splitting by capability and bounded context, the strangler fig, sync questions vs async facts, data per service and its price.
  5. Trade-offs and failure modes: the distributed monolith, cascading failure, retry storms, eventual-consistency surprises, version drift, undebuggable requests.
  6. Close: the six decisions, and the three-question boundary test — deploy alone, fail alone, one owner.
