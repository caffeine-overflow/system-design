Lesson 13 · Core Building Blocks

Distributed Locks

One program needing exclusive access to something is easy: a lock in memory does the job. But when ten copies of your program run on ten different servers, no memory they share exists — and a lock inside one machine locks out nobody else. This lesson is about locking across machines: the Redis lock that gets you 90% there, the TTL pause that breaks it, and the fencing token that actually makes it safe. If you want exactly one thing to happen exactly once — charge this card once, book this seat once, count this goal once — this is the machinery.

01

What is a distributed lock?

A lock is a promise: "while I hold this, nobody else touches the thing." In one program it's trivial. Spread the program across servers and the promise needs a referee that everyone can see.

⚽ The running example: the shared scoreboard

One scoreboard, three operators, zero double-counts

Championship final. The stadium has one big scoreboard, but the match data comes from three operators — one watching the live feed, one watching VAR, one reading the referee's mic — each running on their own laptop, all updating the same board. A goal is scored. All three operators see it at the same instant and all three reach for the "add one goal" button.

Without coordination, the scoreboard reads 3–0 when the real score is 1–0: each operator read "0", each added one, each wrote back. The lock is the rule that says only one operator may hold the "update the scoreboard" right at a time — like one referee's whistle counting, not three. Every idea in this lesson lands on this scoreboard.

Lock · Mutual exclusion

A lock is a token of exclusive permission: the process that holds it may enter the critical section — the code that must run alone — and everyone else waits or walks away. Mutual exclusion is the property the lock guarantees: no two processes are inside the critical section at the same time.

Distributed lock

A lock that works across multiple machines. Inside one process you'd use a mutex (short for mutual exclusion — a lock that lives in one program's memory and coordinates its threads). But a mutex on server A is invisible to server B. A distributed lock moves the lock into a place all machines can reach — a shared lock service — so ten app servers can still agree on "who goes first."

The single-process story, then why it breaks

One server, four threads, one scoreboard. Thread 1 grabs the mutex, reads the score, adds the goal, writes it back, releases. Threads 2–4 queue politely. The mutex works because all four threads share the same memory — the lock is one flag they can all see.

Now scale out: three operators on three laptops, each running their own program. Laptop A's mutex is a flag in its own memory — laptop B cannot see it, so B's mutex does nothing to stop B. Each machine locking "successfully" in its own memory is exactly the same as no lock at all. That's the whole problem: mutual exclusion needs a single shared reference point, and across machines there isn't one by default. So you build one: a lock service — a small, always-on store (Redis, etcd, ZooKeeper) whose only job is handing out the "you may proceed" token to whoever asks first.

🧠 The sentence that frames the whole lesson

"A distributed lock is just a mutex whose memory lives on another machine." Every design decision — the TTL, the token, the fencing — is about what happens when the network, crashes, and pauses get between you and that far-away memory.

02

The naive approaches and why they die

Before the real tool, the three things people try first — and the exact reason each one fails. Senior rooms want you to have killed these yourself.

1. App-local locks (the mutex on each laptop)

Give each operator program its own mutex. As shown above: laptop A's flag is invisible to laptop B, so all three operators still update the scoreboard at once. App-local locks coordinate threads; they cannot coordinate machines. This is the answer that dies in the first minute — but name it, because the follow-up question is always "so what does span machines?"

2. The database row lock: SELECT ... FOR UPDATE

SELECT FOR UPDATE · Row lock

In SQL, SELECT ... FOR UPDATE reads a row and locks it until your transaction commits or rolls back — anyone else trying to lock the same row waits. A row lock is exactly that: the database refusing to let two transactions touch the same row concurrently.

The design: keep a locks table with one row per scoreboard resource. To update the score, an operator opens a transaction, runs SELECT * FROM locks WHERE name = 'scoreboard' FOR UPDATE, does the update, commits. It genuinely works — the database is a shared reference point. So why not?

  • Your database becomes your lock server. Every lock acquisition is a transaction holding a connection and a row lock for the whole critical section. Lock traffic competes with your real query traffic on the same connection pool — a lock holder that pauses (section 4) now holds a database connection hostage too.
  • The hot row. All three operators fight over one row — every acquisition serializes on it. That's fine at three operators; at three thousand lock acquisitions a second, the row becomes a contention furnace.
  • Failover pain. If the database fails over to a replica mid-transaction, in-flight row locks evaporate — two operators can hold "the lock" on opposite sides of the failover. The lock store's own consistency (section 5) bites here just as hard.

Verdict: correct for low contention, honest about the coupling. Fine for "two cron jobs must not overlap." A poor lock service at real concurrency.

3. A dedicated lock service — the actual answer

Run something whose whole job is lock state: fast, in-memory, single-purpose. The industry default is Redis; the consensus-store family (etcd, ZooKeeper — section 7) is the heavy-duty alternative. Why a separate service instead of the DB:

  • Latency: a Redis lock acquire is a sub-millisecond in-memory write, not a transaction with a commit.
  • Isolation: lock traffic can't starve your application's queries — it has its own box, its own failure budget.
  • TTL as a first-class citizen: locks that auto-expire if the holder dies (section 4) are built into the primitive, not bolted on with a watchdog column.

⚠️ The mental model to carry forward: the lock service is a referee with a short memory and a stopwatch. It hands the whistle to whoever asks first, and if the whistle-holder goes silent past the stopwatch, it hands the whistle to someone else. Everything in sections 3–5 is about the consequences of that stopwatch.

03

Redis lock anatomy

One Redis command does 90% of distributed locking in the industry. Learn its three letters and its one rule, and you can build the whole thing.

The command

SET lock:scoreboard <random-token> NX PX 5000
NX · PX

NX means "set this key only if it does not already exist" (Not eXists). It's the atomic "first one wins" — two operators racing to SET NX the same key get exactly one winner, decided inside Redis, with no race. PX 5000 sets the key's TTL — Time To Live — to 5000 milliseconds: Redis deletes the key automatically after 5 seconds unless someone deletes or renews it first.

Token · TTL · Lease

The token is a random unique value the acquirer invents — e.g. a UUID like 7f3a…c9e1 — stored as the key's value. It's how you prove later that you are the holder: "I hold lock:scoreboard" means "lock:scoreboard currently contains my token." The TTL (time to live) is how long the key survives without renewal. A TTL on a lock is called a lease: you hold the lock for at most the TTL — after that, the lock service considers it expired and hands it to the next asker, whether you're done or not.

Why a random token and not the value "locked"? Because release has to be selective: when your TTL expires and someone else acquires the lock, the key holds their token. If release were just DEL lock:scoreboard, you'd delete their lock — kicking the new holder out of a lock you no longer own. The token makes release answerable to "is this still mine?"

The acquire loop

token = random_uuid()
deadline = now() + 10_000          # give up trying after 10s
while now() < deadline:
    if redis.SET("lock:scoreboard", token, NX, PX, 5000):
        return token              # we hold the lock for ~5s
    sleep(100ms)                  # someone else holds it; retry
raise LockNotAcquired

Two numbers, both deliberate: the retry sleep (100 ms) avoids hammering Redis with a hot spin, and the acquire timeout (10 s) guarantees a caller never waits forever — waiting forever is how one stuck lock holder freezes your whole fleet. If you can't get the lock in 10 seconds, fail loudly and let the caller decide (retry later, shed load, alert).

The broken release — then the fix

The naive release is a check-then-set race: two separate commands with a gap between them that another process can slip through.

❌ Broken release
if redis.GET("lock:scoreboard") == token:
    # ← another operator's SET NX can land HERE
    redis.DEL("lock:scoreboard")
✅ Fixed release (Lua)
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end

The bug, step by step: operator A's TTL expires. Operator B acquires — the key now holds B's token. Operator A wakes up and runs the broken release: the GET returns… wait, A's token no longer matches, so A's GET == token is false and A deletes nothing. Fine so far. Now the real race: A's GET returns A's token (still hers), and before A's DEL runs, A's TTL expires and B acquires. A's DEL then deletes B's lock. B is inside the critical section believing it's protected — and C can now acquire too. Two holders, one lock, scoreboard double-counted.

Lua script · Atomic compare-and-delete

Redis runs Lua scripts — small programs you send to the server — atomically: while a script runs, no other command can interleave with it. The fixed release is a Lua script that does compare-and-delete: "delete this key only if its value is my token" as one indivisible step. The GET-check and the DEL can no longer be split by another client's acquire.

The 90% lock, stated as a recipe: acquire with SET key <random-token> NX PX <ttl> in a bounded retry loop; do the critical work; release with the atomic Lua compare-and-delete. The token proves ownership, NX makes acquisition race-free, PX bounds the damage of a dead holder, and Lua makes release race-free. Everything from here on is about the one thing this recipe does not protect you from: time running out while you're still working.

04

The TTL problem

This is the heart of the lesson. The TTL saves you from dead holders — and then a pause turns it into a double-execution machine. Follow the numbers.

Why the TTL exists at all

Operator A acquires the scoreboard lock, then her laptop crashes — kernel panic, power cut, the process just stops. Without a TTL, the key sits in Redis forever and no operator ever updates the scoreboard again: a deadlock by crash. The TTL is the escape hatch: the lock self-destructs after 5 seconds, so a dead holder can only wedge the system for 5 seconds, not forever. The lease is the price of surviving crashes. But it has a dark side: the lock service cannot tell "the holder crashed" apart from "the holder is slow." Both look identical from Redis's side: silence. So the TTL fires on the slow holder too — and that's the whole problem.

The pause scenario, with numbers

GC pause · Stop-the-world

A GC pause is when a language's garbage collector freezes the program to reclaim memory. A stop-the-world pause freezes everything — your lock holder stops mid-critical-section, not executing a single instruction, while the rest of the world keeps moving. These are real: multi-second pauses happen under memory pressure in JVM/Go/.NET runtimes.

⚽ The 8-second freeze — follow the clock:

t = 0.0s — Operator A acquires lock:scoreboard with TTL = 5s and token A1. She reads the score (0–0) and starts adding the goal.

t = 1.0s — A's runtime hits a stop-the-world GC pause. A freezes mid-write. She is not crashed — she is paused, invisible to herself and everyone.

t = 5.0s — A's lease expires in Redis. The key vanishes. As far as the lock service is concerned, the lock is free.

t = 5.1s — Operator B, retrying in her acquire loop, wins SET NX with token B2. B reads the score — still 0–0, because A never finished her write — adds the goal, writes 1–0, releases.

t = 9.0s — A's GC pause ends (an 8-second pause: 1.0s → 9.0s). A wakes up believing she still holds the lock. She finishes her write: score 1–0 — computed from the 0–0 she read at t=0.

Result: the goal was counted twice in intent but written twice from the same stale read — and worse, if B's write and A's write had been increments rather than full rewrites, you'd see 2–0 for one goal. Two operators were inside the critical section at once. The mutual exclusion guarantee broke, and nothing crashed, nothing logged an error, and both operators believe they did the right thing.

This is why senior rooms push on it: the failure is silent and correct-looking. The recipe from section 3 is intact — token, NX, PX, Lua release — and the lock still broke. The TTL is a lease on permission, and a pause longer than the lease means you act on an expired permission. Two candidate fixes, one real one.

Candidate fix 1: renewal / heartbeat (helps, doesn't solve)

Lock renewal · Heartbeat

Renewal is a background thread in the holder that re-extends the TTL (e.g. every TTL/3) while the critical section runs — a heartbeat saying "I'm still alive, keep my lease." If the holder crashes, the heartbeats stop and the TTL expires as before.

Renewal raises the bar: now the pause has to outlast the renewal interval's failure, not just one TTL. But notice the hole: the renewal thread pauses too. A stop-the-world pause freezes the heartbeat thread along with the worker — an 8-second pause with a 1.6-second heartbeat interval still lets the lease expire at 5s. Renewal converts "pause > TTL" into "pause > (time until renewal thread notices)" — better odds, same failure shape. And it adds its own failure mode: if the renewal thread dies while the worker lives (an exception in the heartbeat loop), the lease expires mid-work and you're back to double execution — now with a component whose death is silent. Renewal is worth doing; it is not a correctness argument.

The real fix: fencing tokens

Fencing token

A fencing token is a monotonically increasing number — each one strictly larger than the last — handed out by the lock service with every successful acquisition. The holder must include its token with every write to the protected resource, and the resource rejects any write carrying a token older than the highest it has seen. "Fencing" as in fencing off the stale holder: even if it wakes up and acts, its writes bounce off.

The mechanism needs two cooperating pieces:

  1. The lock service issues increasing tokens. Redis's INCR on a counter key is the simple version: A acquires and gets fencing token 34; after A's lease expires, B acquires and gets 35. (In practice the token can be the Redis counter value returned alongside the lock grant.)
  2. The storage layer enforces them. The scoreboard store remembers the highest fencing token it has accepted — say 34. Every "set score" request must carry a token; the store applies the write only if token > last seen, otherwise rejects it.

Replay the 8-second freeze with fencing: A holds lease with token 34, pauses at t=1s. Lease expires at t=5s. B acquires, gets token 35, writes 1–0 with token 35 — the store records "highest seen = 35". A wakes at t=9s and tries to write with token 34 → rejected: 34 < 35. A's stale write dies at the storage door. The score stays 1–0. Mutual exclusion at the storage level holds even though the lock level briefly didn't.

🧠 The senior one-liner for this section

"A TTL can't distinguish a crashed holder from a paused one, so a pause longer than the lease means two holders. I don't try to prevent that with timing — I make it harmless with fencing tokens: the storage rejects any write carrying an older token than it has already seen. The lock coordinates; the fencing token protects."

⚠️ Fencing has a prerequisite: the resource itself must check the token. If your "storage" is a plain Redis key, a file, or a third-party API with no token check, fencing tokens are just numbers in a log — unenforced. Fencing is a contract between the lock service and the storage layer; both sides have to play. When the storage can't check (an external API), fall back to making the operation idempotent (section 6) so a double execution is a no-op.

05

Failure modes of the lock store

So far the lock service was a perfect referee. Now break the referee: crashes, failovers, and the quorum debate.

1. Lock-holder crash — the case TTL was built for

A acquires, then the process dies outright (not paused — dead). Heartbeats stop, the 5s TTL expires, B acquires cleanly. This is the happy path of the TTL design: worst case, the lock is wedged for one TTL. Note the asymmetry with section 4: a crash is safe because the holder can never act again; a pause is dangerous precisely because the holder comes back. When someone says "TTL handles failures," the precise version is: TTL handles crashes; it does not handle pauses.

2. Lock-store failover — the lock that forgot it was held

Failover · Split-brain

Failover is when a primary node dies and a replica is promoted to take its place. Split-brain is the nightmare version: the old primary isn't actually dead — a network partition isolated it — so two nodes both believe they're the primary and both accept writes. Each half of the split sees a different truth.

The scenario: your Redis lock service is primary + async replica. A acquires lock:scoreboard on the primary. The SET NX hasn't replicated yet when the primary dies. The replica is promoted — it never saw A's lock. B asks the new primary for the lock and gets it. A is alive, holding what she believes is a valid lease, inside the critical section — and so is B. Two holders, zero pauses involved. The root cause: the lock store's own replication wasn't as strong as the guarantee you built on top of it. This is why the fencing-token discipline from section 4 matters again here: even with a perfect TTL story, a failover can mint two valid-seeming leases, and only storage-level fencing rejects the stale one.

3. Clock skew — mentioned so you can dismiss it correctly

Clock skew

Clock skew is the difference between two machines' clocks — server A thinks it's 12:00:00.000, server B thinks it's 12:00:00.150. Clocks drift; NTP keeps them close but never identical.

Here's the good news: the Redis recipe doesn't care about clock skew. The TTL is enforced by Redis's own clock — expiry is measured on one machine, not compared across machines. Nobody's local timestamp decides anything. Clock skew becomes your problem only in designs where clients compare timestamps (e.g. "my lease is valid until 12:00:05" computed locally) — which is a reason to prefer server-side TTLs. If a senior asks about clocks, the answer is: "expiry is measured by the lock service's clock alone, so skew between clients is irrelevant."

Redlock: the quorum idea, in one paragraph

Quorum

A quorum is a majority vote: with 5 nodes, any 3 agree and the decision stands. The point is overlap — any two majorities share at least one node, so two conflicting decisions can't both win a majority.

Redlock is Redis's official answer to the failover problem: run 5 independent Redis masters (not replicas — independent), and acquire the lock on a majority (3+) of them within a bounded time. If 3 of 5 grant it, you hold it: a single node failing over can't resurrect a conflicting grant, because any other majority overlaps yours on at least one node that already said yes to you. The debate, honestly stated: critics (notably the Jepsen-style analyses) argue Redlock's safety still rests on timing assumptions — expiry measured across machines that can pause — so it doesn't achieve the ironclad guarantees of a consensus system, while adding real operational cost (5 masters to run). The common production posture: a single well-run Redis with short TTLs + fencing tokens at the storage layer. You get the practical safety without operating a fleet — and you say so out loud, which is what the senior room actually wants to hear.

The failure-mode summary

Holder crash → TTL expires, next holder proceeds (the designed case). Holder pause > TTL → two holders; fencing tokens make the stale one's writes bounce. Store failover → the new primary may not know the lock; fencing again, or accept the window. Split-brain → two primaries, two grants; only fencing at storage (or a real consensus store) saves you. Clock skew → irrelevant here; expiry is the server's clock. The through-line: the lock coordinates, but only fencing protects.

06

When NOT to lock

Locks are the heaviest coordination tool in the box: they serialize, they add a network round trip to every critical section, and they fail in silent ways. The senior move is reaching for them last. Four lighter tools, in order of preference.

1. Idempotency first — make repeats harmless

Idempotency

An operation is idempotent if doing it twice has the same effect as doing it once (Lessons 9 and 12 used this for message consumers; it applies to critical sections too).

Back to the scoreboard: if each goal carries a unique goal ID and the scoreboard records "goal g-9917 counted" before incrementing — skipping IDs it's seen — then two operators processing the same goal is a no-op the second time. No lock, no contention, no TTL, no fencing. Idempotency beats locking whenever the work can be made repeat-safe, because it removes the coordination entirely instead of managing it. Always ask first: "can I make the double-execution harmless instead of preventing it?"

2. Optimistic concurrency — the version column

Optimistic concurrency · CAS

Optimistic concurrency skips the lock and instead checks at write time that nothing changed since you read: the row carries a version number, and your write says "set score = 1, version = 5 where version is still 4." If someone else wrote first, the version moved and your write affects zero rows — you re-read and retry. CAS (compare-and-swap) is the same idea as a CPU/storage primitive: "swap this value only if it's still what I saw."

The scoreboard version: operator A reads (score 0, version 7). Operator B reads (score 0, version 7), writes (score 1, version 8) — succeeds. A writes (score 1, version 8) where version = 7 — zero rows affected. A re-reads (score 1, version 8) and retries cleanly. No lock held during the read-modify window; contention only costs a retry. This wins when conflicts are rare — three operators, occasional simultaneous goals. It loses when conflicts are constant: if every write collides, everyone retries forever (that's livelock — all progress, no completion), and a lock's orderly queue beats a retry storm.

3. Queue serialization — one worker, no lock needed

Route all scoreboard updates through one queue with one consumer (Lesson 9's competing-consumers pattern run in reverse: a single consumer). The three operators don't touch the scoreboard — they publish "goal scored" events, and the lone scoreboard worker applies them in order. Serialization by construction: there's only one writer, so there's nothing to coordinate. The trade: the worker is a throughput ceiling and a single point of failure — but for many workloads that's a fine trade, and it composes beautifully with the async patterns from Lessons 9 and 12.

4. Single-writer design — decide ownership up front

The heaviest hammer, used at design time: partition the resource so each piece has exactly one owner. Scoreboard updates for the first half go to operator A's service, second half to B's — or shard by match ID so one service owns each match's board. If only one writer can ever touch a piece of state, locks are unnecessary by construction. This is the same instinct as sharding (Lesson 6): ownership replaces coordination.

If you must lock: granularity and hold time

Two rules that separate careful lock users from the rest:

  • Lock the smallest thing possible (granularity). Lock lock:scoreboard:match-4821, not lock:scoreboard — operators updating different matches shouldn't queue behind each other. Coarse locks serialize the world; fine locks serialize only the true conflicts.
  • Hold it for the shortest time possible, and measure it. Measure your critical section's p99 hold time (the 99th percentile — the duration 99% of executions finish within), then set TTL to a few multiples of p99 — e.g. p99 = 200 ms → TTL ≈ 1–2 s. Too short and pauses eat you alive; too long and a crashed holder wedges everyone for ages. "A few × p99" is the sizing rule to state out loud.

🧠 The restraint ladder, in one breath

"Before a distributed lock I try, in order: idempotency (make repeats harmless), optimistic concurrency (version-check the write; best when conflicts are rare), queue serialization (one writer, no coordination), single-writer ownership (partition so nobody shares). The lock is for what's left: true mutual exclusion across writers that can't be designed away — and then I lock the smallest scope for the shortest measured time."

ZooKeeper / etcd in one table

Redis is the default, but the consensus-store family does locks differently — with stronger guarantees and more machinery. One table, then when you'd switch.

Ephemeral means the node vanishes automatically when the client's session drops; sequential means the store appends an increasing number (lock-0001, lock-0002…) so contenders can order themselves.

When you'd switch

Stay on Redis when the lock guards efficiency or convenience — "don't run this cron twice," "don't send this email twice" — where a rare double-execution is annoying, not catastrophic, and fencing or idempotency covers the gap. Reach for etcd/ZooKeeper when the lock guards correctness you can't recover from — leader election for the one writer that must exist, a schema migration that must run once — and when you want fair queuing rather than a retry stampede. The honest senior framing: Redis for speed and simplicity with fencing as the backstop; consensus stores when the lock itself must be the source of truth.

Leader election

Leader election is distributed locking's most famous application: N identical servers agree that exactly one of them is the leader — the one that runs the cron, the one that writes. It's "a lock held indefinitely, with re-election when the leader dies." If you can explain locks, you can explain leader election in one sentence.

🧠 What to notice

Pause longer than TTL, fencing off: A's lease expires mid-pause, B acquires and records her goal, then A wakes up and writes from her stale read — B and C's goals get silently overwritten (a lost update), the scoreboard ends wrong, and the log shows nobody errored. Watch what happens next: A sees the rejection, re-acquires with a fresh token 37, re-reads the true score, and records her goal properly — fencing turned silent corruption into a detectable, retryable rejection. Pause shorter than TTL: nothing bad happens at all — the lease covers the pause, which is exactly why you size TTL as a few × p99.

09

Q&A — with full model answers

Four questions that come up constantly, each with the spoken answer — verdict first, reasoning, and what earns the top mark.

Q1 · DESIGN
"How would you prevent double-booking the last seat on a flight?"
The classic lock question wearing a product costume. They want the Redis recipe plus the TTL honesty, not just "use a lock."
Reveal model answer
Verdict

"Serialize the booking decision per flight with a short-lived Redis lock — SET NX PX with a random token, released via Lua compare-and-delete — and protect the seat write with a fencing token or an idempotent booking record. The lock stops the race; the fencing stops the pause."

Reasoning

"Two passengers tap 'book' on the last seat at the same instant, hitting two different app servers. An app-local mutex is invisible across servers, so both servers would read '1 seat left' and both would write '0 seats left, booked twice.' The lock has to live somewhere both servers see: Redis. The booking service acquires lock:flight:BA249 with SET key <random-token> NX PX 2000 — first one wins atomically, the loser retries briefly or gets 'seat unavailable, try another flight.' Inside the critical section: re-check availability, write the booking, release with the Lua script that deletes only if the value is still my token — so I can never delete someone else's lock if my lease expired mid-write.

The TTL is sized deliberately: measure the p99 of the book-seat transaction — say 150 ms — and set the TTL to a few multiples, ~1–2 seconds. Short enough that a crashed holder only wedges the flight for a second; long enough that a normal booking never outruns it.

Then the part I'd volunteer unprompted: the TTL can't tell a crashed holder from a paused one. If the holder GC-pauses past the TTL, a second server acquires and books the seat, the first wakes up and books it again — double-booking with a perfectly correct lock. So the seat write carries a fencing token: the lock service issues increasing tokens per acquisition, and the booking store rejects any write with a token older than the highest it's seen. And belt-and-braces: the booking row itself is idempotent on a client booking ID, so even if both writes somehow land, the second is a duplicate of the same booking, not a second passenger."

What earns top marks

The full recipe (NX, PX, token, Lua release) stated crisply, the TTL sized from p99 rather than plucked from air, volunteering the pause problem before being asked, and the fencing-plus-idempotency backstop named as the thing that makes the lock safe rather than merely fast.

Q2 · MECHANICS
"Why does the Redis lock use a random token? And why Lua for release?"
A depth check on the recipe. They want the delete-not-yours race explained, not recited.
Reveal model answer
Verdict

"The token proves which holder is releasing; Lua makes the check-and-delete atomic. Without the token you can't tell your lock from someone else's; without Lua, the check and the delete can be split by another client's acquire."

Reasoning

"The token exists because of expiry. Say my TTL is 5 seconds and my critical section overruns it — the key expires, another server acquires, and the key now holds their token. If release were a bare DEL, I'd walk in late and delete their lock while they're inside the critical section — kicking the rightful holder out. The random token turns 'delete the lock' into 'delete the lock only if it's still mine,' which is the only safe release.

But 'check the token, then delete' as two commands has a race in the gap between them: my GET returns my token — still mine — and before my DEL executes, my TTL expires and someone else acquires. My DEL then deletes their lock. The window is small but it's exactly the kind of race that only shows up at 3 a.m. under load. The Lua script fuses the GET-check and the DEL into one atomic step — Redis runs scripts without interleaving other commands — so the check and the delete can never be split. Token for ownership, Lua for atomicity; you need both."

What earns top marks

Walking the interleaving concretely (GET returns mine → TTL expires → other acquires → my DEL kills their lock) rather than saying "it's a race condition" abstractly, and the crisp division of labor: token = ownership, Lua = atomicity.

Q3 · FAILURE MODES
"Your lock holder pauses for 8 seconds with a 5-second TTL. Walk me through what happens — and how you'd fix it."
The heart-of-the-lesson question. They want the timeline with numbers, then fencing — not "make the TTL longer."
Reveal model answer
Verdict

"Two holders, one silent double-execution — and longer TTLs don't fix it, they just move the cliff. The real fix is fencing tokens enforced at the storage layer."

Reasoning

"Timeline: t=0, holder A acquires with TTL 5s and starts the critical section. t=1s, A's runtime hits a stop-the-world GC pause — A freezes mid-work, not dead, just silent. t=5s, the lease expires in Redis; from the lock service's view the lock is free — it cannot distinguish 'crashed' from 'paused,' silence looks identical. t=5.1s, holder B's retry loop wins SET NX, enters the critical section, and does the work. t=9s, A's 8-second pause ends; A wakes up believing she still holds the lock and finishes her write. Both did the critical section. Nothing crashed, nothing logged — both believe they were correct.

'Just make the TTL longer' is the tempting fix and it's wrong in an important way: a 30-second TTL survives an 8-second pause, but now a crashed holder wedges the lock for 30 seconds, and a 40-second pause breaks you again. You're trading one cliff for a taller cliff — timing can never distinguish pause from crash, so no TTL value is correct, only lucky.

The fix that doesn't depend on luck: fencing tokens. The lock service hands out a monotonically increasing token with each grant — A gets 34, B gets 35. Every write to the protected resource carries the token, and the storage layer applies a write only if its token exceeds the highest already seen. A's stale write arrives with 34 after B's 35 was recorded → rejected at the storage door. The lock coordinated as best it could; the fencing token protected. One caveat I'd state: the storage has to enforce it — if the resource is a third-party API with no token check, fencing is unenforced, and I'd fall back to making the operation idempotent so the double execution is a no-op."

What earns top marks

The timestamped walk-through (not hand-waving), the explicit rejection of "longer TTL" with the crashed-holder trade-off, fencing explained as a storage-enforced contract with its prerequisite named, and the idempotency fallback for unenforceable storage.

Q4 · JUDGMENT
"When would you reach for ZooKeeper/etcd over Redis for locking — and when is a lock the wrong tool entirely?"
Two judgments in one: the store choice and the restraint ladder. They want both answered crisply.
Reveal model answer
Verdict

"etcd/ZooKeeper when the lock guards unrecoverable correctness and I want fair, consensus-backed grants; Redis for everything else. And before any lock, I'd try idempotency, optimistic concurrency, queue serialization, and single-writer ownership — in that order."

Reasoning

"Redis is the default: one box, sub-millisecond acquires, TTL leases. Its weaknesses are the failover window — an async replica promoted without the lock grants a conflicting lease — and unfair acquisition: whoever's SET NX lands first wins, so a tight retry loop can starve everyone else. For 'don't run this cron twice' or 'don't double-send this email,' those are acceptable, covered by fencing or idempotency.

I'd switch to etcd or ZooKeeper when the lock is load-bearing for correctness: leader election — exactly one writer must exist — or a run-once migration. There I want three things Redis doesn't give: consensus-backed grants (a majority agrees, so failover can't forget a lock), ephemeral sequential nodes forming a fair queue (lowest number holds; watches notify instead of polling, so no herd effect and no starvation), and session-based expiry tied to client liveness rather than a wall-clock guess. The price is a 3–5 node cluster to operate and higher acquire latency — worth it when the lock itself must be the source of truth.

And the restraint ladder before any lock: first idempotency — give each goal a unique ID and skip seen ones, and the double-execution is harmless with zero coordination. Then optimistic concurrency — a version column, 'write only if version is still what I read,' retry on conflict; best when conflicts are rare, degenerates into a retry storm when they're constant. Then queue serialization — one consumer applies all updates in order, no lock needed. Then single-writer ownership — shard by match so one service owns each board. The lock is for what's left: genuine mutual exclusion across writers I can't design away — and then I lock the smallest scope for the shortest measured time, TTL at a few × p99 hold time."

What earns top marks

The store choice tied to what the lock guards (recoverable annoyance vs unrecoverable incorrectness), the three etcd/ZooKeeper advantages named concretely (consensus, fair sequential queue, session liveness), the restraint ladder in order with the conflict-rate caveat on optimistic concurrency, and the TTL-sizing rule stated out loud.

Practice drills

Untimed — think like you're whiteboarding. Write your answer, then check the rubric.

Drill 1 — Trace the pause

Holder A acquires lock:payments with TTL = 4s at t=0 and begins a charge that takes 1s of work. At t=0.5s A hits a stop-the-world pause lasting 6s. Holder B retries every 200ms. (1) At what time does B acquire the lock? (2) At what time does A wake up, and what does A believe? (3) Name the two things that would each independently prevent a double charge, and which layer each lives at.

Reveal rubric
  • (1) t ≈ 4.0–4.2s. The lease expires at t=4s; B's next retry (every 200ms) wins SET NX almost immediately after. Accept any answer in 4.0–4.2s with the expiry reasoning.
  • (2) t = 6.5s, believing she still holds the lock. Pause runs 0.5s → 6.5s. Full marks for the sentence "nothing tells A her lease expired" — the pause is invisible to the paused process.
  • (3) Fencing token at the storage layer — the charge store rejects A's write carrying an older token than B's; idempotency at the application layer — the charge carries a unique payment ID and the second identical charge is a no-op. Full marks for naming the layer of each: fencing protects the write, idempotency makes the repeat harmless.

What earns top marks: the timeline with timestamps, the "invisible to the paused process" line, and both fixes placed at their correct layers — plus the note that a longer TTL only moves the cliff (a 7s pause would break a 6s TTL the same way).

Drill 2 — Spot the release bug

A teammate's release code is:
if redis.get("lock:report") == my_token: redis.delete("lock:report")
(1) Construct the exact interleaving that breaks it — name the three events in order. (2) Write the fix. (3) Explain why the token alone (without your fix) is insufficient.

Reveal rubric
  • (1) The interleaving: (i) my GET returns my token — the check passes; (ii) before my DEL runs, my TTL expires and another holder acquires (key now holds their token); (iii) my DEL executes and deletes their lock. Full marks for all three events in order — the gap between check and delete is the whole bug.
  • (2) The Lua compare-and-delete: if redis.call("GET",KEYS[1])==ARGV[1] then return redis.call("DEL",KEYS[1]) else return 0 end — full marks for noting Redis runs the script atomically, so no command can interleave.
  • (3) The token tells you whose lock it is; it doesn't make the check-and-delete atomic. The token answers "is this still mine?" — but the answer can go stale between the asking and the acting. Full marks for the one-liner: "the token fixes ownership, Lua fixes atomicity."

What earns top marks: the three-event interleave with the expiry placed between GET and DEL, and the crisp ownership-vs-atomicity split.

Drill 3 — Choose the tool

Three scenarios. For each, pick: Redis lock, etcd/ZooKeeper lock, or no lock (name the lighter tool) — with one sentence of justification each.
(a) A nightly cron that emails a digest — must not run twice if two schedulers fire.
(b) Electing the single leader that assigns referees to matches — a second leader assigning overlapping crews would be a real incident.
(c) Incrementing a per-player goal counter fed by three operators, where each goal event carries a unique goal ID.

Reveal rubric
  • (a) Redis lock — a double email is annoying, not catastrophic; a short TTL lease with the cron's idempotency key as backstop is the proportionate tool. (No-lock with idempotency on the digest ID is also acceptable if argued: "the email send is idempotent on digest-date, so a lock adds nothing.")
  • (b) etcd/ZooKeeper lock — the lock guards unrecoverable correctness (two leaders = real incident); you want consensus-backed grants, fair sequential queuing, and session-based expiry. Full marks for "the lock itself must be the source of truth."
  • (c) No lock — idempotency. Record seen goal IDs; a repeated goal event is a no-op. Full marks for the sentence "coordination removed beats coordination managed" — and for noting a lock here would serialize three operators for no benefit.

What earns top marks: each pick tied to what failure costs (annoyance vs incident vs free), the (a) alternative accepted when argued from idempotency, and the restraint ladder visible in the reasoning.

✓

Cheat sheet: the 6 lock decisions

Every distributed-lock design is these six decisions, in this order. Tape this to your mental whiteboard.

1. Do I need a lock at all? Try in order: idempotency (repeats harmless) → optimistic concurrency (version-check the write; best when conflicts are rare) → queue serialization (one writer) → single-writer ownership (partition so nobody shares). Lock only what's left.

2. Where does the lock live? Redis by default (sub-ms, one box, TTL leases). etcd/ZooKeeper when the lock guards unrecoverable correctness — consensus-backed grants, fair sequential queue, session liveness. Never app-local; the DB row lock only for low contention.

3. How do I acquire? SET key <random-token> NX PX <ttl> in a bounded retry loop (sleep ~100ms, give up loudly after seconds). NX = first wins atomically; PX = the lease; token = proof of ownership.

4. How do I release? Lua compare-and-delete only — never GET-then-DEL. The token answers "is it still mine," Lua makes the answer atomic.

5. How do I size the TTL? Measure p99 hold time; TTL = a few × p99. Too short: pauses eat you. Too long: crashes wedge everyone. And accept the truth: no TTL is correct — a pause longer than any TTL breaks the lease, which is why decision 6 exists.

6. What makes it actually safe? Fencing tokens: the lock service issues increasing tokens per grant; the storage rejects writes carrying an older token than it has seen. The lock coordinates; fencing protects. Where storage can't enforce, fall back to idempotency.

🎙️ Locks in 60 seconds — the recital

"A distributed lock is a mutex whose memory lives on another machine — usually Redis, via SET with NX for atomic first-wins, PX for the TTL lease, and a random token proving ownership, released with an atomic Lua compare-and-delete so I never delete someone else's lock. The TTL exists so a crashed holder only wedges the lock for seconds — but it can't distinguish a crash from a pause, so a pause longer than the lease means two holders and a silent double-execution, which no TTL value fixes. The real safety is fencing tokens: increasing tokens per grant, enforced at the storage layer, so the stale holder's writes bounce. Before any of that I try idempotency, optimistic concurrency, queue serialization, and single-writer ownership — the lock is the last resort, scoped as small and held as short as measured p99 allows."

How to talk about locks in the room

When the question is "prevent double-booking" or "how do these servers coordinate," run this five-step structure. It turns a Redis command into a senior answer.

  1. Kill the local lock first. "An app-local mutex is invisible across servers — each machine locking in its own memory is the same as no lock." This shows you know why the problem is distributed.
  2. State the recipe crisply. "SET key token NX PX ttl in a bounded retry loop; Lua compare-and-delete to release." Name what each piece does: NX = atomic first-wins, PX = the lease, token = ownership, Lua = atomic release. Forty seconds, no rambling.
  3. Volunteer the pause problem. Don't wait to be asked: "the TTL can't tell a crashed holder from a paused one — a GC pause longer than the lease means two holders, silently." Walk the 8-second-pause/5-second-TTL timeline if they bite.
  4. Land fencing as the fix. "So I don't rely on timing — fencing tokens: increasing token per grant, storage rejects stale writes. The lock coordinates; fencing protects." Name the prerequisite: storage must enforce it.
  5. Close with restraint. "And before the lock, I'd check whether idempotency or optimistic concurrency removes the need — the lock is the last resort, scoped small, TTL at a few × measured p99." Senior rooms reward the engineer who reaches for the heavy tool last.

Senior-depth traps — land these unprompted

TTL handles crashes, not pauses. Silence looks identical from the lock service's side — crashed and paused are indistinguishable, and only one of them comes back.

No TTL value is correct. Longer TTLs survive longer pauses but wedge longer on crashes. Timing can never solve it; fencing can.

The token is ownership, Lua is atomicity. Two different bugs, two different fixes — the delete-not-yours race needs both halves of the answer.

The lock coordinates; fencing protects. Mutual exclusion at the lock level can briefly break; mutual exclusion at the storage level is what actually prevents the double write.
