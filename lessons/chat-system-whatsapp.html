01

What is a chat system?

Before any architecture: what the thing actually is, defined from zero, with one running example carried through the whole lesson.

Definition

A chat system moves short messages between people with near-real-time delivery (under ~1 second while both sides are online), keeps messages ordered per conversation, and stores and forwards — persists each message and holds it until an offline recipient returns — so no message is lost to a dead phone or a tunnel.

Our running example: Riverside FC, a football club. The coach runs a squad group chat (35 members: players, physio, kit staff). Players also send each other 1:1 direct messages. The club has a fan announcement channel with 100,000 subscribers for fixture news. Every concept below gets tested against this one club.

Chat is different from email — and from a feed

Three expectations make chat its own design problem:

  • Latency is a UX contract. A message that arrives 30 seconds late feels broken; a tweet that arrives 30 seconds late is fine. Humans start feeling delay around 1 second.
  • Phones are hostile infrastructure. Radios sleep to save battery, networks flap on trains, apps get killed by the OS. The system must assume the recipient's device is usually half-dead — this is why store-and-forward exists.
  • Order is meaning. "Yes" arriving before "Training at 7?" reads as a different conversation than "yes" arriving after. Delivery without ordering is a bug, not a feature.

Two axes

Every chat feature sits on two axes. Topology: 1:1 (two people) vs group (N people, one shared sequence). Reachability: online (push it down a live socket now) vs offline (hold it; deliver on reconnect). The whole design is the machinery that makes those four combinations work.

The one-sentence architecture

A chat system is: persistent sockets for instant delivery + a durable message store so nothing is lost + cursors so every device picks up exactly where it left off + a roster (who-is-connected-where) so the router knows which socket to push to.

02

Requirements and back-of-the-envelope sizing

Say the numbers out loud first — they decide which parts of the design are allowed to be simple.

Functional requirements

  • 1:1 and group conversations; send text, images, video.
  • Near-real-time delivery when the recipient is online; reliable delivery when they are not.
  • Per-conversation ordering; read receipts; typing indicators; presence (online / last seen).
  • Multi-device: phone + desktop stay in sync.
  • End-to-end encryption for message content (server routes ciphertext it cannot read).

The math

  • Traffic: 50M daily users × 100 messages/day = 5B messages/day. Average: 5B ÷ 86,400 ≈ 58K messages/sec. Peak (match evenings, 4–5×) ≈ 250–300K/sec.
  • Storage: average payload ~150 bytes → 5B × 150B ≈ 750 GB/day of raw payload. With replication and indexes (~3×) ≈ 2.2 TB/day, ≈ 800 TB/year, multi-petabyte over a 5-year retention. Big, but cheap object-store big — not the hard part.
  • Connections: 50M daily users, ~30% online at peak → ~15M concurrent sockets to hold. That number drives the entire connection layer (§5).

Reading the numbers: this is a connection-and-fan-out problem, not a storage problem. The database writes are 58K/sec — any sharded store handles that in its sleep. The hard constraints are holding 15M live sockets, pushing each message to the right ones in under a second, and never losing a message to a flapping phone.

Non-functional requirements

  • Latency: send → delivered to an online recipient, p99 under 1 second.
  • Availability: chat is treated like a utility — survive a single-region failure without losing messages.
  • Consistency: per-conversation ordering guaranteed; global total order across all conversations not needed (and not paid for).
  • Durability: once the server says "sent," the message exists even if every connection server dies that second.
03

The API: three endpoints and a state machine

The surface is small on purpose. Three endpoints, one event stream, and a message lifecycle the client drives.

Send: POST /messages

Request: { conversation_id, client_msg_id, payload, media_ref? }. The client_msg_id is a UUID the sender's phone generates — an idempotency key, a unique token that lets the server recognize "this is the same send attempt I already processed" and drop duplicates. Response: 202 Accepted { server_seq, ts }.

Why 202 and not 201: the durable write is the commit. Routing to recipients happens asynchronously, off the critical path — the sender's wait ends at persistence, exactly like the Twitter fan-out lesson's "POST returns after the durable write."

History: GET /conversations/{id}/messages?cursor={seq}&limit=50

Cursor pagination on the per-conversation sequence number — no offsets, no deep-pagination collapse. The client keeps a cursor (the highest sequence number it has seen) per conversation and asks for "everything after this." Reconnect sync is literally this endpoint.

The live stream: one WebSocket per device

Events pushed down the socket: message.new, presence.update, typing.start/stop, receipt.read. (WebSocket itself is defined in §5.)

The message state machine

Every message walks four states on the sender's phone: sending (not yet acknowledged by the server) → sent (persisted, 202 received) → delivered (recipient's device acknowledged receipt) → read (recipient opened the chat; their client advanced its read cursor and told us). The transitions are driven by acknowledgements flowing back — each hop confirms to the previous one.

Riverside FC check

The coach sends "Formation change: 4-3-3 for Saturday." to the squad chat. His phone shows one tick (sent) the moment the 202 lands — before a single player has received anything. Two ticks when a player's device acks; blue ticks when the player opens the chat. The sender's UX is decoupled from the fan-out, by construction.

04

Data model: sharded conversations, cursors, cold history

The store is write-optimized and boring — chat's drama is never in the database schema.

Messages table

Shard by conversation_id (consistent hashing across the fleet — the same ring idea from the consistent-hashing lesson, now mapping conversations to database nodes). Row key: (conversation_id, seq). Columns: sender_id, payload (ciphertext under E2EE), ts (server-assigned), client_msg_id with a uniqueness constraint for dedupe (§7).

The per-conversation sequence

Each conversation owns a sequence counter — a single atomic integer that hands out the next seq when a message is persisted. One counter per conversation means one writer's worth of coordination per conversation, and conversations are independent, so the whole fleet scales: 58K writes/sec spread over millions of counters is ~zero contention per counter. This counter is the ordering guarantee — messages are ordered by the sequence they were assigned at persist time. (Group-chat interleaving is discussed in §7.)

Per-user state

  • Conversation list: per user, their conversations ordered by last activity — a small index, heavily read.
  • Read cursors: per (user, conversation), the highest seq the user has read — this is what read receipts and unread badges are built from.
  • Sync cursor: per (device, conversation), the highest seq the device has received — offline catch-up replays from here.

Storage tiers

The workload is append-heavy and rarely updated — a textbook fit for an LSM-tree store (memtable → SSTables, from the indexing lesson): Cassandra/Scylla-style. Hot data (recent conversations) on fast disks; history older than N days (or N messages) migrates to cheap object storage and is served from there on scroll-back. Media lives in blob storage from the start — the message row carries only a reference.

05

The connection layer: fifty million sockets

The piece that makes chat "real-time." Why HTTP can't do it, what holds 15M sockets, and the design decision that makes crashes boring.

Why not HTTP?

A WebSocket is a persistent TCP connection: client and server complete one HTTP handshake, then keep the same socket open and exchange tiny frames (a few bytes of header) in both directions, any time. HTTP polling is the alternative — the client asks "anything new?" every N seconds — and it loses three ways:

  • Overhead: every HTTP request carries ~1 KB of headers for a 150-byte message. Polling 15M devices every 2 seconds is ~7.5M requests/sec of pure header tax.
  • Latency floor: with polling, delivery latency can never beat the poll interval. WebSocket delivery is limited only by network time.
  • Battery: each poll wakes the phone's radio. Persistent sockets with infrequent heartbeats let the radio sleep — this is why real chat apps feel instant and don't drain the battery.

Connection servers: a stateful edge tier

One WebSocket per device, held by a fleet of connection servers — machines whose only job is holding sockets and shoving frames down them. Each box holds roughly 500K–1M sockets (each socket costs tens of KB of kernel + app memory). 15M peak sockets ÷ 750K per box ≈ 20 boxes — small fleet, but every box is load-bearing.

The roster: who is connected where

The roster is a fast lookup — user_id → connection server — held in a low-latency store (Redis-style). When a device connects, it registers. When the router needs to deliver to a user, it asks the roster which box holds their socket. Users are mapped to connection servers by consistent hashing on user_id, so a reconnecting phone usually lands on the same box and the roster barely churns.

Heartbeats and NAT

NAT (network address translation) is the box between a phone and the internet that quietly drops idle mappings — typically after a few minutes. A heartbeat is a tiny ping every 30–60 seconds that keeps the mapping alive and doubles as a liveness check: miss several heartbeats and the roster entry is expired, marking the user offline. (Lab Part A makes you feel this cost at 15M sockets.)

The decision that makes crashes boring: the connection server holds no authoritative state. Messages live in the message store (§4); routing state lives in the roster. A connection server crash loses only sockets — clients reconnect within seconds, re-register in the roster, and replay from their cursor. There is nothing to recover, because there was nothing to lose. Stateless-by-design at the edge is what lets this tier be simple.

Graceful drain

Deploying new code to a box holding 750K sockets can't be a kill −9. The box stops accepting new connections, waits for existing sockets to migrate (clients reconnect to a new box via the consistent-hash mapping), and only then shuts down. The roster is updated as each client re-registers.

06

One message, start to finish — the full path

The coach's formation-change message, traced through every component. Six steps; notice what is skipped as well as what runs.

  1. Connect. The coach opens the app. His phone opens a WebSocket to a connection server and registers coach → conn-server-7 in the roster. A player on a train with no signal has no roster entry — that absence is the offline signal.
  2. Compose. He types "Formation change: 4-3-3 for Saturday." and taps send. His phone stamps a client_msg_id (a fresh UUID) on the message — the idempotency key from §3.
  3. Persist. POST /messages hits the API tier: validate, rate-limit, then write to the message store with the conversation's next sequence number (atomic increment on the squad-chat counter). The server returns 202. The coach sees one tick. The send path ends here — everything after is asynchronous.
  4. Route. A router (async worker) reads the persisted message, looks up the 34 other members in the roster, and for each online member pushes the message to their connection server, which writes it down the open socket. Roster misses — the player on the train — are simply skipped.
  5. Ack. Each receiving device sends a receipt ack. The coach's phone advances those messages to "delivered" (two ticks) as acks arrive. The player on the train gets nothing yet — and that's fine, because the message is already durable.
  6. Read. A player opens the squad chat. Her client advances its read cursor past the message's seq and publishes a read receipt to the conversation's members — the coach sees blue ticks.

The ordering rule that must never break: persist before route, always. If you route first and crash before persisting, some players saw a message the system has no record of — it can never be re-fetched, re-synced, or shown on the coach's second device. Persist-first means a crash between steps 3 and 4 is harmless: the router replays from the durable record. Idempotent routing (same message, same seq, delivered twice = deduped by the client) makes the replay safe.

Reconnect: the player on the train

Signal returns. His phone opens a socket, registers in the roster, and calls GET /messages?cursor={last_seq} for each conversation. The server returns everything after his cursor — the formation change, the physio's reply, the kit man's thumbs-up — in sequence order. His client walks its cursor forward. No special "offline queue" exists: the conversation store is the offline queue. (Contrast with the Twitter lesson's per-user inbox writes — chat doesn't need them, because a conversation's members are bounded and reads are cursor scans.)

07

The hard parts

One idea at a time. Each of these is a question that comes up in the room — and each has a crisp, defensible answer.

Ordering: whose "first" wins?

Ordering is defined as arrival order at the per-conversation writer: whichever message gets the next sequence number from the counter is "earlier," full stop. In a 1:1 chat this matches intuition. In the squad group, two players replying simultaneously get whatever order the counter assigned — and that is correct by definition, because there is no physical "simultaneous" across two phones with unsynchronized clocks. Never trust client timestamps for ordering (clock skew — phones disagree about the time by seconds); the server assigns ts at persist. Total order across conversations is never attempted — nobody needs the physio's DM ordered against the squad chat.

Exactly-once UX over an at-least-once network

The network gives at-least-once delivery: a phone whose POST times out will retry, and the retry can arrive after the original actually persisted. The fix is the idempotency key: the client_msg_id has a uniqueness constraint in the message store, so a retried send is recognized and dropped — the client just gets the original server_seq back. On the receiving side, the client keeps a small dedupe cache of recent client_msg_ids and ignores replays. Formula to say in the room: at-least-once network + idempotent writes = exactly-once user experience. (Retry storms — a phone hammering retries — are bounded by the same rate limiter from the rate-limiting lesson.)

Presence: who is online?

Presence rides a separate, lightweight channel — never the message path. Heartbeats refresh a TTL key per user (say 60 seconds); expiry means offline. Updates are last-writer-wins: the newest heartbeat overwrites, no coordination needed. The subtle decision is fan-out scope: you do not broadcast "coach is online" to all 100K fans. Presence goes only to people with an open or recent conversation with you — O(open chats), not O(contacts). Typing indicators are even more ephemeral: a typing.start event with a few-seconds TTL, never persisted, never replayed on reconnect.

Read receipts without a write storm

A read receipt is just the per-conversation read cursor advancing (§4) — one tiny write per conversation opened, fanned out only to that conversation's members. The coach sees blue ticks because the squad chat has 35 members, not because the system did 35 expensive things per reader.

Groups at scale: the announcement-channel problem

Groups are capped (1K–50K members) precisely because fan-out cost is O(members). The club's 100K-subscriber fan announcement channel breaks that model — so it's a different product shape, a broadcast channel: the message is persisted once, and subscribers pull with their cursor (or receive it via a segmented fan-out that walks the roster in batches, not one giant push). No per-member roster walk on the send path; readers who are offline just sync later. The honest framing: chat is push for the conversational scale, pull for the broadcast scale.

End-to-end encryption

Under end-to-end encryption (E2EE), message payloads are ciphertext the server cannot read — it routes opaque blobs. The standard construction is the Signal protocol: at session setup the two devices perform a key exchange (X3DH — each side combines long-term and one-time keys so they agree on a secret without ever sending it), then a double ratchet derives a fresh encryption key per message, so compromising one key doesn't expose past or future messages (forward secrecy). What the server still sees: metadata — who talked to whom, when, how many bytes. Encryption hides content, not the fact of conversation. Key verification (comparing safety numbers) happens out of band between the humans.

Media: never through the message path

Photos and video never ride the WebSocket. The client uploads to blob storage first (resumable upload — a half-uploaded video survives a tunnel), the server generates a thumbnail, and the message carries only a blob reference. Downloads come from the CDN. The message path stays small and fast because the bytes went around it.

Push notifications: the dead-app path

When the app is killed, there is no socket — delivery falls back to push notifications (FCM on Android, APNs on iOS), the OS-level channels that can wake an app. The payload is an opaque "new message" nudge (under E2EE the phone decrypts after waking); a silent push can wake the app to sync via the normal cursor endpoint instead of showing a banner. Push is the backup generator, not the architecture.

Multi-device

Each device is an independent socket with its own sync cursor. A message to the coach is fanned out to all of his devices — the roster maps user_id → [conn-server per device]. "Read on desktop" advances the shared read cursor, so the phone's badge clears too: read state is per user, sync state is per device.

Senior-depth traps (know these cold)

  • "Just use Kafka for delivery." A log is great for durability, but per-user delivery needs per-recipient routing state (the roster) and socket affinity — a queue doesn't know which box holds the player's phone. Kafka can sit behind the API as the durable buffer before routing, but the last mile is always roster → socket.
  • "Why not one global sequence?" A single counter for all messages is a single point of contention at 58K writes/sec — and buys nothing, since no conversation needs ordering against another. Per-conversation counters are the whole trick.
  • "Deliver to 100K members synchronously." That's the broadcast problem wearing a group-chat costume — §7's answer: it's a different product shape, pull-based.

09

Q&A with full model answers

Four questions that come up in the room, answered the way a senior engineer would answer them — verdict first, reasoning after.

Q1
Why WebSockets? Why not just have the client poll every couple of seconds?
A "prove you did the math" question. They want the three costs named with numbers, not vibes.

Model answer: "Polling loses three ways, and I can price all three. One: header tax — every HTTP request carries roughly a kilobyte of headers for a 150-byte message. Polling 15M devices every 2 seconds is 7.5M requests a second of pure overhead; a WebSocket frame is a few bytes on a connection we already paid to open. Two: latency floor — with polling, delivery can never beat the poll interval, so 'real-time' is a lie you tune with the interval knob; a socket delivers in network time. Three: battery — each poll wakes the phone's radio, while a socket with a 45-second heartbeat lets the radio sleep between pings. That's why every real chat app is sockets at the edge. The price we pay is stateful servers — 15M sockets across ~20 boxes — and the roster to find which box holds whom. But the alternative is burning bandwidth and battery to simulate what a socket does natively."

Q2
A player hits send as the train enters a tunnel. The POST times out, the phone retries, and he emerges with signal. Is the message delivered once, twice, or never?
A delivery-semantics question wearing a UX costume. They're checking idempotency, not networking trivia.

Model answer: "Once — by construction, not by luck. Walk it through. The first POST may or may not have persisted before the tunnel ate the response; the phone doesn't know, so it retries with the same client_msg_id. The message store has a uniqueness constraint on that key: if the first attempt persisted, the retry is recognized as a duplicate and the server just returns the original server_seq — no second row, no second sequence number. If the first attempt never landed, the retry persists normally. Either way the conversation holds exactly one copy. On the receive side, devices keep a small dedupe cache of recent client_msg_ids, so even a replayed push is ignored. The formula: at-least-once network plus idempotent writes equals exactly-once user experience. The failure mode I'd actually worry about is a retry storm — a phone hammering POSTs in a flap — and that's what the per-user rate limiter is for."

Q3
The club launches a 100K-subscriber announcement channel. Your group-chat design does a roster lookup and a push per member. Defend or redesign.
They're testing whether you recognize when a problem changes shape. The wrong answer is "shard it harder."

Model answer: "Redesign — because at 100K members this stopped being a group chat. The per-message cost of my design is O(members): 100K roster lookups and up to 100K socket pushes per announcement, and one popular post an hour makes the router do this all day. That's the broadcast problem, and broadcast wants pull, not push. So: the channel becomes a single persisted, sequenced log — one durable write per announcement. Subscribers read with their cursor, exactly like offline sync; online subscribers get a lightweight 'new posts available' nudge rather than the full payload pushed. No per-member fan-out on the send path at all. The trade is honest: announcements arrive with pull latency instead of push latency, which is fine for fixture news and wrong for a conversation. The general principle: push for conversational scale where every member might reply, pull for broadcast scale where 99.9% of members only read. Same building blocks, different shape."

Q4
A connection server dies mid-evening with 700K sockets on it. Walk me through what the users feel.
A failure-mode question. They want the blast radius named precisely — and what doesn't break.

Model answer: "Almost nothing — and that's the design working. What dies: 700K TCP sockets. What doesn't die: any message, any conversation, any cursor — because the connection server holds no authoritative state. Messages live in the message store, routing state lives in the roster. So each affected phone's socket drops; the client reconnects within seconds — consistent hashing usually lands it on a nearby box — re-registers in the roster, and replays from its per-conversation cursor. Messages sent during the gap were persisted by the API tier before routing, so they're waiting in the store; the reconnect sync picks them up in order. What the user feels: the app shows 'connecting…' for a few seconds, then everything arrives — possibly a burst of catch-up messages, all in sequence. The thing I'd watch on the dashboard is the reconnect thundering herd: 700K clients reconnecting at once is its own spike, so clients reconnect with jittered backoff. The deeper point: this is why the edge is stateless by design — crashes are a reconnect event, not a recovery event."

10

Practice drills (untimed)

Untimed, rubric-graded. Do them on paper or out loud — the point is the reasoning, not the clock.

Drill 1 — Size it: matchday spike

Riverside FC reaches the cup final. DAU doubles to 100M for the evening, 50% are online at peak, and message rate hits 8× the daily average. Using §2's baseline (50M DAU, 58K msgs/sec avg), compute: peak concurrent sockets, connection servers needed at 750K sockets/box, and peak messages/sec. Then name what breaks first and your first two mitigations.

Rubric: sockets = 100M × 50% = 50M → ~67 boxes (up from ~20) · peak writes = 58K × 8 ≈ 464K/sec, still fine for a sharded LSM store spread over per-conversation counters · identifies the connection tier and router fan-out as the first bottleneck, not the database · mitigation 1: pre-scale connection servers ahead of the known event (it's on the calendar) · mitigation 2: shed load gracefully — stretch heartbeat intervals, degrade typing indicators/presence first (ephemeral features), protect message persist+route · bonus: notes the reconnect herd if a box dies under the spike, and jittered backoff.

Drill 2 — Defend the choice: per-conversation sequence vs timestamps

Your interviewer says: "Sequence counters are coordination overhead. Just stamp each message with the server's receive time and sort by it — simpler, no counters." Give the two-minute rebuttal.

Rubric: concedes timestamps look simpler · names the two-message-same-millisecond tie problem and that ties need a tiebreaker anyway (which is a sequence) · notes clock granularity across API servers and that sorting 50-message pages by (ts, tiebreak) at read time pushes ordering cost to every read · lands on: the counter's 'coordination' is one atomic increment per conversation — conversations are independent, so there is no global contention; it buys O(1) ordered writes and trivial cursor pagination · bonus: mentions hybrid logical clocks as the real alternative and why they're overkill here.

Drill 3 — Design disappearing messages

Riverside FC wants disappearing messages: the coach sets the squad chat to 24-hour expiry, and every message vanishes from every device 24h after sending. Sketch the design — where the timer lives, what "vanish" means for the store, the caches, and E2EE — and name what you deliberately don't guarantee.

Rubric: timer is server-side (client clocks can't be trusted) — an expiry timestamp on the message row, enforced at read time ("don't serve expired") plus a background sweeper for the store · tombstone or hard delete from hot storage; media blobs deleted from blob store · read-path enforcement covers caches (cache entries keyed with TTL ≤ remaining life, or checked against the row) · under E2EE the server deletes ciphertext it can't read — same mechanism works · explicitly does not guarantee deletion from screenshots, rooted devices, or backups already taken — says this out loud · bonus: notes the read-receipt/cursor edge (a message expiring before its read cursor passes it) and resolves it (cursors advance past expired seqs on sync).

11

Cheat sheet & 60-second framing

Chat system — six decisions

  1. Transport: one WebSocket per device; connection servers hold sockets, roster maps user → box; edge holds no authoritative state, so crashes are reconnect events.
  2. Commit: persist before route — the 202 ends the send path; routing is async, idempotent, and replayable from the durable record.
  3. Ordering: per-conversation sequence counter (one atomic increment, no global contention); arrival order is definitionally correct; never trust client clocks.
  4. Delivery: at-least-once network + idempotent writes (client_msg_id) = exactly-once UX; offline is just cursor replay — the store is the queue.
  5. Ephemerals: presence and typing ride a separate channel with TTLs, fanned out to open conversations only — never the message path, never persisted.
  6. Scale shapes: push for conversational scale (bounded groups), pull for broadcast scale (100K channels); media via blob store + CDN, never through the socket; FCM/APNs as the dead-app fallback; E2EE hides content, not metadata.

60-second framing — how to open in the room:

"A chat system moves short messages between people in under a second while they're online, keeps them ordered per conversation, and never loses one to a dead phone. Scope: 1:1 and group chat, text plus media, presence, typing, read receipts, multi-device, end-to-end encryption. Sizing: 50M daily users at 100 messages a day is 5B messages a day — about 58K writes a second average, 4–5× at peak — and roughly 15M concurrent sockets at the busiest minute, so this is a connection-and-fan-out problem, not a storage problem. The design: one WebSocket per device held by a fleet of connection servers, with a roster mapping each user to their box — and the edge holds no authoritative state, so a crash is a reconnect event, not a recovery. Sending is POST with a client-generated idempotency key; the server persists the message with the conversation's next sequence number and returns 202 — that ends the send path. Routing happens async: roster lookup per recipient, push down live sockets, skip the offline. Offline isn't a special case — the client keeps a per-conversation cursor and replays everything after it on reconnect. Ordering comes from the per-conversation counter, which is one atomic increment with no global contention. Presence and typing ride a separate TTL-based channel, never the message path. Groups past ~tens of thousands of members change shape into broadcast channels, which are pull-based. Media goes via blob store and CDN, never through the socket; killed apps fall back to OS push; encryption hides content but not metadata."
