READ · WHAT TIME COMPLEXITY IS

Learn what "it gets slower" really means

Get the core idea and the three words this whole lesson runs on.

A time complexity describes how much work an algorithm does as its input grows. Not seconds on your laptop — work, counted in basic steps — so the same answer holds on any machine.

Picture a referee checking eligibility before kickoff. If there is exactly one question — "is the captain eligible?" — she checks one page of the rulebook, once. Now imagine she must check every player in the squad. The work doubles when the squad doubles. Time complexity is the sentence that describes how the work grows when the squad gets bigger: "constant," "grows with the squad," "grows with the square of the squad." One sentence, no timing involved.

The three words that run this lesson
  • n — the size of the input. The number of players, events, users, keys. Every complexity statement is a sentence about n: "when n doubles, the work…"
  • Operation — one basic step: a comparison, an array access, a pointer move. We count operations, not seconds, because seconds change with hardware and load.
  • Growth rate — the shape of the curve as n grows: flat, straight, or exploding. Growth rate is what you compare; exact step counts don't matter.

Trade-off stated out loud: counting operations loses machine-level accuracy — but gains machine-independence. You can compare two algorithms on a napkin, years before a benchmark exists.

READ · READING BIG-O

Read the O like a plain sentence

Learn the three simplification rules, then practice reading each one aloud.

Big-O is notation for "the work grows at most this fast." O(n) reads: "proportional to n, in the worst case." The O is just a promise: no matter the input, the growth stays within this shape.

RULE 1Keep the fastest-growing term only. In 3n² + 2n + 7, the n² term dominates everything else as n grows. The rest is noise.
RULE 2Drop all constants. 3n² becomes O(n²). A machine twice as fast removes the 3; the n² shape stays.
RULE 3Name the worst case. Big-O is a ceiling, not an average. A linear search that usually finds its target early is still O(n).

Say them out loud until they feel obvious: 2n + 5 is O(n) ("grows linearly"). n² / 2 is O(n²) ("grows quadratically"). Two nested loops over n elements — one loop inside the other — is O(n²) even if the inner loop is short.

The two words people mix upWorst case is the slowest input (Big-O's default). Average case is the typical input, which you only quote when you can defend the distribution. In interviews, state the worst case first; mention the average case only if asked, and say so explicitly.

Trade-off stated out loud: Big-O deliberately throws away information — exact constants, best cases, typical inputs — to buy one thing: a fair comparison of how algorithms behave when n gets large.

READ · THE SIX CLASSES

Meet the six shapes that matter

Follow one running example through all six shapes. Learn to feel the gaps between them, not memorize formulas.

The running example: a season's match-event log with n events — goals, cards, substitutions. One example, six operations, six growth shapes.

Notice the gaps: at n = 1,000, O(n log n) is about 10,000 operations while O(n²) is 1,000,000 — a hundred-fold difference from one extra n. Section 04 makes you feel this with real numbers.

Why logarithms keep showing upEvery time you halve a sorted space — binary search, a balanced tree lookup — you get O(log n): log₂(1,000,000) is only about 20 steps. A binary search tree stays balanced so each comparison discards half the remaining keys. If the tree degrades into a linked list, lookups fall back to O(n) — which is exactly why balanced variants (AVL, red-black) exist.

READ · AMORTIZED COST

Average the expensive moment over the cheap ones

Learn why a dynamic array's append is "O(1)" even though some appends cost O(n).

Amortized complexity spreads one expensive operation's cost over the many cheap operations that came before it. The claim is about the average per operation across a whole sequence — not about any single call.

A dynamic array (the list in Python, ArrayList in Java) starts with a small backing array. Appends are cheap — until the array fills up. Then it allocates an array twice the size and copies everything over: an O(n) copy. But that copy only happens after n cheap appends filled the array. Spread the cost of the copy over all the appends that triggered it: each append costs about 2 operations on average. So append is O(1) amortized.

The stadium version: the club builds a stand with spare rows. Filling a seat is instant. When the stand sells out, they add a whole new tier — one painful construction summer — but they built enough seats that the next rebuild is years away. Divide one summer's construction over every seat sold since the last rebuild, and each seat's share is small.

Why doubling, not +1?If the array grew by one slot per resize, every append would trigger a copy and appends would cost O(n) each — O(n²) for n appends. Doubling means each resize covers exponentially more appends, which is what makes the amortization work. Halving-on-shrink usually waits until the array is quarter-full to avoid resizing back and forth on one oscillating append/remove.

Trade-off stated out loud: amortized O(1) is an average promise. Any single append can still hit the expensive resize — fine for a list of match events, risky for a latency budget with a hard tail-latency ceiling.

READ · SPACE COMPLEXITY

Count the extra memory, not the input

Learn the one rule that makes space analysis simple.

Space complexity is Big-O for memory: how much extra memory an algorithm needs as n grows. The input itself doesn't count — only what the algorithm adds.

O(1) space

A running tally: counting goals with a single integer. The log can be a billion events long and you still hold one number.

Wins when: you can fold results into a fixed set of accumulators.

O(n) space

A lookup table: goals per player in a hash map with one entry per player. Memory grows with the input.

Wins when: you trade memory for speed — the map makes each lookup O(1).

O(log n) / O(n) recursion

Merge sort's call stack is O(log n) deep; naive quicksort's worst case is O(n) deep. Recursion depth is memory too — a deep call stack is a hidden space cost.

Wins when: you pick iterative code or tail-safe recursion for deep structures.

Hidden O(n²)

Building a "similarity matrix" of every player pair as a real 2D array — versus just storing each pair's score in one flat list, which is also O(n²) but honest. The trap is allocating structure you never needed.

Wins when: you notice the matrix before it ships.

Trade-off stated out loud: time and space are the oldest trade in computing. Caching is exactly this bargain: spend O(n) memory to buy O(1) lookups. In interviews, name the trade — "I'll use O(n) extra space to drop lookup from O(n) to O(1)" — instead of silently assuming one of them.

READ · BACK-OF-THE-ENVELOPE SIZING

Use complexity before you draw boxes

This is where complexity stops being an algorithms topic and becomes a system design skill.

Before choosing servers, sharding, or caches, ask: what is the complexity of the work itself? No amount of horizontal scaling saves an O(n²) algorithm at web scale.

PLAYERS (n)500
PAIRWISE CHECKS (n²)125,000
AT 10⁸ OPS/S~1 ms

500 players, pair-wise: 125,000 operations, a millisecond — harmless. Now the "users who like each other's posts" version: 100 million users is 10¹⁶ operations — over three years on one machine, and throwing more machines at it is a losing fight because the work itself explodes. The correct move is not scaling; it is changing the algorithm: precompute pairs incrementally, sample, or rank candidates instead of comparing everyone.

The interview habit to build: when someone proposes "compare every X with every Y" or "sort the entire table every request," immediately say the complexity out loud — O(n²) per request at our traffic — and propose the alternative. Sorting 10 million rows per request is O(n log n) per request; caching the sorted result and updating incrementally is O(log n) per new row. That sentence is the interview answer.

What a strong answer sounds like"Loading each user's feed by scanning all posts is O(n) per user, which is O(n²) total at our scale — so I'll fan out writes to per-user feeds instead. Each write is O(followers), and reads become O(1)-ish." You named the complexity, named the scale, and named the trade.
QUIZ YOURSELF · FULL MODEL ANSWERS

Answer first, then open the model

For each question, name the complexity, say why, and state the consequence at scale before revealing the answer.

1. You need "goals per player" from a season log of n events. What is the time and space complexity, and why?

Model answer: Time is O(n): one pass over the log, and a hash-map lookup plus increment per event is O(1) on average. Space is O(n) in the worst case — one map entry per distinct player, and distinct players can approach n for tiny squads.

The key sentence: I trade O(n) extra memory to avoid an O(n²) double loop (for each player, re-scan the log). At 10 million events the single pass is fractions of a second; the nested version would be 10¹⁴ operations.

2. Binary search is O(log n). Your log isn't sorted. Is the search still O(log n)?

Model answer: No. Sorting first costs O(n log n), so the total is O(n log n) — and if you sort on every query, every query pays it. The correct breakdown: one O(n log n) sort, then unlimited O(log n) lookups. This is why "precompute once, query many times" is a design principle: move the expensive work out of the hot path.

If the interviewer pushes, add: inserting into a sorted array costs O(n) per insert (shifting elements), which is why write-heavy sorted data goes to a balanced tree — O(log n) inserts and lookups.

3. Your service does a pairwise comparison of users on every request. At 1M users and 1,000 requests/s, is more hardware the answer?

Model answer: No. Each request is O(n²) = 10¹² operations; at 1,000 requests/s that's 10¹⁵ ops/s — more than any server fleet reasonably does, and every doubling of users quadruples the work. Hardware can't fix growth rate.

The fix changes the algorithm, not the fleet: precompute candidate pairs offline or incrementally, restrict comparison to a shortlist (O(k) with small k), or invert the direction — index by interest and only compare users who share one. If n² pairs are truly needed, batch them in an offline job where throughput matters and latency doesn't.

4. When is O(n log n) sorting "wrong" in a system design?

Model answer: When the sort sits in a hot path and its input barely changes. Sorting a 10-million-row table per request is O(n log n) per request; caching the sorted result and maintaining it incrementally on writes is O(log n) per write. Same answer as before: precompute, invalidate on change.

The other classic case: sorting just to find the top k. Full sort is O(n log n); a k-sized heap is O(n log k). For a "top 10 trending" query over millions of rows, that difference is the whole optimization.

TAKEAWAYS · REMEMBER THESE

Use the senior-level checklist

Before endorsing any design, say its complexity out loud.

  • Big-O counts operations, not seconds — growth shape beats step counts.
  • Drop constants, keep the dominant term, and always name the worst case.
  • Feel the gaps: at n = 10⁶, O(n²) is a trillion and O(n log n) is twenty million.
  • Amortized O(1) is an average across a sequence, not a per-call guarantee.
  • Space complexity counts extra memory; recursion depth counts too.
  • Time and space are a trade: say which one you're spending.
  • No cluster survives a hot path with the wrong complexity.
  • Precompute once, query cheaply: move work out of the request path.
  • "For every X, every Y" is O(n²) — flag it the moment you hear it.
  • Top-k wants a heap, not a full sort.
The sentence to remember

Complexity is the first sizing calculation of every system design. Before you draw boxes and arrows, ask what the work itself costs as n grows — because the wrong growth rate can't be cached, sharded, or bought away.
