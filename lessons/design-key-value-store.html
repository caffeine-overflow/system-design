Lesson 38 · Classic design

Design a Distributed Key-Value Store — the engine behind DynamoDB, Cassandra, and every session store

It is the cup final at Riverside FC. One million fans have the app open: the live score, each player's goal tally, every shopping cart, every login session — all of it is just a label with a value attached. One fan's phone asks for match:today:score and expects "Riverside 2–1" back in a few milliseconds, from a store holding a billion such pairs, spread across thirty servers, while servers die mid-match and nobody notices. That store is the key-value store, and it is the quiet engine underneath almost everything else you have designed: the session store in the auth lesson, the cart in the payment lesson, the timelines in the feed lesson. Today you design it from zero.

What is a key-value store?

Start from zero. A key-value store is the simplest database there is: it stores pairs — a key, which is a unique label, and a value, which is whatever you attach to that label — and it offers exactly three operations: put(key, value) to store one, get(key) to fetch one back, and delete(key) to remove one. That is the whole interface. The value is opaque to the store: it does not know whether the value is a JSON shopping cart, a session token, or a number — it just stores the bytes and hands them back. The soccer running example: the Riverside FC kit room has a wall of numbered pegs. Peg player:9:goals holds the number 27. Peg match:today:score holds "Riverside 2–1". Peg session:8f3a… holds a fan's login token. You walk in, read the label, take the item — no searching through shelves, no asking the kit manager to join three tables. A key-value store is that wall of pegs, scaled to a billion pegs, spread across many rooms, where any peg can be found in one hop.

Terms, defined as they appear

Key: the unique label for one item — player:9:goals. Value: the bytes attached to the key — 27, a JSON cart, a session blob. Put / get / delete: the only three operations — store, fetch, remove. Replication factor (N): how many copies of each key the store keeps — usually 3. Preference list: the N nodes responsible for one key, in ring order. Coordinator: the node that receives a request and talks to the preference list on the client's behalf. Quorum: a number of replicas that must agree — W for writes, R for reads. Vector clock: a per-replica version counter that records which writes have seen which — the tool that detects concurrent writes. Tombstone: a marker that says "this key was deleted", kept until every replica has seen it. Hinted handoff: a write held temporarily by a healthy neighbour when its real owner is down. Anti-entropy: the background process that compares replicas and fixes drift — usually with Merkle trees. Gossip protocol: nodes periodically exchanging state with a few random peers, so the whole cluster learns about a dead node in seconds. Sloppy quorum: letting a healthy node outside the preference list stand in for a dead one, so writes still succeed. LSM tree: the storage engine inside most key-value stores — writes go to an in-memory table, then flush to sorted files on disk. Memtable: that in-memory table. SSTable: the sorted, immutable file on disk that the memtable flushes into.

Why not just use a relational database? A relational database gives you joins, transactions, and ad-hoc queries — and charges you for them in complexity and latency. A key-value store gives those up and gets something in return: lookups in constant time, because the key hashes straight to the node that holds it, with no index to walk and no query planner to consult. That is the trade, and it is the right trade for a huge class of work: sessions, carts, user profiles, feature flags, counters, caches, leaderboards — anything where you always know the key and never need to ask "find all players with more than 20 goals". The moment you need that second kind of question, you need a different store, or a secondary index on top — and knowing which question you are answering is the first design decision. A key-value store is not a worse database; it is a database that chose one job — given this key, give me this value, fast, even when machines die — and does that job better than anything else.

The one idea to carry through the whole lesson: a distributed key-value store is three decisions wearing a trench coat — where a key lives, how many replicas must agree, and what happens when two writes disagree. Where a key lives is consistent hashing on a ring (Lesson 10). How many replicas must agree is the quorum dial (Lesson 5, Lesson 7). What happens when two writes disagree is conflict resolution — vector clocks and the choice between last-write-wins and letting the client merge. Everything else — the gossip, the hints, the Merkle trees, the LSM engine — is machinery that makes those three decisions survive real hardware, which fails constantly and without warning.

Requirements and back-of-the-envelope math

Scope first. We are designing the store behind Riverside FC's app: sessions, live scores, player stats, shopping carts, feature flags. One billion keys, each with a value of about 1 KB on average. The workload is read-heavy — about 100,000 reads a second, 10,000 writes a second — and the latency target is single-digit milliseconds for a get. Availability matters more than perfect consistency: if a fan's cart shows a stale item for a few seconds, nobody's match is ruined; if the store refuses writes during the cup final, everybody notices. So this is an AP-flavoured store in CAP terms (Lesson 7): it keeps answering during a network partition, and reconciles afterwards.

  • Storage: 1 billion keys is about 1 TB, and 3 copies make it about 3 TB. 1,000,000,000 keys × 1 KB of value = 1,000,000,000 × 1,024 bytes = about 1.02 TB of values. The keys themselves add 1 billion × 32 bytes ≈ 32 GB — small next to the values. With a replication factor of 3, the cluster stores about 3.1 TB in total. Spread across 30 nodes, that is about 103 GB per node — a comfortable size for one machine, with room to grow, and small enough that a node can be rebuilt from its neighbours in minutes rather than hours.
  • Throughput: the read load is the load. 100,000 reads a second × 1 KB = 100 MB/s of values flowing out. But each read touches R = 2 replicas (the quorum dial, below), so the cluster actually performs 200,000 replica-reads a second — about 6,700 replica-reads a second per node on 30 nodes, or 6.7 MB/s each. Writes are lighter: 10,000 writes a second × 1 KB = 10 MB/s of new data, × W = 2 replicas = 20 MB/s of replica writes, under 1 MB/s per node. The network is never the constraint; the per-node disk and CPU are, and they are nowhere near their limits — which is the point: the design has headroom for the cup-final spike, and the spike is the day that matters.
  • The write path's hidden cost: the LSM engine multiplies writes about 10×. Inside each node, writes land in the memtable and are later flushed and compacted through the SSTable levels (Lesson 8). A leveled LSM tree rewrites each byte roughly 10 times over its life — so 10,000 writes a second × 1 KB × 10 = 100 MB/s of disk writes cluster-wide, about 3.3 MB/s per node. That is still trivial for a modern SSD, but it is the number that decides your disk budget, and the number that bites if you ever raise the write rate tenfold without re-checking it. The read path, by contrast, is nearly free once the working set is in the page cache: a get is a hash, a memtable check, and usually one SSTable read — a few milliseconds, most of them network.
  • Adding a node: 32 GB moves with consistent hashing, 968 GB with naive hashing. With 30 nodes and 1 billion keys, each node holds about 33.3 million keys. Add a 31st node: the ring (Lesson 10) hands the new node 1/31 of the key space — about 32.3 million keys, 32 GB — and only that much moves. With naive hash(key) mod N rehashing, changing N from 30 to 31 moves about 30/31 of all keys — 968 million keys, 968 GB — nearly the whole dataset, across the network, while the match is on. That 30× difference is the entire case for the ring, and it is why no production key-value store rehashes naively. (Lab B lets you run these numbers yourself.)
  • Quorum math: W = 2, R = 2, N = 3 gives you strong reads and one dead node. The rule is W + R > N: 2 + 2 = 4 > 3, so every read overlaps every write on at least one replica, and a read after a write sees the write — read-your-writes. And the store survives one dead node for both reads and writes, because N − R = 1 and N − W = 1: two replicas are still up. How available is one key? If each node is up 99.9% of the time, the chance that at least 2 of 3 replicas are up is 3 × 0.999² × 0.001 + 0.999³ = 0.999997 — 99.9997%, or about 1.6 minutes of downtime per key per year. Compare W = 1, R = 1: the key is available unless all three replicas are down — 1 − 0.001³ = 99.9999999% — but reads can return stale values, because a read may miss the replica that got the latest write. Availability and freshness are the same dial, turned opposite ways. (Lab A plots the whole dial.)
  • The hot key: one key can break a balanced ring. At full time, one million fans a minute ask for match:today:score — about 16,667 reads a second on a single key. That key lives on 3 replicas, so each one serves about 5,556 reads a second for that key alone — before any other key's traffic. Consistent hashing balances key counts, not load; a hot key is a hot partition (Lesson 24) wearing a different shirt. The fixes are the same family: cache the key at the edge or in the client (a 5-second TTL turns 16,667 origin reads a second into one fetch per edge node per 5 seconds), replicate the hot key more widely than RF = 3, or split the key by suffix and aggregate at read time.
The decision the numbers force

Three numbers decide the shape of the store, and they are all dials, not constants. The replication factor decides the storage bill — 3 copies of 1 TB is 3 TB, and every extra copy is a terabyte you pay to store and to keep in sync. The quorum decides the consistency–availability trade — W = 2, R = 2 buys read-your-writes and one dead node at the price of waiting for the second-slowest replica on every operation. And the ring decides the cost of growth — 32 GB moved per added node with consistent hashing, against 968 GB with naive hashing. A design that quotes one of these without the other two has not designed a store; it has picked a favourite number. The interviewer is listening for all three, stated together, with the arithmetic behind them.

The architecture, in one pass

Follow one fan's tap — the app asks for player:9:goals — from phone to value and back. There are six stages, and each one exists to answer a different failure.

  1. Client — hash the key, or ask the router. The client library hashes the key (MD5 or SHA-1, the same idea as Lesson 10) and walks the ring to find the preference list — the three nodes that own that key. Some stores keep the ring on the client (DynamoDB's client does not, but Cassandra's drivers do); others put a thin routing layer in front. Either way, the client sends the request to the first node on the list, which becomes the coordinator for this request. No central directory, no single point of failure: every node knows the whole ring from gossip, and every client can find any key from the hash alone.
  2. Coordinator — fan the request out, wait for the quorum. The coordinator forwards the get to all three replicas in the preference list and waits for R = 2 replies — the two fastest, not the two nearest. It does not wait for the slowest replica: the slowest replica is the tail (Lesson 37), and waiting for it would make every read as slow as the worst node in the cluster. For a put, it forwards to all three and waits for W = 2 acknowledgements before telling the client the write succeeded. The third replica gets the write too, eventually — through hinted handoff if it is down, through anti-entropy if it missed it.
  3. Preference list — three nodes, in ring order, and the sloppy stand-in. The key's owner is the first node clockwise from the key's hash on the ring; the next two clockwise nodes are the other two replicas. If one of the three is down, the coordinator does not fail the request — it writes to the next healthy node clockwise instead, the sloppy quorum, and that node holds the write as a hint until the real owner returns. The preference list is also where virtual nodes (Lesson 10) do their quiet work: each physical node owns many small ring segments, so the key space is spread evenly and a new node takes a little from many neighbours instead of a lot from one.
  4. Storage engine — the LSM tree inside each node. A write lands in the memtable in memory and in a write-ahead log on disk, and the coordinator is acknowledged — the write is durable before the client hears back. When the memtable fills, it flushes to an immutable SSTable; background compaction merges SSTables and drops overwritten and tombstoned entries. A read checks the memtable, then the newest SSTables, using a Bloom filter per SSTable (Lesson 20) to skip files that cannot contain the key. Deletes are not erasures: a delete writes a tombstone, and the key only truly disappears when compaction drops it — after the tombstone has had time to reach every replica, or a returning node would resurrect the deleted value.
  5. Conflict resolution — when two writes race, someone has to decide. Two fans update the same cart from two phones at the same time, and the writes land on different replicas before either has seen the other. The store cannot pick a winner by the wall clock — clocks skew (Lesson 21's warning) — so it keeps both versions, each stamped with a vector clock, and hands both back on the next read. The client, or the application, merges them: a cart merges by union, a counter merges by taking the max, a "last writer wins" field takes the newest timestamp and accepts the risk. The rule: the store detects the conflict; the application resolves it. A store that silently picks a winner has chosen to lose somebody's write without telling them.
  6. Background repair — gossip, hints, and Merkle trees. Three processes run forever. Gossip spreads membership and failure news: every node periodically tells a few random peers what it knows, so a dead node is suspected cluster-wide within a few seconds. Hinted handoff replays held writes when a node returns. And anti-entropy compares replicas with Merkle trees: each node builds a hash tree over its key ranges, and two nodes compare roots — if they match, the ranges agree; if they differ, they descend until they find the differing leaves, and only those ranges are exchanged. With 33 million keys per node and leaves of 1,024 keys, the tree is about 15 levels deep: a handful of hashes finds the drift, where a full copy would move 103 GB.

Two supporting facts complete the picture. First, there is no master and no leader: every node can coordinate any request, which is why the store has no single point of failure and no failover event — a dead node is just a node that stops answering, and the ring routes around it. That is the Dynamo design, and it is the opposite of the consensus design in Lesson 14: Raft elects a leader and refuses minority writes to stay strongly consistent, while Dynamo accepts writes on any side of a partition and reconciles later. Same problem, opposite trade — and the right answer depends on whether your data can tolerate a merge. Second, the store does not do range queries: asking for "all players sorted by goals" means scanning every node, because the keys are scattered by hash. If you need that question, you add a sort key inside a partition (DynamoDB's partition key + sort key), build a secondary index, or pick a different store. A key-value store that pretends to be a query engine is a store that has forgotten its one job.

The heart of it: three decisions that make or break the design

1. Where a key lives — the ring, and why virtual nodes matter

The ring is the whole addressing scheme: hash the key, hash the nodes, walk clockwise, and the first node you meet owns the key (Lesson 10). The subtlety is not the ring but the virtual nodes. Without them, a physical node owns one big arc of the ring, and arcs are never equal — one node gets 5% of the keys and another gets 1%, and the unlucky node carries five times the load. With, say, 100 virtual nodes per physical node, each machine owns 100 small arcs scattered around the ring, and the law of large numbers evens the load out: each node holds close to 1/30th of the keys, within a few percent. Virtual nodes also make growth graceful: adding a node takes 100 small slices from 30 different neighbours instead of one big slice from one, so no single node is hammered by the rebalance and no single node has to stream 32 GB at once. And they make heterogeneous hardware work: give the big machine 200 virtual nodes and the small one 50, and the load follows the capacity. The soccer analogy: one steward covering a whole stand gets swamped when that stand erupts, but a hundred stewards each covering a few rows in different stands spread the surge evenly — and adding a steward takes a few rows from many stands, not a whole stand from one.

2. How many replicas must agree — the quorum dial, and what it really buys

N = 3, W = 2, R = 2 is the default for a reason: it is the cheapest configuration that buys read-your-writes, and it survives one dead node. But the dial turns both ways, and each setting buys something different. W = 1, R = 1 is the fastest setting — one replica's acknowledgement and you are done, and the key is available unless all three replicas are down — but a read can return a stale value, because it may hit the replica that has not seen the latest write yet. W = 3, R = 1 makes writes strong: every write reaches all three replicas before it succeeds, so any single read sees it — but one dead node blocks every write to its keys, and write availability collapses to the availability of all three nodes at once. W = 1, R = 3 makes reads strong and writes cheap, which is right when reads must never be stale and writes are rare. The rule the dial obeys is simple: W + R > N buys read-your-writes; W + R ≤ N buys eventual consistency and higher availability. Two things the dial does not buy: it does not order concurrent writes — two writes can both reach quorum on different replicas and still conflict, which is what vector clocks are for — and it does not make a single replica fast, it only makes the system wait for the second-fastest of three. Tune the dial per use case, not per store: sessions can run W = 1, R = 1, carts want W = 2, R = 2, and the one key that must never be stale gets W = 3.

3. What happens when two writes disagree — vector clocks, and the merge that belongs to the application

Take the worked example. Two fans edit the same cart at the same moment, from two phones, and the writes land on different replicas. Replica 1 stamps the first write with the vector clock [1, 0, 0] — "replica 1 has seen one write, the others have seen none". Replica 3 stamps the second write [0, 0, 1]. Neither clock dominates the other — each has a count the other lacks — so the clocks are concurrent, and the store knows the writes raced. The next get returns both versions, the siblings, and the application merges them: for a cart, the union of the items; for a counter, the maximum; for a profile field, the newest timestamp. The merged write goes back with the clock [1, 0, 1] — "both writes seen" — and the conflict is resolved. Compare the alternative, last-write-wins: pick the write with the newest wall-clock timestamp and throw the other away. It is simpler, and it silently deletes one fan's cart items whenever two clocks disagree by a millisecond — which, on machines whose clocks skew by tens of milliseconds, is often. The senior rule: the store detects conflicts, the application resolves them, and last-write-wins is only acceptable when losing a write is genuinely harmless — a "last seen" timestamp, a cached score, never a cart, a balance, or a booking. Dynamo, Cassandra, and Riak all made this choice, and the interviewer will ask which side of it your data falls on.

The senior line on the three decisions

Every key-value store is the same three sentences, and the interview is won by saying them with numbers attached. The ring says where a key lives — 1 billion keys over 30 nodes is 33 million a node, and adding a node moves 32 GB, not 968 GB. The quorum says how many replicas must agree — W + R > N buys read-your-writes at 99.9997% per-key availability, and every step away from it trades freshness for speed in a way you can name. The conflict rule says what happens when two writes race — vector clocks detect it, the application merges it, and last-write-wins is a choice to lose data, not a default. Say those three sentences, with the arithmetic, and the rest of the design — the gossip, the hints, the Merkle trees — is machinery that follows.

Senior-depth traps

  • "Quorum means strongly consistent." It does not. W + R > N guarantees that a read overlaps a write on at least one replica, so a read after a write sees it — but it says nothing about two writes that race each other. Both can reach quorum on different replicas, and the store hands you two siblings and asks you to merge them. Quorum is about intersection, not about ordering, and an answer that treats a quorum as a lock has confused a read guarantee with a write guarantee. The follow-on question is always: who resolves the conflict, and what does the merge look like for this data?
  • "More replicas means more availability and more speed." More replicas means more copies to keep in sync: writes wait for W acknowledgements out of a larger set, storage multiplies, repair traffic grows, and a hot key still lives on only N of them. Reads can go to the nearest replica, which helps latency, but writes pay for every extra copy — and with W = 3 out of N = 5, a write waits for the third-fastest of five, which is slower than the second-fastest of three. The right replication factor is the smallest one that survives the failures you actually expect: 3 for one dead node, 5 only when two simultaneous failures are a real scenario, not a theoretical one.
  • "Consistent hashing solves hot keys." It solves the opposite problem: it balances the number of keys per node, so adding a node moves 3% of the data instead of 97%. It does nothing for a single key that takes 16,667 reads a second, because that key lives at one ring position on three replicas, however evenly the other 999,999,999 keys are spread. The fix for a hot key is caching, wider replication of that key, or splitting it — and the engineer who reaches for more virtual nodes when the problem is one hot key has fixed the load balancer and left the fire burning.

Questions, with full model answers

Q1. Design a session store for 50 million users: put/get by session id, 5-minute TTL, 100,000 reads a second, and a login must never block on the store.

Model answer. I start from the workload, because it picks the dial. Sessions are write-once, read-a-few-times, and a stale session is harmless — the worst case is a fan logging in again — so this data wants availability over freshness, and the store is a key-value store with the key as the session id and the value as the session blob. I size it the same way as the lesson: 50 million sessions × 1 KB = 50 GB of live data, so even with RF = 3 the cluster holds 150 GB, and 10 nodes carry 15 GB each — the store is small, and the read rate is the real load: 100,000 reads a second, R = 1, so each read touches one replica and returns in single-digit milliseconds. I set W = 1, R = 1: a login writes to one replica and succeeds even if two replicas are down, because a login that blocks on the store is a fan locked out of the match, and a session that takes a second to reach the other replicas costs nothing. The TTL lives in the storage engine — the key carries an expiry, the LSM compaction drops it, and a tombstone is unnecessary because expiry is not a delete that a returning node can resurrect. I would add two guards: a client-side cache with a 60-second TTL for the hottest sessions, because the same fan's session is read on every tap; and a hard cap on session size, because a 1 MB session blob turns a 100,000-reads-a-second store into a 100 GB/s store. And I would close with the check: if a session read ever returns stale data, the consequence is a re-login, not lost money — which is exactly why W = 1, R = 1 is the right dial here, and why the same dial would be wrong for a cart.

Q2. Two fans update the same shared cart from two phones at the same moment, and the writes land on different replicas. What does each fan see, and how do you resolve it?

Model answer. I start by naming the race, because the resolution follows from it. The two writes are concurrent: neither replica has seen the other write, so the vector clocks are [1, 0, 0] and [0, 0, 1] — neither dominates the other, and the store cannot pick a winner without losing somebody's items. Each fan sees their own write succeed, because each write reached its quorum, and the next get returns both versions as siblings — the store detects the conflict and refuses to hide it. The resolution belongs to the application, not the store: a cart merges by union, so the merged cart holds both fans' items, and the merged write goes back with the clock [1, 0, 1], which dominates both parents and ends the conflict. I would be explicit about what I would not do: last-write-wins, because it would silently delete one fan's items whenever two wall clocks disagree by a millisecond, and clocks skew by tens of milliseconds. And I would name the case where the merge does not work: if the two writes both removed the same item, or both set the same quantity to different values, the union is ambiguous — and the honest answer is to surface it to the user ("your cart changed on another device") rather than invent a winner. The rule from the lesson: the store detects, the application resolves, and a mergeable data type is the reason a cart can live in an eventually consistent store at all.

Q3. A node dies at the cup final. Walk through what happens to reads and writes for its keys, minute by minute.

Model answer. I start with what does not happen: there is no failover event, because there is no leader to fail over from — every node can coordinate any request, so the ring simply routes around the dead node. In the first seconds, gossip spreads the news: each node tells a few random peers the node is unresponsive, and within a few seconds the whole cluster suspects it. Meanwhile, requests keep flowing: a get for one of its keys goes to the preference list, the dead node does not answer, and the coordinator returns after R = 2 replies from the two surviving replicas — the read succeeds, slightly slower, because it waited for the two replicas that are up. A put is the same shape: the coordinator writes to the two live replicas, and for the dead one it uses the sloppy quorum — the next healthy node clockwise holds the write as a hint. The write succeeds with W = 2, and the fan never knows a node died. Over the next minutes, the hinted writes accumulate — about 1,000 a second for that node's share, 600,000 hints in ten minutes — and the two surviving replicas carry the full read load for those keys. When the node returns, the hints replay, the node catches up, and Merkle-tree anti-entropy compares hash trees and fixes any range the hints missed — a handful of hashes, not a 103 GB copy. And I would close with the guardrail: if the node stays down for an hour, the hints are capped and expired, and anti-entropy — not the hint log — is what brings the node back, because an unbounded hint log is a second outage waiting to happen.

Q4. Your PM asks for "all players sorted by goals" on the key-value store. What do you say?

Model answer. I start by saying the store cannot answer that question efficiently, and why: the keys are scattered across 30 nodes by hash, so "all players sorted by goals" is a scatter-gather over every node — 30 nodes each scanning their keys, sorting locally, and shipping results back to be merged — which is slow, expensive, and gets slower as the cluster grows. The key-value store's one job is get by exact key, and a sorted scan is a different job. Then I offer the three real options, priced. First, a sort key inside a partition: make the partition key the team and the sort key the goal count, so "top scorers for Riverside" is one partition's range scan — cheap, but it only answers the question per team, not across all teams. Second, a secondary index: a separate structure keyed by goal count that points at the players — which is a second store to keep in sync, with its own lag and its own hot-key problem at the top of the table. Third, a different store for the query: keep the key-value store for lookups and put the same data in a search index or an analytics store for ranking queries — two systems, each doing the job it is good at, with the sync between them made explicit. I would close by asking the PM which question they actually need: if it is "top 10 scorers", a cached leaderboard key updated on every goal is a single get — and the cheapest query is the one you precompute.

Practice drills (untimed — depth over speed)

Drill 1 — Dial the quorum. A store runs N = 5. (a) Pick W and R for read-your-writes with the lowest write latency. (b) Reads must still work when any 2 nodes are down — what is the largest R you can pick, and what W goes with it? (c) Why is W = 5 a bad default? Rubric: (a) W = 3, R = 3 — W + R = 6 > 5 buys read-your-writes, and 3 is the smallest value that makes both sides equal, so write latency is the third-fastest of five rather than the slowest; (b) reads survive 2 down only if R ≤ 3, because 5 − 2 = 3 replicas are still up — so R = 3, and W = 3 keeps read-your-writes; (c) W = 5 needs all five nodes up, and at 99.9% per node the chance all five are up is 0.999⁵ ≈ 99.5%, so writes are unavailable about 0.5% of the time — roughly 44 hours a year — and a single dead node blocks every write to every key.

Drill 2 — Rebalance math. A store holds 500 million keys of 1 KB each on 20 nodes, and you add 5 nodes. How many keys and gigabytes move under consistent hashing, and how many under naive hash mod N rehashing? Rubric: consistent hashing moves 5/25 = 20% of the keys — 100 million keys, 100 GB — because each new node takes 1/25 of the ring; naive rehashing moves about 80% — 400 million keys, 400 GB — because a key stays put only when its hash mod 20 equals its hash mod 25, which happens for roughly 1 in 5 keys; the 4× difference is the rebalance storm, and it is why the ring exists.

Drill 3 — Cool the hot key. A key gets 50,000 reads a second. RF = 3, and each replica can serve 10,000 reads a second. Show the failure, then fix it two ways and price each fix. Rubric: 50,000 ÷ 3 ≈ 16,700 reads a second per replica, above the 10,000 limit — the replicas saturate, queueing grows (Lesson 37's knee), and the p99 for that key climbs while the other 27 nodes idle; fix one, an edge cache with a 5-second TTL: 50 edge nodes each fetch once per 5 seconds, so the origin sees 10 reads a second — the key is now a cache problem, not a store problem, at the price of 5-second staleness; fix two, replicate the hot key to 10 nodes instead of 3, so each serves 5,000 reads a second — no staleness, but the key now costs 10 copies to store and to keep in sync, and every write to it pays 10 replica writes.

Sixty-second framing

"A key-value store is the simplest database there is: a key, a value, and three operations — put, get, delete — and it trades away joins and queries to do one job fast, even while machines die. Riverside's app holds a billion keys at about 1 KB each, so the raw data is about 1 TB, 3 TB at a replication factor of 3, about 100 GB per node on 30 nodes. The design is three decisions. Where a key lives: the consistent-hashing ring, so adding a node moves 32 GB, not the 968 GB that naive rehashing would move. How many replicas must agree: the quorum dial — W = 2, R = 2 gives read-your-writes and survives one dead node, at 99.9997% per-key availability, about a minute and a half of downtime a year; W = 1, R = 1 is faster and can return stale data. And what happens when two writes race: vector clocks detect the conflict and the application merges it, because last-write-wins silently deletes somebody's cart. The rest is machinery that makes those decisions survive real hardware: gossip to spread the news of a dead node, hinted handoff so writes succeed anyway, and Merkle trees so two replicas can find their differences with a handful of hashes instead of a 100 GB copy. And the trap to name: the ring balances key counts, not load — one hot key at 16,000 reads a second will saturate its three replicas while the other 27 nodes idle, and the fix is a cache, not more virtual nodes."

Talk-track for the room

  1. Scope and the one idea: a key-value store is put/get/delete on a billion pairs, and it is three decisions — where a key lives, how many replicas must agree, and what happens when two writes disagree.
  2. Back-of-the-envelope: 1 billion keys × 1 KB is about 1 TB raw, 3 TB at RF = 3, about 103 GB per node on 30 nodes; 100,000 reads a second is 100 MB/s out, 200,000 replica-reads at R = 2; adding a node moves 32 GB with the ring against 968 GB with naive hashing; W = 2, R = 2 is 99.9997% per key, about 1.6 minutes a year.
