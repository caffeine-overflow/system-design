Lesson 12 · Core Building Blocks

Pub/Sub & Event-Driven Architecture

Message queues send work to one worker. But what about when one thing happens and many services each need to react on their own? That's publish/subscribe: one event, broadcast once, and every interested service gets its own copy. This lesson covers the fan-out model, when to pick it over queues, the failure modes that only show up at senior depth, and how event-driven patterns like choreography and orchestration actually work.

01

What is pub/sub?

Pub/sub — publish/subscribe — is a messaging pattern where one program publishes an event exactly once, and any number of interested programs each receive their own copy, without the publisher knowing any of them. If a message queue is a task handed to one worker, pub/sub is a whistle blown once that everyone on the pitch hears.

⚽ The running example: the goal is scored

One event, five reactions, zero waiting

It's the 89th minute. The striker scores. The referee's assistant presses one button — "goal scored, minute 89" — and that single event has to reach five completely different places: the scoreboard updates to 2–1, the commentator feed gets the goal call, the highlights clipper starts cutting the last 30 seconds of footage, betting settlement pays out on all "next goal" wagers, and fan notifications ping every supporter's phone.

Nobody here should wait on anyone else. The scoreboard shouldn't fail because the betting system is down. The assistant referee shouldn't have to call five people. One publish, five independent reactions — that's pub/sub. Every idea in this lesson lands on this goal.

Publisher · Subscriber · Event

A publisher is the program that creates an event and sends it once — like the referee's assistant pressing the goal button. A subscriber is a program that signs up to receive certain kinds of events and reacts to them on its own — the scoreboard, the clipper, the notifications service. An event is a short, named record that something already happened: past tense, immutable, timestamped — {"type": "goal.scored", "minute": 89, "match": "MCI-ARS"}.

Broker · Topic

A broker is the middleman that receives published events and copies them to every subscriber. A topic (also called a channel) is the named stream subscribers sign up to — "goals", "orders.placed", "payments.failed". The publisher addresses the event to the topic; the broker works out who gets a copy.

The three-way split nobody knows: space, time, and who

A direct function call couples three things: space (the caller must know where the callee is — its address), time (both must be alive at the same moment), and who (the caller must know exactly which callee it wants). Pub/sub decouples all three:

  • Decoupled in space: the publisher doesn't know the subscribers' addresses. It publishes to a topic name, not to a URL. Add a sixth subscriber — a new "goal of the season" voting service — and the publisher's code doesn't change at all. In football terms: the whistle-blower doesn't need the phone numbers of everyone in the stadium.
  • Decoupled in time: the publisher and the subscriber don't have to be awake at the same moment. The broker holds the event until the subscriber is ready. If fan-notifications is deploying during the goal, the event waits for it — nothing is lost.
  • Decoupled in "who": the publisher doesn't know how many subscribers exist, or what they do with the event. The assistant referee doesn't need to know there's a betting-settlement service at all.

That third one — the "who" — is what message queues don't give you. A queue worker is known: someone configured the queue to feed that specific worker. Pub/sub is the pattern for when the set of reactors is open-ended and changes over time.

02

How a message actually flows

One publish, then the broker does the multiplying. Follow the goal event from the assistant referee's button to five independent copies.

The three beats: publish → broker → fan-out

publish (once)  →  broker (copies × N)  →  N subscribers (each gets its own copy)
  1. Publish. The publisher builds the event and sends it to the broker, addressed to a topic — e.g. topic goals. It fires and forgets: publish doesn't wait for any subscriber to finish. The assistant referee's button press returns instantly; the scoreboard will catch up on its own.
  2. Broker receives. The broker accepts the event, persists it (writes it to disk or memory, depending on the system — section 8 covers which), and figures out which topics the event matches. This is also where it may filter or route the event: some brokers let subscribers match on attributes, like "only goals in the 2nd half."
  3. Fan-out. The broker makes one copy per subscriber and delivers each copy independently. The scoreboard's copy, the clipper's copy, and the notifications' copy are separate deliveries — if the notifications service is slow, the scoreboard still gets its goal update on time.

Push vs pull: who makes the call?

Push · Pull

In push delivery, the broker calls the subscriber — it actively sends each copy the moment it arrives (SNS pushing to an HTTP endpoint, webhooks). In pull delivery, the subscriber calls the broker — it repeatedly asks "anything new for me?" and the broker hands over what's waiting (Kafka consumers, SQS polling).

  • Push is lower-latency: the copy leaves the moment the goal happens. But it demands the subscriber be reachable and fast — if notifications can't keep up, the broker either queues up (memory pressure) or drops. Think: the stadium PA system announcing the goal to everyone at once.
  • Pull lets each subscriber set its own pace: the highlights clipper can batch-fetch every 5 seconds while the scoreboard polls every 100 ms. But it trades latency for that control — you're never faster than your poll interval. Think: each department checking the official match log on its own schedule.

What the broker guarantees — and what it pointedly doesn't

🧠 The broker's contract

It does: accept the event durably (so a publisher crash right after publish doesn't lose the goal), copy it to every currently subscribed listener, and let each subscriber fail and retry independently. A downed betting service doesn't block the scoreboard's copy — delivery per subscriber is a separate track.

It doesn't: know what the event means (it's just bytes — "goal.scored" is a string to the broker), guarantee every subscriber sees events in the same order (section 5), or guarantee exactly-once delivery (section 5). And crucially: it doesn't know about subscribers that arrive late unless the broker keeps history — a classic Redis pub/sub broker forgets everything the instant it forwards it, so a subscriber that connects after the goal never sees it. Systems with retention (Kafka keeps events for days) fix this: late subscribers replay from the log.

03

Queues vs pub/sub

Lesson 9's queue and today's pub/sub look alike — both have a broker in the middle. But they answer opposite questions: "who does this task?" vs "who needs to know this happened?" If you get this table, you'll never mix them up again.

So when do you pick which?

  • Pick a queue when the message is a task to be done once: process this payment, render this thumbnail, dispatch this runner. You want competing consumers so you can scale workers, and you want delete-on-ack so nothing is done twice.
  • Pick pub/sub when the message is a fact to be known by many: the goal was scored, the order shipped, the price changed. The set of interested parties is open-ended and grows over time.
  • The one-line test: if a new service shows up tomorrow and needs the same events, do you want it to share the existing load (queue) or get its own copy of everything (pub/sub)?

🧠 Kafka does both — and that's the senior unifier

In Kafka, the unit is the topic (a retained, ordered log). Each consumer group — a named set of cooperating consumers — gets its own copy of the whole log (pub/sub across groups: scoreboard-group, notifications-group). Within a group, the members split the topic's partitions between them, competing for messages like queue workers. So: pub/sub across groups, queue within a group. The same system answers both questions — the group boundary is the choice.

04

Fan-out math

Pub/sub's superpower — one event becomes many deliveries — is also its cost model. The publisher does O(1) work; the broker does O(N). Senior rooms always ask what the multiplier costs.

The one equation

deliveries/sec = events/sec × subscribers

One whistle, and 22 players plus the crowd hear it. In systems: if the order service publishes 1,000 events/sec and 8 services subscribe, the broker performs 8,000 deliveries/sec. The publisher only wrote 1,000 — the other 7,000 are the broker's copies. The publisher's cost is constant; the broker's cost scales with the subscriber count. Every new subscriber you add multiplies the broker's work for every event, forever.

The worked cost example

Given: 1,000,000 events per day, 4 subscribers, average message size 2 KB.

Deliveries per day: 1,000,000 × 4 = 4,000,000 deliveries/day.

Data the broker moves: 4,000,000 × 2 KB = 8,000,000 KB ≈ 8 GB/day of egress from the broker to subscribers.

Storage if retained: only the originals are stored — 1,000,000 × 2 KB ≈ 2 GB/day (per copy kept; retention multiplies by days, not subscribers).

The point: the egress bill multiplies by subscribers; the storage bill doesn't. When someone says "pub/sub is cheap because you publish once," answer: publish is cheap, fan-out is the invoice.

Per-subscriber failure isolation — why copies matter

Back to the goal: betting settlement's database is down. It stops acknowledging its copies, so the broker buffers them for betting — and only for betting. The scoreboard's copy was already delivered; the scoreboard never knew there was a problem. Each subscriber's delivery track is independent: its own buffer, its own retries, its own backlog. This is the mirror image of Lesson 9's queue problem, where one poison message blocked the whole line: in pub/sub, a sick subscriber can't slow anyone else — the broker's copies are separate patients. The lab in section 9 lets you watch this live.

⚠️ The isolation has a ceiling: "can't slow anyone else" holds only while the broker has room to buffer. If betting is down for three days and the broker's buffer for betting fills the broker's disk, everyone suffers. Isolation is real, but it's bounded by the broker's capacity — which is why per-subscriber backpressure (section 7, failure mode 4) and buffer limits are part of the design, not an afterthought.

05

Delivery semantics

The broker promises to deliver your copies — but under what guarantee? The same three semantics from Lesson 9 apply here, with pub/sub-specific wrinkles.

At-least-once · At-most-once

At-least-once means a subscriber may receive the same event more than once, but will never miss one it was subscribed for: the broker redelivers until it gets an acknowledgment. At-most-once means an event is delivered once or never: if the subscriber crashes mid-processing, that copy is gone. (Lesson 9's "exactly-once" isn't on offer end-to-end for the same reason as before: the write and the ack are two separate systems, and a crash can always land between them.)

At-least-once duplication, pub/sub style

The classic duplicate: fan-notifications is slow — it takes 40 seconds to send a batch of goal alerts, but the broker expects an acknowledgment within 30. The broker concludes the copy is lost and redelivers the same goal event, while the original processing is still running. Result: some fans get the goal ping twice. The duplicate wasn't a bug in the publisher — it was a slow subscriber tripping the broker's retry logic. In pub/sub this is the most common duplication source: one subscriber's pace, not a broker failure.

Idempotent subscriber

A subscriber whose processing produces the same end state no matter how many times it sees the same event (Lesson 9 covered this for queue consumers; the rule carries over). The standard answer: give every event a unique event ID, and have each subscriber record the IDs it has already processed — check before acting, skip if seen.

At-most-once: the scoreboard that missed the goal

Pick at-most-once when a duplicate is worse than a loss. Betting settlement would rather delay than double-pay — but careful: at-most-once doesn't delay, it drops. Its real niche is firehose data where each datum is worthless and the stream is everything: live player-tracking coordinates, 60 per second. Losing one coordinate out of 3,600 in a minute is invisible; processing one twice could teleport the player. The rule: duplicates hurt → at-least-once + idempotency; losses are cheap and duplicates are dangerous → at-most-once.

Ordering: or the lack of it

Here's the trap the senior room loves: the 89th-minute goal and the 90th-minute goal publish one second apart. The scoreboard receives them in order. But the highlights clipper — subscribed to the same topic — gets them reversed if its two copies travel different broker paths or one gets retried. Pub/sub does not guarantee global ordering across subscribers, and usually not even for one subscriber — unless the system offers it explicitly:

  • Kafka orders within a partition. A partition is an ordered sub-log of a topic; events with the same key (e.g. the match ID) always land in the same partition, so all of one match's events arrive in order. Different matches interleave freely — order is per-key, not global. That's why you key by the entity the order matters for.
  • Forgetful brokers mostly don't bother. Classic Redis pub/sub delivers in publish order on a single connection, but the moment a retry or a second connection is involved, all bets are off — which is accepted as fine, because it's a broadcast channel, not a ledger.
  • When order truly matters: key your events so related ones share an ordered lane (Kafka partition, SQS FIFO message group), and design subscribers to be tolerant of reordering anyway — e.g. the scoreboard applies "minute 89" before "minute 90" by timestamp, not by arrival order.

🧠 The senior one-liner for this section

"At-least-once with idempotent subscribers is the default. I order by key when a single entity's sequence matters, and I design every subscriber to survive duplicates and mild reordering — because the broker's guarantees end at delivery."

06

Event-driven patterns

Once you stop calling services directly and start publishing events, two design choices appear: how much goes in the event, and who conducts the workflow. Get these wrong and the system "works" while becoming unmaintainable.

How much goes in the event? Three answers.

Event notification

The event says only "something happened, here's the ID" — {"type": "goal.scored", "goalId": "g-9917"}. A subscriber that wants details calls the publisher's API to fetch the full goal record. When it wins: the event stays tiny and the schema almost never changes; it loses when ten subscribers all hammer the API for the same details — you've rebuilt the coupling you tried to escape.

Event-carried state transfer

The event carries the full new state — {"type": "goal.scored", "minute": 89, "scorer": "Haaland", "score": "2-1", ...}. Subscribers act on the event alone and never call back. When it wins: subscribers are fully autonomous (the clipper works even if the match service is down); it loses when the payloads get fat and every new field tempts a schema change — which is failure mode 1 in section 7.

Event sourcing

The event log is the source of truth: you don't store "current score = 2-1", you store every goal/kickoff/card event and replay the log to derive the current state. When it wins: audit trails ("prove the 89th-minute goal was recorded before the bet settled") and time-travel queries ("what was the score at minute 70?"). The price: replaying a whole season's log to answer "what's the score now" is expensive, so you keep snapshots (checkpoints of derived state every N events) — and the whole team must think in events, which is a real learning curve.

Choosing between the three

Default to event-carried state transfer — it's the least coupling with the least machinery. Drop to notification when the payload is large or sensitive and subscribers are few. Reach for event sourcing only when you genuinely need history-as-truth (audits, temporal queries) — never as a default, because you're committing every future reader to replay logic.

Who conducts? Choreography vs orchestration

Choreography

Each service reacts to events and emits its own; there is no central controller. The goal event arrives → the clipper starts cutting → the clipper publishes clip.ready → notifications sees it and pings fans. The workflow emerges from services reacting to each other, like players reading the game: the winger sees the striker's run and crosses without anyone telling them to.

Orchestration

A central orchestrator runs the workflow: it issues commands, waits for replies, and decides the next step. The set-piece coach: the corner routine is drawn up, each player's run is assigned, and the taker signals when to start. Nothing happens by reading the game — it happens because the conductor called it.

Saga pattern

A way to run a multi-step transaction across services without distributed locking: break it into a sequence of local transactions, and if any step fails, run compensating actions (the undo steps) for what already succeeded. The textbook orchestration use-case: booking the away trip — orchestrator books hotel ✓, books flights ✗ → runs compensation "cancel hotel". In choreography style the same saga is a chain of events (hotel.booked → flights service tries → flights.failed → hotel service hears it and cancels itself) — which works until step 3 of 7 fails and you can't tell who's supposed to undo what.

The pick rule

Choreography for simple, stable flows with few steps — "goal scored → five independent reactions" needs no conductor. Orchestration the moment a workflow has ordering, branching, or compensation — if step 3 depends on step 2's result, or a failure must undo earlier steps, write the conductor. The senior tell: choreography optimizes for adding steps; orchestration optimizes for understanding the flow.

07

The four failure modes

These are the four ways event-driven systems actually break in production — and the four questions senior rooms ask to check you've operated one, not just read about one.

1. Schema coupling: the event nobody can change

Schema · Schema coupling

The schema is the agreed shape of an event: which fields exist and what types they are. Schema coupling is what happens when the publisher can't change that shape without breaking subscribers — the decoupling you bought in section 1 quietly evaporates the moment the contract is rigid.

The trap: goal.scored starts as {"minute": 89, "scorer": "Haaland"}. Six months later you need "assist" and "xG". Ten subscribers parse the event; two of them crash on unknown fields because someone wrote strict validation. Renaming "scorer" to "scorerId" breaks all ten at once — and because subscribers are decoupled and owned by other teams, you discover this at deploy time, not compile time.

  • The fix, stated as a rule: events are a public API with a deprecation policy. Add fields (never remove or rename), make every subscriber tolerate unknown fields, and version explicitly (goal.scored.v2 as a new topic, or a version field) when the shape must break.
  • The senior sentence: "Pub/sub decouples services in space and time, but the schema re-couples them — so I version events like an API and never break a field."

2. Event storms and the infinite loop

Event storm · Feedback loop

An event storm is a runaway cascade where events trigger more events faster than subscribers can drain them — volume exploding, not a bug in any single handler. A feedback loop is its nastiest form: service A publishes an event that service B reacts to by publishing an event that A reacts to — an A → B → A cycle that never ends.

Concrete loop, with our goal: the scoreboard subscribes to goal.scored and, after updating, helpfully publishes scoreboard.updated. The stats service subscribes to scoreboard.updated and publishes a derived match.stats.changed event. The commentator feed subscribes to match.stats.changed and — to keep its ticker fresh — republishes a normalized goal.scored "correction" with identical content. The scoreboard sees a "new" goal event and updates again… The stadium hears the 89th-minute goal forever: each cycle multiplies the broker's deliveries, buffers fill, and real events drown. Nothing is broken in any one service — the topology is the bug.

  • Prevention, three layers: (1) idempotency by event ID — the scoreboard has seen goal g-9917, so the "correction" is a no-op; (2) cause-tracking: every derived event carries the ID of the event that caused it, and a service refuses to act on an event it can see it already caused (cycle detection); (3) no republishing what you consumed as a design review rule — derived events get new names and new topics.
  • The circuit breaker for storms: rate-limit or shed at the broker (cap deliveries/sec per topic) so a storm degrades instead of drowning the system — the same instinct as Lesson 11's rate limiting, applied to events.

3. Debugging causality: there is no call stack

Correlation ID

A single unique ID generated at the start of a user action and copied into every event and log line that action causes — the thread that stitches a scattered workflow back together.

The fan's complaint: "I got the goal notification but the clip never arrived." In a synchronous system you'd follow the call stack. Here there isn't one — the goal event fanned out to five independent tracks, and the failure is in exactly one of them, hours of logs away from the others. Without a correlation ID you're grepping five services' logs by timestamp and hoping. With one, it's a single query: correlationId = "evt-9917" shows goal published → clipper received → clipper crashed on an ffmpeg error → notifications succeeded. The rule: the publisher mints the correlation ID, every subscriber propagates it into every event it emits and every line it logs. This is also how you answer "who caused this event" in the loop above.

4. The "eventual everything" trap: when you actually need a synchronous read

Event-driven thinking is seductive: make everything an event and the architecture diagrams look beautifully decoupled. Then the product manager asks for "the page that shows whether my bet was settled" — and the settlement is an event that might have been processed already. The user stares at "pending" for a bet that paid out a minute ago, because no service holds the current, queryable state.

The rule: events are for notifying, not for reading. The moment a human or a UI needs the answer now — "was my bet settled?", "is my order shipped?" — some service must hold that state in a database you can query synchronously. The standard shape: subscribers consume events and maintain a read model (their own little database of derived state), and the UI reads the read model, not the event log. Events flow in; queries hit the database. If your design has events but nowhere to SELECT, you've built a write-only system.

⚠️ The room-ready summary of all four: schema coupling (version your events like an API), event storms (idempotency + cause-tracking + never republish what you consumed), causality (correlation IDs end-to-end), and eventual-everything (someone must hold queryable state — events notify, databases answer).

08

Real-world systems

Five tools, one paragraph each, with the honest trade-off. The question is never "which is best" — it's "which one's price fits this requirement."

Kafka — the league's official archive

Kafka stores each topic as a durable, append-only log, split into ordered partitions. Events are kept for a configured retention period (commonly days), so a subscriber that arrives late — or a brand-new analytics service — can replay history from any point using its own offset (its personal bookmark in the log). Ordering holds within a partition; a consumer group (section 3) gets pub/sub across groups and queue-style splitting within. The trade: it handles millions of events/sec and full replay, but you operate a distributed cluster (or pay a managed vendor) — Kafka is the pick when history and replay matter to many consumers, overkill when they don't.

Redis pub/sub vs Redis Streams — shouting in the tunnel vs the match log

Classic Redis pub/sub is fire-and-forget — "fire-and-forget" meaning the broker sends the event to whoever is connected right now and keeps no copy: publish while a subscriber is reconnecting and that goal is gone for them forever. It's blisteringly fast and dead simple, which is exactly the trade: speed for durability. Redis Streams is the grown-up sibling: a persistent, replayable log with consumer groups and explicit acknowledgments — basically "Kafka-lite inside Redis." Pick classic pub/sub for ephemeral broadcasts (live dashboards, "someone scored" pings where missing one is fine); pick Streams the moment a missed event is a bug.

SNS → SQS fan-out — the AWS assembly line

SNS (Simple Notification Service) is the AWS topic: you publish once, and SNS fans out to whatever is subscribed — and the canonical subscriber is an SQS queue, one per team. So the goal event hits the SNS topic, and SNS drops a copy into the scoreboard team's queue, the notifications team's queue, and so on. Each team gets a durable, independently-retried queue with its own dead-letter handling — per-subscriber isolation (section 4) as a managed service. The trade: it's AWS-only, cross-region fan-out adds latency, and strict ordering needs the FIFO variants. The pick when you're on AWS, want zero broker ops, and each subscriber wants its own retryable queue.

NATS — the lightweight winger

NATS is a minimal, high-throughput messaging system: publish/subscribe (and request/reply) with tiny operational overhead — a single binary, no ZooKeeper-style coordination service. JetStream adds persistence, replay, and consumer groups on top. The trade: a smaller ecosystem and fewer managed offerings than Kafka, so you get simplicity at the cost of community tooling and battle-tested scale stories. The pick for internal services that need fast pub/sub without operating a Kafka cluster — the winger who beats Kafka on agility but won't win the aerial duels at massive scale.

Webhooks — the poor man's pub/sub

A webhook is pub/sub with no broker at all: the publisher makes an HTTP POST directly to each subscriber's registered URL when the event happens. It works — Stripe and GitHub run enormous webhook systems on it — but notice what's missing: no buffering (subscriber down = delivery fails unless you build retries), no fan-out multiplication (the publisher does the N deliveries itself), and no replay. Fine at low volume with few subscribers; past that, you've hand-built a worse broker. The pick for integrating with external parties (you can't ask Stripe to join your Kafka cluster) — not for your internal backbone.

10

Q&A — with full model answers

Four questions that come up constantly, each with the spoken answer — verdict first, reasoning, and what earns the top mark.

Q1 · DESIGN
"Design a notification service: how does pub/sub help?"
They want the fan-out shape, not a Kafka feature tour: one domain event, many independent notification channels.
Reveal model answer
Verdict

"Pub/sub turns one domain event into independent deliveries per channel, so a slow or broken channel never blocks the others. I'd publish one goal.scored-style event per thing worth notifying about, and let the push service, email service, SMS service, and in-app feed each subscribe independently."

Reasoning

"The core services publish facts — 'bet settled', 'goal scored' — to topics, knowing nothing about notifications. Each channel is a subscriber with its own buffer, retries, and pace: if the SMS provider is down for an hour, its copies queue up in the broker while push and email keep flowing. That's the per-subscriber isolation from the fan-out math: one publish, N independent delivery tracks.

Two design details I'd state unprompted. First, at-least-once with idempotent subscribers: a slow SMS subscriber will get redelivered copies, so each notification carries a unique event ID and the channel dedupes on it — nobody wants the goal ping twice. Second, ordering by key where it matters: 'goal' then 'full-time' for the same match must arrive in order, so I'd key events by match ID onto ordered partitions and still have subscribers apply by timestamp, not arrival order.

And the trap I'd name myself: notifications are the classic 'eventual everything' failure — so the read side ('did my notification send?') is a queryable status store updated by the subscribers, not the event log. Events notify; the database answers."

What earns top marks

The isolation argument tied to a concrete failure (one channel down, others unaffected), the idempotency mechanism named (event IDs + dedupe), and volunteering the read-model trap before being asked.

Q2 · JUDGMENT
"When would you NOT use events?"
A restraint question. They want the cases where pub/sub is the wrong tool, stated as rules.
Reveal model answer
Verdict

"Three cases: when the caller needs the answer now, when exactly one worker must do the task, and when the flow needs a conductor. Events are a decoupling tool — if there's nothing to decouple, they're pure overhead."

Reasoning

"First, request/response: 'is this seat available?' needs an answer before the user taps buy. Publishing an event and waiting for a reply event is a distributed request with worse latency and no stack trace — just make the synchronous call. The rule: events notify, databases and APIs answer.

Second, single-worker tasks: 'process this payment' should go to exactly one worker with delete-on-ack — that's a queue, not pub/sub. Broadcasting a payment task to five subscribers is how you charge someone five times.

Third, workflows with ordering, branching, or compensation: booking hotel → flights → tickets, where a flight failure must cancel the hotel. That's orchestration with a conductor, not choreography — events alone give you no place to put the 'undo' logic, and debugging it is archaeology across five services' logs.

And one more I'd mention: low-fan-out, stable consumers. If exactly two services will ever consume an event and that never changes, a direct call or a queue is simpler — pub/sub's value is proportional to how open-ended the subscriber set is."

What earns top marks

Rules stated as positive tests ("needs the answer now → synchronous"), the payment-charged-five-times example for the queue case, and naming the cost of events (latency, no stack trace, schema coupling) rather than just listing alternatives.

Q3 · FAILURE MODES
"How do you prevent an event loop from cascading?"
They're checking for the A→B→A feedback loop — the topology bug from section 7. Three layers, in order.
Reveal model answer
Verdict

"Idempotency by event ID stops the damage, cause-tracking stops the cycle, and a design rule stops it being built in the first place. Plus a broker-level rate cap so a loop degrades instead of drowning the system."

Reasoning

"The concrete loop: the scoreboard updates on goal.scored and republishes scoreboard.updated; the stats service derives match.stats.changed; the commentator feed republishes a normalized goal.scored — and the cycle runs forever, multiplying deliveries each round.

Layer one: every subscriber is idempotent on event ID — the scoreboard has already processed goal g-9917, so the republished copy is a no-op. The loop spins, but nothing happens twice. Layer two: cause-tracking — every derived event carries the ID of the event that caused it, and a service refuses to act on an event whose cause chain includes itself. That's actual cycle detection, not just damage control. Layer three, the review rule: never republish what you consumed under a name someone else consumes — derived events get new names and new topics, so consumption graphs stay acyclic by construction.

And the safety net: rate-limit per topic at the broker. If a loop ever escapes the three layers, deliveries/sec per topic gets capped — the storm degrades instead of filling every buffer and starving real events."

What earns top marks

The concrete A→B→A example (not just "loops are bad"), the three layers in prevention order (damage → cycle → construction), and the broker rate cap as the last-resort safety net.

Q4 · ARCHITECTURE
"Choreography vs orchestration — pick one for order fulfillment."
Order fulfillment has payment, inventory, shipping, and refunds — ordering, branching, and compensation. This is the orchestration trap question.
Reveal model answer
Verdict

"Orchestration, with a saga. Order fulfillment is exactly the shape choreography fails at: ordered steps with compensation."

Reasoning

"The flow: charge payment → reserve inventory → book shipping → confirm. Each step's input depends on the previous step's result, and failures need undo: if shipping fails after payment succeeded, someone must refund. In choreography that's a chain of events — payment.charged → inventory service reserves → inventory.reserved → shipping service books → shipping.failed → …and now who refunds? The payment service has to subscribe to a failure event three hops away and remember what to undo. The workflow exists nowhere; it's scattered across five services' reaction logic, and debugging a stuck order is log archaeology.

With an orchestrator running a saga, the workflow is code you can read in one place: it issues the charge, awaits the result, reserves inventory, and on any failure runs the compensating actions for what already succeeded — refund payment, release inventory. The conductor sees the whole flow, owns the failure handling, and the 'what happens when step 3 of 4 fails' question has one answer instead of five.

The price I'd name: the orchestrator is a single logical point of coordination — so it must be stateless-and-retryable or itself highly available, and adding a genuinely independent step (say, a loyalty-points side effect) still goes through choreography on the side. Orchestrate the transaction, choreograph the side effects."

What earns top marks

Picking orchestration because of compensation (not vibes), the "who refunds?" question that kills choreography, and the closing hybrid — orchestrate the transaction, choreograph the side effects — which shows the two aren't religions.

Practice drills

Untimed — think like you're whiteboarding. Write your answer, then check the rubric.

Drill 1 — Price the fan-out

A match-events service publishes 500 events/sec. Seven services subscribe; average message size is 2 KB. One subscriber — the highlights clipper — is 5× slower than its share. Compute (a) the broker's deliveries/sec, (b) broker egress in MB/sec, and (c) how fast the clipper's backlog grows per second. Then state what the broker must track so the clipper doesn't slow the other six.

Reveal rubric
  • (a) 3,500 deliveries/sec. 500 × 7 — the multiplier is the point. Full marks only with the multiplication shown.
  • (b) 7 MB/sec. 3,500 × 2 KB = 7,000 KB ≈ 7 MB/sec. Accept 6.7–7 MB/sec; the working matters, not the rounding.
  • (c) 400 messages/sec. The clipper's fair share is 500/sec; at 5× slower it drains 100/sec, so the backlog grows by 400/sec — 24,000 messages in a minute.
  • The broker must track per-subscriber buffers and cursors (read positions) — the clipper's backlog is its buffer; the other six drain their own copies at full speed. Full marks for the word isolation: a slow subscriber hurts only itself, bounded by broker capacity.

What earns top marks: all three numbers with the arithmetic visible, plus the isolation sentence — and the caveat that isolation holds only while the broker has buffer room (the section 4 warn-box).

Drill 2 — Spot the loop

Three services: Scoreboard subscribes to goal.scored and publishes scoreboard.updated. Stats subscribes to scoreboard.updated and publishes match.stats.changed. Feed subscribes to match.stats.changed and republishes goal.scored with normalized formatting. (1) Trace what happens after one real goal. (2) Name the failure mode. (3) Give two of the three prevention layers.

Reveal rubric
  • (1) The trace: goal → scoreboard updates → stats derives → feed republishes goal.scored → scoreboard sees a "new" goal and updates again → the cycle repeats forever, each round multiplying broker deliveries. Full marks for noting that nothing is broken in any single service — the topology is the bug.
  • (2) Feedback loop (an event storm's nastiest form) — an A→B→A cycle.
  • (3) Any two: idempotency by event ID (republished goal is a no-op); cause-tracking (feed sees the event's cause chain includes itself and refuses); the design rule — never republish what you consumed under a name someone else consumes (derived events get new names/topics). The broker per-topic rate cap is a valid bonus third.

What earns top marks: the trace drawn as a cycle with the "topology is the bug" line, and prevention stated as layers (damage → cycle → construction) rather than a grab bag.

Drill 3 — Choreograph or conduct?

You're designing away-day trip booking: reserve hotel → book flights → buy match tickets → send the itinerary. If flights fail after the hotel is reserved, the hotel must be cancelled. Pick choreography or orchestration, justify in two sentences, and name the pattern you'd use for the failure path.

Reveal rubric
  • Pick: orchestration. Full marks for either justification hitting both beats: (1) steps are ordered — each depends on the previous result; (2) failures need undo (cancel the hotel), which needs a conductor that sees the whole flow.
  • Pattern: saga with compensating actions — each step is a local transaction, and a failure runs the compensations for completed steps (cancel hotel, refund tickets).
  • Deductions for picking choreography "because it's more decoupled" — decoupling is not the goal here; a correct, understandable failure path is. Partial credit for the hybrid: orchestrate the booking transaction, choreograph the side effects (e.g. notify the group chat via events on the side).

What earns top marks: the sentence "the workflow must be code you can read in one place" (or equivalent), the compensating-action mechanism named, and the hybrid close.

✓

Cheat sheet: the 6 pub/sub decisions

Every event-driven design is these six decisions, in this order. Tape this to your mental whiteboard.

1. Queue or pub/sub? Task for one worker → queue (delete on ack, competing consumers). Fact for many reactors → pub/sub (one copy each, independent tracks). The test: does a new consumer share the load or get its own copy?

2. What's in the event? Default to event-carried state transfer (full state, no callbacks). Notification (ID only) when payloads are fat. Event sourcing only when history-as-truth is a requirement (audits, time-travel). Version events like an API: add fields, never rename.

3. Choreography or orchestration? Independent reactions → choreography (players reading the game). Ordered steps, branching, or undo → orchestration (the set-piece coach), with a saga for the failure path. Orchestrate the transaction, choreograph the side effects.

4. At least once — so what? Assume duplicates (slow subscribers trip redelivery) and mild reordering. Every subscriber idempotent on event ID; order by key when one entity's sequence matters; apply by timestamp, not arrival order.

5. How does it fail? Correlation ID minted by the publisher, propagated through every event and log line. Idempotency + cause-tracking + never-republish-what-you-consumed against loops. Per-topic rate caps so a storm degrades. And someone holds queryable state — events notify, databases answer.

6. Which tool, and why? Kafka for replay-at-scale; Redis Streams for light durable pub/sub inside Redis (classic pub/sub only when loss is fine); SNS→SQS for AWS with zero ops; NATS for minimal internal messaging; webhooks for external parties only. One requirement-tied reason — not a feature list.

🎙️ Pub/sub in 60 seconds — the recital

"Pub/sub decouples publishers from subscribers in space, time, and who: one event published once, and the broker fans it out — one copy per subscriber, each delivered on its own track, so a slow subscriber only hurts itself. The price is the multiplier: deliveries equal events times subscribers, and the broker does all of it. Assume at-least-once, so every subscriber is idempotent on event ID, and order by key where a single entity's sequence matters. Keep events small and versioned like an API, use choreography for independent reactions and orchestration with a saga the moment there's ordering or undo, and always keep a queryable read model — events notify, databases answer."

🎯

How to talk about pub/sub in the room

When the question is "design notifications" or "how do these services talk to each other," run this five-step structure. It turns a tour of broker features into a senior answer.

  1. Split the question: task or fact? One worker must do it → queue. Many must know it → pub/sub. Say which, and why, in one sentence.
  2. Draw the fan-out. One publish, N independent copies. Name the multiplier out loud ("500 events/sec × 7 subscribers = 3,500 deliveries/sec — the broker does the multiplying") and the isolation ("a downed SMS provider queues its own copies; push keeps flowing").
  3. Name the semantic. Say "at-least-once, so my subscribers are idempotent on event ID" — with the concrete mechanism (record processed IDs, skip if seen), and the slow-subscriber redelivery story if they ask.
  4. Conduct or choreograph. Independent reactions → choreography; ordering/branching/undo → orchestration with a saga and compensating actions. "Orchestrate the transaction, choreograph the side effects."
  5. Name one failure mode unprompted. Schema versioning, the A→B→A loop, correlation IDs, or the eventual-everything trap — pick the one closest to the design and land it before they ask.

Senior-depth traps — land these unprompted

The multiplier is the invoice. "Publish once" is cheap; fan-out is the work. Every new subscriber multiplies every event's cost forever.

Exactly-once is not on offer. The write and the ack are two systems; a crash lands between them. What's on offer is at-least-once plus idempotent subscribers.

Decoupled in space and time, re-coupled by schema. The event contract is a public API — version it, never break a field, and tolerate unknown fields on the subscriber side.

Events notify; databases answer. If no service holds queryable state, you've built a write-only system with great diagrams.
