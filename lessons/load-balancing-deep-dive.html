SYSTEM DESIGN / LESSON 02 / SENIOR TRACK

Traffic is a control problem.

A load balancer is a traffic router: it receives a connection—a communication channel that can carry one or many requests—or an individual request, chooses a healthy backend server (the machine that performs the application work), and forwards the traffic. This lesson builds that idea one decision at a time—where to route, what signal to use, how to detect failure, and how to add capacity safely.

01 / MENTAL MODEL
READ · Learn the core idea

Balance outcomes, not request counts.

The naive goal is “send equal traffic everywhere.” The real goal is to keep response times and errors low while respecting server capacity, network distance, session needs, and cost.

Two measurements to know: latency is how long one request takes from start to finish. p99 latency is the response time that 99 out of 100 requests finish within; only the slowest 1 out of 100 takes longer. Teams watch p99 because an average can hide a painful slow tail.
01 — OBSERVE

State is delayed

Connection counts, latency, and health are sampled. Every routing decision uses a slightly stale picture of a changing fleet, meaning the full group of available servers.

02 — DECIDE

Policy encodes trade-offs

Round robin rotates evenly; least-load reacts to current work. Hashing turns a stable key, such as a user ID, into a repeatable server choice and preserves affinity, meaning related requests stay near the same server. No policy wins for every workload.

03 — ACT

Actions reshape state

Routing changes queue depth—the number of requests waiting—and response time. Retries add traffic; newly started servers need time to warm. Every action changes the next decision.

!

Senior signal: separate the data plane—the proxies that forward live traffic—from the control plane—the system that discovers servers and distributes routing rules. If the control plane stops updating, the data plane should keep serving with its last known good configuration rather than drop all traffic.

Read the chain left to right. DNS maps a service name to an IP address, the identifier for a network endpoint. Anycast advertises the same IP address from multiple locations so the network tends to choose a nearby one. An edge L4 balancer routes a network connection using an IP address, which identifies a network endpoint, and a port, which identifies a service on that endpoint. An L7 proxy reads application details such as an HTTP path. A service load balancer then chooses one healthy application instance, meaning one running copy of the server program. A region is a separate geographic deployment area, while a connection is a communication channel that can carry one or many requests.

Routes a connection using the 5-tuple: source IP, source port, destination IP, destination port, and protocol.   • +Strength: fast and protocol-agnostic—it can route traffic without understanding the application protocol. TCP provides reliable ordered delivery; UDP sends independent packets with less processor and network overhead.
  • +Strength: direct server return lets the chosen server send the response straight to the client, keeping response traffic off the balancer.
  • −Limit: cannot route by URL path, request header, tenant (an isolated customer or account), or HTTP method (an action such as GET or POST); one connection is usually one routing unit.
  • −Limit: HTTP/2, a version of the web protocol that can multiplex many simultaneous requests over one connection, lets one connection hide uneven work.

Choose L7 when: routing needs application details, a gradual release, per-route rules, or rich telemetry—metrics, logs, and traces that explain behavior. QUIC is a newer encrypted transport used by HTTP/3; the proxy must explicitly support it.

04 / HEALTH & EJECTION
READ + EXPLORE · Open each signal

“Healthy” is a routing opinion.

A server can answer a simple health URL while its database connection pool is exhausted. Expand each signal to learn what it detects and the mistake it prevents. Ejection means temporarily removing a failing server from routing.

Send a small test request on an interval. Use a timeout, require several failures before removal, and add jitter—small random timing variation—so thousands of balancers do not probe at once. Check readiness without synchronously calling every dependency; otherwise the probes can become the outage.

Passive health watches real traffic for connection failures, timeouts, resets, and HTTP 5xx server-error responses. It catches problems synthetic probes miss, but must separate backend faults from caller cancellation or overload elsewhere.

Outlier detection compares a server’s errors or latency with its peers and temporarily removes unusually bad performers. Cap the removable percentage so a bad release does not eject the whole fleet and concentrate traffic on the survivors.

Panic mode is a last-resort policy used when too few servers remain healthy: route some traffic to recently unhealthy servers rather than overload the final healthy subset. Serving degraded responses may be safer than causing total failure.

Slow start gradually increases a recovered or new server’s traffic share. This gives its just-in-time code compiler, caches, connection pools, and local proxy time to warm before full load arrives.

∿

Avoid synchronized behavior. Add random variation to probe intervals, wait progressively longer after repeated recovery failures, and limit how many servers re-enter at once. Identical timers across thousands of balancers create load spikes exactly when the system is weakest.

05 / AUTOSCALING
ESTIMATE · Build a safe fleet size

The balancer reacts in milliseconds. Capacity arrives in minutes.

Autoscaling adds or removes servers from measured demand. It acts slowly because metrics arrive late, machines take time to boot, and warm caches fill gradually. Move the inputs below and read the calculation, not just the final number.

Capacity must be measured at the target SLO. An SLO (service-level objective) is a concrete reliability target, such as “99.9% of requests succeed and p99 stays below 200 ms.” If one server can technically push 1,400 requests per second but misses the SLO above 1,000, use 1,000 as its measured capacity.

Default example: 12,000 peak requests per second ÷ (1,000 measured requests per second × 65% target utilization) = 18.46, so round up to 19 servers. A 20% failure reserve adds 4 more, for 23 servers total. The spare capacity absorbs bursts and a small failure without immediately violating the SLO.

Scale on the bottleneck

CPU utilization matters only when processor time limits capacity. Queue depth, concurrent work, resource saturation, or request latency may predict overload earlier. For background workers, the age of the oldest waiting job often beats CPU.

Keep a warm buffer

If boot, registration, and cache warm-up take 4 minutes while demand can double in 1 minute, reactive scaling cannot catch up. Add servers ahead of a forecast spike or keep spare capacity.

Drain before terminate

Mark the server unready, stop sending new work, wait for active requests, then terminate it. Keep the removal delay longer than normal request duration so a server does not disappear mid-request.

Stabilize the loop

Add capacity quickly and remove it slowly. Use hysteresis—different thresholds for scaling up and down—plus cooldown periods and rate limits. Otherwise the fleet can oscillate, repeatedly adding and removing servers.

06 / FAILURE REASONING
EXPLORE · Trace what happens next

Design for the second-order failure.

A second-order failure is damage caused by the system’s reaction to the first problem—for example, retries creating more traffic after servers slow down. Choose a scenario and read it left to right: mechanism → mitigation → metric.

Retry storm

A 10% failure becomes 40% more load on the same unhealthy fleet.

MECHANISM

Multiple layers retry independently; timeouts overlap; a non-idempotent request—one that changes state each time, such as charging a card—may run twice.

MITIGATION

Give one layer ownership of retries. Use a total deadline, increasing delays with random variation, a cap on retry traffic, and duplicate parallel attempts only for safe reads.

METRIC

Attempts per logical request, retry success rate, deadline exhaustion, retry load as % of originals.

Zone loss

Removing one-third of capacity overloads the two-thirds that remain.

MECHANISM

Fleet ran above 66% utilization; cross-zone failover adds network cost and connection churn.

MITIGATION

Keep enough spare capacity to lose one zone, prefer same-zone traffic, cap traffic per zone, allow controlled cross-zone spillover, and rehearse evacuation.

METRIC

Capacity by failure domain, cross-zone traffic, spillover rate, healthy headroom after loss.

Slow node

It passes health checks but accumulates queues and dominates p99 latency—the response time that 99 out of 100 requests finish within.

MECHANISM

Garbage collection pauses, a competing workload on the same machine, a slow dependency, or an exhausted connection pool increases service time without a hard failure.

MITIGATION

Cap concurrent work, favor servers with better recent latency, eject slow outliers based on real traffic, bound the queue, and pass the caller’s deadline downstream.

METRIC

Per-endpoint latency and inflight work—not fleet averages—plus queue wait versus service time.

Stale control plane

Proxies keep routing to removed nodes—or drop every route during a config outage.

MECHANISM

Discovery updates stop, partial config arrives, or a bad global push invalidates all listeners.

MITIGATION

Keep the last known good rules, replace configuration as one versioned unit, roll out gradually, define how long stale endpoint data remains usable, and let proxies route without calling the controller.

METRIC

Config age, version skew, rejected updates, endpoint staleness, control-plane convergence time.

How would you load-balance a global API serving 2M requests per second?

Start with requirements: regions, latency SLO (the promised response-time target), read/write mix, protocol, session state, data-location rules, and tolerated regional failure. Then propose a hierarchy rather than one global balancer.

GLOBALAnycast—advertising one IP address from many locations—or latency-aware DNS directs clients to a healthy region.
REGIONAL EDGEA redundant L4 fleet routes network connections using IP, port, and protocol.
APPLICATIONL7 proxies read HTTP details, enforce authentication and rate limits, and test a new release with a small share of traffic.
SERVICEClient-side or sidecar balancing chooses one application instance.
  • Scale the traffic-forwarding proxies horizontally by adding more identical instances; never make them call a central controller for every request.
  • Prefer the nearest region, allow controlled spillover, and provision for the agreed failure model—for example, enough spare capacity to lose one region, or an explicit plan to reject lower-priority traffic.
  • Combine synthetic health probes with errors and latency from real requests. Version routing configuration and make proxies retain the last known good version if updates stop.
  • Use consistent hashing only where affinity is required; keep user session state external where practical.
  • Protect capacity with admission control (reject work before overload), per-tenant limits, a cap on retry traffic, and load shedding for lower-priority requests. Observe p50, p95, and p99—the response times that 50%, 95%, and 99% of requests finish within—plus errors, saturation, drops, retry amplification, configuration age, and spare capacity per zone.

Close with trade-off: DNS is simple but client and resolver caches make failover slower. Anycast can redirect traffic faster, but it depends on internet routing behavior. L7 enables rich request-aware policy but consumes more processor capacity and adds another component that can fail.

When would you choose consistent hashing, and what can go wrong?

Consistent hashing is a deterministic way to map a key—such as a tenant ID—to a server while minimizing remapping when servers join or leave. Use it when sending the same key to the same owner improves correctness or efficiency: cache locality, database-shard ownership, tenant affinity, or stateful streaming.

  • Key choice matters: hashing user ID may create tenant affinity; hashing URL may create cache affinity. Low-cardinality or skewed keys create hotspots.
  • Virtual nodes or weighted rendezvous give a physical server multiple positions or a larger score so distribution is smoother and faster servers can own more keys.
  • Bounded-load hashing preserves most key-to-server affinity but sends a key elsewhere when its normal owner crosses a safe load limit.
  • Replication stores a key on multiple servers, giving alternate owners during failure and a way to split hot traffic; define which copy is authoritative.
  • Membership churn still hurts: adding or removing many servers remaps cache keys and creates a cold-cache wave. Introduce new servers gradually and limit the rate of membership changes.

A strong answer states that hashing balances keys, not work. One celebrity tenant or viral object can dominate an otherwise perfect ring.

Why can least-connections perform worse than round robin?

Least-connections relies on a proxy’s local, delayed count and assumes each connection represents comparable remaining work. That breaks in several ways:

  • HTTP/2 and gRPC can multiplex many concurrent requests over one network connection, so connection count under-reports real work.
  • One connection may stream for hours while another serves a 2 ms request.
  • A newly added node has zero connections and can receive a surge before it is warm.
  • Across many independent balancers, each has only a partial view and may simultaneously choose the same apparently idle node.
  • A slow node completes requests less often, so the algorithm eventually avoids it—but only after queues and latency rise.

Prefer least outstanding requests or concurrency when the proxy sees requests; combine with power-of-two sampling, slow start, and passive latency/outlier signals. If requests are uniform and short, round robin may be more stable and cheaper.

Design health checks for a dependency-heavy service.

Separate meanings. Liveness asks whether the process can still make progress and should restart if it cannot. Readiness asks whether it should receive new work now. A shallow readiness probe verifies that the process can handle events, has critical local connection capacity, has valid configuration, and can serve—without synchronously calling every dependency.

  • Use active checks—synthetic probe requests—with a timeout shorter than their interval, random timing jitter, and different failure counts for removal and recovery.
  • Add passive checks from real traffic: connection errors, resets, timeouts, and each server’s rate of 5xx responses, which are HTTP server-error codes.
  • Temporarily eject servers whose error rate or latency is much worse than peers, but cap the percentage removed; increase the ejection duration after repeated failures.
  • If the healthy set becomes dangerously small, decide whether to try recently unhealthy servers instead of overloading the last healthy ones. That is a fail-open or panic-mode choice.
  • On recovery, increase the server’s traffic share gradually. During a release, mark it unready before stopping the process so active requests can finish.

Do not make readiness depend on every optional downstream: a shared dependency outage would remove all callers and turn a partial outage into total unavailability.

How do load balancing and autoscaling interact?

They are coupled feedback loops. The balancer moves demand immediately; the scaler estimates demand and changes supply after delay. Bad coupling produces oscillation, cold-start overload, and premature scale-in.

  • Scale on a measurement close to the bottleneck: concurrent work, waiting queue depth, resource saturation, or response time—not automatically processor utilization.
  • Set target utilization to leave failure and burst headroom. Capacity-test an instance at the target SLO, not at absolute maximum throughput.
  • Scale out aggressively and scale in conservatively with stabilization windows and cooldown.
  • Register only when ready; use slow-start weight after registration. Before scale-in, mark unready and drain longer than relevant request duration.
  • Forecast or pre-scale when traffic can rise faster than boot + warm-up time.

Explicitly model a zone failure: if losing 1 of 3 zones is in scope, normal utilization must be low enough that 2 zones can carry the allowed load or the system must shed lower-priority traffic.

Where should retries live: client, load balancer, or service?

Choose one primary retry owner per network hop and enforce an end-to-end deadline. L7 proxies can retry before response headers and select a different healthy server, but they may not understand whether repeating the business operation is safe. Clients understand the operation better but often lack backend health context.

  • Retry only temporary failures and only idempotent operations—operations whose repeated execution has the same effect as one execution—or require an idempotency key that lets the server detect duplicates.
  • Budget attempts globally: if each of three layers retries three times, one user request can become 27 backend attempts.
  • Use exponential backoff, which waits progressively longer between attempts; add random timing jitter and cap retry traffic relative to successful requests.
  • Never continue beyond the caller’s absolute deadline; propagate cancellation so abandoned work stops.
  • A hedged request sends a delayed duplicate to another server to reduce the slow tail. Use it only for safe reads, delay the duplicate, and cap the extra load.

The key phrase: retries spend shared capacity to buy success probability. During overload, aggressive retries reduce both.

Model answer

Route users to the nearest healthy region using Anycast (one IP address advertised from many locations) or latency-aware DNS, then use redundant regional L7 proxies that can read HTTP request details. Keep payment writes idempotent with a client-supplied key and designate one retry owner so an ambiguous timeout cannot create a second charge.

Provision so the remaining two regions can carry the allowed failover load, or explicitly shed non-checkout traffic. Remove bad servers with active and passive health signals, drain before termination, and watch p99 latency, error rate, saturation, retry amplification, and spare capacity by region.

Trade-off: active-active regions improve availability and read latency, but globally correct writes require a clearly owned data-consistency design; do not imply the load balancer alone solves duplicate payments.
