Lesson 29 · Classic design

Design a Collaborative Document Editor

The Google Docs problem: several people typing in the same document at once, from different devices, sometimes offline — and everyone must end up with the same text, with nobody's words silently eaten.

What is a collaborative document editor?

Start from zero. A document is a sequence of characters (and, in a rich editor, formatting attached to ranges of them). A collaborative editor lets several people edit that one sequence at the same time and see each other's changes within a fraction of a second. Each person's copy is a replica: a full local copy of the document that they type into immediately, before the server has confirmed anything.

The whole design exists to solve one sentence: two people edited the same text at the same time, on different replicas, and the replicas must converge — end up identical — without losing either person's intent. "Intent" is the key word: if you typed a word, it should still be there; if you deleted a word, it should stay deleted. An editor that converges to some shared text by throwing one person's edit away has failed, even though the replicas agree.

The soccer running example for this lesson: Riverside FC's coaching staff are writing Saturday's match plan together. The head coach is on the team bus adding a paragraph about pressing triggers, the analyst at home is correcting the set-piece notes in the same paragraph, and the scout is offline on a train, rewriting the opposition winger section. When the scout reconnects, all three copies must become one match plan — with the coach's paragraph, the analyst's corrections, and the scout's rewrite all present, in sensible places.

Terms, defined as they appear

Operation (op): one small edit, e.g. "insert 'x' at position 7" or "delete the character at position 3". Editors sync ops, not whole documents. Convergence: all replicas eventually holding identical content. Presence: the live "who is here, where is their cursor" layer — separate from the document itself. Server sequence number: a counter the server stamps on each op in the order it receives it, so every client can say "I have seen ops up to #412".

Requirements and back-of-the-envelope math

Scope first, or the numbers are meaningless. We are building a Docs-style editor: many documents, most edited by one person, a few edited live by a small group, documents up to book length, and offline editing that syncs later.

  • Functional: create/share a document; type with sub-second propagation to collaborators; cursors and names visible live; comments and suggested edits; version history and restore; offline edits that merge on reconnect.
  • Non-functional: convergence guaranteed (no silent loss); typing latency under ~100 ms for collaborators on the same region; availability over strict consistency for the editing path — a partition must not freeze typing; durability: no committed edit lost.

The sizing, with every step shown. Assume 5 million monthly users, a peak of 20,000 people actively typing at once, an average typing speed of 5 characters per second while typing, and an average of 4 collaborators per live document (so each op is delivered to 3 other people):

  • Inbound ops: 20,000 typists × 5 chars/sec = 100,000 ops/sec at peak. This is why ops are batched: a client typically sends a small batch every ~50–100 ms rather than one network message per keystroke.
  • Outbound deliveries: 100,000 ops/sec × 3 recipients = 300,000 deliveries/sec. Fan-out, not typing, is the dominant load — the same shape as the feed fan-out in Lesson 16, but with tiny payloads and a latency budget measured in milliseconds.
  • Bandwidth: at ~100 bytes per op (position, character, author, sequence number), 300,000 × 100 bytes ≈ 30 MB/sec of broadcast payload. Small. The hard part is latency and ordering, not bytes.
  • Storage: keeping every op forever is a trap (see tombstones below). With hourly snapshots plus an op log since the last snapshot, a 200 KB document edited daily costs roughly one snapshot a day; 50,000 documents edited per day × 200 KB ≈ 10 GB/day of snapshots before compression and dedup — comfortable for blob storage.
The decision the numbers force

Because the load is many small ops with a tight latency budget, the editing path is a fleet of stateful WebSocket servers holding live documents in memory, with durable storage behind them — not a request/response API that reloads the document from a database per keystroke. That fleet is the architecture; everything else hangs off it.

The architecture, in one pass

Walk a keystroke from the coach's laptop to the analyst's screen:

  1. Client (browser app). Applies the keystroke to its local replica instantly — this is why typing feels instant even on a slow train. It queues the op to send, renders remote cursors, and keeps a pending queue of ops not yet acknowledged by the server.
  2. Collaboration server (WebSocket). One server owns a document's live session (routed by document ID, exactly as chat connections were routed by conversation in Lesson 17). It orders incoming ops, stamps sequence numbers, broadcasts to the other collaborators on that document, and writes ops to durable storage. If this server dies, clients reconnect to another server and replay from the last snapshot plus the op log — the in-memory session is a cache, never the only copy.
  3. Document service + storage. Owns permissions ("who may edit this doc"), metadata, snapshots, and the op log. It is off the keystroke path: the collaboration server consults it on open, not per keystroke.
  4. Presence service. A separate, ephemeral channel for cursors, selections, and "who is online". Presence is never written to the document's durable log — when you close the tab, your cursor simply expires by timeout (the same TTL idea as chat presence in Lesson 17).
  5. Comments, suggestions, history. Separate features layered on the same document model: comments anchor to character ranges, suggestions are ops flagged "proposed, not applied", and version history is a named snapshot plus the ops after it.

Why a server at all, if clients could just send ops to each other? Because someone must be the ordering authority (in the OT design below), someone must hold the session when a phone sleeps, and someone must enforce permissions before an op reaches other readers. Peer-to-peer sync exists in research systems; production editors put a server in the middle and keep the clients dumb about ordering.

Why last-write-wins destroys documents

The naive design is: each client sends its whole document (or its edit) to the server, and the server keeps whichever arrived last. Watch it fail on the match plan. Base text: Riverside wins. The coach inserts "FC" after "Riverside" (position 9). At the same moment, the analyst deletes "wins". Last-write-wins keeps one whole version: either the coach's "Riverside FC wins" (analyst's deletion lost) or the analyst's "Riverside" (coach's insertion lost). One person's intent is gone, silently, with no error.

The same failure happens with positions. If both edits are ops, not whole documents, applying them naively in different orders still diverges: the coach's "insert at position 9" applied after the analyst's deletion lands in a document that is now shorter, so the position means something different. An op's position is only meaningful against the document state its author saw. Every real solution is a way of making ops mean the same thing on every replica despite different states. There are two families of solution, and the choice between them is the heart of this design.

Solution 1: Operational Transformation (OT)

Operational Transformation means: when two ops were written against the same document state but arrive in a different order, rewrite one of them so it has the same effect on the new state. The rewriting function is called transform. The server is the authority that decides the order: it receives ops, transforms each incoming op against every op it has already accepted since the sender last synced, stamps it with the next sequence number, and broadcasts the transformed op.

Worked example, step by step. Base: Riverside wins, counted from 0: R(0) i(1) v(2) e(3) r(4) s(5) i(6) d(7) e(8), space(9), w(10) i(11) n(12) s(13). Coach op A: insert "FC " (3 characters) at position 9, i.e. before the space. Analyst op B: delete the "w" at position 10. Suppose the server accepts A first. B was written against the pre-A document, so B's position is stale: after the 3-character insert, everything from position 9 onward shifted right by 3. Transform shifts B's position by +3, from 10 to 13 — and position 13 in "Riverside FC wins" is exactly the "w". Both replicas apply A then transformed-B, ending at "Riverside FC ins", with both intents preserved. Applied naively, B would delete at position 10 in the new text — the "F" — leaving "Riverside C wins".

The tie-break rule matters: two inserts at the same position — coach inserts "A", analyst inserts "B", both at position 9 — must land in the same order on every replica, or replicas diverge ("AB" vs "BA"). The standard rule is a deterministic tie-break, e.g. lower user ID's character first. It is arbitrary, but it must be identical everywhere; "arbitrary but deterministic" is a phrase worth using in the room.

OT's costs, stated honestly. The transform function must be correct for every pair of op types (insert-insert, insert-delete, delete-delete, plus formatting ops), and the classic correctness condition — that transforming in different orders still converges — is genuinely hard to prove for rich text. That is why OT systems keep a central server: one ordering authority makes the problem tractable. Google Docs uses OT. OT also gives you the server sequence number for free, which makes catch-up trivial: "send me everything after #412".

Solution 2: CRDTs — ops that commute

A CRDT (Conflict-free Replicated Data Type) takes the opposite approach: design the ops so that applying them in any order gives the same result — the ops commute, like addition (3 + 5 = 5 + 3). Then no server ordering is needed at all, and offline replicas can sync peer-to-peer.

How, for text? The trick is to stop addressing characters by position. In a sequence CRDT (the best-known design is RGA, Replicated Growable Array), every character gets a permanent, unique ID when it is created — typically (counter, client ID), where the counter is a Lamport clock (a per-client counter that jumps to max(seen) + 1 on receiving a remote op, so IDs are ordered without wall-clock time). A character also records the ID of the character it was inserted after. Insertion is then "insert character X after character Y", not "insert at position 9" — and that statement is true in every replica, regardless of what else was inserted meanwhile. Deletion does not remove the character; it marks it with a tombstone ("this character is deleted, keep its ID so other ops that reference it still resolve"). Replicas sort characters by their IDs and links, skip tombstones when rendering, and converge by construction.

Worked example: coach inserts "F" after "e" (the last letter of "Riverside"); analyst concurrently deletes "w". The delete marks "w" as a tombstone. The insert references "e", which exists everywhere. Both replicas, in either order, render "Riverside F…" with "w" hidden. No transform, no ordering authority, no tie-break meeting.

CRDT's costs, stated honestly. Tombstones grow forever unless garbage-collected, and safe garbage collection requires knowing every replica has seen the deletion — which is why production CRDT editors take periodic snapshots and drop the op log and tombstones before the snapshot. And a CRDT document is a data structure, not a string: loading a 100,000-character document means materialising 100,000 character-nodes, so implementations keep a compact snapshot representation and only expand the CRDT structure for the editing session. Automerge and Yjs are the libraries to name; Figma's multiplayer and many newer editors use this family.

The verdict to give in the room

For a Docs-style product with a server anyway, pick OT with a central ordering server, or a CRDT with server relay — and say why: the server already exists for permissions, presence, and durability, so OT's central authority costs nothing extra, while CRDT's offline elegance is worth it only if offline-first is a headline requirement. Naming the trade-off beats naming a winner.

Presence, cursors, and the "who is typing" layer

Presence looks trivial and is a distinct system. A cursor is (user, position, selection range, colour) broadcast to collaborators a few times per second, at most — every keystroke does not need a cursor message, and cursor messages are throttled and coalesced (send at most one per ~100 ms, drop intermediate positions). Two rules keep it cheap: presence is ephemeral (never persisted, expires on a heartbeat timeout of a few seconds), and it travels on a separate channel from ops, so a flood of cursor moves can never delay a keystroke. The soccer analogy: the live TV graphic showing where each player is standing is not the match report — losing a frame of it changes nothing, and you would never let it delay the referee's whistle.

Cursor positions have the same staleness problem as ops: your cursor at "position 42" means position 42 in your document. Servers therefore broadcast cursor positions together with the sender's last-seen sequence number, and receivers map the position through the ops they have applied since that number — or, more simply, clients render cursors approximately and correct them as ops arrive. A cursor that is one character off for 100 ms is a cosmetic glitch; an op that is one character off is data loss. Spend precision on ops, not cursors.

Undo, offline editing, and version history

Undo in a shared document is not Ctrl+Z on a stack. A global undo stack would let the coach undo the analyst's last edit — surprising and wrong. The rule: undo inverts your own most recent op, and that inverse op is transformed against everything that happened since (in OT) or issued as a normal op (in CRDT). If the analyst has since typed inside the paragraph you are undoing, the transform shifts your inverse op so it removes only your characters, not theirs.

Offline editing is the same machinery with a longer delay. The scout on the train types into the local replica; ops sit in the pending queue; on reconnect, the client sends its queue with its last-seen sequence number, the server transforms (OT) or relays (CRDT) them against everything missed, and broadcasts. Two disciplines make this survivable: the pending queue is persisted to local storage (a closed tab must not lose a train journey's notes), and the client never applies its own pending ops twice — each op carries a client-generated ID, and the server echoes that ID back in its acknowledgement, so a retried send is deduplicated by ID (the idempotency-key pattern from Lessons 17 and 22).

Version history falls out of the op log for free: a version is a snapshot plus "replay ops up to sequence number N". Named versions ("Match plan — final, Friday") are just snapshots with a label. Restore is "make a new snapshot from the old state and keep editing from there" — never rewrite history in place, because other clients' sequence numbers would stop meaning anything.

Hard parts, failure modes, and senior-depth traps

  • The paste bomb. One user pastes a 10 MB article into a shared doc. As one op per character, that is ~10 million ops — it stalls the broadcast and every collaborator's render. Fix: cap single-op size, split pastes into chunk ops, and apply large inserts as one ranged op ("insert this string at position P"), not one op per character. State the op granularity decision explicitly: character ops are for teaching; production ops carry strings.
  • Hot documents. A cup-final live blog with 10,000 viewers and 50 editors: broadcast fan-out to viewers who never type is wasted work. Fix: viewers subscribe to a throttled snapshot stream (e.g. the document state every 500 ms), editors stay on the op stream — two dissemination tiers, one document.
  • Formatting ops are harder than text ops. Bold on a range that another user just deleted, or two users bolding overlapping ranges, needs attribute transforms (or CRDT maps per character). Say this before being asked: "text convergence is the solved half; attribute convergence is where implementations earn their keep."
  • Server crash mid-broadcast. The server accepted op #413, broadcast it to two of four collaborators, then died. Fix: ops are written to the durable log before broadcast (the persist-before-route rule from Lesson 17), and reconnecting clients ask for "everything after my last sequence number" — the missed op is replayed, never lost.
  • Permission change mid-edit. The coach revokes the scout's edit access while the scout has unsent ops queued. Fix: the server re-checks permission on op receipt, rejects the queued ops, and the client surfaces "you now have view-only access" rather than silently dropping the scout's train notes — and the client keeps a local copy so nothing is lost.
Three senior-depth traps

1. "OT and CRDT are interchangeable." They converge, but they differ in where ordering lives, what offline costs, and what breaks at scale — pick by the product's constraints, not by fashion. 2. "Cursors need the same guarantees as text." They do not; over-engineering presence is how editors get slow. 3. "Version history is a separate feature." It is the op log with a label — building a second history mechanism duplicates the hardest part of the system.

Questions with full model answers

Tap each question to reveal its model answer. The answers are written as you would say them, not as bullet-point hints.

1. Two users type in the same document at the same time. How do you stop one edit from overwriting the other?

Never sync whole documents, and never let last-write-win. Sync small operations — insert/delete at a position — and make concurrent ops safe. Either give a server the job of ordering ops and transforming each incoming op against the ops accepted since the sender last synced (OT), or design ops that commute so order does not matter (CRDT: characters addressed by permanent IDs, not positions, with tombstones for deletes). In both designs, both users' intents survive, and every replica converges to the same text. Then add the production details: ops carry client IDs so retries are deduplicated, and the server persists an op to the log before broadcasting it, so a crash mid-broadcast cannot lose it.

2. OT or CRDT — which would you pick, and why?

It depends on the product's constraints, and I would say so explicitly. If a central server already exists for permissions, presence, and durability — as it does in a Docs-style product — OT is the pragmatic pick: one ordering authority makes transforms tractable, and the server sequence number gives catch-up for free. If offline-first or peer-to-peer sync is a headline requirement, CRDT is the pick, because ops commute and replicas can sync in any order without a server. The honest costs: OT's transform correctness for rich text is hard to prove; CRDT's tombstones grow until snapshot compaction. I would pick OT with a server relay for this product, and name the CRDT alternative and its trigger condition rather than pretending the choice is obvious.

3. A user edits offline for an hour, then reconnects. What happens, step by step?

Their client kept typing into its local replica and queued every op in a pending queue persisted to local storage, each op tagged with a client ID and the last server sequence number the client had seen. On reconnect, the client sends the queue plus that sequence number. The server first re-checks that the user still has edit permission, then transforms the queued ops against every op accepted since that sequence number (OT) or relays them as commuting ops (CRDT), stamps them with new sequence numbers, persists them to the op log, and broadcasts them to current collaborators. The client, meanwhile, receives every op it missed, applies them, and clears its pending queue as acknowledgements arrive — matched by client ID, so a retried send after a dropped acknowledgement is deduplicated, not applied twice. If the document changed a lot while offline, the server may send a fresh snapshot plus the ops after it instead of the whole missed log.

4. The document has 10,000 viewers but only 50 editors. How do you keep broadcast costs sane?

Split dissemination into two tiers. Editors stay on the live op stream — they need every op within ~100 ms. Viewers subscribe to a throttled snapshot stream, e.g. the rendered document state every 500 ms, served from a cache, not from the collaboration server's broadcast loop. That turns a 10,000-way fan-out per keystroke into 50 deliveries plus a periodic snapshot, and it isolates the editors' latency from viewer churn. The same tiering idea applies to presence: viewers do not need per-keystroke cursor updates, and cursor traffic is throttled and kept on a separate channel so it can never delay an op.

Practice drills (untimed)

Work these without a timer. The rubric under each one is what a strong answer covers.

  1. Transform it by hand. Base text: "Riverside FC" (F at position 10, C at 11). User A inserts "X" at position 0 (the start). User B deletes the "F" at position 10. The server accepts A's op first. What is B's transformed op, and what is the final text on both replicas? Rubric: B shifts by +1 (A's insert is before B's position), so B deletes at position 11; final text "XRiverside C". A "no shift needed" answer has missed that inserts before a position move it; deleting at the stale position 10 would remove the space instead.
  2. Design the undo. The coach bolds a paragraph, the analyst then types two words inside it, and the coach presses undo. What must happen, and what must not happen? Rubric: undo inverts only the coach's own op (un-bold), transformed against the analyst's inserts so it touches only the coach's formatting range; it must not remove the analyst's words or undo the analyst's edit. Mentioning the own-op-only rule is the pass mark.
  3. Size the snapshot strategy. A document has 2 million ops in its log and is opened 500 times a day. Sketch a snapshot policy and justify the interval. Rubric: snapshot at least hourly or every N ops (e.g. 10,000), so an open replays at most one interval of ops instead of 2 million; snapshots are immutable blobs, named versions are labelled snapshots, and the op log before a snapshot can be dropped once every live replica has passed it.

60-second framing

Use this when asked to design it cold: "Several people editing one document is a convergence problem, not a storage problem. Each client holds a replica and types into it instantly. Clients sync small operations, not documents. Concurrent operations are made safe either by a server that orders them and transforms each one against what it missed — OT — or by operations designed to commute, addressing characters by permanent IDs instead of positions — CRDT. Presence is a separate, throttled, ephemeral channel, because a cursor is not data. Offline edits queue locally with client IDs, transform on reconnect, and are deduplicated on retry. History is a snapshot plus the op log, and restore means branching from an old snapshot, never rewriting the log. The hard parts are formatting convergence, paste bombs, and hot documents — and each gets its own mitigation, not a bigger server."
