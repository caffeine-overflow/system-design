01

What is a feed?

Before any architecture: what the thing is, in plain words, with the running example we'll carry through the whole lesson.

Feed (home timeline)

A feed is the personalized list of posts from the accounts you follow, shown newest-first when you open the app. It is personalized (every user sees a different one) and assembled (it doesn't exist anywhere as a single object — the system builds it from many authors' posts).

Running example

Matchday — a soccer social app

Imagine Matchday, a soccer version of X. Fans follow clubs (@Arsenal), players (@Saka), and pundits. They post takes ("that offside call was criminal"), lineup news, and goal clips. Open the app and you get your home feed: everything from your follows, newest first. That's the product we're designing — and every decision below is explained through it.

Three terms we'll use constantly, defined once here:

  • Follow graph — the directed network of who-follows-whom. Directed means it isn't mutual: you follow @Saka; @Saka does not follow you. Each edge is one row: follower → followee.
  • Home timeline — your feed: posts from everyone you follow, merged by time.
  • User timeline — one author's posts in order. @Saka's user timeline is just @Saka's posts. This distinction matters enormously in §5.

The central tension of this lesson

Somebody has to do the joining — combining many authors' posts into one home feed. Either it happens when a post is written (the system pushes it into every follower's feed immediately), or it happens when a feed is read (the system gathers each followee's posts at load time). You can't avoid the work; you can only choose where it happens. That choice is called fan-out, and it's the heart of every feed design.

02

Requirements & back-of-the-envelope math

Scope first, numbers second. The numbers tell you this is a fan-out problem, not a storage problem.

Functional requirements

  • Post text (say 280 chars) with optional media (images, video clips).
  • Home timeline: paginated, newest first.
  • Follow / unfollow; like a post.

Out of scope (say this in the room — scoping is a skill): DMs, search, ads, notifications. Also: real X ranks the feed with ML; we'll do chronological and note exactly where a ranker would plug in (§5).

Non-functional requirements

  • Read-heavy. Timeline views outnumber posts ~20:1. Optimize the read path.
  • Availability over strict consistency. A fan seeing a post a minute late is fine; the app being down during a derby is not. This is an AP-flavored system (our CAP lesson's language): the feed is eventually consistent by design.
  • Low latency: p99 timeline load under ~200 ms.

The math

The verdict the math hands you. 36 TB/year is nothing — a handful of database nodes. 1,200 writes/s is nothing. The problem is delivery: each of those 100M posts has to reach hundreds of followers' screens, and 2B timeline loads a day have to assemble in milliseconds. This is a fan-out problem, not a storage problem.

03

The API surface

Four endpoints. Two design decisions hide inside them: cursor pagination and idempotent posting.

POST /posts            { text, media_ids[], idempotency_key } → 201 { post_id, created_at }
GET  /timeline?cursor=<ts:id>&limit=20   → { posts[], next_cursor }
POST /follows           { followee_id } → 201
POST /likes             { post_id } → 201

Cursor pagination, not page numbers

A cursor is a bookmark into the feed — here, the (created_at, post_id) of the last post you saw. The next request says "give me 20 posts older than this bookmark." Contrast with ?page=47 + OFFSET: OFFSET makes the database re-scan and discard the first 46 pages on every request — slower the deeper you go, and it skips/duplicates posts when new ones arrive mid-scroll. A cursor is a position, so each page costs O(limit) regardless of depth. (Same idea as our indexing lesson's keyset pagination.)

Idempotent posting

Idempotent means safe to retry: doing it twice has the same effect as once. Posting from a phone on a flaky stadium connection will be retried — and nobody wants their goal-reaction posted twice. So the client generates an idempotency key (a random UUID per compose) and sends it with the post; the server stores it and ignores repeats. (This is the same idempotency-keys pattern from our message-queues lesson, now protecting the write path instead of a consumer.)

Note the 201 contract

POST /posts returns after the durable write — the post is safely stored — but before it has been delivered to anyone's feed. Delivery (fan-out) happens asynchronously. That split is the critical-path rule from our queues lesson: the user waits only for the write; everything else is background work.

04

Data model: posts, follows, and time-ordered IDs

Four tables. The schema is shaped by the two queries the product lives or dies on.

users    (user_id PK, handle, display_name, created_at, ...)
posts    (post_id PK, author_id, text, created_at, media_ids[])
follows  (follower_id, followee_id, created_at)   -- PK (follower_id, followee_id)
likes    (post_id, user_id, created_at)           -- PK (post_id, user_id)

Query patterns drive the schema

The two hot queries are: "@Saka's recent posts" (user timeline) and "who follows @Saka" (fan-out needs the follower list). The first is served by a composite index on (author_id, created_at DESC) — equality on the author, range on time, exactly the leftmost-prefix pattern from our indexing lesson. The second needs the reverse direction of the follows table, so you keep a second index (or table) keyed by (followee_id, follower_id). One table, two access directions — index both.

Time-ordered IDs

post_id isn't a random UUID. It's a Snowflake-style ID: ~41 bits of millisecond timestamp + worker ID + sequence number. That gives you IDs that are unique across machines with no coordination (the worker + sequence bits) and roughly time-ordered (the timestamp bits). Why it matters: time-ordered IDs make the merge in §5 and cursor pagination in §3 cheap — newer posts sort after older ones without reading a timestamp column — while random UUIDs would scatter every insert across the index (our indexing lesson's page-split tax, paid on every write).

05

The heart of the design: fan-out

One post, N followers. Someone pays N units of work. The only question is who, and when.

Fan-out

Distributing one post to the views of many followers. Write amplification is the multiplier: one logical write (the post) becoming N physical writes, where N is the follower count. Read amplification is the mirror image: one timeline load triggering M lookups, where M is the number of accounts you follow.

Option A — Push: fan-out on write

When @Saka posts, the system writes the post ID into every follower's inbox — a per-user list (a Redis sorted set scored by timestamp works beautifully) holding "the posts I should show this user." Reading your timeline is then one lookup: read my inbox, take the top 20. No joining at read time; the read path is O(1)-ish and screaming fast.

The price is paid at write time: write amplification = follower count. For a fan with 500 followers, that's 500 inbox writes per post — fine. For a superstar with 100M followers posting 10 times a day, that's 1 billion inbox writes a day from one user, ~200 bytes per inbox entry → ~200 GB of writes per day from a single account. The write path burns. Two more papercuts: inactive users accumulate inbox writes nobody will ever read (wasted work), and every celebrity post is a thundering herd against the inbox store.

Option B — Pull: fan-out on read

The post is stored once, in the author's user timeline. Nobody's inbox is touched. When you load your feed, the system fetches your followee list (~200–500 accounts), reads each author's recent posts (one indexed lookup each — §4's composite index), and merges the top 20 by timestamp. Zero write amplification; the data is always fresh.

The price moves to read time: read amplification = followee count per load. At 2B timeline loads a day × 300 followees, that's ~600B index lookups a day, and every load pays a scatter-gather merge — p99 latency suffers, and phones burn data and battery re-merging on every refresh.

Push (fan-out on write)Pull (fan-out on read)
Write cost per postO(followers) — explodes for celebritiesO(1) — stored once
Read cost per timeline loadO(1) — read your own inboxO(followees) — merge hundreds of lists
FreshnessEventual — inboxes fill asynchronouslyAlways fresh
Wasted workWrites for followers who never open the appNone — work happens only on read

Option C — Hybrid: the production answer

Split the world with a threshold — say, 10K followers. Accounts below it get push: their posts fan out to followers' inboxes, keeping reads fast for the 99.99%. Accounts above it are celebrities: their posts are skipped during push. At read time, each timeline load merges the reader's inbox plus the recent posts of the few celebrities they follow — and since a user follows maybe 5 celebrities, that's 5 extra lookups per load, served from a Redis cache of each celebrity's recent posts.

The write storm is dead (the 1B-writes-a-day superstar now costs ~0 push writes), the read cost is bounded (5 cached merges, not 300 live ones), and the trade-off is honest: a celebrity's post can appear seconds later than a friend's — eventual consistency, which our non-functional requirements already blessed.

Fan-out is async — always

POST /posts returns after the durable write; a queue carries the fan-out work to background workers (the critical-path rule again). This is what absorbs the World Cup-final spike in §7: posts keep succeeding at 1,200/s while the fan-out queue drains as fast as the worker fleet allows. Monitor queue depth and fan-out lag — "posts appear N seconds late" is the first thing that degrades, and it's the metric that tells you.

Where ranking would live

Real X doesn't show pure chronological — it scores posts by engagement, recency, and your history. In this design, the ranker plugs into exactly one place: the merge step, where inbox posts and celebrity posts are combined. Swap "sort by timestamp" for "score and sort," and the rest of the architecture doesn't move. Chronological keeps the lesson honest; ranking is a scoring function at the merge, not a different system.

06

Reading fast: timelines, caches, and your own post

The read path is the product — 20× the write volume. Three layers keep it under 200 ms.

Layer 1 — The inbox is the cache

Notice something elegant about push: the per-user inbox is a cache. There's no invalidation problem, because a new post is a write to the inbox, not a stale entry to expire. Your timeline read is: read inbox IDs → fetch those post bodies → render. Inbox lives in Redis (hot, in-memory); overflow goes to SSD-backed storage per user shard.

Layer 2 — Post bodies cached by ID

Inboxes hold post IDs, not post bodies — one reason among several (drill 3 explores another). Bodies live in a post:{id} → JSON cache, so a merge never touches the database per post. The viral-goal-clip problem — one post read by 50M fans — is a hot key: one Redis key hammered by the world. The mitigations are straight from our caching lesson: jittered TTLs so replicas don't expire in lockstep, and request coalescing so 1,000 simultaneous misses become one database read.

Layer 3 — Media never touches your servers

Images and video go to object storage; the timeline API returns CDN URLs and the phone fetches bytes from the edge. Your application servers never proxy a single pixel — the CDN is the media read path.

Read-your-own-write (session guarantee)

After you post, you see it instantly — not because fan-out is fast, but because the 201 response carries the post and your client prepends it to your own timeline locally. Your writes are immediately visible to you (a session guarantee from our consistency lesson); everyone else sees it once fan-out reaches them. This is why your post appears instantly while your friend's takes a minute — §9's Q3.

07

What breaks at soccer scale

Every design has a failure mode with your name on it. Here are this one's, with the fixes.

The World Cup final spike

Full time, controversial penalty, and posting volume goes 10× in minutes. What breaks first is not the post API — the durable write is cheap — it's fan-out lag: the queue depth climbs and posts appear minutes late. The response: the queue absorbs it (that's its job), you scale the fan-out worker fleet, and you alert on depth + lag. If it keeps climbing, degrade gracefully: stretch timeline cache TTLs, lengthen the celebrity-merge cache, and drop back to pure chronological to shed ranking CPU. The product stays up; it's just slightly staler. That's the AP choice, working as designed.

The celebrity write storm

Solved by the hybrid threshold in §5 — but the threshold needs teeth: it must be evaluated per post at fan-out time, because follower counts move. A pundit who goes viral overnight crosses the threshold mid-tournament; the fan-out worker checks the count on every job, not once at account creation.

The viral hot key

One goal clip, 50M views, one Redis key. Jittered TTL + request coalescing (§6, layer 2), and serve celebrity recent-post lists from dedicated cache replicas so the hot key can't starve normal inbox reads.

Deletions

A user deletes a post that's already in 500K inboxes. Eagerly fanning out the delete re-pays the write amplification you worked so hard to avoid. The standard answer is lazy: mark a tombstone (a "this post is deleted" marker) on the post record, and filter tombstoned IDs at read/merge time. The ghost can linger for seconds in someone's feed — acceptable, and far cheaper than a delete storm. Tombstones get a TTL so they don't accumulate forever.

Spam and fake follows

Bot farms mint accounts to amplify posts. The defense is our rate-limiting lesson applied to the social graph: token buckets on posts-per-account and follows-per-account, tighter for new accounts. Rate limiting isn't just API protection — here it's graph hygiene, because every fake follow is future fan-out work.

Deep pagination is a trap. Nobody scrolls 10,000 posts, but an attacker (or a bug) paginating with cursors forever will walk your entire hot set. Cap timeline depth — say 1,000 posts — and return an honest "you're all caught up." Cursor pagination makes each page cheap; the cap keeps the total bounded.

09

Q&A with full model answers

Four questions that come up in the room, answered the way a senior engineer would answer them — verdict first, reasoning after.

Q1
Push or pull for the home timeline — pick one and defend it.
They're not looking for a coin flip. They're listening for you to name where each option dies, then refuse the false choice.

Model answer: "Neither pure option survives contact with the tail. Push makes reads O(1) — beautiful at 20:1 read-heavy — but write amplification equals follower count, so one 100M-follower superstar posting 10 times a day is a billion inbox writes a day from a single account; the write path burns. Pull has zero write amplification and is always fresh, but every one of 2B daily timeline loads merges ~300 followee lists — that's hundreds of billions of index lookups a day and p99 latency nobody would ship. So: hybrid with a threshold around 10K followers. Below it, push — reads stay fast for the 99.99%. Above it, the celebrity's posts skip push entirely and get merged at read time from a cached recent-posts list, which is ~5 extra cached lookups per load. The honest trade is a few seconds of staleness on celebrity posts — eventual consistency, which the product already accepts. The question is really 'where do you pay the fan-out cost,' and the answer is 'below the threshold at write time, above it at read time.'"

Q2
A superstar with 100M followers posts. Walk me through exactly what happens, step by step.
They want the full request path with the hybrid logic visible. Keep it to six steps and name what is skipped, not just what runs.

Model answer: "One: POST /posts arrives with an idempotency key — the server checks it, writes the post durably with a Snowflake-style time-ordered ID, and returns 201. The user waits only for this. Two: a fan-out job goes on the queue with the post ID and author ID. Three: the worker sees the author's follower count is over the 10K threshold, so it skips the inbox push entirely — that's the billion inbox writes we just avoided. Four: it appends the post to the author's user timeline and refreshes the cached 'recent posts' list for that celebrity in Redis. Five: on each follower's next timeline load, the read path merges their push inbox with the cached celebrity lists — about 5 extra cached lookups. Six: post bodies come from the post:{id} cache and media from the CDN. Net: one durable write, zero push writes, and the post is visible within seconds — the staleness window is the fan-out lag, which we monitor."

Q3
Why do I see my own post instantly, but my friend's post takes a minute to show up?
A consistency question wearing a UX costume. They're checking whether you can connect the symptom to the architecture.

Model answer: "Two different mechanisms. Your own post appears instantly because of read-your-own-write: the 201 response carries the post object and your client prepends it to your timeline locally — no server round-trip, no fan-out involved. That's a session guarantee, not system speed. Your friend's post has to travel the real path: durable write, then the async fan-out queue, then the worker writing it into your inbox. That queue is the shock absorber for traffic spikes, so under load the lag grows — seconds normally, minutes at peak. The alternative would be synchronous fan-out, which would make every post take as long as its slowest inbox write — during the World Cup final, posting itself would time out. So the design chooses availability and eventual consistency: your own writes are instant by construction, everyone else's converge as the queue drains."

Q4
It's the World Cup final. Traffic is 10× normal. What breaks first, and what do you do?
A spike question. They want the failure ordered by what breaks first, and degradation framed as a deliberate choice.

Model answer: "What breaks first is fan-out lag, not the post API. The durable write is cheap, so posting keeps succeeding at 10× — but the fan-out queue depth climbs and posts appear minutes late instead of seconds. So: the queue absorbs it, that's its job; I scale the fan-out worker fleet on queue depth, and the metric I watch is lag, not throughput. On the read side I stretch timeline TTLs and lengthen the celebrity-merge cache — the product gets slightly staler, which the AP design already permits. Per-user rate limits hold the line against spam bots riding the spike. If lag keeps climbing, I degrade deliberately: drop the ranking step back to pure chronological to shed CPU, because the merge is where the ranker lives. The site stays up and posting works; freshness is what we spend. That's the trade the requirements section already made."

Practice drills (untimed)

Untimed, rubric-graded. Do them on paper or out loud — the point is the reasoning, not the clock.

Drill 1 — Size it: 1B posts/day

Redo the §2 math for 1 billion posts per day, same 20:1 read ratio, 5-year retention. What breaks first in the design above, and what changes?

Rubric: correct per-second rates (∼11,600 avg / ∼23,000 peak writes; ∼230K/s avg reads) and storage (365B rows × 1 KB ≈ 365 TB post records alone) · identifies the fan-out worker fleet and Redis inbox memory as the first bottlenecks, not the database · notes inboxes must be sharded by user_id (consistent hashing) with hot inboxes in Redis and cold inboxes on SSD · notes the celebrity threshold needs re-tuning and the fan-out queue becomes the most critical piece of infrastructure · bonus: mentions multi-region fan-out and the cross-region replication lag it adds to the staleness window.

Drill 2 — Defend the choice: hybrid vs pure pull

Your interviewer says: "Pure pull is simpler — no fan-out service, no inboxes, no threshold to tune. Data is always fresh. Why carry the hybrid's complexity?" Give the two-minute rebuttal.

Rubric: concedes the simplicity and freshness honestly · names read amplification as the decisive cost (2B loads/day × ~300 followees ≈ 600B lookups/day) and its p99/mobile-data consequences · notes the merge is a scatter-gather across shards with tail-latency math that gets worse exactly when traffic spikes · lands on: hybrid keeps pull's properties for the 0.01% of accounts that need them (celebrities) while push serves the 99.99% where reads dominate — the threshold is one number, not real complexity · bonus: offers the compromise (pull with aggressively cached user timelines) and names what it gives up.

Drill 3 — Design post editing

Matchday wants editable posts: a user fixes a typo and every follower sees the corrected version. Inboxes already hold the post ID. Sketch the design and name the trade-off you're exploiting.

Rubric: exploits the inbox-of-IDs decision: inboxes store IDs, not bodies, so no fan-out is needed at all · edit updates the post row + the post:{id} body cache (invalidate or overwrite) · readers see the fix on next body fetch; in-flight cached bodies converge on TTL · names the alternative honestly (storing full bodies in inboxes would make reads one lookup but edits a fan-out storm) · handles the edge: cap edit window (e.g., 30 min) to bound abuse like bait-and-switch edits · bonus: notes version history as an audit table, not in the hot path.

11

Cheat sheet & 60-second framing

Twitter/X feed — six decisions

  1. Shape: read-heavy (~20:1), AP-flavored — staleness is acceptable, downtime is not.
  2. Fan-out: hybrid — push below a ~10K-follower threshold, pull-merge for celebrities above it; the threshold is evaluated per post at fan-out time.
  3. Critical path: POST returns after the durable write; fan-out rides a queue — lag, not throughput, is the metric to watch.
  4. Reads: inbox is the cache (no invalidation problem); bodies cached by post ID; media via CDN; cursor pagination, depth capped.
  5. IDs: Snowflake-style time-ordered IDs — unique without coordination, cheap merges and cursors.
  6. Failure modes: celebrity write storm (threshold), viral hot key (jittered TTL + coalescing), spike lag (scale workers, degrade to chronological), deletes via tombstones, spam via rate-limited graph.

60-second framing — how to open in the room:

"A feed is a personalized, assembled list of posts from accounts you follow — the system has to join many authors' posts into one timeline, and the whole design is choosing where that work happens. Scope: post, home timeline, follow, like; chronological, with ranking as a scoring function at the merge step. Sizing: 200M daily users, 100M posts a day is ~1,200 writes a second; 2B timeline loads is ~23K reads a second — 20:1 read-heavy, so this is a fan-out problem, not a storage problem. The design: hybrid fan-out. Below a ~10K-follower threshold, push — write the post ID into each follower's inbox so reads are one lookup. Above it, the celebrity skips push and their posts merge at read time from a cached list — that kills the billion-writes-a-day write storm. POST returns after the durable write with a Snowflake-style time-ordered ID; fan-out rides a queue off the critical path. Reads go inbox → post-body cache → CDN for media, cursor-paginated. Consistency is AP by design: your own post appears instantly via read-your-own-write, everyone else's converges as fan-out drains — and during a World Cup-final spike, we spend freshness, not availability."
